```bash

docker stop Mymongo
docker start Mymongo

```

> [!warning] 🔴 `docker pull mongo` **no fija versión** — a diferencia del `mysql:9.7.2` del 04/08
> La [[Práctica 2026-08-04]] pinneaba la imagen (`docker pull mysql:9.7.2`); aquí el tag es `latest`
> implícito: **cada alumno que haga el `pull` en una fecha distinta puede recibir una versión
> distinta**, y `explain()` *(paso 34)* cambia de formato entre versiones mayores. Para que el
> resultado sea reproducible conviene fijar el tag mayor —por ejemplo `mongo:8`— y anotar en la
> entrega qué `db.version()` devolvió el servidor. *(Cuál es la versión que baja hoy no está
> verificado desde esta página → § *Dudas abiertas*.)*
>
> Dos diferencias más con el `run` de MySQL: **no hay variables de entorno** (`-e MONGO_INITDB_ROOT_USERNAME`
> existe pero el TP no la usa → el servidor arranca **sin autenticación**, cualquier conexión al
> `27017` es admin), y **no hay volumen**: si se hace `docker rm Mymongo` se pierden `lab` y todo lo
> insertado. `docker stop`/`start` sí conservan los datos.

> [!tip] El atajo que el TP no menciona: `mongosh` directo, sin `bash` intermedio
> La imagen oficial `mongo` **trae `mongosh` adentro** *(desde la serie 6.0 la imagen dejó de incluir
> el shell `mongo` legacy)*. Entonces alcanza con:
>
> ```bash
> docker exec -it Mymongo mongosh
> ```
>
> Eso contradice en apariencia el aviso que la [[Clase 14 - MongoDB Features]] copia de la
> documentación —*"The MongoDB Shell (mongosh) is not installed with MongoDB Server"*—: ese aviso vale
> para la **instalación nativa** (Community Edition), no para la imagen Docker. Y el `docker cp` de la
> lista sirve para lo que este TP **no** pide todavía: importar un `.json` con `mongoimport`, que

## Introducción *(p. 1)*

> [!quote] Textual
> *"**MongoDB** es una base de datos de documentos, de código abierto que ofrece alto rendimiento,
> alta disponibilidad y escalamiento automático.*
>
> *Un registro en MongoDB es un **documento**, representado por una estructura de datos compuesta por
> pares de campo y valor. Los documentos en MongoDB poseen formato **JSON**. Los valores de los campos
> pueden incluir otros documentos, arreglos y arreglos de documentos."*

**La primera imagen del PDF** es una captura de terminal (fondo negro, texto celeste) con un documento
y cuatro flechas *"← Campo: valor"*:

```javascript
{
    nombre: "Luis",                       // ← Campo: valor
    edad: 34,                             // ← Campo: valor
    estatus: "A",                         // ← Campo: valor
    grupos: ["noticias", "deportes"]      // ← Campo: valor
}
```

> [!note] Es la misma figura de la documentación oficial, traducida
> El ejemplo `{name: "sue", age: 26, status: "A", groups: ["news", "sports"]}` es el de la portada
> del manual de MongoDB (*"Documents"*). El TP lo trae en español. Ilustra los tres tipos de valor que
> la definición enumera: escalares (`"Luis"`, `34`), y un **arreglo** (`grupos`). El caso *"otros
> documentos"* aparece recién en el paso 28 *(`team`)*.
>
> Una precisión que el TP no hace y la [[Clase 14 - MongoDB Features]] sí: el formato de
> almacenamiento es **BSON** *("stored in a binary form of JSON known as BSON")*. Y un comentario
> propio de esta página, que ningún deck trae: *"de código abierto"* es discutible desde 2018, cuando
> MongoDB cambió la licencia a **SSPL**, que la OSI no reconoce como open source.

## Recorrido guiado — pp. 2–6, paso por paso

### COMANDOS BÁSICOS *(pp. 2–3)*

> [!quote] Encabezado, textual
> *"En el cliente **mongosh** (cliente Shell), los comandos son ejecutados a través del objeto db.
> Por ejemplo:*
> - *`db.help()`: Proporciona una lista de los comandos que se pueden ejecutar*
> - *`db.stats()`: Proporciona estadísticas sobre la base de datos*
>
> ***NOTA:** Al tratarse de una consola basada en JavaScript, si ejecuta un comando y omite los
> paréntesis (), se mostrará el cuerpo del método en lugar de la ejecución del mismo."*

> [!tip] La NOTA es la trampa más frecuente del primer día, y el TP la pone antes de todo
> `db.stats` sin paréntesis imprime `[Function: stats] …`; **no es un error, es JavaScript**. La misma
> lógica explica por qué `db.players.find` devuelve una función y `db.players.find()` un cursor.

#### Paso 1 — `db.stats()`

> [!quote]
> *"1. Probemos el comando `db.stats()` → que devuelve información estadística sobre la base a la cual
> están conectados"*

Recién conectado, la base activa es `test`. `db.stats()` devuelve un documento con `db: 'test'`,
`collections: 0`, `objects: 0`, `dataSize: 0`… y `ok: 1`. Es la primera evidencia de que **las bases
no se crean hasta que tienen algo**.

#### Paso 2 — `use lab`

> [!quote]
> *"El método global **use** permite seleccionar la base de datos (No importa si la base de datos no
> existe aún, de hecho la primera colección que crearemos generará efectivamente la base de datos, en
> este caso **lab**):*
>
> *2. Ejecutar `use lab`"*

Respuesta: `switched to db lab`. `show dbs` todavía **no** lista `lab`.

#### Paso 3 — `db.getCollectionNames()`

> [!quote]
> *"3. Una vez seleccionada la base de datos, es posible consultar todas las colecciones que posee con
> `db.getCollectionNames()`*
>
> *Al ejecutar el comando debe obtener un arreglo vacío `[]`. No es necesario crear un esquema para la
> colección, puede simplemente insertar un nuevo documento en la nueva colección."*

> [!important] *"No es necesario crear un esquema"* — ésta es la frase que separa este TP de los ocho anteriores
> Del TP2 al TP8 cada ejercicio empezaba con `CREATE TABLE`. Aquí **no hay DDL**: la colección nace con
> el primer `insertOne`. Es el *schemaless* de la [[Clase 12 - Introduccion a NoSQL]], llevado a la
> práctica. La contracara aparece en el paso 12: **un documento puede no tener un campo**, y hay que
> consultarlo con `$exists`.

#### Paso 4 — el primer `insertOne`

> [!quote]
> *"4. Use el comando **insertOne** para insertar un nuevo documento, suministrando el documento a
> insertar: `db.players.insertOne({name:'Aaron Appindangoye', height: 182, weight:187})`"*

Respuesta esperada: `{ acknowledged: true, insertedId: ObjectId('…') }`.

#### Paso 5 — la colección ya existe

> [!quote]
> *"5. Ejecutar nuevamente el comando `db.getCollectionNames()` → ahora debe aparecer la colección
> players"*

`[ 'players' ]`. Y ahora sí `show dbs` lista `lab`.

#### Paso 6 — `find()` y el `_id`

> [!quote]
> *"6. Usa el comando **find** contra players para retornar los documentos que posee la colección:
> `db.players.find()`*
>
> *Adicional a los datos que se especificaron al insertar el documento, se observa un campo `_id`.
> Todo documento debe tener un campo `_id` único. Se puede asignar uno, o dejar que MongoDB genere
> automáticamente el **ObjectId** correspondiente."*

```javascript
[
  {
    _id: ObjectId('…'),
    name: 'Aaron Appindangoye',
    height: 182,
    weight: 187
  }
]
```

> [!note] `_id` es el único "constraint" que MongoDB impone solo
> Es la clave primaria: **única por colección**, con índice automático, y **no se puede modificar
> después** (un `$set` sobre `_id` falla). El `ObjectId` de 12 bytes codifica timestamp + valor
> aleatorio + contador, lo que lo hace ordenable por tiempo de inserción. La
> [[Clase 14 - MongoDB Features]] linkea la referencia oficial del `ObjectId`.

#### Paso 7 — el segundo documento, con `dob: new Date(…)`

> [!quote]
> *"7. Para agregar un nuevo documento a la colección ejecutar
> `db.players.insertOne({name:'Edinson Cavani', height: 182, dob: new Date(1987,2,14,0,0)})`"*

> [!bug] 🔴 `new Date(1987,2,14,0,0)` **no es el 14 de febrero de 1987**: en JavaScript los meses van de 0 a 11
> `new Date(año, mes, día, h, m)` toma el **mes con base 0**: `2` es **marzo**. Cavani nació el
> **14/02/1987**; el documento guarda **14/03/1987**. **Y el patrón se repite en los 12 inserts del
> paso 10**: todos los `dob` del TP están escritos como si el mes fuera 1-based, así que **cada fecha
> de nacimiento queda un mes corrida** *(verificado uno por uno en § Paso 10)*.
>
> Segunda trampa, menos visible: el constructor con componentes usa la **zona horaria local del
> proceso `mongosh`**, y MongoDB almacena en **UTC**. Desde Argentina (UTC−3), `new Date(1987,2,14,0,0)`
> se guarda como `1987-03-14T03:00:00.000Z`; dentro del contenedor Docker (UTC) se guarda como
> `…T00:00:00.000Z`. **Dos alumnos pueden tener dos valores distintos para el mismo comando.** La

### SELECTORES *(p. 3)*

> [!quote] Encabezado, textual
> *"Los selectores permiten consultar documentos particulares dentro de la colección:*
> - *`{field: value}` es usado para encontrar cualquier documento donde field sea igual a value*
> - *`{field1: value1, field2: value2}` permite realizar una declaración **and***
> - *Los selectores especiales **`$lt`, `$lte`, `$gt`, `$gte` y `$ne`** son usados por las operaciones
> menor que, menor o igual que, mayor que, mayor o igual que y no igual respectivamente"*

#### Paso 11 — AND implícito + `$gt`

> [!quote]
> *"11. Por ejemplo, para obtener todos los jugadores que tengan `preferred_foot` left y pesen más de
> 170 libras (weight > 170), se puede utilizar el siguiente comando:
> `db.players.find({preferred_foot: 'left', weight:{$gt:170}})`"*

**Resultado esperado: un solo documento, Cristiano Ronaldo** (176). Los otros zurdos pesan 148, 148,
159, 165 y 161. *(Si este paso se corriera después del 16, Messi entraría con 180.)*

#### Paso 12 — `$exists`

> [!quote]
> *"12. El operador **`$exists`** es usado para determinar la presencia o ausencia de un campo, por
> ejemplo para ver que documentos de la colección players no posee el campo height, ejecutar:
> `db.players.find({height:{$exists:false}})`"*

**Resultado: Harry Kane.** Es el único insert sin `height`.

> [!important] `$exists: false` ≠ `null`
> `{height: null}` matchea documentos donde el campo **no existe o vale `null`**; `{height: {$exists:
> false}}` solo los que **no lo tienen**. En SQL esta distinción no existe porque toda fila tiene todas
> las columnas. Aquí aparece porque no hay esquema.

>
> ```javascript
> db.players.find({preferred_foot:'right',
>                  $or:[{hobbies:'Playing football'},
>                       {hobbies:'Video games'},

> ```

> El TP no lo explica: cuando el campo es un arreglo, la igualdad simple matchea si **algún elemento**
> es igual al valor. Por eso no hace falta `$in` ni `$elemMatch` para "tiene tal hobby". Es la base

### EXPRESIONES REGULARES *(p. 4)*

> [!quote]
> *"MongoDB soporta expresiones regulares compatibles con **Perl**, para consultas basadas en patrones
> de coincidencia identificados en las cadenas de caracteres."*

#### Paso 14 — `^S`

> [!quote]
> *"14. Consultar todos los jugadores cuyo nombre comience por la letra S:
> `db.players.find({name: { $regex: "^S"}})`"*

**Resultado: Sergio Ramos, Samuel Umtiti.** La regex es **case-sensitive**: `"^s"` no devolvería nada.
Se puede agregar `$options: "i"`, o escribir el literal `/^s/i`.

#### Paso 15 — `o$`

> [!quote]
> *"15. Consultar todos los jugadores cuyo nombre termine con la letra o:
> `db.players.find({name: { $regex: "o$"}})`"*

**Resultado: Cristiano Ronaldo**, único. *(Ramos y Kroos terminan en `s`; Neymar en `r`.)*

> [!note] Solo un regex con `^` anclado **acota** el índice
> Adelanto del paso 34: `^S` sobre un índice en `name` se resuelve con `IXSCAN` sobre un rango
> acotado; `o$` con el mismo índice también da `IXSCAN`, pero con bounds `["", {})` —examina
> **todas** las claves del índice y evalúa la regex contra cada una— y luego `FETCH`; sin índice en
> `name`, `COLLSCAN`. *(Ampliación desde la documentación de `$regex`, § *Index Use*; el enunciado
> no lo dice.)* Es el equivalente del `LIKE 'S%'` vs. `LIKE '%o'` de la
> [[Clase 08 - Explicando el plan]]; el detalle vive en [[1.08.01 - Plan de ejecución|Plan de ejecución]].

### COMANDOS DE ACTUALIZACIÓN *(pp. 4–5)*

> [!quote] Encabezado, textual
> *"En su forma más simple, la operación update tiene dos argumentos: el selector (where) a usar y el
> campo del documento a actualizar (**`$set`**)."*

#### Paso 16 — `$set`

> [!quote]
> *"16. Por ejemplo, el jugador que lleva por nombre Lionel Messi, ha subido de peso, por ello debemos
> actualizar el campo weight: `db.players.updateOne({name: 'Lionel Messi'},{$set:{weight:180}})`"*

`{ acknowledged: true, matchedCount: 1, modifiedCount: 1, upsertedCount: 0 }`. Desde aquí **Messi es
el más pesado (180)**, y eso decide el paso 26.

#### Paso 17 — `$inc`

> [!quote]
> *"17. Adicionalmente a `$set`, podemos aprovechar otros modificadores para hacer actualizaciones.
> Todos estos modificadores adicionales de update operan directamente sobre los campos del documento.
> Por lo tanto el documento completo no será reemplazado o borrado. Por ejemplo, el operador
> **`$inc`** es usado para incrementar o decrementar de acuerdo al parámetro que se utilice (positivo
> o negativo, respectivamente).*
>
> *Si a Luka Modric se le adjudicó incorrectamente un valor de 180 para el campo height, cuando debería
> ser 175, entonces ejecutar lo siguiente para corregirlo:
> `db.players.updateOne({name: 'Luka Modric'},{$inc:{height:-5}})`"*

Modric pasa a **175**. Para corregir un valor conocido, `$set: {height: 175}` sería más honesto que
`$inc: -5` (que depende del valor previo); el TP usa `$inc` para mostrarlo, no porque sea la mejor
herramienta.

> [!warning] *"el documento completo no será reemplazado"* — la frase importa más de lo que parece
> En el shell legacy, `update({…}, {weight: 180})` **sin** `$set` **reemplazaba el documento entero**
> por `{weight: 180}`: Messi perdía nombre, altura y hobbies. `updateOne` moderno **rechaza** un
> documento de actualización sin operadores `$` (error *"Update document requires atomic operators"*),
> y para reemplazar existe `replaceOne`. El TP está del lado seguro.

#### Paso 18 — `$push`

> [!quote]
> *"18. Si David Silva de pronto desarrolla un gusto adicional por la natación, podemos agregarlo a su
> campo hobbies con el modificador **`$push`** (por tratarse de un arreglo).*
>
> *Primero ver los hobbies que tiene actualmente: `db.players.find({name: 'David Silva'})`
> Luego realizar el push: `db.players.updateOne({name: 'David Silva'},{$push:{hobbies:'Swimming'}})`"*

Antes: `['Playing football', 'Watching Movies']`. Después: `[…, 'Swimming']`. Y el conteo del paso 27
**sube de 8 a 9** por este push.

> [!tip] `$push` **duplica**; `$addToSet` no
> Si el paso 18 se ejecuta dos veces, Silva queda con `'Swimming'` dos veces. `$addToSet` agrega solo
> si no está. El TP no lo menciona; conviene saberlo para el ejercicio 4 de la p. 7 si alguien
> decidiera modelar los integrantes como arreglo.

#### Pasos 19–21 — upsert con la colección `hits`

> [!quote]
> *"19. Los updates son compatibles con **upserts**. Un upsert actualiza el documento si lo encuentra o
> lo inserta si no lo encuentra. Los upserts son útiles de emplear en determinadas situaciones. Para
> habilitar upserting tenemos que especificar un tercer parámetro en true en el comando que utilicemos
> para el update.*
>
> *Un ejemplo aplicable de este caso es un contador de visitas a un sitio web. Si se desea mantener un
> recuento total, se tendría que validar si el registro ya existe para la página, y basado en eso
> decidir si ejecutar un update o un insert.*
>
> *Con el tercer parámetro omitido (o establecido en false), la ejecución de la siguiente instrucción
> no tendrá ningún resultado: `db.hits.updateOne({page: 'players'}, {$inc:{hits:1}});`*
>
> *20. Sin embargo, para permitir upserts (tercer parámetro true) y lograr un resultado diferente:
> `db.hits.updateOne({page: 'players'}, {$inc:{hits:1}}, {upsert:true});`*
>
> *21. Dado que no existen documentos con un campo page igual a players, se inserta un nuevo documento.
> Si se ejecuta el comando de nuevo, el documento existente se actualizará y hits se incrementará a 2.
> Ejecutar el comando anterior cuantas veces quieran y verificar la cantidad de hits."*

| Paso | Comando | Resultado |
| :---: | --- | --- |
| 19 | `updateOne({page:'players'}, {$inc:{hits:1}})` | `matchedCount: 0, modifiedCount: 0, upsertedCount: 0` — **no** es "ningún resultado": es un resultado que dice que no tocó nada. La colección `hits` **ni siquiera se crea** |
| 20 | ídem + `{upsert:true}` | `upsertedCount: 1, upsertedId: ObjectId(…)` — nace `hits` con `{page:'players', hits: 1}` |
| 21 | repetir el 20 | `matchedCount: 1, modifiedCount: 1` — `hits: 2`, `3`, … |

> [!bug] 🔶 *"tercer parámetro en true"* describe la firma **vieja**, no la que el TP usa
> `db.col.update(query, update, true)` era la forma del shell legacy (el tercer argumento posicional
> era el booleano `upsert`). En `updateOne` el tercer argumento es un **documento de opciones**
> `{upsert: true}`, que es lo que el paso 20 escribe correctamente. **La prosa y el código no
> coinciden**: la prosa quedó del TP anterior a `mongosh`. Escribir `updateOne(q, u, true)` literal
> **falla** en mongosh (las opciones tienen que ser un objeto).

> [!important] 🎯 El upsert es el `INSERT … ON DUPLICATE KEY UPDATE` de la [[Práctica 2026-09-01]]
> Mismo problema —el contador que puede no existir todavía—, resuelto en el ejercicio 4 del TP7 con
> el `ON DUPLICATE KEY UPDATE` de MySQL. La diferencia: aquí **no hace falta clave única en `page`**
> para que funcione, lo cual también significa que **dos upserts concurrentes pueden insertar dos
> documentos** `{page:'players'}` si no hay índice único. El TP no lo advierte.

#### Paso 25 — `sort`

> [!quote]
> *"25. El método **sort** permite ordenar los resultados por los campos que se indiquen. Se utiliza 1
> para orden ascendente y -1 para descendente. Por ejemplo, podemos consultar los jugadores más altos
> primero: `db.players.find({},{name:1, height:1,_id:0}).sort({height:-1})`"*

Resultado esperado *(con Modric ya en 175 por el paso 17)*:

| `height` | `name` |
| :---: | --- |
| 185 | Cristiano Ronaldo |
| 182 | Toni Kroos · Sergio Ramos |
| 180 | Samuel Umtiti |
| 175 | Luka Modric · Neymar · Antoine Griezmann · Paulo Dybala |
| 172 | Eden Hazard |
| 170 | David Silva · Lionel Messi |
| *(sin campo)* | **Harry Kane — último** |

> [!note] Kane va **último** en descendente, y no por casualidad
> Un campo ausente se ordena como `null`, que en el orden de comparación de BSON está **por debajo de
> los números**. En descendente queda al final; en ascendente, **primero**. Es el equivalente del
> `NULLS FIRST/LAST` que MySQL no tiene. Y **el orden entre empates (los dos 182, los cuatro 175) no
> está definido**: puede variar entre ejecuciones. Para hacerlo determinista se agrega un segundo
> criterio: `.sort({height: -1, name: 1})`.

#### Paso 26 — `limit` y `skip`

> [!quote]
> *"26. También es posible paginar los resultados, a través de los métodos **limit** y **skip**. Para
> obtener solamente el segundo y tercer jugador más pesado, ejecuta el siguiente comando:
> `db.players.find().sort({weight:-1}).limit(2).skip(1)`*
>
> *Usando limit en conjunto con sort, es una buena forma de evitar problemas de performance cuando
> hacemos ordenamiento en campo sin índices."*

Pesos descendentes después del paso 16: Messi **180** · Ronaldo **176** · Kroos **172** · Ramos 165 ·
Umtiti 165 · Hazard 163 · Dybala 161 · Neymar 150 · Silva 148 · Griezmann 148 · Modric 143 · Kane 143.
**Resultado: Cristiano Ronaldo y Toni Kroos.** *(Sin el paso 16 sería Kroos y Ramos/Umtiti.)*

> [!important] `.limit(2).skip(1)` y `.skip(1).limit(2)` dan lo mismo
> El orden de encadenado **no importa**: son modificadores del cursor, y el servidor aplica siempre
> `sort → skip → limit`. El TP los escribe "al revés" de como se lee (*"limitar a 2 y saltear 1"*) y
> funciona igual. Es distinto del `LIMIT 2 OFFSET 1` de SQL solo en la superficie.
>
> Sobre la frase de performance: un `sort` sin índice **carga todo en memoria** y tiene un tope
> (100 MB por defecto; hasta la 5.x, superarlo daba error salvo `allowDiskUse`; desde la 6.0 vuelca a
> disco por defecto, `allowDiskUseByDefault: true`). `limit` acota cuánto hay que
> conservar (top-k), no cuánto hay que leer: sigue siendo un `COLLSCAN` completo.

#### Paso 27 — `countDocuments` vs. `count`

> [!quote]
> *"27. Se puede ejecutar **count** directamente en una colección, para conocer el número de
> documentos que cumplen con determinada condición: `db.players.countDocuments({hobbies:'Swimming'})`
> o `db.players.find({hobbies:'Swimming'}).count()`"*

**Resultado: 9** — Modric, Kane, Neymar, **Silva (por el push del paso 18)**, Griezmann, Messi,
Ronaldo, Umtiti y Dybala. Sin el paso 18 serían 8.

> [!warning] 🔴 La segunda forma está **deprecada** — `mongosh` la acepta con `DeprecationWarning`
> La página de compatibilidad de `mongosh` lista `db.collection.count()` entre los métodos deprecados y
> remite a `countDocuments()` / `estimatedDocumentCount()` *(verificado en la documentación oficial el
> 15/09)*. `cursor.count()` corre la misma suerte. Para la entrega: **`countDocuments`**, que además
> es exacto (el `count` con selector vacío podía devolver metadatos desactualizados tras un crash).

> `db.players.find({'team.team_short_name': 'JUV'})`"*

**Resultado: Cristiano Ronaldo.** La clave con punto **va entre comillas** (`'team.team_short_name'`),
porque `team.team_short_name` sin comillas no es una clave válida en JavaScript.

> [!important] 🎯 *"simular JOINS"* es la frase que conecta este TP con la [[Clase 13 - NoSQL-EmbebidosVSNormalizado]]
> Embeber el equipo dentro del jugador **evita el join** al leer, y **duplica** `Juventus` en cada
> jugador del club al escribir. Si la Juventus cambia de nombre, hay que actualizar N documentos. La
> alternativa normalizada —una colección `teams` y un `team_id` en `players`— obliga a dos consultas
> (o a `$lookup`, que el TP no ve). **Es exactamente el trade-off que la teórica del 14/09 discute**, y
> el que decide el **ejercicio 1** de la p. 7: ¿los discos van embebidos en la banda o en una colección
> aparte? *(La respuesta que se propone abajo: embebidos.)*

### ÍNDICES Y ADMINISTRACIÓN *(p. 6)*

> [!quote]
> *"Los índices en MongoDB funcionan muy parecido a los índices en una base de datos relacional, ayudan
> a mejorar el rendimiento de los queries y ordenados."*

#### Paso 30 — `ensureIndex`

> [!quote]
> *"30. Los índices son creados con el comando **ensureIndex**: `db.players.ensureIndex({name:1})`"*

> [!warning] 🔴 `ensureIndex` **ya no existe en la documentación** — el método es `createIndex`
> La lista de métodos de colección del manual actual tiene `createIndex`, `createIndexes`, `dropIndex`,
> `dropIndexes`, `getIndexes`, `hideIndex`, `unhideIndex` y `totalIndexSize`; **`ensureIndex` no
> aparece** *(verificado el 15/09 contra `docs/manual/reference/method/js-collection/`)*. Era un alias
> deprecado desde MongoDB 3.0. En `mongosh` queda —según entiendo— como alias que imprime una
> advertencia y llama a `createIndex`; **si en la consola falla con `is not a function`, la
> corrección es mecánica**: reemplazar `ensureIndex` por `createIndex` en los pasos 30, 32 y 33. Está
> anotado en § *Dudas abiertas* para verificarlo en el motor.
>
> La [[Clase 14 - MongoDB Features]] usa `ensureIndex` en sus ejemplos de índices —los mismos que
> *Seven Databases* trae con `phones`—, así que **el TP hereda la sintaxis del libro y del deck**, no
> la inventa.

```javascript
db.players.createIndex({name: 1})        // → 'name_1'
```

#### Paso 31 — `dropIndex`

> [!quote]
> *"31. Los índices pueden ser borrados usando **dropIndex**: `db.players.dropIndex({name:1})`"*

Acepta la **especificación** (`{name:1}`) o el **nombre** (`'name_1'`). `{ nIndexesWas: 2, ok: 1 }`
—el `2` incluye el índice automático de `_id`, que **no** se puede borrar—.

#### Paso 32 — índice único

> [!quote]
> *"32. Un índice único se crea utilizando el parámetro **unique**:
> `db.players.ensureIndex({name:1},{unique:true})`"*

Funciona porque los 12 nombres son distintos. Si hubiera dos `'Lionel Messi'`, fallaría con
`E11000 duplicate key error` **y no se crearía**. Nótese que **el paso 31 tiene que ejecutarse
antes**: crear `{name:1}` con `unique:true` cuando ya existe `{name:1}` sin `unique` da
`IndexOptionsConflict`.

> [!note] Es el único "constraint" declarativo que MongoDB ofrece
> Un índice único es lo más parecido a `UNIQUE` de la [[Clase 09 - Restricciones integridad-Parte 1]].
> **No hay `NOT NULL`, ni `CHECK`, ni claves foráneas** *(existe la validación de esquema con
> `$jsonSchema`, que este TP no toca)*. Y con **`sparse` o `partialFilterExpression`** el índice único
> puede permitir documentos **sin** el campo, que es el caso de Kane con `height`.

#### Paso 33 — índices en campos embebidos, arreglos y compuestos

> [!quote]
> *"33. Los índices pueden ser creados en campos embebidos (usando la notación de punto) y en campos
> de arreglos. También, es posible crear índices compuestos: `db.players.ensureIndex({name:1, weight:1})`"*

Tres afirmaciones, un solo ejemplo (el compuesto). Los otros dos, que el TP nombra y no muestra:

```javascript
db.players.createIndex({'team.team_short_name': 1})   // embebido, notación de punto
db.players.createIndex({hobbies: 1})                  // arreglo → índice "multikey": una entrada por elemento
```

El **multikey** es el que no tiene equivalente relacional: indexa **cada elemento** del arreglo, así
que `{hobbies: 'Swimming'}` puede usar índice. Sobre el compuesto `{name:1, weight:1}` vale la regla
del prefijo de la [[Clase 08 - Explicando el plan]]: sirve para `name` solo y para `name+weight`, **no**
para `weight` solo.

#### Paso 34 — `explain()`

> [!quote]
> *"34. Para validar si los queries están usando índices o no, se puede utilizar el método explain, al
> final de la consulta.*
>
> *Si se mantiene el índice del punto 32, veremos con la siguiente query que figura el nombre del índice
> que es usado: `db.players.find({name: 'Lionel Messi'}).explain()`"*

Lo que hay que buscar en la salida *(modo por defecto `queryPlanner`)*:

```javascript
queryPlanner: {
  namespace: 'lab.players',
  winningPlan: {
    stage: 'FETCH',
    inputStage: {
      stage: 'IXSCAN',
      keyPattern: { name: 1 },
      indexName: 'name_1',          // ← "el nombre del índice que es usado"
      isUnique: true,
      indexBounds: { name: [ '["Lionel Messi", "Lionel Messi"]' ] }
    }
  }
}
```

Sin el índice, el `winningPlan` es `{ stage: 'COLLSCAN', filter: {…} }`. Con `explain('executionStats')`
se ven además `totalDocsExamined` (1 vs. 12) y `executionTimeMillis` —el equivalente de `EXPLAIN
ANALYZE` de la [[Práctica 2026-08-18]]—. **Con 12 documentos la diferencia de tiempo es cero**: aquí la
lección es leer `IXSCAN` vs. `COLLSCAN`, igual que en el TP5 con 6 filas.

> [!warning] La forma de la salida depende de la versión del servidor — otra razón para pinnear la imagen
> El bloque de arriba sigue la estructura de las series 5.x–8.x (`queryPlanner.winningPlan.inputStage`).
> En algunas versiones el `winningPlan` viene envuelto en `queryPlan` con `slotBasedPlan`, y las
> claves cambian de lugar. Si lo que se ve no coincide con el ejemplo, **no es que el índice no se use**.

### Ejercicio 10 — la vista `bandas_resumen` y el promedio por género

> [!important] 🔴 Lo que el TP pide y no enseña — **vistas** y **`$group`**
> Los 34 pasos no traen `createView` ni `aggregate`. El enunciado dice *"una vista llamada
> bandas_resumen (que deberán crear)"* como si la sintaxis fuera conocida. **No lo es desde este
> PDF**: hay que ir a la [[Clase 14 - MongoDB Features]] *(aggregation pipeline)* y a la
> documentación de `db.createView()`. Lo que sigue es propuesta propia.

**La vista** — *"solo los datos del solista, el género de la banda, el barrio y los integrantes"* → un
`$project` de cuatro campos, sin `_id`:

```javascript
db.createView(
  'bandas_resumen',           // nombre de la vista
  'bandas',                   // colección origen
  [ { $project: { _id: 0, nombre: 1, genero: 1, barrio: 1, integrantes: 1 } } ]
)
// → { ok: 1 }
db.getCollectionNames()      // [ 'bandas', 'bandas_resumen', … ]
db.bandas_resumen.find().limit(2)
```

**El promedio por género, ordenado alfabéticamente**, se corre **sobre la vista**:

```javascript
db.bandas_resumen.aggregate([
  { $group: { _id: '$genero', promedio_integrantes: { $avg: '$integrantes' } } },
  { $sort:  { _id: 1 } }
])
```

Resultado esperado:

| `_id` (género) | promedio **antes** del ej. 4 | promedio **después** del ej. 4 |
| --- | :---: | :---: |
| FOLKLORE | 7 | 8 |
| HIP HOP / RAP | 1 | 2 |
| INDIE | 4 | 5 |
| INSTRUMENTAL | 1 | 2 |
| POP | 5 *((6+4)/2)* | 6 |
| PUNK | 3 | 4 |
| ROCK | 3 *((3+5+1+3)/4)* | 4 |
| SOLISTA | 1 | 2 |

> [!note] Lo que una vista de MongoDB es y no es
> - Es **un pipeline guardado** con un nombre; cada lectura lo re-ejecuta sobre la colección origen.
>   **No materializa**: refleja el `$inc` del ejercicio 4 al instante. Es lo mismo que la vista
>   relacional de la [[Clase 06 - Vistas-Parte 1]], y por eso el ejercicio 11 se puede correr sobre
>   ella.
> - Es **de solo lectura**: no acepta `insertOne`/`updateOne` *(no hay `INSTEAD OF` ni `WITH CHECK
>   OPTION`)*, y **no admite índices propios** —usa los de `bandas`—.
> - Se **consulta** con `find()` y `aggregate()`, como una colección. Y `getCollectionNames()` la
>   lista junto a las colecciones; `db.getCollectionInfos()` distingue `type: 'view'`.
> - `$avg` sobre documentos que **no tengan `integrantes`** los ignora (no cuenta como 0). Aquí todos lo
>   tienen.

### Ejercicio 11 — bandas por barrio, de más a menos musical

```javascript
db.bandas_resumen.aggregate([
  { $group: { _id: '$barrio', cantidad: { $sum: 1 } } },
  { $sort:  { cantidad: -1, _id: 1 } }
])
```

Resultado esperado: **BARRACAS 3**, y después nueve barrios con **1** *(AGRONOMIA, BALVANERA,
BERAZATEGUI, LA LUCILA, MORENO, PUERTO MADERO, VERSALLES, VILLA DEL PARQUE, VILLA LURO — el `_id: 1`
del `$sort` los deja alfabéticos)*. El enunciado no dice cómo desempatar; *"más musicales"* se leyó
como **más bandas**, no más integrantes *(con esa otra lectura, BARRACAS —3 + 3 + 1 = 7— y BERAZATEGUI
—7— empatan antes del ejercicio 4, y después del 4 gana BARRACAS 10 a 8; la ambigüedad solo cambia el
resto del orden)*.

> [!tip] `$sum: 1` es el `COUNT(*)` — y `$count` es el atajo
> `{ $group: { _id: '$barrio', cantidad: { $sum: 1 } } }` es la traducción literal de
> `SELECT barrio, COUNT(*) FROM bandas_resumen GROUP BY barrio`. Desde MongoDB 5.0 existe el
> acumulador `{ $count: {} }` con el mismo efecto. El `$sort` **después** del `$group` es el
> `ORDER BY`; `_id` es el nombre que MongoDB obliga a darle a la clave de agrupación.
