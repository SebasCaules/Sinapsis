# Práctica del 15/09 — TP9 MongoDB Parte I

## Resumen general

Esta práctica es el TP9 Parte I, la primera de la mitad NoSQL de la cursada, resuelta en `mongosh`
sobre MongoDB. A diferencia de toda la Unidad-01, el enunciado está escrito en el mismo motor que se
usa para correrlo: no hay traducción de sintaxis, aunque sí un desfasaje **de versión** (`ensureIndex`
en vez de `createIndex`, `find().count()` en vez de `countDocuments()`). La página cubre dos partes:
un recorrido guiado de **34 pasos acumulativos** sobre la colección `players` —CRUD básico,
selectores, `$regex`, `$set`/`$inc`/`$push`, upsert, proyección, `sort`/`limit`/`skip`, documentos
embebidos, índices y `explain()`— y **once ejercicios** sobre una colección `bandas` de músicos de
CABA, resueltos aquí con los discos embebidos como subdocumentos.

Para el parcial y para el TP importa sobre todo: que MongoDB es *schemaless* (la colección nace con el
primer `insertOne`, sin DDL); que los pasos son **acumulativos** —el resultado de cada uno depende de
si se corrieron los anteriores (el 9 borra los primeros dos jugadores, el 16 sube el peso de Messi, el
18 agrega un hobby a Silva)—; que `{campo: valor}` sobre un arreglo matchea "contiene un elemento
igual"; que embeber evita `$lookup` pero duplica datos al escribir; que un índice único es la única
restricción declarativa de MongoDB (no hay `NOT NULL` ni `CHECK`); y que el enunciado pide una vista
(`createView`) y un `$group` que los 34 pasos **no enseñan**, así que hay que resolverlos con lo visto
en la teórica o en la documentación.

Para llevarse al parcial: la sintaxis vigente de CRUD, proyección, índices y agregación; la lista de
métodos deprecados (§ *Qué del TP está deprecado*); y la resolución completa de los once ejercicios de
bandas, con las decisiones de modelado que hay que declarar (fechas como `Date` ISO, discos como
arreglo de subdocumentos, `EFECTO ALFONS` cargado como dos documentos).

## Setup del entorno

### Instalación del motor — Docker *(p. 1)*

El enunciado ofrece instalar Docker Desktop/Engine y levantar un contenedor con la imagen oficial de
MongoDB:

```bash
docker pull mongo
docker run --name Mymongo -p 27017:27017 -d mongo
docker exec -it Mymongo bash  # bash dentro del contenedor; adentro: mongosh
docker stop Mymongo
docker start Mymongo
docker ps -a
docker cp <filename> Mymongo:/<filename>
```

> [!warning] (crítico) `docker pull mongo` **no fija versión** — a diferencia del `mysql:9.7.2` del 04/08
> El tag es `latest` implícito: cada alumno que haga el `pull` en una fecha distinta puede recibir una
> versión distinta, y `explain()` (paso 34) cambia de formato entre versiones mayores. Conviene fijar
> el tag mayor —por ejemplo `mongo:8`— y anotar en la entrega qué `db.version()` devolvió el servidor.
> *(Qué versión baja hoy no está verificado → § Dudas abiertas.)*
>
> Dos diferencias más con el `run` de MySQL: **no hay variables de entorno** de autenticación (el
> servidor arranca **sin auth**; cualquier conexión al `27017` es admin), y **no hay volumen**: si se
> hace `docker rm Mymongo` se pierden `lab` y todo lo insertado. `docker stop`/`start` sí conservan
> los datos.

> [!tip] El atajo que el TP no menciona: `mongosh` directo, sin `bash` intermedio
> La imagen oficial `mongo` trae `mongosh` adentro (desde la serie 6.0 dejó de incluir el shell
> `mongo` legacy):
>
> ```bash
> docker exec -it Mymongo mongosh
> ```
>
> Esto no contradice el aviso que la [[Clase 14 - MongoDB Features]] copia de la documentación —*"The
> MongoDB Shell (mongosh) is not installed with MongoDB Server"*—: ese aviso vale para la
> **instalación nativa** (Community Edition), no para la imagen Docker. Y el `docker cp` de la lista
> sirve para lo que este TP **no** pide todavía: importar un `.json` con `mongoimport`.

## Introducción *(p. 1)*

> [!quote] Textual
> *"**MongoDB** es una base de datos de documentos, de código abierto que ofrece alto rendimiento,
> alta disponibilidad y escalamiento automático.*
>
> *Un registro en MongoDB es un **documento**, representado por una estructura de datos compuesta por
> pares de campo y valor. Los documentos en MongoDB poseen formato **JSON**. Los valores de los campos
> pueden incluir otros documentos, arreglos y arreglos de documentos."*

**La primera imagen del PDF** es una captura de terminal con un documento y cuatro flechas
*"← Campo: valor"*:

```javascript
{
  nombre: "Luis",  // ← Campo: valor
  edad: 34,  // ← Campo: valor
  estatus: "A",  // ← Campo: valor
  grupos: ["noticias", "deportes"]  // ← Campo: valor
}
```

> [!note] Es la misma figura de la documentación oficial, traducida
> El ejemplo `{name: "sue", age: 26, status: "A", groups: ["news", "sports"]}` es el de la portada del
> manual de MongoDB ("Documents"), traducido al español. Ilustra escalares (`"Luis"`, `34`) y un
> **arreglo** (`grupos`); el caso "otros documentos" aparece recién en el paso 28 (`team`).
>
> Precisión que el TP no hace: el formato de almacenamiento es **BSON**. Y una nota propia: "de
> código abierto" es discutible desde 2018, cuando MongoDB cambió la licencia a **SSPL**, que la OSI
> no reconoce como open source.

## Recorrido guiado — pp. 2–6, paso por paso

### COMANDOS BÁSICOS *(pp. 2–3)*

`mongosh` es una consola basada en JavaScript: si se omiten los paréntesis se muestra el **cuerpo**
del método, no su ejecución. `db.stats` sin paréntesis imprime `[Function: stats] …`; no es un error.
Es la trampa más frecuente del primer día, y el TP la pone antes de todo.

- **Paso 1** — `db.stats()`: recién conectado la base activa es `test`; devuelve `db: 'test'`,
  `collections: 0`, `objects: 0`, `dataSize: 0`… y `ok: 1`. Primera evidencia de que **las bases no
  se crean hasta que tienen algo**.
- **Paso 2** — `use lab` selecciona la base (no hace falta que exista): responde `switched to db
  lab`, pero `show dbs` todavía no la lista.
- **Paso 3** — `db.getCollectionNames()` devuelve `[]`.
- **Paso 4** — primer `insertOne`: `db.players.insertOne({name:'Aaron Appindangoye', height: 182,
  weight:187})` → `{ acknowledged: true, insertedId: ObjectId('…') }`.
- **Paso 5** — `db.getCollectionNames()` ahora devuelve `[ 'players' ]`, y `show dbs` ya lista `lab`.
- **Paso 6** — `db.players.find()` muestra además el `_id` generado. Todo documento debe tener un
  `_id` único; si no se asigna, MongoDB genera el **ObjectId**:

```javascript
[
  {
  _id: ObjectId('…'),
  name: 'Aaron Appindangoye',
  height: 182,
  weight: 187
  }
]
```

> [!note] `_id` es el único "constraint" que MongoDB impone solo
> Es la clave primaria: **única por colección**, con índice automático, y **no se puede modificar
> después** (un `$set` sobre `_id` falla). El `ObjectId` de 12 bytes codifica timestamp + valor
> aleatorio + contador, lo que lo hace ordenable por tiempo de inserción. La
> [[Clase 14 - MongoDB Features]] linkea la referencia oficial del `ObjectId`.

- **Paso 7** — segundo insert: `db.players.insertOne({name:'Edinson Cavani', height: 182, dob: new
  Date(1987,2,14,0,0)})`. Cavani no tiene `weight`, Aaron no tiene `dob`: dos documentos de la misma
  colección con campos distintos, sin que nada lo impida.
- **Paso 8** — `find()` de nuevo: dos documentos; el segundo con `dob: ISODate('1987-03-14T…')`.
- **Paso 9** — `db.players.deleteMany({})` borra los dos (`{ acknowledged: true, deletedCount: 2 }`).
  **Aaron y Cavani desaparecen**; en todo lo que sigue no existen. La colección sigue existiendo
  (vacía): `deleteMany` no es `drop()`.

> [!important] "No es necesario crear un esquema" — la frase que separa este TP de los ocho anteriores
> Del TP2 al TP8 cada ejercicio empezaba con `CREATE TABLE`. Aquí no hay DDL: la colección nace con
> el primer `insertOne`. Es el *schemaless* de la [[Clase 12 - Introduccion a NoSQL]], llevado a la
> práctica. La contracara aparece en el paso 12: un documento puede no tener un campo, y hay que
> consultarlo con `$exists`.

> [!bug] (crítico) `new Date(1987,2,14,0,0)` **no es el 14 de febrero de 1987**: en JavaScript los meses van de 0 a 11
> `new Date(año, mes, día, h, m)` toma el **mes con base 0**: `2` es **marzo**. Cavani nació el
> 14/02/1987; el documento guarda 14/03/1987, y el patrón se repite en los 12 inserts del paso 10: cada
> `dob` está escrito como si el mes fuera 1-based, así que queda **un mes corrido** (verificado uno por
> uno en § Paso 10).
>
> Segunda trampa: el constructor con componentes usa la **zona horaria local del proceso `mongosh`**,
> y MongoDB almacena en **UTC**. Desde Argentina (UTC−3), `new Date(1987,2,14,0,0)` se guarda como
> `1987-03-14T03:00:00.000Z`; en un contenedor Docker (UTC), como `…T00:00:00.000Z` — dos alumnos
> pueden tener valores distintos para el mismo comando. La forma reproducible es
> `new Date("1987-02-14")` o `ISODate("1987-02-14")`, en UTC. Ningún paso consulta por `dob`, pero en
> la resolución del ejercicio 1 se usan strings ISO por esto mismo.

### SELECTORES *(p. 3)*

`{field: value}` matchea igualdad; `{f1: v1, f2: v2}` es un AND implícito; `$lt`/`$lte`/`$gt`/`$gte`/
`$ne` son los comparadores.

- **Paso 11** — `db.players.find({preferred_foot: 'left', weight:{$gt:170}})` → un solo resultado,
  **Cristiano Ronaldo** (176); los demás zurdos pesan 148, 148, 159, 165 y 161. *(Si se corriera
  después del paso 16, Messi entraría con 180.)*
- **Paso 12** — `$exists` verifica presencia/ausencia de un campo: `db.players.find({height:
  {$exists:false}})` → **Harry Kane**, el único sin `height`.
- **Paso 13** — `$or` combinado con AND, textual:

> ```javascript
> db.players.find({preferred_foot:'right',
> $or:[{hobbies:'Playing football'},
> {hobbies:'Video games'},
> {weight:{$lt:150}}]
> })
> ```

Se lee: diestro **y** (juega al fútbol **o** videojuegos **o** pesa menos de 150) → los **6 diestros**
(Modric, Kane, Neymar, Hazard, Kroos, Ramos), cada uno por al menos una rama.

> [!important] `$exists: false` ≠ `null`
> `{height: null}` matchea documentos donde el campo **no existe o vale `null`**; `{height: {$exists:
> false}}` solo los que **no lo tienen**. En SQL esta distinción no existe porque toda fila tiene
> todas las columnas. Aquí aparece porque no hay esquema.

> [!tip] `{hobbies: 'Playing football'}` sobre un arreglo significa "contiene"
> Cuando el campo es un arreglo, la igualdad simple matchea si **algún elemento** es igual al valor.
> No hace falta `$in` ni `$elemMatch` para "tiene tal hobby". Es la base del ejercicio 7 de la p. 7
> (`'discos.anio': 2006`).

### EXPRESIONES REGULARES *(p. 4)*

MongoDB soporta expresiones regulares compatibles con **Perl**.

- **Paso 14** — `db.players.find({name: { $regex: "^S"}})` → **Sergio Ramos, Samuel Umtiti**. Es
  case-sensitive: `"^s"` no devolvería nada (agregar `$options: "i"`, o escribir `/^s/i`).
- **Paso 15** — `db.players.find({name: { $regex: "o$"}})` → **Cristiano Ronaldo**, único (Ramos y
  Kroos terminan en `s`, Neymar en `r`).

> [!note] Solo un regex con `^` anclado **acota** el índice
> `^S` sobre un índice en `name` se resuelve con `IXSCAN` sobre un rango acotado; `o$` con el mismo
> índice también da `IXSCAN`, pero con bounds `["", {})` —examina todas las claves del índice y evalúa
> la regex contra cada una— y luego `FETCH`; sin índice, `COLLSCAN`. Es el equivalente del
> `LIKE 'S%'` vs. `LIKE '%o'` de la [[Clase 08 - Explicando el plan]]; el detalle vive en
> [[1.08.01 - Plan de ejecución|Plan de ejecución]].

### COMANDOS DE ACTUALIZACIÓN *(pp. 4–5)*

`update` tiene dos argumentos: el selector y el campo a actualizar (`$set`).

- **Paso 16** — `db.players.updateOne({name: 'Lionel Messi'},{$set:{weight:180}})` →
  `matchedCount: 1, modifiedCount: 1`. Desde aquí Messi es el más pesado (180), lo que decide el
  paso 26.
- **Paso 17** — `$inc` incrementa o decrementa: `db.players.updateOne({name: 'Luka Modric'},
  {$inc:{height:-5}})` corrige su altura a **175**. Para un valor conocido, `$set: {height: 175}`
  sería más honesto que `$inc` (que depende del valor previo); el TP usa `$inc` para mostrar el
  operador.
- **Paso 18** — `$push` agrega a un arreglo: `db.players.updateOne({name: 'David Silva'},
  {$push:{hobbies:'Swimming'}})`. El conteo del paso 27 sube de 8 a 9 por este push. `$push`
  **duplica** si se ejecuta dos veces; `$addToSet` agrega solo si no está (el TP no lo menciona;
  conviene saberlo para el ejercicio 4 si se modelaran los integrantes como arreglo).
- **Pasos 19–21** — upsert con la colección `hits`: sin `{upsert:true}`,
  `updateOne({page:'players'}, {$inc:{hits:1}})` da `matchedCount: 0, modifiedCount: 0` y `hits` ni
  se crea; con `{upsert:true}` (paso 20) nace `hits` con `{page:'players', hits: 1}`
  (`upsertedCount: 1`); repetido (paso 21), `matchedCount: 1, modifiedCount: 1` y `hits` sube a 2, 3…
- **Paso 22** — `updateMany`: `db.players.updateMany({}, {$set:{active:true}})` →
  `matchedCount: 12, modifiedCount: 12`. Todos ganan un campo `active` que ningún insert tenía: un
  `ALTER TABLE ADD COLUMN` sin `ALTER TABLE`, y la forma del **ejercicio 4** de la p. 7.

> [!warning] "el documento completo no será reemplazado" — la frase importa más de lo que parece
> En el shell legacy, `update({…}, {weight: 180})` **sin** `$set` reemplazaba el documento entero.
> `updateOne` moderno **rechaza** un documento sin operadores `$`, y para reemplazar existe
> `replaceOne`. El TP está del lado seguro.

> [!bug] (nota) "tercer parámetro en true" describe la firma **vieja**, no la que el TP usa
> `db.col.update(query, update, true)` era la forma legacy, con el upsert como tercer argumento
> posicional. En `updateOne` es un **documento de opciones** `{upsert: true}` —lo que el paso 20 ya
> escribe bien—; `updateOne(q, u, true)` literal **falla** en `mongosh`.

> [!important] (clave) El upsert es el `INSERT … ON DUPLICATE KEY UPDATE` de la [[Práctica 2026-09-01]]
> Mismo problema —el contador que puede no existir todavía—, resuelto en el ejercicio 4 del TP7. Aquí
> no hace falta clave única en `page`, lo cual también significa que dos upserts concurrentes pueden
> insertar dos documentos `{page:'players'}` si no hay índice único; el TP no lo advierte.

### SELECCIÓN DE CAMPOS *(p. 5)*

`find` acepta un segundo parámetro opcional: la lista de campos a proyectar.

- **Pasos 23–24** — `db.players.find({},{name:1})` devuelve 12 documentos `{_id, name}`; agregando
  `_id:0` deja solo `{name}`. Una proyección **mezcla inclusión (`1`) y exclusión (`0`) solo para
  `_id`**: `{name: 1, weight: 0}` es error.
- **Paso 25** — `.sort({height:-1})`: `1` asc, `-1` desc. Resultado esperado *(con Modric ya en 175
  por el paso 17)*:

  | `height` | `name` |
  | :---: | --- |
  | 185 | Cristiano Ronaldo |
  | 182 | Toni Kroos · Sergio Ramos |
  | 180 | Samuel Umtiti |
  | 175 | Luka Modric · Neymar · Antoine Griezmann · Paulo Dybala |
  | 172 | Eden Hazard |
  | 170 | David Silva · Lionel Messi |
  | *(sin campo)* | **Harry Kane — último** |

  Un campo ausente ordena como `null`, que en BSON está por debajo de los números: en descendente
  queda al final, en ascendente iría primero. El orden entre empates (los dos 182, los cuatro 175) no
  está definido; para hacerlo determinista se agrega un segundo criterio,
  `.sort({height: -1, name: 1})`.
- **Paso 26** — `limit`/`skip`: `.sort({weight:-1}).limit(2).skip(1)`. Pesos descendentes después del
  paso 16: Messi **180** · Ronaldo **176** · Kroos **172** · Ramos 165 · Umtiti 165 · Hazard 163 ·
  Dybala 161 · Neymar 150 · Silva 148 · Griezmann 148 · Modric 143 · Kane 143. **Resultado: Cristiano
  Ronaldo y Toni Kroos** *(sin el paso 16 serían Kroos y Ramos/Umtiti)*. El orden de encadenado —
  `limit(2).skip(1)` o `skip(1).limit(2)`— no importa: el servidor aplica siempre
  `sort → skip → limit`.
- **Paso 27** — `countDocuments({hobbies:'Swimming'})` o `find({hobbies:'Swimming'}).count()` → **9**
  (Modric, Kane, Neymar, Silva —por el push del paso 18—, Griezmann, Messi, Ronaldo, Umtiti, Dybala;
  sin el paso 18 serían 8). La segunda forma está **deprecada** en `mongosh` (verificado en la
  documentación oficial el 15/09; `cursor.count()` corre la misma suerte): usar `countDocuments`, que
  además es exacto.

> [!important] `.limit(2).skip(1)` y `.skip(1).limit(2)` dan lo mismo
> Un `sort` sin índice **carga todo en memoria** y tiene un tope (100 MB por defecto; hasta la 5.x,
> superarlo daba error salvo `allowDiskUse`; desde la 6.0 vuelca a disco por defecto,
> `allowDiskUseByDefault: true`). `limit` acota cuánto hay que conservar (top-k), no cuánto hay que
> leer: sigue siendo un `COLLSCAN` completo.

### DOCUMENTOS EMBEBIDOS *(p. 6)*

El valor de un campo puede ser otro documento JSON — sirve, por ejemplo, para simular joins.

- **Paso 28** — `db.players.updateOne({name: 'Cristiano Ronaldo'},{$set:{team:{ team_long_name:
  'Juventus', team_short_name: 'JUV'}}})`. Ningún otro jugador tiene `team`.
- **Paso 29** — notación de punto: `db.players.find({'team.team_short_name': 'JUV'})` → **Cristiano
  Ronaldo**. La clave con punto va **entre comillas** (`'team.team_short_name'`), porque sin ellas no
  es una clave válida en JavaScript.

> [!important] (clave) "simular JOINS" conecta este TP con la [[Clase 13 - NoSQL-EmbebidosVSNormalizado]]
> Embeber el equipo dentro del jugador evita el join al leer, y duplica `Juventus` en cada jugador del
> club al escribir: si cambia de nombre hay que actualizar N documentos. La alternativa normalizada
> —una colección `teams` y un `team_id` en `players`— obliga a dos consultas (o a `$lookup`, que el TP
> no ve). Es exactamente el trade-off que decide el **ejercicio 1** de la p. 7: ¿los discos van
> embebidos en la banda o en una colección aparte? *(La respuesta que se propone abajo: embebidos.)*

### ÍNDICES Y ADMINISTRACIÓN *(p. 6)*

Los índices en MongoDB funcionan parecido a los de una base relacional.

- **Paso 30** — `db.players.ensureIndex({name:1})`. Hoy se escribe:

```javascript
db.players.createIndex({name: 1})  // → 'name_1'
```
- **Paso 31** — `dropIndex({name:1})` acepta la especificación o el nombre (`'name_1'`);
  `{ nIndexesWas: 2, ok: 1 }` —el `2` incluye el índice automático de `_id`, que no se puede borrar—.
- **Paso 32** — índice único: `ensureIndex({name:1},{unique:true})`. Funciona porque los 12 nombres
  son distintos; con un duplicado fallaría con `E11000 duplicate key error` y no se crearía. El paso
  31 tiene que ejecutarse antes: crear `{name:1}` único cuando ya existe `{name:1}` sin único da
  `IndexOptionsConflict`.
- **Paso 33** — índices en campos embebidos, arreglos y compuestos. El único ejemplo que trae el TP es
  el compuesto (`ensureIndex({name:1, weight:1})`); los otros dos, sin ejemplo. El **multikey** (sobre
  un arreglo) no tiene equivalente relacional: indexa cada elemento, así que `{hobbies: 'Swimming'}`
  puede usar índice. Sobre el compuesto vale la regla del prefijo de la
  [[Clase 08 - Explicando el plan]]: sirve para `name` solo y para `name+weight`, **no** para `weight`
  solo.

```javascript
db.players.createIndex({'team.team_short_name': 1})  // embebido, notación de punto
db.players.createIndex({hobbies: 1})  // arreglo → índice "multikey": una entrada por elemento
```

- **Paso 34** — `explain()`: `db.players.find({name: 'Lionel Messi'}).explain()`. Lo que hay que
  buscar en la salida (modo por defecto `queryPlanner`) es el `winningPlan`; sin el índice sería
  `{ stage: 'COLLSCAN', filter: {…} }`:

```javascript
queryPlanner: {
  namespace: 'lab.players',
  winningPlan: {
  stage: 'FETCH',
  inputStage: {
  stage: 'IXSCAN',
  keyPattern: { name: 1 },
  indexName: 'name_1',  // ← "el nombre del índice que es usado"
  isUnique: true,
  indexBounds: { name: [ '["Lionel Messi", "Lionel Messi"]' ] }
  }
  }
}
```

Con `explain('executionStats')` se ven además `totalDocsExamined` (1 vs. 12) —el equivalente de
`EXPLAIN ANALYZE` de la [[Práctica 2026-08-18]]—. Con 12 documentos la diferencia de tiempo es cero:
la lección es leer `IXSCAN` vs. `COLLSCAN`, igual que en el TP5 con 6 filas.

> [!warning] (crítico) `ensureIndex` **ya no existe en la documentación** — el método es `createIndex`
> La lista de métodos de colección del manual actual tiene `createIndex`, `createIndexes`,
> `dropIndex`, `dropIndexes`, `getIndexes`, `hideIndex`, `unhideIndex` y `totalIndexSize`;
> `ensureIndex` **no aparece** (verificado el 15/09 contra
> `docs/manual/reference/method/js-collection/`). Era un alias deprecado desde MongoDB 3.0. En
> `mongosh` queda —según entiendo— como alias que imprime una advertencia y llama a `createIndex`;
> **si en la consola falla con `is not a function`**, la corrección es mecánica: reemplazar
> `ensureIndex` por `createIndex` en los pasos 30, 32 y 33 (`db.players.createIndex({name: 1})` →
> `'name_1'`). Está anotado en § *Dudas abiertas* para verificarlo en el motor.
>
> La [[Clase 14 - MongoDB Features]] usa `ensureIndex` en sus ejemplos de índices —los mismos que
> *Seven Databases* trae con `phones`—, así que el TP hereda la sintaxis del libro y del deck, no la
> inventa.

> [!note] Es el único "constraint" declarativo que MongoDB ofrece
> Un índice único es lo más parecido a `UNIQUE` de la [[Clase 09 - Restricciones integridad-Parte 1]].
> No hay `NOT NULL`, ni `CHECK`, ni claves foráneas (existe la validación de esquema con
> `$jsonSchema`, que este TP no toca). Con **`sparse`** o **`partialFilterExpression`** el índice
> único puede permitir documentos **sin** el campo, que es el caso de Kane con `height`.

> [!warning] La forma de la salida depende de la versión del servidor — otra razón para pinnear la imagen
> El bloque de arriba sigue la estructura de las series 5.x–8.x (`queryPlanner.winningPlan.
> inputStage`). En algunas versiones el `winningPlan` viene envuelto en `queryPlan` con
> `slotBasedPlan`, y las claves cambian de lugar. Si lo que se ve no coincide con el ejemplo, no es
> que el índice no se use.

### Ejercicio 1 — modelo propuesto *(propuesta propia)*

**Una sola colección, `bandas`, con los discos embebidos.** Justificación siguiendo el *hint*
("revise las consultas"):

| Consulta | Qué necesita | Consecuencia para el modelo |
| :---: | --- | --- |
| 2, 3, 4 | ordenar y modificar `integrantes` | escalar numérico en el documento raíz |
| 5, 6 | `genero` exacto y `estilo` por patrón | dos strings; `estilo` ausente cuando no hay |
| 7, 8 | *"han lanzado disco en/después de"* un año | los discos tienen que tener el **año como número**, no dentro del string `"MERIDIANO (2006)"` |
| 9, 11 | contar por `barrio` | string en la raíz |
| 10 | vista con solista, género, barrio, integrantes | todos en la raíz: la vista es un `$project` |

**Ninguna consulta pide nada "por disco"** (ni cuántos discos, ni el más viejo, ni buscar un título):
los discos solo se filtran por año **desde la banda**. Es el caso canónico de **embeber**: los discos
se leen siempre junto con su banda, son pocos, y no se comparten entre bandas. Una colección `discos`
aparte obligaría a `$lookup` en 7 y 8 sin ganar nada.

> [!important] Las tres decisiones que hay que declarar al entregar
> 1. **`fecha_inscripcion` como `Date`**, no como string `"20/01/2018"`: un string `dd/mm/yyyy` no
> ordena cronológicamente. Y se escribe como ISO `new Date("2018-01-20")`, no como
> `new Date(2018, 0, 20)`, por el problema del mes con base 0 del paso 7.
> 2. **`discos` como arreglo de `{titulo, anio}`** con `anio` numérico. Las bandas sin discos no
> llevan el campo (alternativa defendible: `discos: []`; cambia solo la forma de preguntar "sin
> discos": `$exists` vs. `$size: 0`).
> 3. **`EFECTO ALFONS` se carga como dos documentos**, tal como está en la tabla: es la lectura
> literal, y es la que hace que el ejercicio 9 dé 3 (Barracas: Efecto Alfons ×2 + Jaydee M).
> Fusionarlos en uno con dos discos y dos fechas da **2** en el 9 y cambia los promedios del 10 (→
> § Preguntas para el docente).

```javascript
use lab

db.bandas.insertMany([
```

### Ejercicio 10 — la vista `bandas_resumen` y el promedio por género

> [!important] (crítico) Lo que el TP pide y no enseña — **vistas** y **`$group`**
> Los 34 pasos no traen `createView` ni `aggregate`. El enunciado dice "una vista llamada
> bandas_resumen (que deberán crear)" como si la sintaxis fuera conocida. No lo es desde este PDF: hay
> que ir a la [[Clase 14 - MongoDB Features]] (aggregation pipeline) y a la documentación de
> `db.createView()`. Lo que sigue es propuesta propia.

**La vista** — "solo los datos del solista, el género de la banda, el barrio y los integrantes" → un
`$project` de cuatro campos, sin `_id`:

```javascript
db.createView(
  'bandas_resumen',  // nombre de la vista
  'bandas',  // colección origen
  [ { $project: { _id: 0, nombre: 1, genero: 1, barrio: 1, integrantes: 1 } } ]
)
// → { ok: 1 }
db.getCollectionNames()  // [ 'bandas', 'bandas_resumen', … ]
db.bandas_resumen.find().limit(2)
```

**El promedio por género, ordenado alfabéticamente**, se corre **sobre la vista**:

```javascript
db.bandas_resumen.aggregate([
  { $group: { _id: '$genero', promedio_integrantes: { $avg: '$integrantes' } } },
  { $sort:  { _id: 1 } }
])
```

Resultado esperado:

| `_id` (género) | promedio **antes** del ej. 4 | promedio **después** del ej. 4 |
| --- | :---: | :---: |
| FOLKLORE | 7 | 8 |
| HIP HOP / RAP | 1 | 2 |
| INDIE | 4 | 5 |
| INSTRUMENTAL | 1 | 2 |
| POP | 5 *((6+4)/2)* | 6 |
| PUNK | 3 | 4 |
| ROCK | 3 *((3+5+1+3)/4)* | 4 |
| SOLISTA | 1 | 2 |

> [!note] Lo que una vista de MongoDB es y no es
> Es **un pipeline guardado** con un nombre; cada lectura lo re-ejecuta sobre la colección origen. No
> materializa: refleja el `$inc` del ejercicio 4 al instante — igual que la vista relacional de la
> [[Clase 06 - Vistas-Parte 1]], y por eso el ejercicio 11 se puede correr sobre ella. Es **de solo
> lectura** (no acepta `insertOne`/`updateOne`, no hay `INSTEAD OF` ni `WITH CHECK OPTION`) y **no
> admite índices propios** —usa los de `bandas`—. Se consulta con `find()` y `aggregate()`, como una
> colección; `db.getCollectionInfos()` distingue `type: 'view'`. `$avg` sobre documentos sin
> `integrantes` los ignora (no cuenta como 0); aquí todos lo tienen.

### Ejercicio 11 — bandas por barrio, de más a menos musical

```javascript
db.bandas_resumen.aggregate([
  { $group: { _id: '$barrio', cantidad: { $sum: 1 } } },
  { $sort:  { cantidad: -1, _id: 1 } }
])
```

Resultado esperado: **BARRACAS 3**, y después nueve barrios con **1** (AGRONOMIA, BALVANERA,
BERAZATEGUI, LA LUCILA, MORENO, PUERTO MADERO, VERSALLES, VILLA DEL PARQUE, VILLA LURO — el `_id: 1`
del `$sort` los deja alfabéticos). El enunciado no dice cómo desempatar; "más musicales" se leyó como
**más bandas**, no más integrantes (con esa otra lectura, BARRACAS —3+3+1=7— y BERAZATEGUI —7—
empatan antes del ejercicio 4 y después gana BARRACAS 10 a 8).

> [!tip] `$sum: 1` es el `COUNT(*)` — y `$count` es el atajo
> `{ $group: { _id: '$barrio', cantidad: { $sum: 1 } } }` es la traducción literal de
> `SELECT barrio, COUNT(*) FROM bandas_resumen GROUP BY barrio`. Desde MongoDB 5.0 existe el
> acumulador `{ $count: {} }` con el mismo efecto. El `$sort` después del `$group` es el `ORDER BY`;
> `_id` es el nombre que MongoDB obliga a darle a la clave de agrupación.

## Qué del TP está deprecado — y cómo se escribe hoy

| Paso | Como está en el TP | Estado | Forma actual |
| :---: | --- | --- | --- |
| 27 | `find({…}).count()` | **deprecado** en `mongosh` *(verificado en la página de compatibilidad, 15/09)* | `countDocuments({…})` — la primera forma del mismo paso |
| 30, 32, 33 | `ensureIndex(…)` | **fuera de la documentación**; alias deprecado desde 3.0 | `createIndex(…)`, mismos argumentos |
| 19 | *"tercer parámetro en true"* | prosa de la firma legacy `update(q, u, true)` | `updateOne(q, u, {upsert: true})` — como el paso 20 ya lo escribe |

| p. 1 | `docker pull mongo` | `latest` implícito | `docker pull mongo:8` *(o el tag que fije la cátedra)* |

Todo lo demás —`insertOne`, `find` con proyección, `deleteMany`, `updateOne`/`updateMany` con
operadores, `$regex`, `$exists`, `$or`, `sort`/`limit`/`skip`, `dropIndex`, `explain`— es la API
vigente. Comparado con la Unidad-01, el desfasaje es **mínimo y de versión**, no de motor.

> [!note] Comparación con la teórica del mismo lunes
> La [[Clase 14 - MongoDB Features]] usa `db.towns.update(…)` con salida `WriteResult({…})` y
> `db.internos.count()`, más viejos que lo que el TP usa (`updateOne`, `countDocuments`). El TP está
> más al día que el deck en CRUD, y a la par en índices (`ensureIndex` en los dos).
