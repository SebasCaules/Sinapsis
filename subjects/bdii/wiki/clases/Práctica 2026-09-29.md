# Práctica del 29/09 — TP10 Cassandra Parte I

## Resumen general

Esta práctica es el TP10 Parte I, la primera sobre Cassandra y la primera de la `Unidad-03`. El
enunciado trae el setup con Docker y un único ejercicio guiado en 18 pasos: un servicio de música
con un *keyspace* `demo_cql_music`, una tabla `canciones` con clave `uuid` y una tabla
`lista_reproduccion` desnormalizada, con clave de partición `id` y clave de *clustering*
`nro_cancion`. Sobre ese modelo se ejercitan `now()`, `ORDER BY`, `ALLOW FILTERING`, un índice
secundario, una colección `set<text>` con `CONTAINS` y los `DELETE` por clave parcial y completa. Es
la práctica de la [[Clase 15 - Introduccion a Cassandra|Clase 15]] y entra al parcial del 13/10.

Todo se corrió en Cassandra 5.0.9 (lo que baja hoy `docker pull cassandra`) con `cqlsh` 6.2.0, y
cada salida de esta página es real. Los 18 pasos corren tal como están escritos; las diferencias
son de explicación y de entorno. La imagen oficial **no trae autenticación activada**: el usuario y
la clave `cassandra`/`cassandra` se aceptan, pero también cualquier otro par. El error del paso 9
no menciona la clave de partición: pide `ALLOW FILTERING`. `CREATE INDEX` sin `USING` crea el
índice secundario *legacy* (tabla oculta), no el SAI que agrega la 5.0. Y el comando del
enunciado para DataGrip reutiliza el nombre `Mycassandra`, así que choca con el contenedor anterior.

Para el parcial: qué `WHERE` acepta CQL y por qué (partición completa, *clustering* en orden, o
índice, o `ALLOW FILTERING`), que `ORDER BY` solo ordena dentro de una partición y por columnas de
*clustering*, que `INSERT` es un *upsert* y que un `DELETE` exige la clave de partición. Todo eso
está en [[3.15.06 - Clave primaria en Cassandra — partition key, clustering key y ALLOW FILTERING|Clave primaria en Cassandra]]
y [[3.15.03 - CQL y modelado orientado a consultas|CQL y modelado orientado a consultas]]. El
[[Parcial 1Q2026]] pidió escribir el `CREATE KEYSPACE` del paso 1.

## Ejercicio 1 — el servicio de música

> [!quote] Enunciado, textual
> *"Para efectos de la práctica, utilizaremos un servicio de música como ejemplo, que requiere de
> una Column Family canciones. Este servicio está compuesto por las columnas título, álbum, artista
> y una columna datos que contiene el archivo de audio real. La tabla utiliza una columna id del
> tipo UUID como clave primaria o clave de particionamiento."*

### Paso 1 — crear el *keyspace*

```sql
create KEYSPACE demo_cql_music WITH replication = {'class': 'SimpleStrategy', 'replication_factor': '1' };
```

**Salida real:** ninguna (éxito silencioso). `DESCRIBE KEYSPACE` lo confirma:

```sql
CREATE KEYSPACE p0929_demo_cql_music WITH replication = {'class': 'SimpleStrategy', 'replication_factor': '1'}  AND durable_writes = true;
```

El enunciado explica bien el factor de replicación: RF 1 = **una sola copia** de cada fila, sin
réplicas adicionales. `SimpleStrategy` ignora la topología de *data centers*; para varios *data
centers* se usa `NetworkTopologyStrategy` (slide 59 de la Clase 15,
[[3.15.02 - Arquitectura de Cassandra — anillo peer-to-peer, particionado y replicación|Arquitectura de Cassandra]]).
El `durable_writes = true` que agrega el motor es el que manda cada escritura al *commit log*.

(clave) Esta sentencia es la Pregunta 31 del [[Parcial 1Q2026]] (*"Escriba en CQL la sentencia
correcta para crear un keyspace"*). El signo es `=`: la respuesta que se dio en ese examen,
`CREATE KEYSPACE nombre_keyspace WITH replication : {…};`, corrida tal cual, da
`SyntaxException: line 1:49 no viable alternative at input ':'` y no crea nada (la plataforma le
dio 3/3 igual).

### Paso 2 — usar el *keyspace*

```sql
USE demo_cql_music;
```

Sin salida. A partir de ahí el *prompt* interactivo pasa a `cqlsh:demo_cql_music>` y las tablas se
nombran sin prefijo.

### Paso 3 — la tabla `canciones`

```sql
create TABLE canciones (id uuid PRIMARY KEY, titulo text, album text, artista text, data blob);
```

Sin salida. `id` es a la vez la clave primaria y la **clave de partición** (una fila por partición).
(nota) El texto habla de *"una columna datos"*; el DDL la llama `data`, de tipo `blob`.

### Paso 4 — un `INSERT`

```sql
INSERT INTO canciones (id, titulo, album, artista)
VALUES (7db1a490-5878-11e2-bcfd-0800200c9a66, 'Asilo', 'Salvavidas de Hielo','Jorge Drexler');
```

**Salida real** de `SELECT * FROM canciones;`:

```
 id                                   | album               | artista       | data | titulo
--------------------------------------+---------------------+---------------+------+--------
 7db1a490-5878-11e2-bcfd-0800200c9a66 | Salvavidas de Hielo | Jorge Drexler | null |  Asilo

(1 rows)
```

(nota) `SELECT *` no respeta el orden del `CREATE TABLE`: pone primero la clave y después el resto
de las columnas **en orden alfabético**. `data` no se insertó y figura `null`.

> [!quote] Enunciado, entre los pasos 4 y 5
> *"En una base de datos relacional, para simular una lista de reproducción generada por el
> usuario, se debería crear una tabla lista_reproduccion con una clave foránea a la tabla
> canciones. Sin embargo, en Cassandra se deben desnormalizar los datos porque los joins no son
> soportados."*

Es la idea central de [[3.15.03 - CQL y modelado orientado a consultas|CQL y modelado orientado a consultas]]:
`lista_reproduccion` **copia** `titulo`, `album` y `artista` en vez de referenciarlos.

### Paso 5 — la tabla `lista_reproduccion`

```sql
create TABLE lista_reproduccion (id uuid, nro_cancion int, cancion_id uuid, titulo text,
  album text, artista text, PRIMARY KEY (id, nro_cancion));
```

Sin salida. `DESCRIBE TABLE` agrega lo que el motor deduce:
`PRIMARY KEY (id, nro_cancion)) WITH CLUSTERING ORDER BY (nro_cancion ASC)`. Las tres viñetas del
enunciado son correctas: `id` es la **clave de partición** (todas las canciones de una lista viven
juntas en la misma partición) y `nro_cancion` la **clave de *clustering*** (ordena las filas dentro
de la partición, ascendente por defecto) →
[[3.15.06 - Clave primaria en Cassandra — partition key, clustering key y ALLOW FILTERING|Clave primaria en Cassandra]].
La función de cada clave es la Pregunta 7 del [[Parcial 1Q2026]].

### Paso 6 — la primera canción de la lista

```sql
INSERT INTO lista_reproduccion (id, nro_cancion, cancion_id, titulo, artista, album)
VALUES (62c36092-82a1-3a00-93d1-46196ee77204, 1, 7db1a490-5878-11e2-bcfd-0800200c9a66,
        'Asilo', 'Jorge Drexler', 'Salvavidas de Hielo');
```

**Salida real** (`SELECT * FROM lista_reproduccion;`):

```
 id                                   | nro_cancion | album               | artista       | cancion_id                           | titulo
--------------------------------------+-------------+---------------------+---------------+--------------------------------------+--------
 62c36092-82a1-3a00-93d1-46196ee77204 |           1 | Salvavidas de Hielo | Jorge Drexler | 7db1a490-5878-11e2-bcfd-0800200c9a66 |  Asilo
```

Que la lista de columnas del `INSERT` esté en otro orden que la tabla (`titulo, artista, album`) no
importa: los valores van por nombre.

### Paso 7 — `now()` para generar los `id`

> [!quote] Enunciado
> *"Insertar varios registros en el Column Family canciones utilizando la función now() para
> rellenar el campo id. Luego obtener los id generados, e insertar los nuevos registros en el
> Column Family lista_reproduccion en el orden que quiera"*

```sql
INSERT INTO canciones (id, titulo, album, artista) VALUES (now(), 'Todo se transforma', 'Eco', 'Jorge Drexler');
INSERT INTO canciones (id, titulo, album, artista) VALUES (now(), 'Tu falta de querer', 'Mon Laferte Vol. 1', 'Mon Laferte');
INSERT INTO canciones (id, titulo, album, artista) VALUES (now(), 'Hasta la raiz', 'Hasta la raiz', 'Natalia Lafourcade');
SELECT id, titulo, artista, token(id) FROM canciones;
```

**Salida real** (los `id` cambian en cada corrida):

```
 id                                   | titulo             | artista            | system.token(id)
--------------------------------------+--------------------+--------------------+----------------------
 166affd0-bc2c-11f1-b54b-8d1a232e398e | Tu falta de querer |        Mon Laferte | -8684286806439741081
 7db1a490-5878-11e2-bcfd-0800200c9a66 |              Asilo |      Jorge Drexler | -6878047519264737593
 166affda-bc2c-11f1-b54b-8d1a232e398e |      Hasta la raiz | Natalia Lafourcade |   711196793423188942
 166ad8c0-bc2c-11f1-b54b-8d1a232e398e | Todo se transforma |      Jorge Drexler |   974387194318479819

(4 rows)
```

Con esos `id`, las tres canciones nuevas entran a la lista **desordenadas a propósito** (3, 2, 4):

```sql
INSERT INTO lista_reproduccion (id, nro_cancion, cancion_id, titulo, artista, album)
VALUES (62c36092-82a1-3a00-93d1-46196ee77204, 3, 166affda-bc2c-11f1-b54b-8d1a232e398e, 'Hasta la raiz', 'Natalia Lafourcade', 'Hasta la raiz');
INSERT INTO lista_reproduccion (id, nro_cancion, cancion_id, titulo, artista, album)
VALUES (62c36092-82a1-3a00-93d1-46196ee77204, 2, 166ad8c0-bc2c-11f1-b54b-8d1a232e398e, 'Todo se transforma', 'Jorge Drexler', 'Eco');
INSERT INTO lista_reproduccion (id, nro_cancion, cancion_id, titulo, artista, album)
VALUES (62c36092-82a1-3a00-93d1-46196ee77204, 4, 166affd0-bc2c-11f1-b54b-8d1a232e398e, 'Tu falta de querer', 'Mon Laferte', 'Mon Laferte Vol. 1');
```

**Salida real** de un `SELECT` sin `ORDER BY`: `nro_cancion` sale **1, 2, 3, 4**, no en el orden de
inserción. La clave de *clustering* ordena físicamente las filas dentro de la partición.

Tres cosas que el enunciado no dice:

- **Las filas de `canciones` salen en orden de *token*, no de inserción.** El `SELECT` recorre el
  anillo: `token(id)` crece de arriba abajo. Es el hash del particionador
  `Murmur3Partitioner` (el que reporta `system.local`), un entero de 64 bits con signo →
  [[3.15.02 - Arquitectura de Cassandra — anillo peer-to-peer, particionado y replicación|Arquitectura]].
- **(atención) `now()` devuelve un `timeuuid` (UUID versión 1) y la columna es `uuid`.** El motor
  lo acepta, porque todo `timeuuid` es un `uuid` válido. Pero las funciones de tiempo no se aplican a
  una columna `uuid`:
  `SELECT titulo, toTimestamp(id) FROM canciones;` →
  `Invalid call to function totimestamp, none of its type signatures match (known type signatures: system.totimestamp : (date) -> timestamp, system.totimestamp : (timeuuid) -> timestamp)`.
  Si interesa el instante de creación, la columna debería declararse `timeuuid`; si no, `uuid()`
  (UUID versión 4, aleatorio) es la función que corresponde a una columna `uuid`. *(Resolución del
  vault.)*
- (nota) Los UUID fijos del enunciado son de dos tipos distintos: `7db1a490-5878-11e2-…` es versión 1
  (basado en tiempo: 07/01/2013) y `62c36092-82a1-3a00-…` es versión 3 (basado en nombre). A
  Cassandra le da igual en una columna `uuid`.

### Paso 8 — `ORDER BY` sobre la clave de *clustering*

```sql
SELECT * FROM lista_reproduccion where id = 62c36092-82a1-3a00-93d1-46196ee77204 ORDER BY nro_cancion DESC;
```

**Salida real:**

```
 id                                   | nro_cancion | album               | artista            | cancion_id                           | titulo
--------------------------------------+-------------+---------------------+--------------------+--------------------------------------+--------------------
 62c36092-82a1-3a00-93d1-46196ee77204 |           4 |  Mon Laferte Vol. 1 |        Mon Laferte | 166affd0-bc2c-11f1-b54b-8d1a232e398e | Tu falta de querer
 62c36092-82a1-3a00-93d1-46196ee77204 |           3 |       Hasta la raiz | Natalia Lafourcade | 166affda-bc2c-11f1-b54b-8d1a232e398e |      Hasta la raiz
 62c36092-82a1-3a00-93d1-46196ee77204 |           2 |                 Eco |      Jorge Drexler | 166ad8c0-bc2c-11f1-b54b-8d1a232e398e | Todo se transforma
 62c36092-82a1-3a00-93d1-46196ee77204 |           1 | Salvavidas de Hielo |      Jorge Drexler | 7db1a490-5878-11e2-bcfd-0800200c9a66 |              Asilo

(4 rows)
```

Funciona porque se cumplen **las dos** condiciones de CQL. Las dos variantes que las rompen,
corridas en el motor:

| Consulta | Error real |
| --- | --- |
| `SELECT * FROM lista_reproduccion ORDER BY nro_cancion DESC;` (sin fijar la partición) | `ORDER BY is only supported when the partition key is restricted by an EQ or an IN.` |
| `SELECT * FROM lista_reproduccion WHERE id = … ORDER BY titulo;` (columna que no es de *clustering*) | `Order by is currently only supported on the clustered columns of the PRIMARY KEY, got titulo` |

Es lo que dice el slide 67 de la Clase 15 sobre los criterios de ordenamiento: *"Siempre han de ser
sobre columnas que estén incluidas en la clustering key"*. `ORDER BY` no ordena la tabla: elige el sentido en que se
lee **una** partición que ya está ordenada.

### Paso 9 — filtrar por `artista`

```sql
SELECT * FROM lista_reproduccion WHERE artista='Jorge Drexler';
```

**Salida real** (error, como anticipa el enunciado):

```
InvalidRequest: Error from server: code=2200 [Invalid query] message="Cannot execute this query as it might involve data filtering and thus may have unpredictable performance. If you want to execute this query despite the performance unpredictability, use ALLOW FILTERING"
```

> [!warning] (atención) El enunciado explica bien la causa, pero el mensaje no dice eso
> El TP afirma que *"Cassandra rechaza la consulta porque el campo artista no es una columna de la
> clave de partición"*. El motor no menciona la clave de partición: dice que la consulta
> *podría requerir filtrar* y ofrece `ALLOW FILTERING`. La causa de fondo es más amplia que la del
> enunciado: el `WHERE` no fija ninguna partición y `artista` no es parte de la clave primaria ni
> tiene índice, así que la única forma de responder es leer todas las filas y descartar. Restringir
> **solo** una columna de *clustering* da el mismo error (verificado con la tabla `blogs` del slide
> 70: `WHERE time1 = …` sin `blogId` → el mismo mensaje). Es el texto del slide 70 de la Clase 15,
> salvo el prefijo: el deck lo muestra como `Bad Request: …`, y `cqlsh` 6.2.0 lo imprime como
> `InvalidRequest: Error from server: code=2200 [Invalid query] message="…"`.

(clave) La tabla `blogs` del slide 70 volvió como Pregunta 34 del [[Parcial 1Q2026]], con
`PRIMARY KEY ((blogId, time1), time2)`: ahí `time1` es la mitad de una clave de partición compuesta.
Corrido con esa definición: `WHERE time1 = 5` da el mismo error de filtrado del paso 9, y el literal
del enunciado (`1418306451235`) no llega a filtrar, porque no entra en `int`:
`Unable to make int from '1418306451235'`.

### Paso 10 — `ALLOW FILTERING`

```sql
SELECT * FROM lista_reproduccion WHERE artista='Jorge Drexler' ALLOW FILTERING;
```

**Salida real:** dos filas, `nro_cancion` 1 (*Asilo*) y 2 (*Todo se transforma*).

El enunciado dice que la consulta *"realiza una búsqueda secuencial en todos los nodos que contienen
datos de la tabla"*. `TRACING ON` lo muestra (extracto de la salida real):

```
Submitting range requests on 17 ranges with a concurrency of 1 (0.0 rows per range expected)
Executing seq scan across 0 sstables for (min(-9223372036854775808), min(-9223372036854775808)]
Read 4 live rows and 0 tombstone cells
```

Planifica la consulta sobre **los 17 rangos de *tokens*** del anillo (el nodo tiene
`num_tokens: 16`); como hay un solo nodo, los agrupa en una única petición
(`Submitted 1 concurrent range requests`) que recorre el anillo entero, de `min` a `min`, y lee las
**4** filas de la tabla para devolver **2**. Con cuatro filas es inocuo; con millones es el
problema que describen los slides 70–71. `min(-9223372036854775808)` es −2⁶³, el extremo inferior
del anillo de `Murmur3Partitioner`.

### Paso 11 — índice secundario sobre `artista`

```sql
CREATE INDEX indice_artista ON lista_reproduccion (artista);
```

Sin salida. Después, la consulta del paso 9 **sin** `ALLOW FILTERING` devuelve las mismas dos filas.

**Qué índice creó** (`system_schema.indexes`, salida real):

```
 keyspace_name        | table_name         | index_name     | kind       | options
----------------------+--------------------+----------------+------------+-----------------------
 p0929_demo_cql_music | lista_reproduccion | indice_artista | COMPOSITES | {'target': 'artista'}
```

`kind = COMPOSITES` sin `class_name` es el **índice secundario nativo (*legacy*)**: el valor por
defecto de `default_secondary_index` en el `cassandra.yaml` de 5.0 es `legacy_local_table`. Se
guarda como una **tabla oculta** (el directorio `.indice_artista` aparece dentro del de la tabla en
`/var/lib/cassandra/data/`), exactamente lo que dice el slide 62 de la Clase 15. El índice nuevo de la
5.0, **SAI** (*Storage-Attached Index*), hay que pedirlo:
`CREATE INDEX … ON lista_reproduccion (artista) USING 'sai';` (verificado: `kind = CUSTOM`,
`options = {'class_name': 'sai', 'target': 'artista'}`, y responde la misma consulta).

El trazado de la consulta con índice (extracto real):

```
Index mean cardinalities are indice_artista:1. Scanning with indice_artista.
Submitting range requests on 17 ranges with a concurrency of 17 (0.05625 rows per range expected)
Executing read on p0929_demo_cql_music.lista_reproduccion using index indice_artista
Read 2 live rows and 0 tombstone cells
```

Lee **2** filas en lugar de 4, pero **sigue consultando los 17 rangos**. Eso justifica la segunda
mitad del comentario del enunciado (*"una búsqueda utilizando índices es más lenta que si el campo
fuese parte de la clave de particionamiento"*): el índice es **local a cada nodo**, así que una
consulta por `artista` igual tiene que preguntarle a todo el anillo; una consulta por clave de
partición va directo a las réplicas de esa partición. *(Resolución del vault con el trazado real.)*

### Paso 12 — agregar una colección

```sql
ALTER TABLE lista_reproduccion ADD etiquetas set <text>;
```

Sin salida. El espacio entre `set` y `<text>` se acepta; `DESCRIBE TABLE` lo muestra como
`etiquetas set<text>`. Las filas existentes quedan con `etiquetas` en `null` (se ve en la salida del
paso 13).

### Paso 13 — `UPDATE` sobre el `set`

```sql
UPDATE lista_reproduccion SET etiquetas = etiquetas + {'2017'}        WHERE id = 62c36092-82a1-3a00-93d1-46196ee77204 AND nro_cancion=1;
UPDATE lista_reproduccion SET etiquetas = etiquetas + {'guitarra'}    WHERE id = 62c36092-82a1-3a00-93d1-46196ee77204 AND nro_cancion=1;
UPDATE lista_reproduccion SET etiquetas = etiquetas + {'Mon Laferte'} WHERE id = 62c36092-82a1-3a00-93d1-46196ee77204 AND nro_cancion=1;
```

**Salida real** (`SELECT nro_cancion, titulo, etiquetas … WHERE id = …`):

```
 nro_cancion | titulo             | etiquetas
-------------+--------------------+-------------------------------------
           1 |              Asilo | {'2017', 'Mon Laferte', 'guitarra'}
           2 | Todo se transforma |                                null
           3 |      Hasta la raiz |                                null
           4 | Tu falta de querer |                                null
```

Un `set` **ordena y no repite**: los elementos salen ordenados por su valor (dígitos, después
mayúsculas, después minúsculas), no en el orden en que se agregaron, y repetir
`etiquetas + {'guitarra'}` no cambia nada (verificado). El `WHERE` de un `UPDATE` necesita la clave
primaria **completa**: con solo `id`, el motor responde
`Some clustering keys are missing: nro_cancion` (corrido sobre esta misma tabla).

### Paso 14 — índice sobre la colección y `CONTAINS`

```sql
CREATE INDEX indice_etiquetas ON lista_reproduccion (etiquetas);
SELECT * FROM lista_reproduccion WHERE etiquetas CONTAINS 'guitarra';
```

**Salida real:** una fila, `nro_cancion` 1 (*Asilo*) con `{'2017', 'Mon Laferte', 'guitarra'}`. El
índice queda con `target = 'values(etiquetas)'`: sobre un `set`, `CREATE INDEX` indexa los
**valores** sin que haya que pedirlo.

| Variante (corrida) | Resultado |
| --- | --- |
| `CONTAINS 'guitarra'` **antes** de crear el índice | error `Cannot execute this query as it might involve data filtering …` (el mismo del paso 9) |
| `CONTAINS 'Guitarra'` | `(0 rows)`: la comparación distingue mayúsculas |
| `WHERE etiquetas = {'guitarra'}` | `Collection column 'etiquetas' (set<text>) cannot be restricted by a '=' relation` |

> [!warning] (atención) En un script, el índice recién creado puede no estar listo
> Corriendo los 18 pasos de una sola vez (`cqlsh < archivo.cql`), el `SELECT` que sigue a cada
> `CREATE INDEX` falló con
> `ReadFailure: Error from server: code=1300 [Replica(s) failed to execute read] message="Operation failed - received 0 responses and 1 failures: UNKNOWN from /172.17.0.4:7000"`.
> El log del nodo da la causa: `IndexNotAvailableException: The secondary index 'indice_etiquetas' is not yet available`.
> El índice se construye en segundo plano; escribiendo los comandos a mano no se nota porque la construcción
> termina en milisegundos. En un script, conviene esperar o repetir la consulta.

### Paso 15 — `DELETE` de una fila

```sql
DELETE FROM lista_reproduccion WHERE id = 62c36092-82a1-3a00-93d1-46196ee77204 AND nro_cancion = 1;
```

**Salida real** del `SELECT` posterior sobre la partición: quedan `nro_cancion` 2, 3 y 4. El
trazado de ese `SELECT` dice `Read 3 live rows and 1 tombstone cells`: la fila borrada **no
desapareció**, quedó una **lápida** (*tombstone*) que se purga en la compactación, pasado
`gc_grace_seconds = 864000` (10 días, visible en `DESCRIBE TABLE`) →
[[3.15.04 - Escritura y lectura en Cassandra — commit log, MemTable, SSTable y compactación|Escritura y lectura en Cassandra]],
slides 38–39 de la Clase 15.

Lo que **no** se puede borrar así (corrido):

| Intento | Error real |
| --- | --- |
| `DELETE FROM lista_reproduccion WHERE nro_cancion = 2;` | `Some partition key parts are missing: id` |
| `DELETE FROM lista_reproduccion WHERE artista = 'Mon Laferte';` | `Some partition key parts are missing: id` |
| `DELETE FROM lista_reproduccion WHERE artista = 'Mon Laferte' ALLOW FILTERING;` | `SyntaxException: line 1:61 mismatched input 'ALLOW' expecting EOF` |

Un `DELETE` no tiene `ALLOW FILTERING`: exige la clave de partición.

### Paso 16 — `DELETE` de la partición entera

```sql
DELETE FROM lista_reproduccion WHERE id = 62c36092-82a1-3a00-93d1-46196ee77204;
```

**Salida real:** el `SELECT` sobre esa partición devuelve `(0 rows)`. Con solo la clave de partición,
el `DELETE` borra **todas** las filas de la lista de una vez (una lápida de partición). También se
puede borrar un **rango** dentro de la partición (verificado):
`DELETE FROM lista_reproduccion WHERE id = … AND nro_cancion >= 2;` deja solo la fila 1.

### Paso 17 — `DROP TABLE`

```sql
DROP TABLE lista_reproduccion;
```

Sin salida; `DESC TABLES` muestra solo `canciones`.

### Paso 18 — `DROP KEYSPACE`

```sql
DROP KEYSPACE demo_cql_music;
```

Sin salida; el *keyspace* desaparece de `DESCRIBE KEYSPACES` (en un contenedor recién creado quedan
solo los `system*`).

> [!note] (nota) `DROP` no libera el disco en el acto
> La imagen trae `auto_snapshot: true`: cada `DROP TABLE` o `DROP KEYSPACE` deja una copia en
> `snapshots/`. `nodetool listsnapshots` mostró `dropped-…-lista_reproduccion` (entre 27 y 33 KiB
> según la corrida) y `dropped-…-canciones` (6,5 KiB) después del paso 18. Se borran con
> `nodetool clearsnapshot`.

## Trampas del enunciado

- [ ] (clave) **`INSERT` es un *upsert*.** Insertar de nuevo `(id, nro_cancion) = (…, 1)` con otro
  `titulo` **pisa** la fila sin error (verificado: el `titulo` pasó a `'otra'`). Para que falle si
  existe: `INSERT … IF NOT EXISTS` (transacción liviana), que devolvió `[applied] = False` y la fila
  vigente.
- [ ] (clave) **`ORDER BY` no es el de SQL**: solo sobre la clave de *clustering* y con la partición
  fijada por igualdad o `IN`.
- [ ] (clave) **`WHERE` sin la clave de partición** → error que pide `ALLOW FILTERING`; con un
  índice secundario, el mismo `WHERE` funciona, pero igual consulta todo el anillo.
- [ ] (atención) **Restringir una columna de *clustering* sin la anterior** también falla, con otro
  mensaje: `PRIMARY KEY column "time2" cannot be restricted as preceding column "time1" is not restricted`
  (tabla `blogs` del slide 70, `WHERE blogId = 1 AND time2 = 1`).
- [ ] (atención) **Los `set` distinguen mayúsculas** y se ordenan solos; `=` sobre una colección no
  se acepta, se usa `CONTAINS`.
- [ ] (nota) **`SELECT count(*)` sin clave de partición** corre, pero con el aviso
  `Aggregation query used without partition key`: recorre la tabla entera.
