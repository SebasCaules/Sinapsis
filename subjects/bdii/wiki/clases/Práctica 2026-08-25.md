### Ejercicio 1 — empresa de desarrollo de software

```
EMPLEADO ──R1──▶ TRABAJA_EN ◀──R2── PROYECTO ──R3──▶ AUSPICIO ◀╌╌R4╌╌ EMPLEADO
```

| Tabla | PK | Otros atributos |
| --- | --- | --- |
| **EMPLEADO** | `TipoE`, `NroE` | `Nombre` NOT NULL · `Cargo` NOT NULL |
| **TRABAJA_EN** | `TipoE`(FK), `NroE`(FK), `IdProy`(FK), `Anio`, `Mes` | `cant_horas` NOT NULL · `tarea` NOT NULL |
| **PROYECTO** | `IdProy` | `NombreProy` NOT NULL · `AnioComienzo` NOT NULL · **`AnioFinal` NULL** |
| **AUSPICIO** | `IdProy`(FK), `NombreAuspiciante` | **`TipoE`(FK) NULL** · **`NroE`(FK) NULL** |

| RIR | De → a | Columnas | Borrado | Modificación |
| --- | --- | --- | --- | --- |
| **R1** | `TRABAJA_EN` → `EMPLEADO` | `(TipoE, NroE)` | **C** `CASCADE` | **R** `RESTRICT` |
| **R2** | `TRABAJA_EN` → `PROYECTO` | `(IdProy)` | **R** `RESTRICT` | **C** `CASCADE` |
| **R3** | `AUSPICIO` → `PROYECTO` | `(IdProy)` | **R** `RESTRICT` | **R** `RESTRICT` |
| **R4** | `AUSPICIO` → `EMPLEADO` | `(TipoE, NroE)` | **N** `SET NULL` | **R** `RESTRICT` |

**La instancia** *(el enunciado aclara: "solo se incluyen los atributos que se consideran relevantes")*:

| Tabla | Tuplas |
| --- | --- |
| `EMPLEADO` | `(A,1,…)` · `(B,2,…)` · `(A,2,…)` |
| `PROYECTO` | `(1,…)` · `(2,…)` · `(3,…)` |
| `TRABAJA_EN` | `(A,1,1,…)` · `(A,2,2,…)` |
| `AUSPICIO` | `(2, Arcor, A, 2)` |

> [!important] Tres cosas del diagrama que hay que leer antes de resolver nada
> 1. **R1 y R4 son FKs compuestas** `(TipoE, NroE)` — por eso el punto **c** puede preguntar por
>    matching. R2 y R3 son de una sola columna: ahí el matching **no aplica**.
> 2. **En `AUSPICIO`, `TipoE` y `NroE` son `NULL`-ables y NO forman parte de la PK.** Es lo que hace
>    posible el `SET NULL` de R4 y lo que hace posible el ejercicio de matching. En `TRABAJA_EN`, en
>    cambio, la FK **está adentro de la PK** y es `NOT NULL`: ahí `SET NULL` sería ilegal — por eso R1
>    es `CASCADE` y no `SET NULL`.
> 3. **R4 es no identificante** (línea punteada en el diagrama); R1, R2 y R3 son identificantes.
>    Es la lectura visual del punto anterior.

**Esquema A** — artículos y palabras clave:

**Esquema B** — productos, proveedores y sucursales:

| Tabla | PK | Otros atributos |
| --- | --- | --- |

> Es el detalle que hace funcionar el ejercicio B.9. `PROVEE` identifica un par (producto, proveedor);

> localidad"* **no puede violarse** — no hay sucursal contra la cual comparar. El `JOIN` de la
> `ASSERTION` lo maneja solo, pero conviene saber que es a propósito.

## Ejercicio 1 — resuelto

### 1.a · Las cuatro `ALTER TABLE`

*"Considere que las tablas ya se encuentran creadas con sus correspondientes PRIMARY KEY. Escriba las
sentencias de alteración de tabla que incorporan las RIRs definidas"*

```sql
ALTER TABLE TRABAJA_EN
  ADD CONSTRAINT R1 FOREIGN KEY (TipoE, NroE)
      REFERENCES EMPLEADO (TipoE, NroE)
      ON DELETE CASCADE
      ON UPDATE RESTRICT;

ALTER TABLE TRABAJA_EN
  ADD CONSTRAINT R2 FOREIGN KEY (IdProy)
      REFERENCES PROYECTO (IdProy)
      ON DELETE RESTRICT
      ON UPDATE CASCADE;

ALTER TABLE AUSPICIO
  ADD CONSTRAINT R3 FOREIGN KEY (IdProy)
      REFERENCES PROYECTO (IdProy)
      ON DELETE RESTRICT
      ON UPDATE RESTRICT;

ALTER TABLE AUSPICIO
  ADD CONSTRAINT R4 FOREIGN KEY (TipoE, NroE)
      REFERENCES EMPLEADO (TipoE, NroE)
      ON DELETE SET NULL
      ON UPDATE RESTRICT;
```

> [!tip] Tres cosas que conviene decir al entregar
> 1. **La `ALTER TABLE` va siempre sobre la tabla referenciante**, la que *tiene* la FK — nunca sobre
>    la referenciada. Es el error más común del punto.
> 2. **El orden de las columnas en `FOREIGN KEY (…)` y en `REFERENCES …(…)` tiene que corresponderse
>    posición a posición.** `(TipoE, NroE)` → `(TipoE, NroE)`, no al revés.
> 3. **R4 solo puede ser `SET NULL` porque `AUSPICIO.TipoE` y `.NroE` admiten nulos** y están fuera de
>    la PK. Vale escribirlo como justificación: es lo que el slide 9 de la teórica pone entre
>    paréntesis.
>
> El `REFERENCES EMPLEADO (TipoE, NroE)` puede abreviarse a `REFERENCES EMPLEADO` cuando se apunta a
> la PK — la teórica lo muestra así en el slide 11. Escribir las columnas es más claro y siempre vale.

### 1.b · Las seis operaciones *(resultados individuales, no acumulativos)*

> [!important] El método, en tres preguntas
> Para cada operación, en este orden:
> 1. **¿Sobre qué tabla es?** Si es sobre la **referenciante**, no hay acción referencial ninguna:
>    es un chequeo común de FK. *(Es el caso del punto v.)*
> 2. **Si es sobre una referenciada: ¿qué FKs le apuntan, y hay filas que la referencien?** Si no hay
>    ninguna fila referenciante, **la operación pasa siempre**, sea cual sea la acción.
> 3. **Si hay varias FKs involucradas, ¿alguna es `RESTRICT`/`NO ACTION`?** Si sí, **gana ella** — por
>    el slide 38, `RESTRICT` se evalúa antes que las reparaciones.

| # | Operación | Veredicto | Por qué |
| --- | --- | --- | --- |
| **i** | `DELETE FROM PROYECTO WHERE IdProy = 3;` | ✅ **Aceptada** | Nadie referencia el proyecto 3: `TRABAJA_EN` tiene `IdProy` 1 y 2, `AUSPICIO` tiene 2. Ni R2 ni R3 tienen qué hacer |
| **ii** | `UPDATE PROYECTO SET IdProy = 7 WHERE IdProy = 3;` | ✅ **Aceptada** | Mismo motivo. `PROYECTO` pasa a `(1),(2),(7)` |
| **iii** | `DELETE FROM PROYECTO WHERE IdProy = 1;` | ❌ **Rechazada — R2** | `TRABAJA_EN(A,1,1,…)` referencia el proyecto 1, y **R2 tiene `ON DELETE RESTRICT`**. R3 no interviene: `AUSPICIO` no tiene `IdProy = 1` |
| **iv** | `DELETE FROM EMPLEADO WHERE TipoE='A' AND NroE=2;` | ✅ **Aceptada, con dos efectos** | ver abajo |
| **v** | `UPDATE TRABAJA_EN SET IdProy = 3 WHERE IdProy = 1;` | ✅ **Aceptada** | ver abajo |
| **vi** | `UPDATE PROYECTO SET IdProy = 5 WHERE IdProy = 2;` | ❌ **Rechazada — R3** | ver abajo |

#### iv · `DELETE FROM EMPLEADO WHERE TipoE = 'A' AND NroE = 2;` — **la que dispara dos acciones distintas**

`EMPLEADO(A,2)` está referenciado desde **dos** tablas, con **dos acciones distintas**, y ninguna es
restrictiva:

| Regla | Quién referencia | Acción `ON DELETE` | Efecto |
| --- | --- | --- | --- |
| **R1** | `TRABAJA_EN(A,2,2,…)` | `CASCADE` | **se borra esa fila de `TRABAJA_EN`** |
| **R4** | `AUSPICIO(2, Arcor, A, 2)` | `SET NULL` | `TipoE` y `NroE` pasan a **`NULL`** |

Estado resultante:

| Tabla | Después |
| --- | --- |
| `EMPLEADO` | `(A,1)` · `(B,2)` — se fue `(A,2)` |
| `TRABAJA_EN` | `(A,1,1,…)` — se fue `(A,2,2,…)` **por cascada** |
| `AUSPICIO` | **`(2, Arcor, NULL, NULL)`** — la fila **sobrevive**, con la FK anulada |
| `PROYECTO` | sin cambios |

> [!important] Ésta es **la operación más rica del ejercicio** y conviene explicarla al entregar
> Muestra las dos filosofías del slide 9 de la teórica actuando **al mismo tiempo sobre la misma
> operación**:
> - `CASCADE` dice *"si se va el padre, se va el hijo"* → la fila de `TRABAJA_EN` **desaparece**.
> - `SET NULL` dice *"si se va el padre, el hijo se queda huérfano"* → la fila de `AUSPICIO`
>   **se queda, sin padre**.
>
> **Y el diseño lo justifica**: `TRABAJA_EN` sin empleado **no tiene sentido** —el empleado es parte de
> su clave, es una fila de "quién trabajó en qué"—, mientras que un auspicio sigue existiendo aunque el
> empleado que lo consiguió se vaya de la empresa. Por eso R1 es `CASCADE` y R4 es `SET NULL`, y por
> eso las FKs de `AUSPICIO` son nullables y las de `TRABAJA_EN` no.
>
> **La elección de la acción referencial es una decisión de modelado, no un detalle de sintaxis.**
> Es lo que hay que saber contestar si lo preguntan.

> [!note] ¿El borrado en cascada de `TRABAJA_EN` dispara algo más?
> No. **`TRABAJA_EN` no es referenciada por ninguna tabla**, así que la cascada se detiene ahí. Si
> alguien la referenciara, habría que seguir la cadena — y ahí el orden del slide 38 empieza a
> importar de verdad.

#### v · `UPDATE TRABAJA_EN SET IdProy = 3 WHERE IdProy = 1;` — **la trampa del ejercicio**

> [!warning] `TRABAJA_EN` es la tabla **referenciante**, no la referenciada
> **Ninguna acción referencial se dispara.** Las acciones de R1 y R2 están definidas para cuando se
> toca `EMPLEADO` o `PROYECTO`, no para cuando se toca `TRABAJA_EN`. Acá lo único que corre es el
> **chequeo** de la FK: *¿el valor nuevo existe en la referenciada?*

Dos chequeos, los dos pasan:

| Chequeo | Resultado |
| --- | --- |
| **R2** — ¿`IdProy = 3` existe en `PROYECTO`? | ✅ sí, la instancia tiene `(1),(2),(3)` |
| **PK de `TRABAJA_EN`** — la fila pasa de `(A,1,1,Anio,Mes)` a `(A,1,3,Anio,Mes)`: ¿choca con otra? | ✅ no, la otra fila es `(A,2,2,…)` |

**Aceptada.** `TRABAJA_EN` queda `{(A,1,3,…), (A,2,2,…)}`.

> [!tip] Cómo contestarlo bien
> No alcanza con decir *"pasa"*. Lo que se está evaluando es que uno **note que la operación es del
> otro lado de la FK**. La respuesta completa es: *"aceptada; R2 no dispara ninguna acción referencial
> porque la operación es sobre la tabla referenciante — solo se verifica que el valor nuevo exista en
> `PROYECTO`, y `IdProy = 3` existe"*.
>
> Y hay un segundo motivo por el que puede fallar y hay que chequearlo igual: **`IdProy` forma parte de
> la PK de `TRABAJA_EN`**, así que cambiarlo puede provocar una **colisión de clave primaria**. Acá no
> pasa, pero es lo que había que verificar.

#### vi · `UPDATE PROYECTO SET IdProy = 5 WHERE IdProy = 2;` — **dos reglas en conflicto**

`PROYECTO(2)` está referenciado desde dos lugares, con acciones **opuestas**:

| Regla | Quién referencia | Acción `ON UPDATE` | Qué querría hacer |
| --- | --- | --- | --- |
| **R2** | `TRABAJA_EN(A,2,2,…)` | `CASCADE` | propagar `IdProy` 2 → 5 |
| **R3** | `AUSPICIO(2, Arcor, A, 2)` | **`RESTRICT`** | **abortar** |

> [!important] ❌ **Rechazada por R3.** Y la clave está en el **orden**, no en "la más severa gana"
> Por el slide 38 de la teórica, el motor aplica `Apply RESTRICT Rules` **antes** de
> `Apply CASCADE, SET NULL, SET DEFAULT Rules`. O sea: **R3 aborta la operación entera antes de que la
> cascada de R2 llegue a ejecutarse.** No es que se ejecute la cascada y después se deshaga: nunca
> empieza.
>
> Es exactamente el par de slides 9 + 38 puesto a trabajar, y es **el ejercicio que justifica que el
> deck haya explicado el modelo de ejecución**. Al entregar conviene citarlo: *"R3 es `RESTRICT`, y
> `RESTRICT` se evalúa antes que `CASCADE` (SQL-99, slide 38), así que la operación se rechaza sin que
> la cascada de R2 se aplique"*.

> [!note] Comparar **vi** con **iv** — es el mismo dibujo con distinto resultado
> Las dos tocan una fila referenciada desde dos tablas. La diferencia es una sola:
>
> | | R de `TRABAJA_EN`/`INSTALACION` | R de `AUSPICIO` | Resultado |
> | --- | --- | --- | --- |
> | **iv** (`DELETE EMPLEADO`) | R1 `CASCADE` | R4 `SET NULL` | ✅ **las dos reparan** → pasa |
> | **vi** (`UPDATE PROYECTO`) | R2 `CASCADE` | R3 **`RESTRICT`** | ❌ **una rechaza** → no pasa |
>
> **Regla en una línea: basta con que una sola regla sea restrictiva para que la operación caiga.**

### 1.c · Matching sobre R4

R4 es `AUSPICIO(TipoE, NroE)` → `EMPLEADO(TipoE, NroE)`, y `EMPLEADO` = `{(A,1), (B,2), (A,2)}`.
Las columnas de `AUSPICIO` en orden son `(IdProy, NombreAuspiciante, TipoE, NroE)`.

| # | `INSERT INTO AUSPICIO VALUES (…)` | FK = `(TipoE, NroE)` | Simple | Parcial | Full |
| --- | --- | --- | :---: | :---: | :---: |
| **i** | `(1, 'Dell', 'B', null)` | `('B', null)` | ✅ | ✅ | ❌ |
| **ii** | `(2, 'Oracle', null, null)` | `(null, null)` | ✅ | ✅ | ✅ |
| **iii** | `(3, 'Google', 'A', 3)` | `('A', 3)` | ❌ | ❌ | ❌ |
| **iv** | `(1, 'HP', null, 3)` | `(null, 3)` | ✅ | ❌ | ❌ |

**El razonamiento, uno por uno:**

| # | Simple | Parcial | Full |
| --- | --- | --- | --- |
| **i** `('B', null)` | hay **un** nulo → se saltea el chequeo | el no nulo es `TipoE='B'`, y **existe** `(B,2)` en `EMPLEADO` → pasa | mezcla de nulo y no nulo → **prohibida** |
| **ii** `(null, null)` | hay nulos → pasa | todo nulo, no hay nada que verificar → pasa | **todos** nulos → pasa |
| **iii** `('A', 3)` | **sin nulos** → tiene que existir la combinación; `(A,3)` **no está** → falla | ídem → falla | ídem → falla |
| **iv** `(null, 3)` | hay **un** nulo → pasa | el no nulo es `NroE=3`, y **`EMPLEADO` no tiene ningún `NroE=3`** (los valores son 1, 2, 2) → **falla** | mezcla → **prohibida** |

> [!important] Los casos **iii** y **iv** son los que separan a quien entendió de quien memorizó
> - **iii `('A',3)`** — la trampa de la **combinación**. `A` **existe** como `TipoE` *(en `(A,1)` y
>   `(A,2)`)* y `3` … no existe como `NroE`. Pero aunque existiera, tampoco importaría: el matching
>   exige que **el par entero** aparezca en una **misma tupla**. Es el caso 2 del slide 14 de la
>   teórica.
> - **iv `(null,3)`** — la única fila donde `SIMPLE` y `PARTIAL` **difieren**. Las dos ignoran los
>   nulos; la diferencia es que `PARTIAL` **sí mira** el valor no nulo. Es el caso 5 del slide 14.
>
> **Chequeo de sanidad:** las respuestas de cada fila tienen que ser **monótonas de izquierda a
> derecha** —`SIMPLE` ⊇ `PARTIAL` ⊇ `FULL`—. Un ✅ a la derecha de un ❌ es un error seguro.

> [!warning] Hay que verificar **R3 y la PK** también, o el ejercicio se contesta mal
> El punto pregunta por R4, pero un `INSERT` tiene que pasar **todas** las restricciones. Por suerte
> las cuatro filas pasan las otras:
>
> | # | R3: ¿`IdProy` existe en `PROYECTO {1,2,3}`? | PK `(IdProy, NombreAuspiciante)`: ¿única? |
> | --- | --- | --- |
> | i | `1` ✅ | `(1,'Dell')` ✅ |
> | ii | `2` ✅ | `(2,'Oracle')` — la existente es `(2,'Arcor')` ✅ |
> | iii | `3` ✅ | `(3,'Google')` ✅ |
> | iv | `1` ✅ | `(1,'HP')` ✅ |
>
> O sea que **cuando una fila se rechaza, es por R4 y solo por R4** — que es lo que el ejercicio
> quiere. Vale decirlo explícitamente al entregar: demuestra que se chequeó.

> [!warning] 🔴 Este punto **no se puede verificar en MySQL**
> InnoDB **parsea e ignora** la cláusula `MATCH`: siempre se comporta como `MATCH SIMPLE`. Si se corren
> estos cuatro `INSERT` en MySQL, el resultado va a ser la **columna Simple** en los cuatro casos,
> independientemente de lo que se haya escrito.
>
> **Es un ejercicio de estándar, no de motor.** Ver [[MySQL]] § *5*.

## Ejercicio 2 — resuelto

### 2.a · Las cinco operaciones, **acumulativas y en orden**

> [!warning] 🔴 Acá el enunciado cambia la regla del ejercicio 1 — y de la teórica
> *"considerando que se ejecutan **en el orden dado** y que **son acumulables**"*.
>
> El ejercicio 1 decía *"los resultados no son acumulativos"* y el slide 11 de la teórica también.
> **Acá es al revés: cada operación parte del estado que dejó la anterior.**
>
> Es *la* trampa del ejercicio: **las operaciones ii y v dan distinto** según se evalúen sobre la
> instancia original o sobre el estado acumulado. Quien resuelva las cinco contra los datos iniciales
> se equivoca en las dos.

#### i · `DELETE FROM CLIENTE WHERE NroC = 1;`

Afecta **dos** clientes: `(A,1)` y `(B,1)`.

| Regla | Quién los referencia | Acción `ON DELETE` | Efecto |
| --- | --- | --- | --- |
| **R1** | `INSTALACION (A,1,S1,5,2011)` y `(B,1,S2,5,2012)` | `CASCADE` | **se borran las dos filas** |
| **R4** | `REFERENCIA` con `(Zona,NroC)` ∈ {(A,1),(B,1)}: **ninguna** *(las que hay son `(D,3)` y `(C,2)`)* | `RESTRICT` | **no interviene** |

✅ **Aceptada.**

| Tabla | Estado después de **i** |
| --- | --- |
| `CLIENTE` | `(A,2)` · `(C,2)` · `(D,3)` |
| `INSTALACION` | `(C,2,S1,4,2010,9,T2)` · `(A,2,S3,8,2009,6,T2)` |
| `SERVICIO` | sin cambios |
| `REFERENCIA` | sin cambios |

> [!note] El `RESTRICT` de R4 **estaba ahí y no hizo nada** — y hay que decirlo
> Es la clase de cosa que se pregunta: *"si R4 es `ON DELETE RESTRICT`, ¿por qué no rechazó?"*. Porque
> **no había ninguna fila de `REFERENCIA` apuntando a los clientes borrados.** Un `RESTRICT` sin filas
> referenciantes no bloquea nada. Si `REFERENCIA` hubiera tenido una fila con `(A,1)`, esta operación
> se caía y **todo el ejercicio cambiaba**.

#### ii · `UPDATE INSTALACION SET IdServ = 'S5' WHERE IdServ = 'S2';`

> [!important] 🎯 **Aquí se cobra el "acumulables"**
> La fila `(B,1,S2,5,2012,…)` era la **única** de `INSTALACION` con `IdServ = 'S2'` … y **la borró la
> cascada del paso i**.
>
> ✅ **Aceptada, sin efecto: afecta 0 filas.** Nada que chequear, nada que cambiar.
>
> **Si se hubiera evaluado sobre la instancia original, el resultado sería el opuesto:** habría una
> fila que actualizar, el nuevo valor `'S5'` **no existe** en `SERVICIO` `{S1,S2,S3}`, y **R2 la
> rechazaría** por violación de FK. Dos respuestas contrarias según se lea o no la palabra
> *"acumulables"*.

Estado: **sin cambios respecto de i.**

> [!note] Además, es otra operación sobre la tabla **referenciante**
> Como el 1.b.v: `INSTALACION` tiene la FK, así que las acciones de R2 no aplican. Solo se chequea que
> el valor nuevo exista. Van dos ejercicios que meten este caso.

#### iii · `UPDATE CLIENTE SET Zona = 'Z' WHERE Zona = 'D';`

Afecta `CLIENTE(D,3)` → `(Z,3)`.

| Regla | Quién referencia `(D,3)` | Acción `ON UPDATE` | Efecto |
| --- | --- | --- | --- |
| **R1** | `INSTALACION`: después de i quedan `(C,2,…)` y `(A,2,…)` — **ninguna con `(D,3)`** | `RESTRICT` | **no interviene** |
| **R4** | `REFERENCIA (S1,'Puntualidad',D,3)` y `(S1,'Atención',D,3)` | **`SET NULL`** | `Zona` y `NroC` → **`NULL`** en las dos |

✅ **Aceptada.**

| Tabla | Estado después de **iii** |
| --- | --- |
| `CLIENTE` | `(A,2)` · `(C,2)` · **`(Z,3)`** |
| `REFERENCIA` | **`(S1,'Puntualidad',null,null)`** · `(S2,'Calidad inst.',C,2)` · `(S3,'Costo',C,2)` · **`(S1,'Atención',null,null)`** |

> [!warning] `SET NULL` en un `ON UPDATE` es semánticamente raro, y este ejercicio lo muestra
> El cliente **no se fue**: solo cambió de zona, de `D` a `Z`. Y sus dos referencias **perdieron el
> vínculo con él para siempre**. Con `CASCADE` habrían seguido apuntándole; con `SET NULL` quedaron
> huérfanas.
>
> Es el punto que la teórica marca en el slide 9 y que conviene señalar al entregar: **`SET NULL` tiene
> sentido en `ON DELETE`** —el padre ya no existe— **y casi nunca en `ON UPDATE`**, donde el padre
> sigue ahí con otra clave. Que el ejercicio lo ponga es deliberado.
>
> Y ojo con el otro efecto: **las dos filas de `REFERENCIA` quedan con `(null,null)`**, o sea que ahora
> pasan cualquier matching, incluido `FULL`. La restricción se satisface — pero la información se
> perdió.

> [!note] ¿La PK de `REFERENCIA` sigue siendo válida?
> Sí. Es `(IdServ, Motivo)`, y las dos filas afectadas son `(S1,'Puntualidad')` y `(S1,'Atención')`:
> **distintas**. Lo anulado es `Zona`/`NroC`, que no forman parte de la clave. Vale chequearlo — si el
> `Motivo` hubiera sido el mismo, la operación se caía por PK duplicada.

#### iv · `DELETE FROM SERVICIO WHERE IdServ = 'S3';`

| Regla | Quién referencia `S3` | Acción `ON DELETE` | Efecto |
| --- | --- | --- | --- |
| **R2** | `INSTALACION (A,2,S3,8,2009,…)` — **sigue ahí**, no la tocó ningún paso anterior | **`RESTRICT`** | ❌ **rechaza** |
| **R3** | `REFERENCIA (S3,'Costo',C,2)` | **`RESTRICT`** | ❌ **también rechazaría** |

❌ **Rechazada. Dos reglas en conflicto, las dos `RESTRICT`: R2 y R3.**

Estado: **sin cambios respecto de iii.** *(Una operación rechazada no deja rastro — importa para el
paso v, que parte de acá.)*

> [!tip] El enunciado pide *"determine qué regla/s entra/n en conflicto"* — hay que nombrar **las dos**
> Es tentador parar en la primera. Pero el punto dice *"regla/s"* en plural a propósito, y acá son
> genuinamente dos caminos independientes: aunque no existiera `INSTALACION`, R3 rechazaría igual por
> `REFERENCIA`. **Para que este `DELETE` pasara habría que borrar antes las filas de las dos tablas.**

#### v · `UPDATE SERVICIO SET IdServ = 'S5' WHERE IdServ = 'S2';`

> [!important] 🎯 **Segunda vez que el "acumulables" cambia la respuesta**

| Regla | Quién referencia `S2` **en el estado actual** | Acción `ON UPDATE` | Efecto |
| --- | --- | --- | --- |
| **R2** | `INSTALACION`: la fila con `S2` **la borró la cascada del paso i** → **ninguna** | `RESTRICT` | **no interviene** |
| **R3** | `REFERENCIA (S2,'Calidad inst.',C,2)` | **`CASCADE`** | `IdServ` **S2 → S5** |

✅ **Aceptada.**

| Tabla | Estado **final** |
| --- | --- |
| `CLIENTE` | `(A,2,'Alberto Efe',C1)` · `(C,2,'José Ge',C3)` · `(Z,3,'Luis Ene',C2)` |
| `SERVICIO` | `(S1,'Serv 1',2010,2012)` · **`(S5,'Serv 2',2012,2012)`** · `(S3,'Serv 3',2009,null)` |
| `INSTALACION` | `(C,2,S1,4,2010,9,T2)` · `(A,2,S3,8,2009,6,T2)` |
| `REFERENCIA` | `(S1,'Puntualidad',null,null)` · **`(S5,'Calidad inst.',C,2)`** · `(S3,'Costo',C,2)` · `(S1,'Atención',null,null)` |

> [!important] Sobre la instancia original, esta operación se **rechazaba**
> `INSTALACION` tenía `(B,1,S2,5,2012,…)`, y **R2 es `ON UPDATE RESTRICT`** → bloqueaba. La cascada
> del paso **i** es lo que quitó del medio a esa fila y dejó pasar el paso **v**.
>
> **El ejercicio está diseñado para que eso se note**: pone la misma operación de dos formas —ii sobre
> la referenciante, v sobre la referenciada— y las dos dependen de un borrado que ocurrió cuatro pasos
> antes. Al entregar conviene decirlo con todas las letras: *"pasa porque el paso i eliminó por cascada
> la única `INSTALACION` que referenciaba a S2"*.

> [!note] Chequeo de PK, otra vez
> `REFERENCIA` pasa de `(S2,'Calidad inst.')` a `(S5,'Calidad inst.')`. No hay otra fila con `S5`, así
> que no hay colisión. Y `SERVICIO` pasa de `S2` a `S5`, que tampoco existía. Las dos limpias.

#### Resumen del ejercicio 2.a

| # | Operación | Veredicto | Regla decisiva | Depende de un paso anterior |
| --- | --- | --- | --- | --- |
| i | `DELETE CLIENTE … NroC=1` | ✅ | R1 `CASCADE` *(R4 `RESTRICT` no aplica: sin filas)* | — |
| ii | `UPDATE INSTALACION … S2→S5` | ✅ *(0 filas)* | ninguna | 🎯 **sí** — i borró la fila |
| iii | `UPDATE CLIENTE … D→Z` | ✅ | R4 `SET NULL` *(R1 `RESTRICT` no aplica)* | i |
| iv | `DELETE SERVICIO … S3` | ❌ | **R2 y R3, las dos `RESTRICT`** | — |
| v | `UPDATE SERVICIO … S2→S5` | ✅ | R3 `CASCADE` *(R2 `RESTRICT` no aplica)* | 🎯 **sí** — i borró la fila |

> [!tip] Un patrón que atraviesa las cinco
> **En cuatro de las cinco hay un `RESTRICT` que no llegó a dispararse** porque no había filas
> referenciantes. La pregunta que decide cada operación no es *"¿qué acción tiene la regla?"* sino
> **"¿hay alguna fila que referencie a lo que estoy tocando, *en este momento*?"**. La acción recién
> importa después de contestar eso.

### 2.b · `INSERT` sobre `REFERENCIA` para los tres matchings

> [!quote] La consigna
> *"Plantee **distintos ejemplos** de operaciones INSERT sobre la tabla REFERENCIA teniendo en cuenta
> los distintos casos de valores nulos con respecto a la RIR con CLIENTE (la R4). Considere los
> diferentes tipos de matching (full, parcial, simple). Indique los resultados de las operaciones y
> justifique. **Utilice los datos iniciales de la BD**, sin tener en cuenta los posibles efectos del
> punto anterior"*

`CLIENTE` **inicial** = `{(A,1), (A,2), (B,1), (C,2), (D,3)}`.
Columnas de `REFERENCIA`: `(IdServ, Motivo, Zona, NroC)`. La FK de R4 es `(Zona, NroC)`.

> [!important] A diferencia del 1.c, acá **los ejemplos los propone uno** — y hay que cubrir los cinco casos
> El enunciado dice *"distintos ejemplos … los distintos casos de valores nulos"*. Los casos posibles
> de una FK compuesta son **exactamente cinco**, y una respuesta completa los tiene todos. Los `IdServ`
> se eligen entre `{S1,S2,S3}` para que R3 pase, y los `Motivo` distintos para no chocar con la PK.

| # | `INSERT INTO REFERENCIA VALUES (…)` | FK = `(Zona, NroC)` | Caso | Simple | Parcial | Full |
| --- | --- | --- | --- | :---: | :---: | :---: |
| **1** | `('S1', 'Rapidez', 'A', 1)` | `('A', 1)` | sin nulos, **existe** | ✅ | ✅ | ✅ |
| **2** | `('S1', 'Precio', 'A', 3)` | `('A', 3)` | sin nulos, **no existe** | ❌ | ❌ | ❌ |
| **3** | `('S2', 'Trato', null, null)` | `(null, null)` | **todos** nulos | ✅ | ✅ | ✅ |
| **4** | `('S2', 'Garantía', null, 2)` | `(null, 2)` | mezcla, el no nulo **existe** | ✅ | ✅ | ❌ |
| **5** | `('S3', 'Limpieza', 'E', null)` | `('E', null)` | mezcla, el no nulo **no existe** | ✅ | ❌ | ❌ |

**Las justificaciones, que es lo que el enunciado pide explícitamente:**

| # | Justificación |
| --- | --- |
| **1** | El par `(A,1)` está en `CLIENTE` (*Juan Ro*). Sin nulos y con coincidencia exacta → pasa los tres matchings, que es el caso de la primera línea del slide 13 |
| **2** | ⚠️ **`A` existe como `Zona` y `3` existe como `NroC` — pero no en la misma tupla.** `(A,3)` no está. Sin nulos, los tres matchings exigen la **combinación** completa → rechazan los tres |
| **3** | Todas las columnas de la FK nulas. `SIMPLE` y `PARTIAL` no tienen nada que verificar; `FULL` lo admite explícitamente (*"Todas las columnas de la FK son NULL"*) → pasa los tres |
| **4** | `SIMPLE`: hay un nulo, se saltea. `PARTIAL`: el valor no nulo es `NroC = 2`, y **existen** clientes con `NroC = 2` — `(A,2)` y `(C,2)` — → pasa. `FULL`: **mezcla nulo/no nulo → prohibida** |
| **5** | `SIMPLE`: hay un nulo, pasa. `PARTIAL`: el valor no nulo es `Zona = 'E'`, y **no hay ningún cliente con `Zona = 'E'`** → rechaza. `FULL`: mezcla → rechaza |

> [!tip] Cómo se elige un buen conjunto de ejemplos — el criterio, no la lista
> Los cinco casos salen de cruzar **dos preguntas**:
>
> | | los no nulos **coinciden** | los no nulos **no coinciden** |
> | --- | --- | --- |
> | **ningún** nulo | caso 1 · ✅✅✅ | caso 2 · ❌❌❌ |
> | **algunos** nulos | caso 4 · ✅✅❌ | caso 5 · ✅❌❌ |
> | **todos** nulos | caso 3 · ✅✅✅ *(la otra columna no existe)* | |
>
> **Con menos de cinco filas no se distinguen los tres matchings.** Si faltan la 4 y la 5, `PARTIAL` y
> `FULL` dan igual en todo y no hay forma de mostrar la diferencia — que es justo lo que el ejercicio
> quiere ver.

> [!warning] Vale agregar un sexto caso, y suma
> `('S3', 'Puntualidad', 'D', null)` → `('D', null)`: mezcla, y el no nulo `Zona='D'` **sí** existe
> *(en `(D,3)`)*. Da **✅ ✅ ❌**, igual que el caso 4, pero **por la otra columna**. Mostrar que la
> regla de `PARTIAL` es simétrica —le da igual cuál de las dos columnas sea la nula— es exactamente lo
> que el enunciado llama *"los distintos casos de valores nulos"*.
>
> Ojo con el `Motivo`: `(S3,'Costo')` ya existe, así que hay que usar otro o el `INSERT` cae por PK
> antes de llegar al matching.

## Ejercicio 3 — resuelto

### 3.a · La tabla de restricciones

> [!important] El criterio de clasificación, en una pregunta
> **¿Cuánto hay que mirar para saber si la restricción se cumple?**
>
> | Alcanza con… | Tipo | Recurso SQL-1999 |
> | --- | --- | --- |
> | una **columna** de una fila | **de dominio/atributo** | `CHECK` |
> | **varias columnas** de la **misma** fila | **de registro/tupla** | `CHECK` |
> | **varias filas** de la **misma** tabla | **de tabla** | `CHECK` *(con subconsulta)* |
> | **más de una tabla** | **global/base de datos** | `ASSERTION` |
>
> Es la jerarquía del slide 15 de la [[Clase 09 - Restricciones integridad-Parte 1|teórica]]. El
> disparador de la respuesta es siempre **contar tablas y contar filas**.

| Restricción | Tabla/s | Atributo/s | Tipo de restricción | Recurso declarativo |
| --- | --- | --- | --- | --- |
| **A.1** *(dada de ejemplo)* | `ARTICULO` | `nacionalidad` | De atributo | `CHECK` |
| **A.2** | `ARTICULO` | `fecha_pub` | De atributo | `CHECK` |
| **A.3** | `ARTICULO` | `fecha_pub`, `nacionalidad` | **De registro/tupla** | `CHECK` |
| **A.4** | `CONTIENE` | `id_articulo` | **De tabla** | `CHECK` *(con subconsulta)* |
| **A.5** | `ARTICULO`, `CONTIENE` | `nacionalidad`, `id_articulo` | **Global / base de datos** | `ASSERTION` |
| **B.6** | `PROVEE` | `nro_prov` | **De tabla** | `CHECK` *(con subconsulta)* |
| **B.7** | `SUCURSAL` | `cod_suc` | De atributo | `CHECK` |
| **B.8** | `PRODUCTO` | `descripcion`, `presentacion` | **De registro/tupla** | `CHECK` |
| **B.9** | `PROVEE`, `PROVEEDOR`, `SUCURSAL` | `cod_suc`, `nro_prov`, `localidad` | **Global / base de datos** | `ASSERTION` |

> [!tip] Cómo se reconoce cada tipo de un vistazo
> - **de atributo** — el enunciado nombra **una sola columna**: *"que las nacionalidades sean…"*,
>   *"los códigos de sucursal deben comenzar con…"*.
> - **de registro/tupla** — nombra **dos columnas y las relaciona dentro de la misma fila**: *"los
>   artículos publicados **en 2017** deben ser **de nacionalidad Argentino**"*, *"la **descripción** y
>   la **presentación** no pueden ser ambas nulas"*.
> - **de tabla** — aparece un **conteo** o un **cuantificador**: *"**como máximo** 10 palabras"*,
>   *"**no más de** 20 productos"*, *"**cada** proveedor"*. Casi siempre hay un `COUNT` escondido.
> - **global** — hay que **cruzar tablas**: *"artículos **argentinos** (`ARTICULO`) que contengan más
>   de 10 palabras (`CONTIENE`)"*, *"sucursales **de su localidad**" (`SUCURSAL` vs. `PROVEEDOR`)*.

> [!warning] A.4 y B.6 son **de tabla**, no globales — el error más fácil de cometer
> Las dos tienen un `COUNT` con `GROUP BY`, y eso hace pensar en `ASSERTION`. Pero **la consulta toca
> una sola tabla**: A.4 cuenta filas de `CONTIENE` agrupadas por `id_articulo`; B.6 cuenta filas de
> `PROVEE` agrupadas por `nro_prov`. **Una tabla ⇒ `CHECK` de tabla**, que es exactamente el ejemplo
> del slide 22 (*"no más de 30 empleados por área"*).
>
> A.5 y B.9 **sí** cruzan tablas — y por eso son las dos únicas `ASSERTION` del ejercicio.

### 3.b · Las sentencias en SQL estándar

#### Esquema A

```sql
-- A.1 · De atributo. "Controlar que las nacionalidades sean 'Argentino', 'Español',
--                     'Inglés', 'Alemán' o 'Chileno'"
ALTER TABLE ARTICULO
  ADD CONSTRAINT ck_articulo_nacionalidad
  CHECK (nacionalidad IN ('Argentino','Español','Inglés','Alemán','Chileno'));
```

```sql
-- A.2 · De atributo. "Para las fechas de publicaciones se debe considerar que sean
--                     fechas posteriores o iguales al 2010"
ALTER TABLE ARTICULO
  ADD CONSTRAINT ck_articulo_fecha_pub
  CHECK (fecha_pub >= DATE '2010-01-01');
```

```sql
-- A.3 · De registro/tupla. "Los artículos publicados en el año 2017 deben ser
--                           solamente de nacionalidad 'Argentino'"
ALTER TABLE ARTICULO
  ADD CONSTRAINT ck_articulo_2017_argentino
  CHECK ( EXTRACT(YEAR FROM fecha_pub) <> 2017
          OR nacionalidad = 'Argentino' );
```

```sql
-- A.4 · De tabla. "Los artículos pueden tener como máximo 10 palabras claves
--                  indexadas, sin importar el idioma"
ALTER TABLE CONTIENE
  ADD CONSTRAINT ck_contiene_max_10
  CHECK ( NOT EXISTS ( SELECT 1
                       FROM CONTIENE
                       GROUP BY id_articulo
                       HAVING COUNT(*) > 10 ) );
```

```sql
-- A.5 · Global. "Sólo se pueden publicar artículos argentinos que contengan más de
--                10 palabras claves indexadas, pero con un tope de 15"
CREATE ASSERTION as_articulo_argentino_palabras
CHECK ( NOT EXISTS (
          SELECT 1
          FROM ARTICULO A
          WHERE A.nacionalidad = 'Argentino'
            AND ( SELECT COUNT(*)
                  FROM CONTIENE C
                  WHERE C.id_articulo = A.id_articulo ) NOT BETWEEN 11 AND 15 ) );
```

> [!bug] 🔴 **A.4 y A.5 se contradicen: juntas hacen imposible publicar un artículo argentino**
> - **A.4**: *"Los artículos pueden tener como máximo 10 palabras claves indexadas, **sin importar el
>   idioma**"* → para **todo** artículo, `COUNT ≤ 10`.
> - **A.5**: *"Sólo se pueden publicar artículos argentinos que contengan **más de 10** palabras claves
>   indexadas, pero con un tope de 15"* → para los argentinos, `10 < COUNT ≤ 15`.
>
> **`COUNT ≤ 10` y `COUNT > 10` no pueden valer a la vez.** Con las dos restricciones activas,
> **ningún artículo argentino puede tener palabras clave** — de hecho ninguno puede existir con
> `COUNT` válido. Y encadenado con **A.3** *(los de 2017 deben ser argentinos)*, sale que **en 2017 no
> se puede publicar nada**.
>
> **Las dos lecturas posibles**, y hay que declarar cuál se toma:
>
> | Lectura | A.4 | A.5 | Consecuencia |
> | --- | --- | --- | --- |
> | **(a) A.5 es la excepción a A.4** *(la más probable)* | máx. 10 **para los no argentinos** | 11 a 15 para los argentinos | consistente; A.4 hay que reescribirla con `nacionalidad <> 'Argentino'` |
> | **(b) las dos valen tal cual** | máx. 10 para todos | >10 para los argentinos | **contradictorio**: ningún argentino publicable |
>
> Bajo la lectura **(a)**, A.4 pasa a ser **global también** —necesita mirar `ARTICULO.nacionalidad`—
> y su clasificación en la tabla del 3.a cambia de *de tabla* a *global/BD*.
>
> **Va a [[#Preguntas para el docente]].** Mientras tanto, la respuesta de arriba usa la lectura
> literal **(b)**, que es lo que dice el enunciado, y se aclara la contradicción por escrito. Es la
> respuesta más defendible: la contradicción es del enunciado, no de quien resuelve.

#### Esquema B

```sql
-- B.6 · De tabla. "Cada proveedor no puede proveer más de 20 productos"
ALTER TABLE PROVEE
  ADD CONSTRAINT ck_provee_max_20
  CHECK ( NOT EXISTS ( SELECT 1
                       FROM PROVEE
                       GROUP BY nro_prov
                       HAVING COUNT(*) > 20 ) );
```

```sql
-- B.7 · De atributo. "Los códigos de sucursal deben comenzar con el string 'S_'"
ALTER TABLE SUCURSAL
  ADD CONSTRAINT ck_sucursal_cod
  CHECK ( cod_suc LIKE 'S\_%' ESCAPE '\' );
```

```sql
-- B.8 · De registro/tupla. "La descripción y la presentación de un producto no
--                           pueden ser ambas nulas"
ALTER TABLE PRODUCTO
  ADD CONSTRAINT ck_producto_desc_o_pres
  CHECK ( descripcion IS NOT NULL OR presentacion IS NOT NULL );
```

```sql
-- B.9 · Global. "Cada proveedor sólo puede proveer productos a sucursales de su
--                localidad"
CREATE ASSERTION as_provee_misma_localidad
CHECK ( NOT EXISTS (
          SELECT 1
          FROM PROVEE PV
               JOIN PROVEEDOR P ON P.nro_prov = PV.nro_prov
               JOIN SUCURSAL  S ON S.cod_suc  = PV.cod_suc
          WHERE S.localidad <> P.localidad ) );
```

> [!warning] 🔴 **B.7: el `_` de `'S_'` es un comodín de `LIKE`, y si no se escapa la restricción no restringe**
> `CHECK (cod_suc LIKE 'S_%')` **acepta `SX123`, `SA9`, `S-1`** — cualquier código que empiece con `S`,
> porque `_` matchea **un carácter cualquiera** *(slide 18 de la teórica)*.
>
> Tres formas correctas:
> ```sql
> CHECK ( cod_suc LIKE 'S\_%' ESCAPE '\' )   -- explícita, la más portable
> CHECK ( cod_suc LIKE 'S$_%' ESCAPE '$' )   -- con otro carácter de escape
> CHECK ( SUBSTRING(cod_suc FROM 1 FOR 2) = 'S_' )  -- sin LIKE, sin ambigüedad
> ```
> Es **la trampa del ejercicio 3**, y es fácil no verla porque el `CHECK` ingenuo *parece* andar: se
> crea sin error y rechaza los códigos que no empiezan con `S`. Falla en silencio justo en el caso que
> hay que atajar.

> [!note] B.8 y la regla de `NULL` de los `CHECK`
> `CHECK (descripcion IS NOT NULL OR presentacion IS NOT NULL)` funciona porque `IS NULL` **nunca
> devuelve `UNKNOWN`**: siempre da `TRUE` o `FALSE`. Si en vez de eso se escribiera algo como
> `CHECK (descripcion <> '' OR presentacion <> '')`, con las dos columnas en `NULL` la condición daría
> `UNKNOWN` y **el `CHECK` aceptaría** — por la regla *"verdadera o desconocida"* del slide 17.
> Es el ejercicio donde esa regla se cobra.

> [!note] B.9 y los `cod_suc` nulos
> `PROVEE.cod_suc` es opcional. Las filas con `cod_suc = NULL` **no entran al `JOIN`** y por lo tanto
> nunca aparecen en el `SELECT` de violaciones: se consideran válidas. **Es el comportamiento correcto**
> —sin sucursal no hay localidad que comparar— pero conviene decirlo, porque es la clase de detalle que
> distingue una respuesta pensada de una copiada.

> [!note] B.6 cuenta filas, y eso es correcto **por cómo está la PK**
> *"No más de 20 **productos**"* pide contar **productos distintos** por proveedor. `COUNT(*)` cuenta
> **filas**. Coinciden porque la PK de `PROVEE` es `(cod_producto, nro_prov)`: **no puede haber dos
> filas con el mismo par**, así que una fila = un producto. Si la PK incluyera `cod_suc`, un mismo
> producto podría aparecer varias veces y habría que escribir `COUNT(DISTINCT cod_producto)`.

### 3.c · Qué soporta MySQL

> [!quote] La consigna
> *"Plantee las sentencias de alteración de tablas de las restricciones que **puedan ser soportadas
> por MySQL**"*

> [!important] 🎯 La respuesta corta, y el criterio detrás
> **MySQL soporta A.1, A.2, A.3, B.7 y B.8. No soporta A.4, A.5, B.6 ni B.9.**
>
> Y **el corte no es arbitrario: es exactamente la jerarquía del slide 15**. Dos limitaciones de MySQL
> lo producen:
> 1. **No admite subconsultas dentro de un `CHECK`** → cae todo lo de **ámbito tabla**.
> 2. **No implementa `CREATE ASSERTION`** *(ningún motor lo hace)* → cae todo lo **global**.
>
> | Ámbito | Restricciones | ¿MySQL? |
> | --- | --- | --- |
> | de atributo / dominio | A.1 · A.2 · B.7 | ✅ |
> | de registro / tupla | A.3 · B.8 | ✅ |
> | **de tabla** | A.4 · B.6 | ❌ *(subconsulta)* |
> | **global / BD** | A.5 · B.9 | ❌ *(`ASSERTION`)* |
>
> **La línea cae entre *tupla* y *tabla*.** Es lo más rendidor de todo el TP: una regla, cuatro casos,
> y sirve para cualquier ejercicio del tema.

Las cinco que sí, en MySQL:

```sql
-- A.1 — igual que el estándar
ALTER TABLE ARTICULO
  ADD CONSTRAINT ck_articulo_nacionalidad
  CHECK (nacionalidad IN ('Argentino','Español','Inglés','Alemán','Chileno'));

-- A.2 — el literal de fecha va sin la palabra DATE
ALTER TABLE ARTICULO
  ADD CONSTRAINT ck_articulo_fecha_pub
  CHECK (fecha_pub >= '2010-01-01');

-- A.3 — YEAR() es la forma idiomática; EXTRACT(YEAR FROM …) también existe
ALTER TABLE ARTICULO
  ADD CONSTRAINT ck_articulo_2017_argentino
  CHECK (YEAR(fecha_pub) <> 2017 OR nacionalidad = 'Argentino');

-- B.7 — el escape del guion bajo, igual que en el estándar
ALTER TABLE SUCURSAL
  ADD CONSTRAINT ck_sucursal_cod
  CHECK (cod_suc LIKE 'S\_%');

-- B.8 — igual que el estándar
ALTER TABLE PRODUCTO
  ADD CONSTRAINT ck_producto_desc_o_pres
  CHECK (descripcion IS NOT NULL OR presentacion IS NOT NULL);
```

> [!note] Detalles de MySQL en estas cinco
> - **`DATE '2010-01-01'`** es sintaxis estándar; MySQL prefiere el literal `'2010-01-01'` a secas.
>   Acepta las dos, pero conviene la corta.
> - **`YEAR(fecha_pub)`** es determinística, así que el `CHECK` la admite. **MySQL prohíbe funciones no
>   determinísticas** dentro de un `CHECK` — `NOW()`, `RAND()`, `CURRENT_DATE` quedan afuera. Nada de
>   este TP las necesita, pero es la otra restricción a tener presente.
> - **En `LIKE 'S\_%'` no hace falta el `ESCAPE '\'`**: en MySQL la barra invertida ya es el carácter
>   de escape por defecto dentro de las cadenas. Ponerlo igual no molesta y hace el `CHECK` portable.
> - **Alternativa para A.1**: `nacionalidad ENUM('Argentino','Español','Inglés','Alemán','Chileno')`
>   como tipo de columna. Es lo más parecido que MySQL tiene a un `CREATE DOMAIN`. Cambia el mensaje
>   de error y no se puede ampliar sin un `ALTER`, así que **el `CHECK` es la respuesta al ejercicio**;
>   el `ENUM` vale mencionarlo.

Y las cuatro que no — **qué se hace en su lugar**:

| # | Por qué no | Sustituto en MySQL |
| --- | --- | --- |
| **A.4** | `CHECK` con subconsulta | trigger `BEFORE INSERT` **y** `BEFORE UPDATE` sobre `CONTIENE` |
| **B.6** | `CHECK` con subconsulta | trigger `BEFORE INSERT` **y** `BEFORE UPDATE` sobre `PROVEE` |
| **A.5** | `ASSERTION` | triggers sobre `CONTIENE` **y** sobre `ARTICULO` *(cambiar la nacionalidad puede violarla)* |
| **B.9** | `ASSERTION` | triggers sobre `PROVEE`, **y también** sobre `PROVEEDOR` y `SUCURSAL` cuando cambia `localidad` |

Un ejemplo de la traducción, para B.6:

```sql
DELIMITER $$
CREATE TRIGGER tr_provee_max_20_ins
BEFORE INSERT ON PROVEE
FOR EACH ROW
BEGIN
    IF (SELECT COUNT(*) FROM PROVEE WHERE nro_prov = NEW.nro_prov) >= 20 THEN
        SIGNAL SQLSTATE '45000'
          SET MESSAGE_TEXT = 'Un proveedor no puede proveer más de 20 productos';
    END IF;
END$$
DELIMITER ;
```

*(Razonamiento propio: la teórica no muestra sintaxis de MySQL. `SIGNAL SQLSTATE '45000'` es la forma
MySQL del `funcion_error()` del slide 34, y `DELIMITER` hace falta porque el cuerpo tiene `;`
adentro.)*

> [!warning] 🔴 Los triggers **no son una traducción equivalente**, y el propio deck lo dice
> El slide 37 de la [[Clase 09 - Restricciones integridad-Parte 1|teórica]]:
>
> - *"un trigger definido para forzar una RI **no verifica su cumplimiento para los datos ya
>   almacenados** en la BD"* → al crear el trigger, **los proveedores que ya tienen 25 productos siguen
>   ahí**. Con un `CHECK`, el `ALTER TABLE` habría fallado.
> - Hace falta **un trigger por evento** —`INSERT` y `UPDATE`, y para B.9 y A.5 también sobre las otras
>   tablas—, así que una restricción declarativa se convierte en **dos a cuatro** piezas de código que
>   hay que mantener sincronizadas.
> - Y **MySQL prohíbe que un trigger modifique la tabla que disparó la sentencia** *(error 1442)*, lo
>   que complica algunos patrones.
>
> Al entregar el 3.c conviene decirlo: **no es que MySQL "lo haga distinto", es que lo hace peor**.
> Ésa es la respuesta que muestra que se entendió el slide 37.
