# DDL — creación y alteración de tablas

## Resumen general

Referencia de sintaxis del lenguaje de definición de datos —`CREATE TABLE` con tipos y
restricciones, `ALTER TABLE` y `DROP TABLE`— según los decks de las Clases 03 y 04, traducida al
motor de la cursada. El punto central es un desfasaje: los decks están escritos en PostgreSQL (el
bloque D lo declara en su slide 3; el bloque C enlaza el catálogo de tipos de PostgreSQL 9.5), pero
la cursada y el script del TP (`esq_peliculas.sql`) corren sobre MySQL. Por eso cada tabla trae una
columna MySQL, y `verificar` marca lo que no se pudo confirmar.

Reglas que hay que saber: los `CREATE TABLE` de los slides corren en MySQL sin cambios, salvo dos
tipeos. Toda clave compuesta va como `table_constraint`, porque la forma de columna no admite lista;
en MySQL/InnoDB el `REFERENCES` inline no crea la foreign key, así que las FK van como
`table_constraint` o por `ALTER TABLE`, que además resuelve los ciclos de referencias entre tablas.
De las siete formas de `ALTER TABLE` del slide, tres no compilan en MySQL —cambio de tipo, poner y
quitar `NOT NULL`— y se resuelven con `MODIFY COLUMN`, que redeclara la columna entera y pierde todo
atributo que no se repita. Una FK se borra con `DROP FOREIGN KEY` y una PK con `DROP PRIMARY KEY`,
porque MySQL descarta el nombre que se le dé. `DROP TABLE` acepta `CASCADE` y `RESTRICT` pero los
ignora: hay que soltar las FK antes o desactivar `FOREIGN_KEY_CHECKS`. Y el DDL en MySQL hace
*commit* implícito, sin `ROLLBACK` posible.

Para el parcial: la tabla de traducción PostgreSQL → MySQL del `ALTER TABLE`, la diferencia entre
`column_constraint` y `table_constraint`, y las trampas de copiar del PDF (acentos agudos y comillas
curvas que no compilan). Sigue abierto qué motor se toma.

## `CREATE TABLE`

### La gramática (bloque C, slides 23–24)

Corchetes = opcional; llaves con `|` = alternativas.

```
CREATE [ TABLE [ IF NOT EXISTS ] nombre_tabla (
[
  { nombre_columna tipo_dato [ column_constraint [ ... ], ]
  | table_constraint }
  [, ... ]
] );
```

> [!bug] El corchete del slide 23 no cierra
> Abre dos `[` y cierra uno: en el *synopsis* de PostgreSQL el primero envuelve
> `TEMPORARY`/`TEMP`/`UNLOGGED`, que el deck borró (razonamiento propio). Léase
> `CREATE TABLE [ IF NOT EXISTS ] nombre_tabla ( … )`.

### La forma que usan todos los ejemplos (slide 9)

```sql
CREATE TABLE ALUMNO(
  LU  integer  NOT NULL,
  Documento  integer  NOT NULL,
  Apellido  varchar(30)  NOT NULL,
  Nombre  varchar(30)  NOT NULL,
  Tutor  varchar(50),
  Calle  varchar(40)  NOT NULL,
  Nro  integer  NOT NULL,
  Ciudad  varchar(60)  NOT NULL,
  CONSTRAINT PK_ALUMNO PRIMARY KEY (LU)
);
```

El slide dice `varchar(6 0)`; aquí va corregido. **Convención de nombres de constraint** de los
ejemplos (nunca enunciada como regla): `PK_<TABLA>` / `Pk_<Tabla>` (`PK_ALUMNO`, `Pk_Alumno`),
`FK_<TABLA>_<TABLAREFERENCIADA>` (`FK_ALUMNOSXCARRERA_CARRERA`, `Fk_Alumno_Univ`), `U_<algo>`
(`U_tit`); `esq_peliculas.sql` la mezcla con la automática de PostgreSQL, `<tabla>_<columna>_fkey`.

## Tipos de datos

El deck solo dice que *"cada columna debe tener un determinado tipo de dato"* y que este *"limita el
conjunto de valores posibles que se pueden asignar a una columna"*; el slide 10 del bloque C **es solo
un link**, *"Tipos de datos Postgresql"* → `https://www.postgresql.org/docs/9.5/static/datatype.html`:
versión sin soporte y motor equivocado; para el TP vale el catálogo de **MySQL**. Los tipos de los
ejemplos existen igual en MySQL: `integer` (`LU`, `Nro`, `Documento`), `varchar(n)`, `char(n)` para
códigos de longitud fija (`IdCarrera char(5)`, `PlanEstudio char(6)`), `date` (`FechaNac`) y el
`VARCHAR(10)` de `condicion` en el `ALTER` del bloque D. **Los `CREATE TABLE` de los slides 9, 15 y 16
corren en MySQL sin cambios**, salvo los dos tipeos: el problema de motor está en el `ALTER TABLE`.

> [!note] Tipos de Oracle en el bloque E (ampliación, no está en el deck)
> `VARCHAR2(n)` → `VARCHAR(n)`; `NUMBER(p,s)` → `DECIMAL(p,s)` (o `INT` si `s = 0`). Aparecen en los
> ejercicios → [[Clase 05 - Consultas de Datos–Parte 2]].

## Restricciones declarativas

El deck las parte según **dónde se escriben**. `column_constraint`, pegada a una columna:

```
[ CONSTRAINT constraint_name ]
{ NOT NULL |
  NULL |
  DEFAULT default_expr |
  UNIQUE index_parameters |
  PRIMARY KEY index_parameters |
  REFERENCES reftable [ ( refcolumn ) ] }
```

`table_constraint`, un ítem más de la lista, después de las columnas:

```
[ CONSTRAINT constraint_name ]
{ CHECK ( expression ) |
  UNIQUE ( column_name [, ... ] ) |
  PRIMARY KEY ( column_name [, ... ] )  |
  FOREIGN KEY ( column_name [, ... ] )
  REFERENCES reftable [ ( refcolumn [, ... ] ) ]
}
```

| Restricción | `column_constraint` | `table_constraint` | En MySQL |
| --- | --- | --- | --- |
| `NOT NULL` / `NULL` | ✓ | ✗ | igual |
| `DEFAULT valor` | ✓ | ✗ | (atención) **restringe** las expresiones; el `default_expr` arbitrario es PostgreSQL |
| `UNIQUE` | ✓ sin lista | ✓ **con lista** | igual; **es un índice** |
| `PRIMARY KEY` | ✓ sin lista | ✓ **con lista** | igual; se llama siempre `PRIMARY` |
| `CHECK (expr)` | ✗ **no está en el slide** | ✓ | (atención) **verificar la versión**: lo ignoró silenciosamente durante años |
| Referencia a otra tabla | `REFERENCES reftable` | `FOREIGN KEY (…) REFERENCES reftable` | (atención) la forma inline **no crea la FK** en InnoDB |
| `index_parameters` en `UNIQUE`/`PRIMARY KEY` | ✓ *(en el slide)* | — | ✗ **no existe**; es PostgreSQL |

Dos consecuencias (razonamiento propio, no están en el deck):

- **Clave compuesta → siempre `table_constraint`**: `CONSTRAINT PK_ALUMNOSXCARRERA PRIMARY KEY
  (LU, IdCarrera)` no cabe en la forma de columna. Ahí caen N:N, entidad débil y multivaluado →
  [[1.03.01 - Derivación de MER a esquema relacional|Derivación de MER a esquema relacional]].
- **`REFERENCES` inline en MySQL/InnoDB se acepta y no crea la foreign key**: va como
  `table_constraint` (`FOREIGN KEY (col) REFERENCES …`) o por `ALTER TABLE`, como todos los ejemplos
  del deck; el riesgo es copiar la gramática del slide 23. **Confirmar contra el manual de MySQL.**

### Declarar las claves aparte

Para el deck son **alternativas** (*"O puede colocarse la definición de la clave primaria en
sentencia aparte"*): tras el `CREATE TABLE` del slide 9, este `ALTER` falla porque la PK ya existe.

```sql
ALTER TABLE ALUMNO
ADD CONSTRAINT PK_ALUMNO PRIMARY KEY (LU);
```

```sql
ALTER TABLE Alumno
  ADD  CONSTRAINT Fk_Alumno_Univ  FOREIGN KEY (nom_univ)
  REFERENCES Universidad (nom_univ)  ;
```

> [!tip] Por qué las FK van aparte (razonamiento propio, no está en el deck)
> Una FK solo puede apuntar a una tabla **que ya exista**: dentro del `CREATE` obliga a un orden
> topológico, imposible **con ciclos** (`empleado.id_jefe → empleado`). Con `ALTER TABLE` el orden no
> importa; `esq_peliculas.sql`, con dos ciclos, hace exactamente eso: todos los `CREATE TABLE`, luego
> las PKs, luego las FKs.

## `ALTER TABLE`

> [!quote] Bloque D, slide 3
> *"Una vez creada una tabla es posible realizar algunas modificaciones en su definición (ej, agregar
> o quitar columnas, especificar valores por defecto, incorporar restricciones o quitarlas, etc.*
> **La sintaxis de PostgreSQL**"

Las **siete formas**, tal como figuran en el slide:

```sql
ALTER TABLE tabla ADD COLUMN columna tipo;  -- → Agrega columna

ALTER TABLE tabla DROP COLUMN columna;  -- → Elimina columna

ALTER TABLE tabla RENAME COLUMN
  Columna_vieja TO columna_nueva;  -- → renombra una columna

ALTER TABLE tabla columna TYPE nuevo_tipo;  -- → cambia tipo de dato

ALTER TABLE tabla ALTER COLUMN columna
  [SET DEFAULT value | DROP DEFAULT]  -- → Asigna o elimina valor por defecto

ALTER TABLE tabla ALTER COLUMN columna
  [SET NOT NULL | DROP NOT NULL]  -- → Asigna o elimina rest. nulidad

ALTER TABLE tabla ADD CONSTRAINT name constraint-definition  -- → incorpora restricción
```

> [!bug] La cuarta sentencia está mal escrita, y dos veces
> A `ALTER TABLE tabla columna TYPE nuevo_tipo;` le falta el `ALTER COLUMN` (PostgreSQL:
> `ALTER TABLE tabla ALTER COLUMN columna TYPE nuevo_tipo;`); no vale en ningún motor. Se repite en el
> slide 5 (`ALTER TABLE Alumno condicion TYPE VARCHAR(30);`): no es un artefacto de renderizado.
> **Verificar en clase.**

### Tabla maestra de traducción PostgreSQL → MySQL

| Operación | PostgreSQL — *el slide* | MySQL — *el TP* |
| --- | --- | --- |
| Agregar columna | `ALTER TABLE t ADD COLUMN c tipo;` | **igual** (`COLUMN` es opcional en ambos) |
| Eliminar columna | `ALTER TABLE t DROP COLUMN c;` | **igual** |
| Renombrar columna | `ALTER TABLE t RENAME COLUMN vieja TO nueva;` | **igual** en MySQL 8.0+; antes `ALTER TABLE t CHANGE vieja nueva tipo;` (se repite el tipo) |
| **Cambiar tipo** | `ALTER TABLE t ALTER COLUMN c TYPE nuevo_tipo;` | `ALTER TABLE t MODIFY COLUMN c nuevo_tipo;` — **sin `TYPE`** |
| Asignar default | `ALTER TABLE t ALTER COLUMN c SET DEFAULT v;` | **igual** |
| Quitar default | `ALTER TABLE t ALTER COLUMN c DROP DEFAULT;` | **igual** |
| **Poner `NOT NULL`** | `ALTER TABLE t ALTER COLUMN c SET NOT NULL;` | **no existe** → `ALTER TABLE t MODIFY COLUMN c tipo NOT NULL;` |
| **Quitar `NOT NULL`** | `ALTER TABLE t ALTER COLUMN c DROP NOT NULL;` | **no existe** → `ALTER TABLE t MODIFY COLUMN c tipo NULL;` |
| Agregar `UNIQUE` | `ALTER TABLE t ADD CONSTRAINT n UNIQUE (c);` | **igual** |
| Agregar `PRIMARY KEY` | `ALTER TABLE t ADD CONSTRAINT n PRIMARY KEY (c);` | **igual** *(el nombre `n` se pierde)* |
| Agregar `FOREIGN KEY` | `ALTER TABLE t ADD CONSTRAINT n FOREIGN KEY (c) REFERENCES t2 (c2);` | **igual** (requiere InnoDB) |
| **Eliminar una FK** | `ALTER TABLE t DROP CONSTRAINT n;` | `ALTER TABLE t DROP FOREIGN KEY n;` (la forma de `esq_peliculas.sql`) |
| Eliminar una PK | *(no está en el deck)* | `ALTER TABLE t DROP PRIMARY KEY;` |
| Eliminar una `UNIQUE` | *(no está en el deck)* | `ALTER TABLE t DROP INDEX n;` |
| `DROP CONSTRAINT` genérico | `ALTER TABLE t DROP CONSTRAINT n;` | **`verificar`**: existe en MySQL 8 moderno, no consta desde qué versión; usar las tres formas específicas de arriba, que sí son seguras |

> [!warning] Las tres operaciones que no compilan en MySQL
> La cuarta sentencia del slide (cambio de tipo) y la sexta (**dos** operaciones de nulidad en una
> línea) van con `MODIFY COLUMN`:
> ```sql
> ALTER TABLE Alumno MODIFY COLUMN condicion VARCHAR(30);  -- cambiar el tipo
> ALTER TABLE Alumno MODIFY COLUMN tutor VARCHAR(50) NOT NULL;  -- poner NOT NULL
> ALTER TABLE Alumno MODIFY COLUMN tutor VARCHAR(50) NULL;  -- quitar NOT NULL
> ```
> **Trampa:** `MODIFY` redeclara la columna **entera**; lo que no se repita se pierde (con
> `DEFAULT 'Regular'`, `MODIFY COLUMN condicion VARCHAR(30)` a secas borra el default).

**Nombre de la PK:** MySQL acepta `ADD CONSTRAINT Pk_Alumno PRIMARY KEY (…)` pero la llama siempre
`PRIMARY`; se borra con `DROP PRIMARY KEY`, no por nombre. **Verificar en clase** si el nombre importa.

### `MODIFY` vs. `CHANGE` vs. `RENAME COLUMN` en MySQL

Ampliación, no está en el deck:

| Sentencia | Qué cambia | ¿Repite el tipo? |
| --- | --- | --- |
| `MODIFY COLUMN c tipo` | la definición; **conserva el nombre** | sí |
| `CHANGE COLUMN viejo nuevo tipo` | **nombre y definición** | sí |
| `RENAME COLUMN a TO b` *(8.0+)* | solo el nombre | no |

`ALTER TABLE` admite **varias acciones en una sentencia**, separadas por coma; `SHOW CREATE TABLE t;`
imprime la definición completa con los nombres de todas las FK.

### El `(OJO)!!!` del `SET NOT NULL`

El slide 5 del bloque D lo marca con *"(OJO)!!!"* sin explicar por qué. Dos hipótesis (razonamiento
propio), a confirmar en clase: (1) poner `NOT NULL` sobre una columna que **ya tiene filas con
`NULL`** hace fallar la sentencia entera; hay que rellenar los nulos con un `UPDATE` antes. (2) `tutor`
era el ejemplo de atributo **opcional** del MER: hacerlo obligatorio **contradice el modelo
conceptual**.

## `DROP TABLE`

```sql
DROP TABLE nombre_tabla [CASCADE | RESTRICT]
```

> [!quote] Bloque D, slide 7
> *"Se elimina la definición de la tabla y todas las filas que contiene"* → ***"tener precaución en su
> uso"***

| Opción | Qué hace, textual del slide |
| --- | --- |
| **`RESTRICT`** | *"se rechaza si hay objetos definidos a partir de la tabla"* — **la opción por defecto** |
| **`CASCADE`** | *"se eliminan **todos** los objetos dependientes de la tabla (también los objetos que dependan a su vez de ellos)"* |

> [!warning] En MySQL `CASCADE` y `RESTRICT` **no hacen nada**
> Las acepta para facilitar el porteo de scripts, pero **las ignora**: no hay borrado en cascada.
> `DROP TABLE` sobre una tabla referenciada por una FK **falla**; dos salidas:
> ```sql
> -- (a) soltar la FK primero, o borrar en orden inverso a las dependencias
> ALTER TABLE hija DROP FOREIGN KEY fk_hija_madre;
> DROP TABLE madre;
>
> -- (b) desactivar el chequeo, borrar todo, reactivarlo
> SET FOREIGN_KEY_CHECKS = 0;
> DROP TABLE madre, hija;
> SET FOREIGN_KEY_CHECKS = 1;
> ```
> La (a) es la de `esq_peliculas.sql` en su encabezado comentado.

### `DROP TABLE` vs. `DELETE FROM` vs. `TRUNCATE`

`TRUNCATE` no está en el deck (razonamiento propio); entra al parcial con frecuencia, **verificar si
la cátedra lo toma**.

| Sentencia | Borra la definición | Borra los datos | ¿Se puede filtrar? |
| --- | --- | --- | --- |
| `DROP TABLE t` | **sí** | sí | no |
| `DELETE FROM t [WHERE …]` | no | sí, **fila por fila** | **sí**, con `WHERE` |
| `TRUNCATE TABLE t` | no | sí, **de golpe** | no |

> [!warning] En MySQL el DDL hace *commit* implícito
> Razonamiento propio, no está en el deck: `ALTER TABLE` y `DROP TABLE` **no se deshacen con
> `ROLLBACK`** y cierran la transacción abierta; en PostgreSQL el DDL **sí** es transaccional. Es una
> diferencia de fondo, no de sintaxis, y por eso el *"tener precaución"* del slide 7 pesa más en MySQL
> → [[1.11.03 - Transacciones y ACID|Transacciones ACID]].
