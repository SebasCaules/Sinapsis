# DDL — creación y alteración de tablas

Referencia de sintaxis del **lenguaje de definición de datos**: crear una tabla, ponerle
restricciones, modificarla cuando el modelo cambia y borrarla. Sale de dos decks —
[[Clase 03 - Derivación a Esquema Lógico]] (slides 9, 15, 16, 23–24) y
[[Clase 04 - AlteraciónActualizaciónTablas]] (slides 3–7).

> [!warning] Los dos decks están escritos en PostgreSQL y la cursada corre sobre MySQL
> El bloque D lo dice **textualmente** en su slide 3: *"La sintaxis de **PostgreSQL**"*. El bloque C
> linkea el catálogo de tipos de **PostgreSQL 9.5**. La cursada corre sobre **MySQL**
> ([[_cronograma]]) y el script del TP (`esq_peliculas.sql`) usa sintaxis MySQL.
> **Cada tabla de esta página trae la columna MySQL.** Donde dice `verificar` es porque no hay certeza:
> no está inventado ni adivinado.

De qué **no** habla esta página: el `INSERT`/`UPDATE`/`DELETE` es **DML**, no DDL, aunque el bloque D
lo dé en los mismos nueve slides → [[Clase 04 - AlteraciónActualizaciónTablas]]
slides 8–9. Las consultas están en [[1.05.01 - SQL — consultas|SQL — consultas]].

## `CREATE TABLE`

### La gramática (bloque C, slides 23–24)

Notación de *synopsis*: corchetes = opcional, llaves + `|` = alternativas.

```
CREATE [ TABLE [ IF NOT EXISTS ] nombre_tabla (
[
  { nombre_columna tipo_dato [ column_constraint [ ... ], ]
    | table_constraint }
    [, ... ]
] );
```

> [!bug] El corchete del slide 23 no cierra
> Abre dos `[` y cierra uno solo. **Razonamiento propio:** en el *synopsis* real de PostgreSQL ese
> primer corchete envuelve `TEMPORARY`/`TEMP`/`UNLOGGED`, que el deck borró dejando el `[` huérfano.
> Se lee como si dijera `CREATE TABLE [ IF NOT EXISTS ] nombre_tabla ( … )`.

### La forma que usan todos los ejemplos

```sql
CREATE TABLE ALUMNO(
    LU             integer      NOT NULL,
    Documento      integer      NOT NULL,
    Apellido       varchar(30)  NOT NULL,
    Nombre         varchar(30)  NOT NULL,
    Tutor          varchar(50),
    Calle          varchar(40)  NOT NULL,
    Nro            integer      NOT NULL,
    Ciudad         varchar(60)  NOT NULL,
    CONSTRAINT PK_ALUMNO PRIMARY KEY (LU)
);
```

Dos hechos del deck que sostienen esto: *"cada columna debe tener un determinado **tipo de dato**"* y
*"el tipo de dato **limita el conjunto de valores posibles** que se pueden asignar a una columna"*.

> [!bug] En el slide 9 dice `varchar(6 0)`, con un espacio en el medio
> Tal cual está **no compila**. Acá va corregido a `varchar(60)`. El mismo tipo de tipeo aparece en el
> slide 16 con `PK_ ALUMNOSXCARRERA`.

**Convención de nombres de constraint** que siguen los ejemplos de los dos decks (nunca se enuncia
como regla):

| Tipo | Patrón | Ejemplos del deck |
| --- | --- | --- |
| Primaria | `PK_<TABLA>` · `Pk_<Tabla>` | `PK_ALUMNO`, `Pk_Alumno` |
| Extranjera | `FK_<TABLA>_<TABLAREFERENCIADA>` | `FK_ALUMNOSXCARRERA_CARRERA`, `Fk_Alumno_Univ` |
| Unicidad | `U_<algo>` | `U_tit` |

*(El script `esq_peliculas.sql` mezcla esa convención con la que genera PostgreSQL automáticamente,
`<tabla>_<columna>_fkey`.)*

## Restricciones declarativas

El deck las parte en dos según **dónde se escriben**, y esa división es la que decide todo.

**`column_constraint`** — pegada a una columna:

```
[ CONSTRAINT constraint_name ]
{ NOT NULL |
  NULL |
  DEFAULT default_expr |
  UNIQUE index_parameters |
  PRIMARY KEY index_parameters |
  REFERENCES reftable [ ( refcolumn ) ] }
```

**`table_constraint`** — como un ítem más de la lista, después de las columnas:

```
[ CONSTRAINT constraint_name ]
{ CHECK ( expression ) |
  UNIQUE ( column_name [, ... ] ) |
  PRIMARY KEY ( column_name [, ... ] )  |
  FOREIGN KEY ( column_name [, ... ] )
  REFERENCES reftable [ ( refcolumn [, ... ] ) ]
}
```

| Restricción | `column_constraint` | `table_constraint` | En MySQL |
| --- | --- | --- | --- |
| `NOT NULL` / `NULL` | ✅ | ❌ | igual |
| `DEFAULT valor` | ✅ | ❌ | ⚠️ MySQL **restringe** qué expresiones acepta el `DEFAULT`; el `DEFAULT default_expr` arbitrario es PostgreSQL |
| `UNIQUE` | ✅ (sin lista) | ✅ **con lista** de columnas | igual · en MySQL una `UNIQUE` **es un índice** |
| `PRIMARY KEY` | ✅ (sin lista) | ✅ **con lista** de columnas | igual · MySQL la llama internamente `PRIMARY` siempre |
| `CHECK (expr)` | ❌ **no está en la lista del slide** | ✅ | ⚠️ **verificar la versión**: MySQL lo ignoró silenciosamente durante años |
| Referencia a otra tabla | `REFERENCES reftable` | `FOREIGN KEY (…) REFERENCES reftable` | ⚠️ la forma **inline no crea la FK** en InnoDB — ver abajo |
| `index_parameters` en `UNIQUE`/`PRIMARY KEY` | ✅ *(en el slide)* | — | ❌ **no existe en MySQL**, es PostgreSQL |

> [!important] Por qué toda clave compuesta va sí o sí como `table_constraint`
> **Razonamiento propio, no está en el deck** — pero es la razón de forma detrás de todos sus ejemplos:
> `CONSTRAINT PK_ALUMNOSXCARRERA PRIMARY KEY (LU, IdCarrera)` **solo** se puede escribir como
> `table_constraint`, porque la versión de columna no acepta lista. Toda PK compuesta —N:N, entidad
> débil, tabla de multivaluado— cae acá → [[1.03.01 - Derivación de MER a esquema relacional|Derivación de MER a esquema relacional]].

> [!warning] La trampa de `REFERENCES` inline en MySQL
> **Razonamiento propio, no está en el deck:** en **MySQL/InnoDB**, `columna tipo REFERENCES otra(col)`
> se **acepta sintácticamente y no crea la foreign key**. Hay que declararla como `table_constraint`
> (`FOREIGN KEY (col) REFERENCES …`) o con `ALTER TABLE`. **Los ejemplos del deck están del lado
> seguro** porque siempre usan `ALTER TABLE`; el riesgo es copiar la gramática del slide 23.
> **Confirmar contra el manual de MySQL.**

### Declarar las claves aparte

El deck presenta las dos formas como **alternativas** (*"O puede colocarse la definición de la clave
primaria en sentencia aparte"*):

```sql
ALTER TABLE ALUMNO
ADD CONSTRAINT PK_ALUMNO PRIMARY KEY (LU);
```

```sql
ALTER TABLE Alumno
    ADD   CONSTRAINT Fk_Alumno_Univ  FOREIGN KEY (nom_univ)
               REFERENCES Universidad (nom_univ)  ;
```

> [!tip] Por qué las FK se declaran aparte
> **Razonamiento propio, no está en el deck:** una FK solo puede apuntar a una tabla **que ya exista**.
> Declarándolas dentro del `CREATE` hay que crear las tablas en orden topológico, y **con ciclos no hay
> orden posible** (`empleado.id_jefe → empleado`). Sacando las FK a `ALTER TABLE`, el orden de creación
> deja de importar. `esq_peliculas.sql` tiene dos ciclos y usa exactamente este patrón: primero todos
> los `CREATE TABLE`, después el bloque de PKs, después el de FKs.

> [!note] La PK del slide 9 queda declarada dos veces
> Si se ejecuta el `CREATE TABLE` **y después** el `ALTER TABLE`, el segundo falla porque la PK ya
> existe. Son alternativas, no una secuencia.

## `ALTER TABLE`

> [!quote] Bloque D, slide 3
> *"Una vez creada una tabla es posible realizar algunas modificaciones en su definición (ej, agregar
> o quitar columnas, especificar valores por defecto, incorporar restricciones o quitarlas, etc.*
> **La sintaxis de PostgreSQL**"

Las **siete formas**, exactamente como figuran en el slide:

```sql
ALTER TABLE tabla ADD COLUMN columna tipo;                      -- → Agrega columna

ALTER TABLE tabla DROP COLUMN columna;                          -- → Elimina columna

ALTER TABLE tabla RENAME COLUMN
     Columna_vieja TO columna_nueva;                            -- → renombra una columna

ALTER TABLE tabla columna TYPE nuevo_tipo;                      -- → cambia tipo de dato

ALTER TABLE tabla ALTER COLUMN columna
  [SET DEFAULT value | DROP DEFAULT]                            -- → Asigna o elimina valor por defecto

ALTER TABLE tabla ALTER COLUMN columna
  [SET NOT NULL | DROP NOT NULL]                                -- → Asigna o elimina rest. nulidad

ALTER TABLE tabla ADD CONSTRAINT name constraint-definition     -- → incorpora restricción
```

> [!bug] La cuarta sentencia está mal escrita, y dos veces
> Dice `ALTER TABLE tabla columna TYPE nuevo_tipo;` — **le falta el `ALTER COLUMN`**. No es válida en
> ningún motor. En PostgreSQL sería `ALTER TABLE tabla ALTER COLUMN columna TYPE nuevo_tipo;`. El
> mismo error se repite en el slide 5 (`ALTER TABLE Alumno condicion TYPE VARCHAR(30);`), o sea que
> **no es un artefacto de renderizado**. **Verificar en clase.**

### Tabla maestra de traducción PostgreSQL → MySQL

Columna izquierda: **lo que dice el slide**. Columna derecha: **lo que hay que tipear en el TP**.

| Operación | PostgreSQL — *el slide* | MySQL — *el TP* |
| --- | --- | --- |
| Agregar columna | `ALTER TABLE t ADD COLUMN c tipo;` | **igual** (`COLUMN` es opcional en los dos) |
| Eliminar columna | `ALTER TABLE t DROP COLUMN c;` | **igual** |
| Renombrar columna | `ALTER TABLE t RENAME COLUMN vieja TO nueva;` | **igual** en MySQL 8.0+. En versiones previas: `ALTER TABLE t CHANGE vieja nueva tipo;` (hay que repetir el tipo) |
| **Cambiar tipo de dato** | `ALTER TABLE t ALTER COLUMN c TYPE nuevo_tipo;` | `ALTER TABLE t MODIFY COLUMN c nuevo_tipo;` — **sin `TYPE`** |
| Asignar valor por defecto | `ALTER TABLE t ALTER COLUMN c SET DEFAULT v;` | **igual** |
| Quitar valor por defecto | `ALTER TABLE t ALTER COLUMN c DROP DEFAULT;` | **igual** |
| **Poner `NOT NULL`** | `ALTER TABLE t ALTER COLUMN c SET NOT NULL;` | **no existe** → `ALTER TABLE t MODIFY COLUMN c tipo NOT NULL;` |
| **Quitar `NOT NULL`** | `ALTER TABLE t ALTER COLUMN c DROP NOT NULL;` | **no existe** → `ALTER TABLE t MODIFY COLUMN c tipo NULL;` |
| Agregar `UNIQUE` | `ALTER TABLE t ADD CONSTRAINT n UNIQUE (c);` | **igual** |
| Agregar `PRIMARY KEY` | `ALTER TABLE t ADD CONSTRAINT n PRIMARY KEY (c);` | **igual** *(el nombre `n` se pierde, ver abajo)* |
| Agregar `FOREIGN KEY` | `ALTER TABLE t ADD CONSTRAINT n FOREIGN KEY (c) REFERENCES t2 (c2);` | **igual** (requiere InnoDB) |
| **Eliminar una FK** | `ALTER TABLE t DROP CONSTRAINT n;` | `ALTER TABLE t DROP FOREIGN KEY n;` ← la forma que usa `esq_peliculas.sql` |
| Eliminar una PK | *(no está en el deck)* | `ALTER TABLE t DROP PRIMARY KEY;` |
| Eliminar una `UNIQUE` | *(no está en el deck)* | `ALTER TABLE t DROP INDEX n;` *(en MySQL una `UNIQUE` es un índice)* |
| `DROP CONSTRAINT` genérico | `ALTER TABLE t DROP CONSTRAINT n;` | **`verificar`** — existe en MySQL 8 moderno, pero no consta desde qué versión; usar las tres formas específicas de arriba, que sí son seguras |

> [!warning] Las tres operaciones que no compilan en MySQL
> De las siete sentencias del slide, la cuarta (cambio de tipo) y la sexta (que agrupa en una línea con
> corchetes **dos** operaciones de nulidad) → **tres operaciones**, todas resueltas con `MODIFY COLUMN`:
> ```sql
> ALTER TABLE Alumno MODIFY COLUMN condicion VARCHAR(30);            -- cambiar el tipo
> ALTER TABLE Alumno MODIFY COLUMN tutor VARCHAR(50) NOT NULL;       -- poner NOT NULL
> ALTER TABLE Alumno MODIFY COLUMN tutor VARCHAR(50) NULL;           -- quitar NOT NULL
> ```
> **Trampa de `MODIFY`:** redeclara la columna **entera**, así que **todo atributo que no se vuelva a
> escribir se pierde**. Si la columna tenía `DEFAULT 'Regular'` y se hace
> `MODIFY COLUMN condicion VARCHAR(30)` a secas, **el default desaparece**.

> [!note] El nombre de la PK en MySQL
> MySQL acepta `ADD CONSTRAINT Pk_Alumno PRIMARY KEY (…)`, pero internamente la clave primaria se llama
> siempre `PRIMARY`: el nombre que uno le ponga se pierde, y por eso una PK **no se borra por nombre**
> sino con `DROP PRIMARY KEY`. **Verificar en clase** si a la cátedra le importa el nombre.

### `MODIFY` vs. `CHANGE` vs. `RENAME COLUMN` en MySQL

> [!note] Ampliación, no está en el deck

| Sentencia | Qué cambia | ¿Hay que repetir el tipo? |
| --- | --- | --- |
| `MODIFY COLUMN c tipo` | la definición, **conservando el nombre** | sí |
| `CHANGE COLUMN viejo nuevo tipo` | **nombre y definición** a la vez | sí |
| `RENAME COLUMN a TO b` *(8.0+)* | solo el nombre | no |

Y dos cosas más, también fuera del deck:

- **`ALTER TABLE` admite varias acciones en una sola sentencia**, separadas por coma.
- **Para averiguar los nombres de las restricciones antes de borrarlas:** `SHOW CREATE TABLE t;`
  imprime la definición completa con los nombres de todas las FK.

### El `(OJO)!!!` del `SET NOT NULL`

El slide 5 del bloque D marca `SET NOT NULL` con *"(OJO)!!!"* y **no explica por qué**.

> [!important] Dos hipótesis, ninguna está en el deck
> **Razonamiento propio:**
> 1. Poner `NOT NULL` sobre una columna que **ya tiene filas con `NULL`** hace fallar la sentencia
>    entera. Hay que hacer primero un `UPDATE` que rellene los nulos.
> 2. `tutor` es justamente el atributo que el MER usaba como ejemplo de atributo **opcional**:
>    hacerlo obligatorio **contradice el modelo conceptual**.
>
> **Confirmar en clase cuál de las dos es el "OJO".**

## `DROP TABLE`

```sql
DROP TABLE nombre_tabla [CASCADE | RESTRICT]
```

> [!quote] Bloque D, slide 7
> *"Se elimina la definición de la tabla y todas las filas que contiene"* → ***"tener precaución en su
> uso"***

| Opción | Qué hace, textual del slide |
| --- | --- |
| **`RESTRICT`** | *"se rechaza si hay objetos definidos a partir de la tabla"* — **es la opción por defecto** |
| **`CASCADE`** | *"se eliminan **todos** los objetos dependientes de la tabla (también los objetos que dependan a su vez de ellos)"* |

> [!warning] En MySQL `CASCADE` y `RESTRICT` **no hacen nada**
> MySQL acepta las dos palabras clave —están para facilitar el porteo de scripts— pero **las ignora**:
> no hay borrado en cascada de objetos dependientes. `DROP TABLE` sobre una tabla referenciada por una
> FK **falla**, y hay dos salidas:
> ```sql
> -- (a) soltar la FK primero, o borrar en orden inverso a las dependencias
> ALTER TABLE hija DROP FOREIGN KEY fk_hija_madre;
> DROP TABLE madre;
>
> -- (b) desactivar el chequeo, borrar todo, reactivarlo
> SET FOREIGN_KEY_CHECKS = 0;
> DROP TABLE madre, hija;
> SET FOREIGN_KEY_CHECKS = 1;
> ```
> La (a) es la que usa `esq_peliculas.sql` en su encabezado comentado.

### `DROP TABLE` vs. `DELETE FROM` vs. `TRUNCATE`

> [!note] `TRUNCATE` no está en el deck
> **Razonamiento propio.** Entra al parcial con frecuencia; **verificar si la cátedra lo toma.**

| Sentencia | Borra la definición | Borra los datos | ¿Se puede filtrar? |
| --- | --- | --- | --- |
| `DROP TABLE t` | **sí** | sí | no |
| `DELETE FROM t [WHERE …]` | no | sí, **fila por fila** | **sí**, con `WHERE` |
| `TRUNCATE TABLE t` | no | sí, **de golpe** | no |

> [!warning] En MySQL el DDL hace *commit* implícito
> **Razonamiento propio, no está en el deck:** un `ALTER TABLE` o un `DROP TABLE` en MySQL **no se
> puede deshacer con `ROLLBACK`** y además cierra la transacción abierta. En PostgreSQL el DDL **sí**
> es transaccional. Es una diferencia de fondo entre los motores, no de sintaxis, y explica por qué el
> *"tener precaución"* del slide 7 pesa más en MySQL. Se retoma en [[1.11.03 - Transacciones y ACID|Transacciones ACID]].
