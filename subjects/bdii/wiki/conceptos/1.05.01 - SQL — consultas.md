# SQL — consultas

Referencia del **`SELECT`**: cómo se escribe una consulta, en qué orden se evalúa, y qué hace cada
cláusula cuando aparecen nulos, duplicados o grupos. Sale de las **tres partes del bloque E** de la
teórica del 03/08 —[[Clase 05 - Consultas de Datos–Parte 1]],
[[Clase 05 - Consultas de Datos–Parte 2|(Parte 2)]] y
[[Clase 05 - Consultas de Datos–Parte 3|(Parte 3)]]— que son el recorrido slide por
slide. **Esta página es la hoja de referencia**: una sección por cláusula, en el orden en que se
escribe una consulta.

Lo que **no** está acá: crear y modificar tablas → [[1.03.02 - DDL — creación y alteración de tablas|DDL — creación y alteración de tablas]];
`INSERT`/`UPDATE`/`DELETE` → [[Clase 04 - AlteraciónActualizaciónTablas]];
consultas guardadas como objeto → [[1.06.01 - Vistas|Vistas]]; cómo el motor **ejecuta** la consulta → [[1.08.02 - Índices|Índices]].

## 1. La sentencia completa y el orden de evaluación

Los decks dan **tres diagramas de sintaxis distintos** (parte 1 slide 3, parte 2 slide 2, parte 1
slide 29), todos incompletos y uno con un corchete sin cerrar. Esta es la unión de los tres:

```sql
SELECT   [DISTINCT] { * | columna | expresion [AS] [alias] , ... }
FROM     <lista tablas> [alias_tabla]
[WHERE   condicion/es]                  -- filtra FILAS, sin agregados
[GROUP BY lista columnas]               -- particiona en grupos
[HAVING  condicion sobre agregados]     -- filtra GRUPOS
[ORDER BY columna [ASC|DESC], ...]      -- última cláusula lógica
[LIMIT   {numero | ALL}]                -- LIMIT ALL es PostgreSQL
[OFFSET  numero];
```

Lo **único obligatorio** es `SELECT` y `FROM`; todo lo que va entre `[ ]` es opcional.

| Rol | Cláusula | Frase de la cátedra |
| --- | --- | --- |
| Qué columnas recuperar | `SELECT` | **EL QUE** |
| De qué tabla/s | `FROM` | **DE DONDE** |
| Qué filas | `WHERE` | *"se usa para realizar las restricciones"* |

Notación de los diagramas: `|` alternativa · `{ }` agrupación · `[ ]` opcional · `,...` repetible.
‡ *La notación no se explica en ningún deck.*

### Los dos hechos de fondo

- SQL es **declarativo**: se especifica **qué** información se requiere, no **cómo** obtenerla. Del
  *cómo* se ocupa el optimizador → [[1.08.02 - Índices|Índices]].
- **El resultado de una consulta es una tabla** (un número es una tabla de 1 fila × 1 columna) →
  propiedad de **cierre**, y por eso una consulta se puede anidar dentro de otra (§ 10).

### ⚠️ El orden de evaluación ‡

**No es el orden en que se escribe.** Es lo que organiza toda esta página y explica casi todas las
trampas de abajo.

```
FROM  →  WHERE  →  GROUP BY  →  HAVING  →  SELECT  →  DISTINCT  →  ORDER BY  →  LIMIT/OFFSET
```

| Consecuencia | Por qué |
| --- | --- |
| `WHERE COUNT(*) > 7` **falla** | `WHERE` corre **antes** que `GROUP BY`: los grupos todavía no existen |
| `HAVING COUNT(*) > 7` **anda** | `HAVING` corre **después** del agrupamiento |
| **No** se puede usar un alias del `SELECT` en el `WHERE` | `WHERE` corre antes de que el alias exista |
| Sí se puede `ORDER BY` por un **alias** del `SELECT` | `ORDER BY` corre **después** de `SELECT` |
| `DISTINCT` deduplica **después** de proyectar | por eso deduplica la **lista entera**, no una columna |
| `LIMIT` sin `ORDER BY` es no determinístico | `LIMIT` corta lo último, sobre un orden indefinido |

> [!bug] Ningún deck del bloque E enuncia este orden
> La parte 1 sí trae el 1-2-3 del `HAVING` (*agrupar → aplicar la función → mostrar los grupos que
> satisfacen*), que es el mismo hecho para media cadena. El resto es reconstrucción. **Es la sección
> que hay que memorizar**: casi todas las trampas del § 16 son un corolario suyo.

### Convenciones de escritura (parte 1, slide 4)

| Regla | Consecuencia |
| --- | --- |
| **NO** son sensibles a mayúsculas/minúsculas (palabras clave) | `select` = `SELECT` = `SeLeCt` |
| Pueden ocupar una o más líneas | cierra el `;`, no el salto de línea |
| Las palabras clave **no** se abrevian ni se parten entre líneas | no existe `SEL`, ni `SEL\nECT` |
| Cláusulas en líneas separadas y con sangría | legibilidad |
| **MAYÚSCULAS** para reservadas, minúsculas para el resto | convención de la cátedra |

‡ La insensibilidad es de las **palabras reservadas**. Los **identificadores** dependen del motor y del
sistema de archivos; los **datos** comparados con `=` o `LIKE` dependen de la *collation*.

### Comentarios

```sql
SELECT *
FROM personas
/* WHERE apellido = 'Maradona'*/
```

Uso mostrado en la parte 3: **comentar una cláusula para desactivarla** — la consulta corre como
`SELECT * FROM personas`, sin filtro.

| Forma | Alcance | Motor | Nota |
| --- | --- | --- | --- |
| `/* … */` | bloque, multilínea | portable a todos | **es la única que muestran los decks** |
| `-- ` | una línea | MySQL ‡ | el **espacio después del `--` es obligatorio** en MySQL |
| `#` | una línea | MySQL ‡ | — |

## 2. `FROM` — de dónde salen las filas

### Alias de tabla

```sql
SELECT * FROM personas AS p
SELECT * FROM personas p        -- AS opcional; en la práctica nunca se escribe
```

Habilita `p.columna`. Los decks lo presentan como abreviatura cosmética, pero ‡ **es obligatorio** en
dos casos: el **self-join** (§ 2.4) y toda **subconsulta correlacionada** (§ 10.3).

Regla operativa (parte 2, slide 6): *"Si los nombres de columnas se repiten, hay que anteponer el
nombre de la tabla para evitar ambigüedades."*

### 2.1 Lista de tablas en el `FROM` (forma clásica)

```sql
SELECT nombre, apellido
FROM voluntario v, institucion i, direccion d
WHERE v.id_institucion = i.id_institucion   -- ensamble
  AND i.id_direccion   = d.id_direccion     -- ensamble
  AND d.provincia = 'Texas';                -- selección, NO es ensamble
```

> [!important] La regla que hay que memorizar
> **Condiciones de ensamble = (cantidad de tablas − 1).** Tres tablas → dos condiciones. Es el chequeo
> rápido para no olvidarse una y terminar en un **producto cartesiano**. *(El deck enuncia la regla; no
> la justifica ni nombra al producto cartesiano.)*

### 2.2 Ensambles internos

```sql
SELECT nombre, apellido
FROM voluntario v INNER JOIN institucion i
     ON (v.id_institucion = i.id_institucion)
     NATURAL JOIN direccion d
WHERE d.provincia = 'Texas';
```

| Tipo | Sintaxis | Qué devuelve | Trampa |
| --- | --- | --- | --- |
| `INNER JOIN` | `FROM t1 a INNER JOIN t2 b ON (a.k = b.k)` | solo las filas con **valores idénticos** en las columnas comparadas; las tuplas **sin pareja no se muestran** | admite cualquier predicado, no solo `=` |
| **Equi-join** | `INNER JOIN` cuya condición es una **comparación de igualdad** | ídem | la definición del slide 6 es **circular** (*"es un caso particular de INNER JOIN"*) → verificar en clase |
| `NATURAL JOIN` | `FROM t1 a NATURAL JOIN t2 b` | equi-join por **columnas homónimas**; de las columnas repetidas **incluye solo una** | depende de los **nombres**: si aparece una columna homónima nueva, el join **cambia de significado en silencio** ‡ |

| | Lista en `FROM` (parte 2, slide 5) | `JOIN` explícito (slide 7) |
| --- | --- | --- |
| Dónde va el ensamble | en el `WHERE` | en el `FROM`, con `ON` |
| Dónde va el filtro | en el `WHERE`, mezclado con el ensamble | en el `WHERE`, solo |

### 2.3 Ensambles externos (*outer join*)

Formato general, textual del slide 19 de la parte 2:

```sql
SELECT nombre_columnas_a_seleccionar
FROM t1 [NATURAL] [LEFT|RIGHT|FULL] [OUTER] JOIN t2
{ON condiciones| [USING (columna [,columna...])}
[WHERE condiciones];
```

El ensamble externo **incluye las tuplas sin pareja** y **rellena con `NULL`** los valores
inexistentes. Ese es el **tipo 6** de información faltante del § 11.1: un nulo que **lo pone el join**,
no el dato.

| Tipo | Sintaxis | Qué devuelve | MySQL |
| --- | --- | --- | --- |
| `LEFT [OUTER] JOIN` | `FROM A LEFT JOIN B ON A.Key = B.Key` | todo `A` + lo que matchee de `B` | ✅ |
| `RIGHT [OUTER] JOIN` | `FROM A RIGHT JOIN B ON A.Key = B.Key` | todo `B` + lo que matchee de `A` | ✅ |
| `FULL [OUTER] JOIN` | `FROM A FULL OUTER JOIN B ON A.Key = B.Key` | `A` ∪ `B`, con o sin pareja | ❌ **no existe** |

> [!bug] Los ejemplos del slide 20 no compilan
> `FROM entrega RIGHT JOIN video;` y `FROM empresa_productora LEFT JOIN pelicula;` **no tienen
> `ON`/`USING`/`NATURAL`**, y el slide 21 dice *"la cláusula `ON` la debo especificar cuando las
> columnas de ensamble no coinciden en nombre"*. **Escribir siempre el `ON`**, o usar
> `NATURAL LEFT JOIN` si se quiere el ensamble implícito.

**Los 7 patrones del diagrama de Venn** (parte 2, slide 22, © C.L. Moffatt, 2008):

| # | Qué devuelve | Query | MySQL |
| --- | --- | --- | --- |
| 1 | Todo `A` + match de `B` | `FROM TableA A LEFT JOIN TableB B ON A.Key = B.Key` | ✅ |
| 2 | Todo `B` + match de `A` | `FROM TableA A RIGHT JOIN TableB B ON A.Key = B.Key` | ✅ |
| 3 | Solo la intersección | `FROM TableA A INNER JOIN TableB B ON A.Key = B.Key` | ✅ |
| 4 | **Solo `A`** sin intersección *(anti-join)* | `… LEFT JOIN … ON A.Key = B.Key WHERE B.Key IS NULL` | ✅ |
| 5 | **Solo `B`** sin intersección | `… RIGHT JOIN … ON A.Key = B.Key WHERE A.Key IS NULL` | ✅ |
| 6 | Todo `A` ∪ `B` | `… FULL OUTER JOIN … ON A.Key = B.Key` | ❌ |
| 7 | **Diferencia simétrica** | `… FULL OUTER JOIN … WHERE A.Key IS NULL OR B.Key IS NULL` | ❌ |

> [!tip] El patrón que hay que entender, no memorizar
> Los casos **4, 5 y 7** son el mismo truco: outer join + **filtrar por `IS NULL` la clave del lado
> opuesto**. Una fila con `B.Key IS NULL` después de un `LEFT JOIN` es una fila de `A` **que no
> encontró pareja**.
>
> **Cuidado ‡:** el filtro debe ser sobre una columna **que no admita nulos propios**, típicamente la
> clave; si no, mezcla "no matcheó" con "matcheó pero el campo es nulo".

Emulación del `FULL OUTER JOIN` en MySQL ‡:

```sql
SELECT * FROM A LEFT  JOIN B ON A.key = B.key
UNION
SELECT * FROM A RIGHT JOIN B ON A.key = B.key;
```

### 2.4 Self-join

Misma tabla, **dos alias**. La parte 2 lo hace (slide 18) **sin nombrarlo**.

```sql
SELECT nro_voluntario, nombre, apellido
FROM voluntario V1
WHERE [NOT] EXISTS
       (SELECT 1
        FROM voluntario V2
        WHERE V1.nro_voluntario = V2.id_coordinador);
```

Sirve para relaciones **reflexivas** (FK de la tabla a sí misma: `id_coordinador → nro_voluntario`).
**Sin los alias el query es inescribible.**

## 3. `WHERE` — filtro de filas

> *"Las filas recuperadas son aquellas cuyos datos satisfacen **todas** la/s condición/es lógicas."*

**`WHERE` devuelve la fila solo si la condición evalúa a `TRUE`**: descarta `FALSE` **y** `UNKNOWN`
(§ 11). Es la mitad de las trampas de la materia.

### 3.1 Operadores

| Familia | Operadores (textual del slide) |
| --- | --- |
| Comparación | `<`, `>`, `=`, `<=`, `>=`, `<>`, `!=` |
| Lógicos | `AND`, `OR`, `NOT` |

`<>` y `!=` son **sinónimos**; `<>` es el estándar SQL, `!=` lo aceptan MySQL, PostgreSQL y Oracle.
Para el parcial, cualquiera.

| Operador | Sintaxis | Equivale a / devuelve | Trampa |
| --- | --- | --- | --- |
| Rango | `a BETWEEN x AND y` | `a >= x AND a <= y` — **extremos incluidos** | `BETWEEN 120 AND 100` **devuelve vacío**: siempre el menor primero ‡. Si `a IS NULL` → `UNKNOWN` ‡ |
| Fuera de rango | `a NOT BETWEEN x AND y` | `a < x OR a > y` | ídem |
| Patrón | `col [NOT] LIKE 'patrón'` | filas que matchean el patrón | § 3.2 |
| Pertenencia | `col [NOT] IN (…)` | valor dentro de una lista o subconsulta | § 3.3 — **`NOT IN` con nulos devuelve vacío** |
| Test de nulo | `col IS [NOT] NULL` | **la única forma** de testear un nulo | `= NULL` compila y devuelve **cero filas sin error** |
| Conjunción | `c1 AND c2` | `T` solo si **ambas** `T` | `F AND U = F` |
| Disyunción | `c1 OR c2` | `T` si **alguna** `T` | `T OR U = T` |
| Negación | `NOT c` | invierte el resultado | **`NOT UNKNOWN = UNKNOWN`** |

```sql
SELECT nombre, apellido
FROM   voluntario
WHERE  nro_voluntario BETWEEN 100 AND 120;   -- 100 y 120 incluidos
```

### 3.2 `LIKE` — comodines

> *"No siempre se conoce el valor exacto a buscar. Se puede buscar coincidencias con un patrón de
> caracteres mediante el operador `LIKE`."*

| Comodín | Significado (textual) | Matchea vacío |
| --- | --- | --- |
| `%` | *"cualquier secuencia de **cero o más** caracteres"* | **sí** |
| `_` | *"denota **un solo** carácter"* | **no** |

La **posición** del `%` define el significado:

| Patrón | Qué devuelve |
| --- | --- |
| `LIKE 'Garcia%'` | **empieza con** `Garcia` |
| `LIKE '%Garcia'` | **termina con** `Garcia` |
| `LIKE '%G%'` | **contiene** una `G` |
| `LIKE 'G_rcia'` | matchea `Garcia`, `Gorcia`; **no** `Grcia` |
| `LIKE '_a%n'` | 1 char + `a` + lo que sea + `n` final → `Karen`, `Jason`; **no** `Ana` ‡ |

| Trampa de `LIKE` | Detalle |
| --- | --- |
| Mayúsculas ‡ | **PostgreSQL: `LIKE` es sensible** (usar `ILIKE`). **MySQL: depende de la *collation*** — con la default `utf8mb4_..._ci` es **insensible** |
| `%` o `_` literales ‡ | requieren `ESCAPE`. No aparece en ningún deck |
| Clase de caracteres | `LIKE 'A[nm]%'`, `LIKE '[-acfi]%'` son **T-SQL** → ver abajo |

> [!bug] Específico de motor — los corchetes `[…]` de la parte 3
> | Motor | `[…]` dentro de `LIKE` | Alternativa |
> | --- | --- | --- |
> | SQL Server / MS Access | clase de caracteres (funciona) | — |
> | **MySQL** | **literal**: `'A[nm]%'` busca los 5 caracteres `A[nm]` → **no devuelve nada**. Solo conoce `%` y `_` | `REGEXP` (sinónimo `RLIKE`) |
> | **PostgreSQL** | tampoco funciona con `LIKE` | `SIMILAR TO` o el operador `~` |
>
> ```sql
> WHERE apellido REGEXP '^A[nm]'      -- las que empiezan con An o Am
> WHERE apellido REGEXP '^[-acfi]'    -- las que empiezan con -, a, c, f o i
> ```

### 3.3 `[NOT] IN` con lista literal

> *"La sentencia `IN` sirve para comparar un campo con un conjunto de datos"* · *"Permite determinar si
> los valores de una columna, o conjunto de ellas, están contenidos (o no) en una lista definida o
> dentro de otra tabla (subconsulta)."*

```sql
SELECT * FROM productos WHERE nombre IN('Fernet','Coca Cola','Hielo');
```

Equivalencias, textual de la parte 2 slide 13:

```
IN (v1, v2, …., vn)      ≡  ((x=v1) or (x=v2) …or (x=vn))
NOT IN (v1, v2, …., vn)  ≡  NOT ((x=v1) or (x=v2) …or (x=vn))
                         ≡  ((x<>v1) and (x<>v2) …and (x<>vn))
```

**Con nulos cambia todo** → § 11.4. La versión con subconsulta está en § 10.2.

### 3.4 `IS [NOT] NULL`

> *"Si una columna en particular carece de un valor se dice que contiene un `NULL`."*
> *"Si se desea incluir en el resultado los datos de aquellas columnas que tengan nulos hay que hacerlo
> **explícitamente**."*

```sql
SELECT * FROM voluntario
WHERE  porcentaje <= 0.1
   OR  porcentaje IS NULL;      -- incluir los nulos: hay que pedirlo
```

En SQL el separador decimal es **el punto**; la coma separa argumentos (el slide escribe `0,10` en el
texto y `0.1` en la consulta).

### 3.5 Precedencia y paréntesis

| Precedencia ‡ | `NOT` > `AND` > `OR` |
| --- | --- |
| **Regla de oro** | **si en un `WHERE` conviven `AND` y `OR`, poner paréntesis siempre**, aunque sean redundantes |

```sql
-- correcta
WHERE (id_coordinador=100 OR id_coordinador=124) AND id_institucion=50

-- sin paréntesis se agrupa así, y devuelve filas de más:
WHERE id_coordinador=100 OR (id_coordinador=124 AND id_institucion=50)
```

> [!bug] El deck dice *"No es válida la consulta sin los paréntesis"* y es impreciso
> La consulta **es válida y el motor no da error**: ejecuta perfecto y devuelve **el conjunto
> equivocado**. Es peor que un error de sintaxis, no mejor.

## 4. Funciones de agregación

> *"Estas funciones operan sobre **conjuntos de filas** para proporcionar **un resultado por grupo**."*

Sin `GROUP BY`, **toda la tabla es un solo grupo** y devuelven **una sola fila**.

| Función | Definición del slide | Tipo de dato | Nulos | Trampa |
| --- | --- | --- | --- | --- |
| `SUM(col)` | sumatoria de la columna especificada | **numérico** | ignora | — |
| `AVG(col)` | promedio de la columna especificada | **numérico** | ignora | es `SUM(col)/COUNT(col)`, **no** `/COUNT(*)` |
| `STDDEV(col)` | desvío estándar | **numérico** | ignora | MySQL devuelve el **poblacional**, PostgreSQL el **muestral** → números distintos. **Verificar** |
| `MAX(col)` | valor máximo | **cualquier tipo**, incl. fechas | ignora | sobre fechas, `MAX` = **la más reciente = el más joven** |
| `MIN(col)` | valor mínimo | **cualquier tipo**, incl. fechas | ignora | `MIN(fecha_nacimiento)` = el **más viejo** |
| `COUNT(*)` | *"devuelve el **número de filas** de una tabla"* | — | **cuenta la fila igual** | — |
| `COUNT(expr)` | *"devuelve el número de filas con **valores no nulos** para `expr`"* | cualquiera | **descarta nulos** | `COUNT(col) ≤ COUNT(*)` siempre |

```sql
SELECT SUM(horas_aportadas), AVG(horas_aportadas),
       MAX(horas_aportadas), MIN(horas_aportadas)
FROM   voluntario;
```

‡ **Se puede operar entre agregados**: `MAX(x) - MIN(x)` es una expresión válida del `SELECT`.

### `COUNT(*)` vs. `COUNT(col)` — la pregunta de parcial del tema

| | Cuenta | Si `col` es `NOT NULL` | Si `col` admite nulos |
| --- | --- | --- | --- |
| `COUNT(*)` | **filas** (aunque la fila sea toda `NULL`) | igual a `COUNT(col)` | mayor |
| `COUNT(col)` | **valores no nulos de `col`** | igual a `COUNT(*)` | `COUNT(*) − cantidad de nulos` |

**`COUNT(DISTINCT col)` no aparece en ningún deck** ‡ — tercera forma, no confirmada para el parcial.

### Agregados y nulos — `COALESCE`

> *"Las funciones de grupo **ignoran** los valores nulos del atributo."*
> *"La función `COALESCE(columna, valor_reemplazo)` […] fuerza a las funciones de grupo a que incluyan
> valores nulos, retornando un valor en ocurrencia de un nulo."*

```sql
SELECT AVG(porcentaje)              AS porcentaje_promedio FROM voluntario;  -- 0.2228571…
SELECT AVG(COALESCE(porcentaje,0))  AS porcentaje_promedio FROM voluntario;  -- 0.0728972…
```

> [!important] `COALESCE` no cambia el numerador, cambia el denominador ‡
> Convierte los nulos en ceros, que **sí** entran en la cuenta: 35 no nulos vs. 107 filas. **Cuál de
> los dos promedios es "el correcto" es una decisión semántica**, no técnica — depende de si un nulo
> significa "no aportó nada" o "no se sabe cuánto aportó".

Y dos hechos más: un agregado sobre una columna **toda nula** devuelve **`NULL`, no `0`**; `COUNT(*)`
es la **única** forma de contar filas sin depender de ninguna columna.

## 5. `GROUP BY` — particionar

> *"se **dividen las filas de la tabla consultada en grupos**"* · *"Se aplica las funciones en la lista
> `SELECT` a cada grupo de filas y retorna **una única fila por cada grupo**"*

```sql
SELECT id_institucion, COUNT(*) AS cantidad_voluntarios
FROM   voluntario
GROUP BY id_institucion;
```

| Regla | Dirección | Detalle |
| --- | --- | --- |
| ***"Todas las columnas de la lista `SELECT`, excepto las funciones de grupo, deben estar en la cláusula `GROUP BY`."*** | `SELECT` → `GROUP BY`: **obligatorio** | textual, en rojo y centrado en el deck |
| *"Las columnas en la cláusula `GROUP BY` **pueden no estar** en la lista del `SELECT`."* | `GROUP BY` → `SELECT`: **opcional** | `SELECT AVG(porcentaje) FROM voluntario GROUP BY id_institucion;` es válido pero **ilegible**: no dice a qué institución corresponde cada promedio |
| `NULL` forma **su propio grupo** | — | contrasta con "los agregados ignoran nulos": **son dos reglas distintas** |
| Los grupos **no salen ordenados** | — | hace falta `ORDER BY` |
| `GROUP BY` **particiona, no descarta** | — | las cantidades por grupo suman el `COUNT(*)` de la tabla entera |

> [!note] La regla del `GROUP BY` también aplica en MySQL ‡
> MySQL históricamente permitía violarla y devolvía un valor **arbitrario** de la columna suelta.
> **Desde MySQL 5.7 `ONLY_FULL_GROUP_BY` está activo por defecto** y esas consultas dan error, igual
> que PostgreSQL → **la regla se aplica tal cual en la cursada**.

## 6. `HAVING` — filtrar grupos

> *"Se puede anexar la cláusula `HAVING` para restringir grupos"*
> 1. Las filas se agrupan por la/s columna/s especificada/s
> 2. Se aplica la función de grupo
> 3. Se muestran los grupos que satisfacen la cláusula `HAVING`

**Ese 1-2-3 es el orden de evaluación del § 1** y es lo que hay que memorizar.

```sql
SELECT id_coordinador, COUNT(*) AS cantidad_de_voluntarios
FROM   voluntario
GROUP BY id_coordinador
HAVING COUNT(*) > 7;
```

### `WHERE` vs. `HAVING` ‡

| | `WHERE` | `HAVING` |
| --- | --- | --- |
| **Filtra** | **filas**, antes de agrupar | **grupos**, después de agrupar |
| **Momento** | sobre la tabla cruda | sobre el resultado del `GROUP BY` |
| **¿Acepta agregados?** | **No** — error del motor | **Sí**, es su razón de ser |
| **¿Necesita `GROUP BY`?** | No | En la práctica sí *(sin él, toda la tabla es un solo grupo)* |
| Ejemplo | `WHERE id_institucion = 50` | `HAVING COUNT(*) > 7` |

Se usan **juntas** y hacen cosas distintas:

```sql
... WHERE id_institucion = 50 GROUP BY id_coordinador HAVING COUNT(*) > 7
-- "contando solo a los de la institución 50, qué coordinadores tienen más de 7"
```

### La sentencia NO VÁLIDA (parte 1, slide 35)

> *"**No se puede utilizar la cláusula `WHERE` para restringir grupos.** […] **No se pueden utilizar
> funciones de grupo en la cláusula `WHERE`.**"*

```sql
SELECT id_coordinador, COUNT(*) AS cantidad_de_voluntarios
FROM voluntario
WHERE COUNT(*) > 7          -- ✗ NO VÁLIDA
GROUP BY id_coordinador;
```

| Motor | Mensaje de error |
| --- | --- |
| **PostgreSQL** (el del deck) | `ERROR: aggregates not allowed in WHERE clause at character 105` |
| **MySQL** ‡ | `ERROR 1111 (HY000): Invalid use of group function` |

‡ La razón: **cuando `WHERE` se evalúa, los grupos todavía no existen**, así que no hay `COUNT(*)` que
calcular. No es una prohibición arbitraria.

## 7. `SELECT` — proyección

| Forma | Sintaxis | Qué devuelve | Trampa |
| --- | --- | --- | --- |
| Todo | `SELECT * FROM t;` | todas las columnas, **en el orden físico de la tabla** | ese orden **no** es el del diagrama del esquema; la cátedra pregunta en rojo por qué **evitarlo** ‡ (más I/O, rompe el código si cambia una columna, impide índice *covering* → [[1.08.02 - Índices\|Índices]]) |
| Lista | `SELECT c1, c2 FROM t;` | solo esas, **en el orden pedido** | el orden lo fija la lista, no la tabla |

### Alias de columna

```sql
SELECT MAX(horas_aportadas) maximo,
       MIN(horas_aportadas) minimo,
       MAX(horas_aportadas) - MIN(horas_aportadas) AS diferencia
FROM voluntario v
WHERE v.id_coordinador = 120;
```

| Tipo | Sintaxis | Dónde va | Nota |
| --- | --- | --- | --- |
| **de columna** | `expr AS alias` · `expr alias` | después de la expresión, en el `SELECT` | **`AS` es opcional** ‡ |
| **de tabla** | `FROM voluntario v` · `FROM voluntario AS v` | después del nombre de tabla | § 2 |

| Trampa | Detalle |
| --- | --- |
| Sin alias, la columna se llama con la **expresión entera** | `CONCAT(apellido,' ',nombre)` y `CASE…END` quedan como nombre de columna, ilegibles |
| Alias con espacios | requiere backticks en MySQL: `` AS `rango de precios` `` |
| `"alias" = expresión` | sintaxis de **T-SQL**, no de MySQL → § 8.2 |
| `ORDER BY` sí lo ve, `WHERE` no ‡ | por el orden de evaluación del § 1 |
| PostgreSQL **baja el alias a minúsculas** ‡ | *case folding* de identificadores sin comillas; **MySQL respeta** las mayúsculas escritas |

## 8. Funciones escalares en el `SELECT`

Devuelven **un valor por fila** — lo contrario de los agregados del § 4.

### 8.1 `CONCAT`

```sql
SELECT CONCAT(apellido, ' ', nombre) FROM personas;
```

| Escrito | Columnas devueltas |
| --- | --- |
| `SELECT apellido, nombre FROM personas` | **dos** |
| `SELECT CONCAT(apellido, ' ', nombre) FROM personas` | **una sola**, con los valores pegados |

El `' '` del medio es un **literal**; sin él, `CONCAT(apellido, nombre)` da `MaradonaDiego`.

| Operador / función | Motor | Qué hace |
| --- | --- | --- |
| `CONCAT(a, b, …)` | MySQL · SQL Server | concatena; ‡ **`NULL` en cualquier argumento → el resultado entero es `NULL`** |
| `CONCAT_WS(sep, a, b, …)` | MySQL ‡ | saltea los `NULL` y pone el separador una sola vez |
| `\|\|` | estándar SQL · PostgreSQL ‡ | concatena |
| `\|\|` | **MySQL** ‡ | ⚠️ es **`OR` lógico**: `apellido \|\| nombre` devuelve 0 o 1, **no concatena** |

### 8.2 `CASE`

```sql
SELECT col,
CASE
    WHEN condición1 THEN valor1
    WHEN condición2 THEN valor2
    [ELSE valor_por_defecto]
END [AS alias]
FROM tabla
```

| Regla | Consecuencia |
| --- | --- |
| Es un `CASE` **de búsqueda**: cada `WHEN` lleva condición completa | no hay valor a comparar delante del `CASE` |
| Las condiciones se evalúan **en orden** y **gana la primera verdadera** | `WHEN precio < 50` puede ir después de `WHEN precio = 0` sin pisarlo |
| `ELSE` atrapa todo lo que no matcheó | **sin `ELSE`, lo no matcheado devuelve `NULL`** |
| `NULL` no matchea **ningún** `WHEN` ‡ | `total < 0` y `total >= 0` **no cubren** `total IS NULL` → sin `ELSE` devuelve `NULL` |

Traza de la escalera de rangos del slide 5 (parte 3):

| `precio` | Rama que gana | Valor devuelto |
| --- | --- | --- |
| `0` | 1ª | `'Producto free'` |
| `10` | 2ª | `'menor a 50'` |
| `50` | 3ª | `'entre 50 y 250'` |
| `250` | 4ª | `'entre 250 y 1000'` |
| `1000` | `ELSE` | `'mayor a 1000'` ← **mal rotulado**: es *igual*, no mayor |
| `-5` | 2ª | `'menor a 50'` ← negativo, probablemente no era la intención |

> [!bug] `"rango de precios" = CASE … END` es **T-SQL**, no MySQL
> | Motor | Qué pasa |
> | --- | --- |
> | SQL Server (T-SQL) | es la forma válida de poner el alias |
> | **MySQL, por defecto** | las comillas dobles delimitan **cadena** → se lee como **comparación de igualdad**; la consulta **corre** y devuelve una columna de **`0`** llamada `"rango de precios" = CASE…END` |
> | **MySQL con `sql_mode = ANSI_QUOTES`** | las comillas dobles son **identificador** → error `Unknown column 'rango de precios' in 'field list'` |
>
> Forma correcta en MySQL — alias **detrás**, con `AS`: `` CASE … END AS `rango de precios` ``.

### 8.3 Funciones de fecha

Las **únicas tres** que corren tal cual en MySQL:

| Función | Definición del slide | Devuelve | MySQL | SQL Server | PostgreSQL |
| --- | --- | --- | --- | --- | --- |
| `DAY(date)` | *"Devuelve un entero que representa el día de la fecha especificada."* | entero | ✔ (sinónimo de `DAYOFMONTH()`) | ✔ | ❌ → `EXTRACT(DAY FROM fecha)` |
| `MONTH(date)` | *"…el mes de la fecha especificada."* | entero | ✔ | ✔ | ❌ → `EXTRACT(MONTH FROM fecha)` |
| `YEAR(date)` | *"…el **mes** de la fecha especificada."* ← **errata del deck** | entero (el **año**) | ✔ | ✔ | ❌ → `EXTRACT(YEAR FROM fecha)` |

El resto de la parte 3 es **T-SQL y no corre en MySQL**:

| Función | Sintaxis | Qué devuelve | Equivalente MySQL |
| --- | --- | --- | --- |
| `DATEPART` | `DATEPART(partedefecha, fecha)` | **entero** de la parte pedida | `EXTRACT(MONTH FROM NOW())` / `MONTH(x)` |
| `DATENAME` | `DATENAME(partedefecha, fecha)` | **texto**: el nombre de la parte | `MONTHNAME()` / `DAYNAME()` |
| `DATEDIFF` | `DATEDIFF(partedelafecha, f1, f2)` | entero = **`f2 − f1`** | `TIMESTAMPDIFF(DAY, f1, f2)` |
| `getdate()` | `getdate()` | fecha y hora del momento de la consulta | `NOW()` (fecha y hora) · `CURDATE()` (solo fecha) |

**Valores admitidos de `partedefecha`** (los nueve del slide 14): `year`, `quarter` *(el slide lo
traduce **cuarto** y dos líneas antes **trimestre**)*, `month`, `day`, `week`, `hour`, `minute`,
`second`, `millisecond`. **`DATEPART` vs. `DATENAME`:** entero vs. texto — para agosto, `8` contra
`August`/`Agosto` según la configuración de idioma del servidor.

> [!bug] Trampa máxima: `DATEDIFF` **existe en MySQL pero es otra función**
> El nombre coincide y el comportamiento no.
>
> | | T-SQL *(el del deck)* | **MySQL** |
> | --- | --- | --- |
> | **Argumentos** | 3 — `(unidad, f1, f2)` | **2 — `(f1, f2)`** |
> | **Unidad** | la que se pida | **siempre días** |
> | **Cuenta** | `f2 − f1` | **`f1 − f2`** ← *orden invertido* |
>
> `DATEDIFF('2005/10/28','2006/10/28')` en MySQL devuelve **−365**, no 365. Escribir
> `DATEDIFF(day, …)` en MySQL da **error**; escribir `DATEDIFF(f1, f2)` da el **signo cambiado**.
> Reemplazo uno a uno:
> ```sql
> SELECT TIMESTAMPDIFF(MONTH, '2005-10-28', '2006-11-29');  -- 13
> SELECT TIMESTAMPDIFF(DAY,   '2005-10-28', '2006-10-28');  -- 365
> ```

Las fechas van con **barras** en los ejemplos del deck (`'2005/10/28'`), no con guiones.

> [!note] `EXTRACT` — la forma genérica portable ‡
> `EXTRACT(unidad FROM fecha)` está en MySQL, en el **estándar SQL** y en PostgreSQL. Ojo: **la unidad
> no va entre comillas y no es un argumento**, va con la palabra `FROM` adentro del paréntesis.

> [!warning] Nada de esto responde *"quién"*
> `MIN`/`MAX` sobre `fecha_nacimiento` devuelven **dos fechas, no al voluntario**. Para saber *quién*
> hace falta una **subconsulta** (§ 10) o `ORDER BY … LIMIT 1` (§ 9.3).

## 9. Ordenar y recortar

### 9.1 `DISTINCT`

> *"Por defecto, ante una consulta, se recuperan todas las filas, **incluidas** las filas duplicadas."*
> *"La cláusula `DISTINCT` se aplica a **todas** las columnas de la lista en el `SELECT`."*

| Hecho | Detalle |
| --- | --- |
| Alcance | deduplica **la tupla completa**, no columna por columna. **No existe "`DISTINCT` de una sola columna"** |
| `NULL` | **conserva una fila `NULL`**: para `DISTINCT` todos los nulos son "el mismo valor", aunque `NULL = NULL` no sea verdadero |
| Orden | **no ordena**; el resultado sale desordenado |
| Semántica ‡ | una tabla SQL es un *multiconjunto* (**bag**), no un conjunto: acá SQL se separa del álgebra relacional |

> [!warning] `DISTINCT` es cláusula, no función — los paréntesis engañan
> La parte 3 escribe `SELECT distinct(autor) FROM libros` y **parece** una función.
> `SELECT DISTINCT(autor), titulo FROM libros` deduplica por el **par** `(autor, titulo)`: como el
> título cambia en cada libro, **no elimina nada**. Escribir siempre `SELECT DISTINCT autor …`, sin
> paréntesis.

### 9.2 `ORDER BY`

> *"El orden de las filas listadas en una consulta es **indefinido**"* · *"se debe colocar como
> **última cláusula** del `SELECT`"* · *"Por defecto […] el orden es ascendente (`ASC`)"* · *"Se puede
> ordenar […] por **más de una columna**"*

```sql
SELECT apellido, nombre
FROM   voluntario
WHERE  id_coordinador = 124
ORDER BY apellido DESC, nombre;   -- DESC afecta SOLO a apellido; nombre queda ASC
```

| Punto | Detalle |
| --- | --- |
| `ASC`/`DESC` | **por columna**, no por cláusula. Para las dos descendentes: `ORDER BY apellido DESC, nombre DESC`. **Es el error más común** |
| Posición | última cláusula lógica; `LIMIT`/`OFFSET` van **detrás** ‡ (el slide 20 de la parte 1 choca con el 21) |
| "Indefinido" | es literal ‡: el motor puede **cambiar el orden entre dos ejecuciones** de la misma consulta. Si el enunciado dice *"listar ordenado por…"*, falta `ORDER BY` aunque el resultado *parezca* ordenado |
| Alias | ‡ se puede ordenar por un alias del `SELECT`; ningún deck lo muestra. **Verificar en clase** |
| **Nulos** | la parte 2 dice *"null es el **'mayor'**"* → eso es **Oracle/PostgreSQL**. ⚠️ **MySQL hace lo contrario**: los pone **primero en `ASC`** y últimos en `DESC` (los trata como el **menor**) |

### 9.3 `LIMIT` / `OFFSET` / `TOP`

> *"Permiten recuperar solamente un subconjunto de filas del total de la consulta."* · *"**Debe ser
> usado siempre con la cláusula `ORDER BY`**."* · *"`LIMIT` limita la cantidad de filas a retornar."* ·
> *"`OFFSET` determina a partir de qué fila del resultado se retorna."*

Los decks presentan **tres sintaxis de tres motores** sin decir que son la misma cosa:

| Forma | Motor de origen | MySQL |
| --- | --- | --- |
| `LIMIT n` | PostgreSQL | **igual** |
| `LIMIT n OFFSET m` | PostgreSQL | **igual** — y es **la forma portable**, la que conviene escribir |
| `LIMIT m , n` ← **offset primero** | MySQL / MariaDB | ✔ · ❌ en PostgreSQL |
| `LIMIT ALL` | PostgreSQL | **no existe** |
| `OFFSET m` **sin `LIMIT`** | PostgreSQL | **no compila**: `OFFSET` exige `LIMIT`. Workaround documentado: `LIMIT 18446744073709551615 OFFSET m` |
| `SELECT TOP n col…` | **T-SQL** / MS Access | **no existe** → `LIMIT n` al final |
| `FETCH FIRST n ROWS ONLY` | estándar SQL | ❌ en MySQL · ✔ en PostgreSQL |

> [!important] El orden de los dos números de `LIMIT m , n` es contraintuitivo
> **Primero el offset, después la cantidad.** `LIMIT 0 , 30` **no** significa "de la 0 a la 30":
> significa "salteá 0 filas y devolvé 30". Es la forma canónica de **paginar**:
>
> | Escrito | Offset | Cantidad | Devuelve |
> | --- | --- | --- | --- |
> | `LIMIT 0 , 30` | 0 | 30 | filas 1 a 30 |
> | `LIMIT 30 , 30` | 30 | 30 | filas 31 a 60 |
> | `LIMIT 30` | 0 *(implícito)* | 30 | filas 1 a 30 |

> [!bug] `TOP` no compila en MySQL, y falla raro
> Como `top` **no es palabra reservada**, el parser lo lee como **una columna llamada `top`** y espera
> que lo que sigue sea su **alias**: se come el `3` como alias inválido y corta con error de sintaxis
> ahí. El mensaje no menciona `TOP` por ningún lado.

> [!warning] Sin `ORDER BY`, "los primeros 3" no significa nada
> Una tabla **no tiene orden garantizado**: `LIMIT` sin `ORDER BY` es **no determinístico**. Los decks
> ponen el `ORDER BY` en todos los ejemplos pero **no lo justifican**. `OFFSET 15` **salta 15 filas y
> empieza por la 16ª** — el enunciado *"a partir del 15TO"* es ambiguo. **Verificar en clase.**

## 10. Subconsultas

*"La cláusula `WHERE` puede contener un `SELECT` anidado o subconsulta. Como una consulta en 2 pasos."*
Es la propiedad de cierre del § 1 en acción.

| Criterio | Regla | Trampa |
| --- | --- | --- |
| Dónde pueden ir *(según el deck)* | en el **`WHERE`** y en el **`HAVING`** | — |
| Devuelve **una** fila | operadores *single-row*: `=`, `>`, `<`, `<>`, `>=`, `<=` | *"Es responsabilidad de quien escribe el `SELECT` asegurar que la subconsulta devolverá una sola fila"* |
| Devuelve **varias** filas | operadores *multiple-row*: `IN`, `ANY`, `ALL`, `EXISTS` | los slides 9 y 11 dan **dos listas distintas** (uno sin `EXISTS`, el otro con) |
| Varias filas + operador single-row | **error de ejecución** | vocabulario y error son de Oracle |

```sql
-- una sola fila: se puede comparar con =
SELECT nombre, apellido
FROM   voluntario
WHERE horas_aportadas = (SELECT MIN(horas_aportadas) FROM voluntario);
```

```sql
-- subconsulta dentro del HAVING; la interna NO está correlacionada con el grupo
SELECT id_tarea, MIN(horas_aportadas)
  FROM voluntario
 GROUP BY id_tarea
HAVING MIN(horas_aportadas) > (SELECT AVG(horas_aportadas) FROM voluntario);
```

### 10.1 Operadores de múltiples filas

| Operador | Sintaxis | Retorna `TRUE` si… | Trampa |
| --- | --- | --- | --- |
| `IN` | `WHERE col IN (SELECT …)` | el valor está incluido en los valores retornados | equivale a un `OR` de igualdades |
| `EXISTS` | `WHERE EXISTS (SELECT 1 FROM …)` | el subquery devuelve **al menos una fila**; `FALSE` si devuelve 0 | *"Tiene la forma de una consulta correlacionada"* |
| `ANY` | `WHERE col <op> ANY (SELECT …)` | la comparación es `TRUE` para **al menos un** valor retornado | ⚠️ el deck lo define y **nunca da un ejemplo**; tampoco menciona `SOME` |
| `ALL` | `WHERE col <op> ALL (SELECT …)` | la comparación es `TRUE` para **todos** los valores retornados | ⚠️ ídem, sin ejemplo |

### 10.2 `[NOT] IN` con subconsulta

```sql
SELECT nro_voluntario, nombre, apellido
FROM voluntario
WHERE id_tarea IN
       (SELECT id_tarea
        FROM tarea
        WHERE nombre_tarea LIKE 'ORG%');
```

`NOT IN` solo sirve *"si `nombre_tarea` no permite nulos"* → § 11.4.

### 10.3 `[NOT] EXISTS`

Plantilla del slide 14 (parte 2):

```sql
SELECT lista de atributos
FROM tabla_externa E
WHERE EXISTS
       (SELECT 1
        FROM tabla_interna I
        WHERE E.atributo1 = I.atributo1
             …..
             AND E.atributoN = I.atributoN);
```

Cómo se ejecuta (slide 15) — **corta al primer match**, fila externa por fila externa:

| Caso | Condición | Búsqueda interna |
| --- | --- | --- |
| Se encuentra una fila en la subconsulta | **verdadera** | **no continúa** |
| No se encuentra ninguna | **falsa** | **continúa** para el siguiente valor de la tabla externa |

> [!note] Por qué `SELECT 1` ‡
> A `EXISTS` **no le importa qué columnas devuelve** la subconsulta, solo **si devuelve filas**. Los
> slides 14, 15, 16 y 18 lo usan sin comentarlo.

### 10.4 Correlacionadas

*"Se utilizan para el procesamiento fila a fila. Cada subconsulta se ejecuta una vez para cada fila de
la consulta externa."* Ciclo: **OBTENER** posible fila de la externa → **EJECUTAR** la interna usando
el valor de esa fila → **UTILIZAR** los valores de la interna para considerar la posible fila → volver
al principio.

Lo que la hace correlacionada es **la referencia a un alias de la tabla externa dentro de la
subconsulta**.

| | Correlacionada | No correlacionada |
| --- | --- | --- |
| Referencia a la externa | **sí** | no |
| Cuántas veces se ejecuta | **una por fila externa** | **una sola**, y el resultado se reutiliza |

> [!tip] Regla operativa ‡
> Si podés **copiar la subconsulta, pegarla sola y ejecutarla**, es **no correlacionada**. Si falla
> porque referencia un alias que no existe, es **correlacionada**.

### 10.5 ⚠️ `IN` ≡ `EXISTS`, pero `NOT IN` ≢ `NOT EXISTS`

> [!important] La frase más examinable del bloque
> *"La sintaxis de `IN` y `EXISTS` deberían dar los mismos registros si la consulta está bien
> construída, aunque la ejecución sean diferente."*
> *"**`NOT IN` y `NOT EXISTS` no son sinónimos. El valor `NULL` determina la diferencia.**"*
>
> **‡ Por qué:** si la subconsulta devuelve **aunque sea un `NULL`**, `x NOT IN (…)` nunca evalúa a
> `TRUE` —queda en `UNKNOWN`— y la consulta externa **devuelve cero filas**. `NOT EXISTS` no compara
> valores, solo **cuenta filas** → **no se ve afectado**.
>
> **Regla práctica: ante la duda, `NOT EXISTS`.**

## 11. `NULL` y lógica trivaluada

Es el tema transversal del bloque E: aparece en las tres partes y toca **todas** las cláusulas.

> *"`null` no es un valor, es la **ausencia de valor**! Esta es la noción aceptada por SQL."*
> *"`NULL` es un valor **inaccesible, sin valor, desconocido o inaplicable**. **No representa ni un cero
> ni un espacio en blanco**."*

### 11.1 Los 6 tipos de información faltante (parte 2, slide 24)

| # | Tipo | Ejemplo del deck |
| --- | --- | --- |
| 1 | Atributos **inaplicables** | `ÁreaDirigida` para quien no es director de área |
| 2 | **Aplicable pero desconocido** | `Comisión` aún no asignada |
| 3 | **Valor no existente** | `NroPasaporte` para quien no lo tiene |
| 4 | **Indefinido** | `NotaPromedio` para quien no rindió finales |
| 5 | **Valor no provisto** | `NoSabe/NoContesta` |
| 6 | **Resultante de una operación algebraica** | caracteres de relleno en los **ensambles externos** (§ 2.3) |

**SQL colapsa los 6 tipos en un único `NULL`** ‡ — de ahí todos los problemas siguientes. *(El deck
solo muestra la reducción al absurdo: si cada ausencia necesitara su propio null y las dependencias
entre ausencias generaran nulls nuevos, harían falta infinitos.)*

### 11.2 Reglas de operación

> *"Surgen complicaciones cuando los valores nulos participan en operaciones aritméticas o de
> comparación (deberían evitarse siempre que sea posible)."*

| Operación | Resultado con un `NULL` |
| --- | --- |
| Aritmética `+ – * /` | **`NULL`** |
| Comparación `< <= > >= !=` | **`UNKNOWN`** (desconocido) |

> [!bug] La parte 1 se contradice y esto entra en el parcial
> Su slide 12 dice a la vez *"el resultado puede ser Verdadero (T) · Falso (F) · **Desconocido (U)**"*
> y *"si se comparan valores nulos […] el resultado será siempre **FALSO**"*. **Lo correcto es
> `UNKNOWN`**, y la parte 2 lo dice bien. **Verificar cuál toma la cátedra**, porque la diferencia se
> ve:
>
> | Expresión, con `x IS NULL` | Real (`UNKNOWN`) | Con la regla del slide ("es FALSE") |
> | --- | --- | --- |
> | `x = 5` | `UNKNOWN` → fila descartada | `FALSE` → descartada ✓ |
> | `NOT (x = 5)` | `NOT UNKNOWN` = `UNKNOWN` → **descartada** | `TRUE` → devuelta ✗ |
> | `x != 5` | `UNKNOWN` → **descartada** | `TRUE` → devuelta ✗ |
>
> `=` y `!=` **no parten el universo en dos**: las filas con `NULL` quedan afuera **en las dos**
> consultas.

### 11.3 Tablas de verdad (parte 2, slide 27)

| `AND` | T | U | F |  | `OR` | T | U | F |  | `NOT` | |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **T** | T | U | F |  | **T** | T | T | T |  | **T** | F |
| **U** | U | U | F |  | **U** | T | U | U |  | **U** | **U** |
| **F** | F | F | F |  | **F** | T | U | F |  | **F** | T |

*(El slide encabeza las columnas `& (AND)`, `I (OR)` y `~(NOT)`; el `I` es una **i mayúscula**,
presumiblemente `|`. **Verificar si la cátedra usa `&`/`|`/`~` o `AND`/`OR`/`NOT`**.)*

> [!tip] Las tres casillas que hay que retener
> **`F AND U = F`** (el falso **absorbe**) · **`T OR U = T`** (el verdadero **absorbe**) ·
> **`NOT U = U`** (la negación **no rescata** un desconocido) ← es la que rompe el `NOT IN`.

### 11.4 `IN` y `NOT IN` con nulos

> *"**Problema si en la lista de valores hay nulos no retorna resultado!!!!!!**"*

Reconstrucción ‡ (la redacción del slide mezcla el caso `x IS NULL` con el caso "x tiene valor"):

| Caso | `x IN (…)` | `x NOT IN (…)` |
| --- | --- | --- |
| `x` es `NULL` | `UNKNOWN` → la fila **no pasa** | `UNKNOWN` → la fila **no pasa** |
| `x` está en la lista | `TRUE` | `FALSE` |
| `x` no está y **la lista no tiene nulos** | `FALSE` | `TRUE` |
| `x` no está y **la lista tiene un `NULL`** | `FALSE` *(sigue funcionando)* | **`UNKNOWN`** → la fila **no pasa** |

`x <> NULL` da `UNKNOWN`, y `TRUE AND UNKNOWN = UNKNOWN` → **ninguna fila sobrevive: el `NOT IN`
devuelve el conjunto vacío**. `IN` **no** tiene el problema porque `FALSE OR UNKNOWN = UNKNOWN` pero
**un solo `TRUE` alcanza** para salvar la expresión.

### 11.5 ⚠️ `NULL` cláusula por cláusula — son reglas distintas

Esta es la tabla que resuelve el 90% de las preguntas de parcial sobre nulos.

| Cláusula / construcción | Qué hace con los nulos |
| --- | --- |
| `WHERE` con `=`, `!=`, `<`, `BETWEEN`, `LIKE` | los **descarta** (la condición da `UNKNOWN`) — *"se requiere que la condición evalúe en VERDADERO, no en FALSO ni DESCONOCIDO"* |
| `IS NULL` / `IS NOT NULL` | **única** forma de testearlos |
| `JOIN` externo | **los produce** como relleno (tipo 6 de § 11.1) |
| `DISTINCT` | **conserva una** fila `NULL`: `null` es duplicado de `null` |
| `GROUP BY` | **`NULL` forma su propio grupo** |
| `SUM`/`AVG`/`MIN`/`MAX`/`COUNT(col)` | los **ignoran**; sobre columna toda nula devuelven **`NULL`, no `0`** |
| `COUNT(*)` | cuenta la fila igual, aunque sea toda `NULL` |
| `CASE` | **no matchea ningún `WHEN`** → cae al `ELSE`, o `NULL` si no hay |
| `CONCAT` (MySQL) | **contagia**: un argumento `NULL` anula el resultado entero |
| `ORDER BY` | deck: *"null es el mayor"* (Oracle/PG) · ⚠️ **MySQL: el menor** |
| `COALESCE(col, v)` | los **reemplaza** para que sí entren en el cálculo |

> [!important] La contradicción aparente que hay que saber explicar
> El deck la señala: *"la proyección implica la eliminación de duplicados, pero `null<>null`, entonces
> dos tuplas aparentemente iguales no podrían ser eliminadas! … **pero eso NO ocurre en SQL**"*.
> ‡ **SQL usa dos criterios de igualdad según el contexto**: en el `WHERE`, `null = null` da `UNKNOWN`
> y la fila no pasa; en `DISTINCT` y `GROUP BY`, dos nulos se consideran **el mismo valor**. No es una
> inconsistencia del motor, es una decisión del estándar. *(Que `UNION` se comporte igual hay que
> verificarlo en el motor: ningún deck lo dice.)*

### 11.6 Alternativas al `NULL`

| Recurso | Qué es | Problemas |
| --- | --- | --- |
| **Valores por defecto** | rellenar el hueco con un valor particular (`'ninguno'`, `'ns/nc'`, `ZZZ` para nombres, `-1` para peso/precio). Son valores → **no se aplica la lógica trivaluada**, y suelen tener **más significado** que un `NULL` | 1) **pueden actualizarse como cualquier otro valor**; 2) hay que **encontrar un valor que no pudiese usarse en ninguna circunstancia**; 3) **riesgo de interpretación incorrecta**; 4) **deben ser del mismo tipo que la columna** (*"No se podría usar 'desconocido' en una columna de enteros!!"*) |
| **Partición de tablas** | **separar a otra tabla las columnas que tienen nulos**; las subtuplas con nulos no se incluyen. En vez de rellenar el hueco, se rediseña el esquema para que no exista | **se introducen nuevas tablas**, la información **se disemina**, las consultas **se vuelven más complejas** y requieren **más ensambles**; para recuperar la tabla original hacen falta **outer joins**, que *"introduce `NULL`s, que retrotrae a todos los problemas ya analizados, nuevamente!!"* |
| **`NULL`s** | el mismo elemento de relleno **para cualquier tipo de dato** | toda la lógica trivaluada de arriba |

> [!question] La pregunta del slide 32
> *"(Observar que `-1` no sería considerado accidentalmente como válido, sin embargo **que pasaría con
> una operación `UPDATE Producto SET Peso = Peso + 3` ??**)"*
>
> ‡ El centinela `-1` pasa a valer `2`, un peso plausible, y **la marca de "faltante" se pierde de
> forma irreversible y silenciosa**. Esa es la diferencia con `NULL`, que es **absorbente**:
> `NULL + 3 = NULL`, la ausencia **se propaga** en vez de perderse.

**Veredicto del deck (slide 36)** — *"Puede ser una decisión personal .. pero debería tenerse en cuenta
que:"*

| Recurso | Veredicto |
| --- | --- |
| Valores por defecto | ***NO* deberían usarse cuando pueden 'confundirse' con valores reales** |
| Partir tablas | ***NO* debería utilizarse en demasía**: más tablas → más ensambles |
| `NULL`s | *"pueden ser (y **frecuentemente son**) usados cuando las otras alternativas parecen inapropiadas"* |
| Combinarlos | *"No es necesario utilizar siempre el mismo recurso… **se pueden combinar de forma inteligente!!**"* |

> [!quote] Cierre del bloque E
> *"**Siempre tener presente donde se pueden encontrar nulos!!! Revisar en el planteo de sentencias las
> sentencias SELECT**"*

| --- | --- | --- | --- |

| `LIMIT n` · `LIMIT n OFFSET m` | PostgreSQL | **iguales**; además `LIMIT m , n` (**offset primero**) | segura |
| `LIMIT ALL` | PostgreSQL | **no existe** | segura |
| `OFFSET m` **sin `LIMIT`** | PostgreSQL | **no compila** → `LIMIT 18446744073709551615 OFFSET m` | segura |
| `SELECT TOP n …` | T-SQL | ❌ → `… ORDER BY … LIMIT n` **al final** | segura |
| `"alias" = CASE … END` | T-SQL | ❌ → `` CASE … END AS `alias` `` | segura |
| `LIKE 'A[nm]%'` | T-SQL | ❌ → `REGEXP '^A[nm]'` | segura |
| `DATEPART(p, f)` · `DATENAME(p, f)` | T-SQL | ❌ → `EXTRACT(MONTH FROM …)` / `MONTHNAME()`, `DAYNAME()` | segura |
| `getdate()` | T-SQL | ❌ → `NOW()` / `CURDATE()` | segura |
| **`DATEDIFF(p, f1, f2)`** | T-SQL | ⚠️ **existe con otra semántica** → `TIMESTAMPDIFF(unidad, f1, f2)` | segura |
| `DAY()`, `MONTH()`, `YEAR()` | MySQL · SQL Server | **iguales** | segura |
| `CONCAT(a, b, …)` | MySQL · SQL Server | **igual** · `NULL` contagia → `CONCAT_WS` | segura |
| `STDDEV(col)` | Oracle / PostgreSQL | existe, pero devuelve el **poblacional** contra el **muestral** de PostgreSQL → **números distintos** | alta, **verificar** |

| *"para `ORDER BY`, null es el 'mayor'"* | Oracle / PostgreSQL | ❌ **al revés**: los pone **primero en `ASC`** | alta |
| `ERROR: aggregates not allowed in WHERE clause` | PostgreSQL | `ERROR 1111 (HY000): Invalid use of group function` | alta |
| *"error de ejecución"* si el subquery devuelve >1 fila | Oracle `ORA-01427` | también falla en ejecución; el mensaje es otro → **verificar el texto exacto** | alta |
