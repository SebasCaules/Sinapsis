# Vistas

Una **vista** es una **relación derivada**: una consulta a la que se le pone nombre. No guarda datos
—es una **tabla virtual**— y sus tuplas se generan al operar sobre ella.

El recorrido slide por slide está en [[Clase 06 - Vistas-Parte 1]] y
[[Clase 07 - Vistas-Parte 2]]. **Esta página es la hoja de referencia operativa**: qué se puede
hacer con una vista, y sobre todo **cuándo se puede escribir a través de ella**. Es la página que se
consulta para el **TP4**.

## Dónde encaja: esquema externo

Las vistas **forman parte del esquema externo** de la base. Presentan a cada grupo de usuarios la
parte de la BD que le interesa, **ocultando el resto**.

```
   👥  👤  🖥️            ← distintos grupos de usuarios
 ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
 │External View1│ │External View2│ │External View3│   ◀── NIVEL EXTERNO ← acá viven las vistas
 └──────────────┘ └──────────────┘ └──────────────┘
              logical to external mappings
                ┌───────────────┐
                │ Logical Schema│                     ◀── NIVEL CONCEPTUAL
                └───────────────┘
              internal to logical mapping
                ┌───────────────┐
                │Internal Schema│                     ◀── NIVEL INTERNO
                └───────────────┘
```

> [!important] La equivalencia que da sentido a todo el tema
> Lo que la arquitectura de tres niveles llama *"vista externa"*, SQL lo llama `VIEW`. **Una vista es
> el mecanismo con el que SQL materializa el nivel externo.** Los tres niveles vienen de
> [[Clase 01 - Introducción_BasesDeDatos]].

Las cuatro afirmaciones del concepto, del slide 3 del deck 06:

1. Es una **relación derivada** de **una o más tablas y/o vistas definidas previamente**.
2. Su contenido se define **dando un nombre a una expresión de consulta**.
3. Es una **tabla virtual** (*"habitualmente no materializada"*) → las tuplas **se generan al operar**
   sobre la vista.
4. *"Pueden consultarse como cualquier tabla"*, pero **para actualizar deben cumplirse ciertas
   condiciones**, y el criterio genérico es la **preservación de la clave**.

> [!tip] Las dos palabras que resumen la página entera
> **"derivada"** y **"virtual"**. Si los datos son derivados, escribir sobre ellos exige poder
> deshacer la derivación; si la tabla es virtual, no hay dónde guardar la escritura salvo en la tabla
> base.

## Sintaxis

```sql
CREATE VIEW nom_vista [(n_col_1, …, n_col_n)]
AS expresión_consulta
[WITH [opción] CHECK OPTION];
```

| Parte | Qué es |
| --- | --- |
| `nom_vista` | nombre de la vista |
| `(n_col_1, …, n_col_n)` | nombres de columnas de la vista *(opcional)* |
| `expresión_consulta` | **consulta SQL que define la relación derivada** |
| `WITH [opción] CHECK OPTION` | opción de chequeo; `opción` ∈ `CASCADED` (default) \| `LOCAL` |

### Las tres reglas de nombres de columna

1. Se pueden renombrar especificando **la lista completa** de atributos entre paréntesis.
2. Si no, los nombres son los de las columnas del `SELECT`.
3. **Se debe especificar con diferente nombre** las columnas provenientes de distintas tablas pero
   con igual nombre.

> [!important] La lista es *completa* o no es
> No se pueden renombrar dos columnas de cinco: o se listan las cinco, o ninguna. Por eso
> `CREATE VIEW TOTAL_ARTICULO (articulo, total) AS SELECT id_articulo, sum(cantidad) …` escribe las
> **dos**, aun cuando lo único que necesitaba nombre era el `sum`.

La regla 3 es la que justifica la lista en el ejemplo `info_tutores` del deck 07: `A.nombre` y
`P.nombre` colisionan y la lista los renombra a `nom_al` y `nom_tut`.

### El `FROM` de una vista puede ser otra vista

```sql
CREATE VIEW PROV_COMP AS
    SELECT id_proveedor, nombre, ciudad
    FROM  PROVEEDOR
    WHERE rubro = 'Computadoras';

CREATE VIEW PROV_COMP_TANDIL AS
    SELECT * FROM PROV_COMP           -- ← el FROM es una vista
    WHERE ciudad = 'Tandil';
```

Encadenar vistas ahorra repetir filtros: la vista de arriba ya trae `rubro` y `ciudad` resueltos.
El precio está en la [[#La cadena de vistas|regla de la cadena]].

### Eliminar

```sql
DROP VIEW nom_vista [opción];
```

| `opción` | Comportamiento |
| --- | --- |
| **`RESTRICT`** | se rechaza si hay objetos que hacen referencia a la vista — **default** |
| **`CASCADE`** | procede siempre y se eliminan también los objetos dependientes |

> [!warning] Motor: MySQL **ignora** `RESTRICT` / `CASCADE` en `DROP VIEW`
> Los acepta sin error de sintaxis, pero **no hacen nada**: el `DROP` procede igual y las vistas
> dependientes quedan inválidas (fallan recién al consultarlas). PostgreSQL sí las implementa.
> **Para el TP4:** en MySQL no se puede confiar en `RESTRICT` como red de seguridad.
> **Verificar contra la versión que use la cátedra.**

> [!missing] `CREATE OR REPLACE VIEW` no aparece en ningún deck
> El deck 07 dice que una vista hay que *"re-crearla"* para que vea columnas nuevas de la tabla base,
> pero no da la sentencia. La única vía documentada en el material es `DROP` + `CREATE`.
> **El TP4 no lo usa** (ver § *Lo que queda abierto después del TP4*), así que sigue sin aparecer en
> ningún material de la cátedra. **Preguntar antes del parcial.**

### Y las desventajas (slide 19)

- **Actualizaciones vista → tabla base restringidas** — el resto de esta página.
- **Rendimiento**: resolver la vista puede exigir acceder a múltiples tablas **cada vez**.

- **Cambios en la tabla base no se ven**: una columna nueva **no aparece** en una vista `SELECT *` ya

> **Razonamiento propio, no está en el deck:** el mismo slide 18 vende la independencia de los datos

## Virtual vs. materializada

| | **Virtual** (la default) | **Materializada** |
| --- | --- | --- |
| ¿Guarda datos? | **no** | **sí**, pre-calculados y almacenados físicamente |
| Actualización desde la tabla base | por **recálculo**: las tuplas se generan al acceder | por **mantenimiento incremental** o regeneración |
| ¿Se le pueden crear índices? | — | **sí**, *"como si fuera una relación común"* |
| Costo | consulta cara cada vez | duplicación de datos + sincronización |

Las tres preguntas que el deck deja abiertas sobre materializadas (slide 17 del deck 07):

- *"¿Qué vistas deberían materializarse?"* → *"(decisión compleja)"*, sin criterio.
- *"¿Actualización por **regeneración** o **incremental**?"*
- *"¿En forma **inmediata**, **periódicamente** o **forzado**?"*

Comparativa por motor, transcripta del slide 20:

| SGBD | Vistas materializadas |
| --- | --- |
| **PostgreSQL** | hay que **actualizarlas manualmente** y **recalcula la vista completa** |
| **MySQL** | **no las admite** |
| **Oracle** | **automáticas**, con opción de actualizar a pedido |
| **SQL Server** | las llama **"vistas indexadas"**; se actualizan **automáticamente** |

```sql
-- PostgreSQL
CREATE MATERIALIZED VIEW view_name
AS query
WITH [NO] DATA;
```

`WITH DATA` carga los resultados **en el momento de la creación**; `WITH NO DATA` la deja vacía.

> Lo dice el propio slide 20. Todo este bloque es **teórico** para el TP4: en MySQL se emula con una

> *siempre* no materializada. **Confirmar si el parcial puede pedirlo.**

# La pregunta que importa: ¿esta vista es actualizable?

Todo lo anterior es preámbulo. **Consultar una vista es gratis; escribirla es el problema.**

## Por qué es un problema

> [!quote] La premisa, deck 07 slide 3
> *"Las vistas no mantienen COPIAS de los datos → cuando se modifica una vista, se están modificando
> las tablas base"*

Las dos direcciones **no son simétricas**:

| Dirección | Qué pasa | Dificultad |
| --- | --- | --- |
| **Tabla base → vista** | *"los cambios se reflejan automáticamente"* | **ninguna**: se recalcula al consultarla |
| **Vista → tabla base** | *"deberían propagarse automáticamente"*, pero *"podrían generarse **ambigüedades** o **carecer de sentido** o **provocar efectos no deseados**"* | **todo el problema** |

Los dos ejemplos de ambigüedad, textuales del deck 06 slide 9:

- *"Borrar una tupla en una vista => borrar la tupla de la tabla base? (una modificación también
  podría hacerla 'desaparecer' de la vista)"*
- *"Insertar una fila en una vista => insertar una tupla en la tabla base? (si se actualiza alguna
  tupla también podría incorporarse en la vista)"*

Y la regla general (slide 10):

> [!quote] La regla
> *"Cada actualización de una tupla en una vista debe poder **propagarse sin ambigüedades** a la/s
> tabla/s base."*
> **"No toda vista se puede actualizar automáticamente"** → *"cuando una actualización sobre la vista
> pueda generar **distintas posibilidades** de actualización a la/s tabla/s base, se deberá recurrir a
> **algún procedimiento específico**"*.

## Preservación de la clave

El **criterio genérico** que decide todo. Deck 06 slide 11, dos incisos:

1. Debe tratarse de **una única actualización y del mismo tipo** en la/s tabla/s base *"cuya clave
   'heredó' la vista"*.
2. Se satisface si **cada fila en la tabla aparece como máximo una vez en la vista**.

Cómo se determina la clave de la vista:

| Tipo de vista | De dónde sale la clave |
| --- | --- |
| **De una tabla** | *"la clave de la vista es la clave de la tabla de la cual procede"* |
| **De ensamble** (join) | *"la clave de la vista es la de **alguna** de las tablas de las cuales procede"* |

Y la definición operativa que agrega el deck 07 slide 4:

> [!quote] SQL:1999
> *"la actualización sobre una vista definida a partir de más de una tabla/vista → **sólo puede
> modificar una de las tablas base**: la que cumpla la propiedad de **preservación de la clave** (la
> que tiene la misma clave de la vista, y entonces aparece a lo sumo una vez en la vista)"*

> [!important] Es una propiedad **del esquema**, no de los datos — esto cae en parcial
> Textual del deck 06: *"La propiedad **NO depende de los datos actuales en las tablas**, sino que es
> una **propiedad estructural de su esquema**."*
>
> Y textual del deck 07 (nota del slide 6): *"Aunque en la vista hubiera sólo un empleado en cada
> departamento – y entonces id_dpto sería único– igualmente la tabla Departamento **NO** sería de la
> cual se preserva la clave!"*
>
> Traducción: que hoy, con los datos que hay, cada fila aparezca una sola vez **no alcanza**. Tiene
> que ser **imposible** que aparezca dos veces por cómo está definida la vista. **Se decide leyendo
> el `CREATE VIEW`, sin mirar una sola fila.**

> [!quote] Genealogía del concepto (deck 06, slide 11)
> *"Este concepto ha sido explicado por distintos autores (ej: **Date**), aplicado por el **estándar
> SQL** como forma de operar, y popularizado por **Oracle** que lo implementó y denominó propiedad
> **'key-preserved'** (los SGBD suelen hacer interpretaciones particulares)."*
>
> El paréntesis final es una advertencia práctica: **cada motor decide un poco distinto.**

### Cómo se identifica en una vista de ensamble

El deck 07 clasifica los joins según **dónde cae la FK** (slide 5), y da un ejemplo de cada uno:

| Caso | Ubicación de la FK | Proviene de | Ejemplo | Tabla que preserva la clave |
| --- | --- | --- | --- | --- |
| **(1)** | **FK ≡ K** | relaciones **tipo-subtipo** | `ING_TANDIL` | **`INGENIERO`** (el subtipo) |
| **(2)** | **FK ⊆ Z** (secundarios), `FK ∩ K = ∅` | **1:1, N:1**, n-arias con una cardinalidad 1 | `EMPL_SISTEMAS` | **`EMPLEADO`** |
| **(3)** | **FK ⊂ K** (subconjunto propio de la clave) | **N:N**, n-arias, entidad fuerte-débil | `EMPL_PROY` | **`TRABAJA`** |

> [!note] La columna "tabla que preserva la clave" es deducción, no texto del slide
> **Razonamiento propio:** los slides **nunca escriben** *"la tabla que preserva la clave es X"*.
> Dicen cuál es la clave de la vista, y en dos de los tres casos una `Nota:` dice cuál **no** es.
> **Verificar en clase.**

> [!tip] Regla práctica para los tres casos
> **Razonamiento propio, no está en el deck:** la tabla que preserva la clave es **la del lado
> "muchos" / la más específica**: `EMPLEADO` frente a `DEPARTAMENTO`, `TRABAJA` frente a `EMPLEADO`,
> `INGENIERO` frente a `EMPLEADO`. Es la tabla cuya clave **coincide con la de la vista** y cuyo
> dominio **no es más extenso** que el de la vista — el argumento textual del slide 8 es
> *"porque es esperable que su dominio de definición sea más extenso"*.

## La cadena de vistas

> [!quote] Recuadro `(*)` presente en los **dos** decks
> *"Puede ser otra vista, que debe ser actualizable. Si T→ V1→ V2→ … →Vn: **Vi será actualizable si
> Vi-1 lo es** y así sucesivamente"*
>
> Y subrayado en el deck 06: *"en una jerarquía de vistas, **basta que una de las vistas involucradas
> no preserve la clave**, para que esta propiedad ya no se cumpla"*

> [!important] La actualizabilidad es hereditaria y frágil
> **Razonamiento propio:** se propaga hacia adelante y **se corta en el primer eslabón que falla**.
> Un solo `GROUP BY` en `V2` vuelve no-actualizables a `V3 … Vn`. El slide enuncia la recursión pero
> no saca esta consecuencia.

### Las cuatro condiciones del estándar, en su forma corta

Deck 06 slide 12, textuales, para una vista sobre **una** tabla:

| # | Condición |
| --- | --- |
| ✓ 1 | **conserva todas las columnas de la clave (primaria)** |
| ✓ 2 | **no contiene funciones de agregación o información derivada** |
| ✓ 3 | **no incluye la claúsula `DISTINCT`** *(el deck escribe "claúsula" [sic])* |

> [!important] El nombre que hay que saber: **vistas σ-π** (y **σ-π-⋈** con joins)
> Una vista es actualizable si su definición se puede escribir usando **sólo** σ (selección =
> `WHERE`), π (proyección = lista del `SELECT`) y —con varias tablas— ⋈ (ensamble por los pares
> **FK → PK** de las RIRs). **Cualquier otro operador la saca de la categoría.**
>
> **La versión corta para el parcial:** *σ-π-⋈ y una sola tabla tocada.* Cualquier cosa que rompa la
> correspondencia **1 fila de la vista ↔ 1 fila de una tabla base** la mata.

### Los tres veredictos del deck, para calibrar

| Vista | Definición | Veredicto | Por qué |
| --- | --- | --- | --- |
| `PROV_TANDIL` | `SELECT id_proveedor, nombre FROM PROVEEDOR WHERE ciudad='Tandil'` | ✅ | σ-π de manual, proyecta la PK |
| `PROV_COMP` | `SELECT nombre, ciudad FROM PROVEEDOR WHERE rubro='Computadoras'` | ❌ | **no proyecta la PK** → viola ✓1 |
| `TOTAL_ARTICULO` | `SELECT id_articulo, sum(cantidad) FROM ENVIO GROUP BY id_articulo` | ❌ | **agregación** → viola ✓2 (y ✓1 por el `GROUP BY`) |

En `PROV_COMP`, dos proveedores homónimos de la misma ciudad son **indistinguibles** dentro de la
vista. En `TOTAL_ARTICULO`, un `UPDATE … SET total = 700` es irresolublemente ambiguo: hay infinitas
formas de repartir 700 entre los envíos del artículo.

### Cuando la vista no es actualizable: `INSTEAD OF`

> [!quote] Deck 07, slide 11
> *"Recurso que permite la actualización de vistas que no son automáticamente actualizables"* ·
> *"el trigger se dispara automáticamente **en lugar de** la sentencia disparadora"* · *"Por defecto,
> los triggers INSTEAD OF son **for each row**"*
>
> **"Importante: Queda en manos del usuario la responsabilidad de implementar las actualizaciones

# `WITH CHECK OPTION`

## El problema que resuelve: migración de tuplas

Aun cuando la vista **sea** actualizable, aparece un segundo problema.

> [!quote] Deck 06, slide 14
> *"Al efectuar actualizaciones en una vista, podría ocurrir que **las tuplas afectadas dejen de
> pertenecer a la vista**."*

```sql
CREATE VIEW PROV_TANDIL AS
    SELECT * FROM PROVEEDOR
    WHERE ciudad = 'Tandil';

UPDATE PROV_TANDIL SET ciudad = 'Azul';   -- sin WHERE: afecta a todas
```

> *"→ En este caso **todos los registros de la vista serían actualizados** con un valor de ciudad
> diferente a Tandil… y entonces **dejarían de pertenecer a la vista** (migración de tuplas)"*

> [!important] El chiste del ejemplo
> La vista es **perfectamente actualizable**: `SELECT *`, conserva la clave, σ-π pura. El `UPDATE` se
> ejecuta **sin error**. Y el resultado es absurdo: **la vista queda vacía**. La actualizabilidad no
> alcanza — hace falta un segundo mecanismo.

## La solución

> [!quote] Deck 06, slide 15
> *"**Solución a la migración de tuplas** → incluir la cláusula `WITH CHECK OPTION` (WCO)"*
>
> *"Si se especifica WCO → **una actualización sobre la vista procede si satisface la condición de
> consulta que la define** (se rechaza cualquier inserción o actualización que haga migrar una tupla
> de la vista)."*

| `opción` | Qué se chequea | Default |
| --- | --- | --- |
| **`CASCADED`** | *"las tuplas son chequeadas contra las condiciones de la vista **y aquellas de las vistas subyacentes**"* | **sí** |
| **`LOCAL`** | *"sólo se chequean contra las condiciones definidas en **la misma vista**"* | no |

Dos notas del slide:

- **"Sólo está soportado en vistas automáticamente actualizables"** *(resaltado en el deck).*
- *"**Date recomienda usar WCO en vistas actualizables y critica la opción 'local'**."*

> [!bug] Al tipear va **`CASCADED`**, con `D`, y **antes** de `CHECK OPTION`
> La palabra clave del estándar y de MySQL es **`CASCADED`**, y la cláusula se escribe
> **`WITH [CASCADED|LOCAL] CHECK OPTION`**. `WITH CHECK OPTION CASCADE` está mal por partida doble:
> ni la palabra ni el orden.
>
> Hay que tenerlo presente porque **el enunciado del TP4 la escribe mal**: dice *"WITH CHECK OPTION
> LOCAL o **CASCADE**"* ([[Práctica 2026-08-11]] § *Ejercicio 4.c*), propagando la forma del
> **deck 07 slide 2** (*"opción: cascade/local"*). El **deck 06 slide 15 la escribe bien**, y es esa
> la que vale al momento de tipear.

> [!success] Motor: acá MySQL sí acompaña
> **MySQL soporta `WITH CASCADED CHECK OPTION` y `WITH LOCAL CHECK OPTION`, y el default es
> `CASCADED`** — igual que el estándar y que el slide. Este pedazo se puede probar tal cual en el TP4.

## Qué cambia el WCO — ejemplo mínimo

```sql
CREATE VIEW Envios500 AS
SELECT * FROM ENVIO
WHERE cantidad >= 500;
```

| Operación | **Sin** WCO | **Con** WCO |
| --- | --- | --- |
| `INSERT … ('P1','A1',500)` | procede; `500 >= 500` → la fila **sí** se ve en la vista | procede igual |
| `INSERT … ('P2','A2',300)` | procede sobre `ENVIO`, pero `300 < 500` → **se inserta y desaparece**: no es visible en la vista que la insertó | **se rechaza** |
| `UPDATE … SET cantidad=1000 WHERE id_proveedor='P1'` | procede; `1000 >= 500` → las filas **siguen** en la vista | **procede igual** |
| `UPDATE … SET cantidad=100 WHERE id_proveedor='P1'` | procede; las filas **migran fuera** de la vista | **se rechaza**: `100 < 500` |

> [!success] El ejercicio que el deck dejó planteado **es el ejercicio 1 del TP4** — con un ítem más
> El deck 06 slide 16 **plantea el ejercicio y no lo resuelve**, y esta página pedía *"verificar en
> clase o en el TP4"*. **El TP4 es ese ejercicio**: la misma vista `ENVIOS500`, las mismas
> operaciones ([[Práctica 2026-08-11]] § *Ejercicio 1*). Lo que agrega es la **tercera fila** —el
> `UPDATE … cantidad=1000`—, que el enunciado intercala **antes** del `cantidad=100`.
>
> **Para qué está ese ítem:** para contrastarlo con el que le sigue. **El WCO no rechaza cualquier
> `UPDATE`, solo el que haría migrar la fila fuera de la vista.** Sin él es fácil salir del tema
> creyendo que WCO ≡ *"por la vista ya no se puede actualizar"*.
>
> Las respuestas de la tabla siguen siendo **razonamiento propio**: el TP entrega el enunciado, no la
> resolución. **Verificar contra la corrección en clase.**

> [!tip] El caso más contraintuitivo es el segundo `INSERT` sin WCO
> Insertás una fila **a través de la vista** y después `SELECT * FROM Envios500` **no te la muestra**.
> No se perdió: está en `ENVIO`. Simplemente nunca perteneció a la vista. Es el mejor argumento a
> favor de poner WCO siempre.

## `CASCADED` vs. `LOCAL` — el ejemplo que se entiende solo

Una cadena de dos vistas, cada una con su filtro:

```sql
CREATE VIEW Envios500 AS                     -- condición: cantidad >= 500
  SELECT * FROM ENVIO
  WHERE cantidad >= 500;

CREATE VIEW Envios500_999 AS                 -- condición: cantidad < 1000
  SELECT * FROM Envios500
  WHERE cantidad < 1000
  WITH { CASCADED | LOCAL } CHECK OPTION;    -- ← la variable del experimento
```

La cadena es `ENVIO → Envios500 → Envios500_999`. Se ejecuta:

```sql
UPDATE Envios500_999 SET cantidad = 300
WHERE id_proveedor = 'P1' AND id_articulo = 'A1';
```

| Definición | Qué se chequea | Resultado |
| --- | --- | --- |
| **`WITH CASCADED CHECK OPTION`** | `cantidad < 1000` **y** `cantidad >= 500` *(la de la vista subyacente)* | `300 < 1000` ✓ pero `300 >= 500` ✗ → **la operación se RECHAZA** |
| **`WITH LOCAL CHECK OPTION`** | **sólo** `cantidad < 1000` | `300 < 1000` ✓ → **la operación PROCEDE**… y la tupla **migra**: desaparece de `Envios500_999` **y** de `Envios500` |

> [!important] Esta es la crítica de Date a `LOCAL`, hecha ejemplo
> Con `LOCAL`, el WCO **no cumple su promesa**: se puso una opción de chequeo y la tupla se fue lo
> mismo. **`LOCAL` no elimina la migración, la esconde un nivel más abajo.** Por eso `CASCADED` es el
> default del estándar y por eso Date dice que `LOCAL` no debería usarse.
>
> **Mnemotécnica:** `CASCADED` chequea **toda la cadena hacia abajo**; `LOCAL` chequea **un solo
> eslabón**. Si la vista se apoya en otras vistas con filtros, `LOCAL` es un agujero.

> [!warning] Matiz del estándar que el slide simplifica
> **Razonamiento propio:** en el estándar SQL, `LOCAL` chequea la condición de la vista **más** las
> de las vistas subyacentes **que a su vez estén definidas `WITH CHECK OPTION`**. En este ejercicio
> `Envios500` se definió **sin** WCO, con lo que el resultado coincide con la lectura simplificada
> del slide — **pero no siempre coincide**. Si `Envios500` tuviera su propio WCO, la fila `LOCAL`
> cambiaría. **Verificar cuál definición se toma como válida para el parcial.**

> [!bug] El ejemplo original del deck no compila
> El slide 17 del deck 06 escribe `FROM ENVIO500` (falta la `S`), nombra la vista `Envios500-999`
> (**el guion es el operador de resta**: habría que escribirla `` `Envios500-999` `` en MySQL o
> renombrarla `Envios500_999`) y deja el paréntesis de cierre **adentro** del literal
> (`id_articulo = 'A1 )';`), con lo que el `where (` nunca se cierra. **Arriba está la versión
> corregida**; el original transcripto tal cual está en [[Clase 06 - Vistas-Parte 1]].
>
> ✅ **Confirmado por el TP4** ([[Práctica 2026-08-11]] § *Ejercicio 1.b*): el enunciado nombra la
> vista **`ENVIOS500_999`** —con guion **bajo**— y la define *"a partir de vista **ENVIOS500**"*, con
> la `S`. Las dos erratas eran **del slide**, no del ejercicio. El registro se deja acá porque el
> slide sigue estando mal y se lo va a volver a leer.

# Vistas en MongoDB

> [!info] Dónde aparece
> [[Clase 12 - Introduccion a NoSQL|Clase 12]], **slides 50, 51 y 52** — los **tres últimos del
> deck**, que termina ahí, sin cierre ni bibliografía. Títulos textuales: *"Vistas en MongoDB"* con la
> viñeta *"Creación de vistas"* *(50)*, *"Ejemplo de Vistas"* *(51)* y *"Uso de la Vista"* *(52)*.
> Los tres slides son **capturas de la documentación oficial de MongoDB** *(fondo cuadriculado, texto
> en inglés)*: el deck no agrega ni una línea propia. Se practica en el **TP9**,
> [[Práctica 2026-09-15]] § *Ejercicio 10* *(la vista `bandas_resumen`)*.
> Se verificó cada transcripción contra el PNG del slide *(16/09)*.

## Qué es

Una vista en MongoDB es una **colección de solo lectura** cuyo contenido se define con un **pipeline
de agregación** ([[2.12.08 - Aggregation pipeline|Aggregation pipeline]]) sobre otra colección
—o sobre otra vista— y **se calcula cada vez que se la lee**. Es exactamente la definición del slide 3
del deck 06 —*"dar un nombre a una expresión de consulta"*, *"tabla virtual"*, *"las tuplas se
generan al operar"*— con dos sustituciones: la *expresión de consulta* es un pipeline y la *tabla*
es una colección. Lo que **no** viaja de un motor al otro es la segunda mitad de esta página:
**no hay actualizabilidad, ni preservación de clave, ni `WITH CHECK OPTION`**, porque la vista de
MongoDB **no se escribe nunca**.

> [!quote] Documentación oficial, *Views* *(consultada el 16/09)*
> *"Views are read-only. Write operations on views return an error."* ·
> *"MongoDB does not persist the view contents to disk. A view's content is computed on-demand when
> a client queries the view."*

## Sintaxis — las dos formas del slide 50

El slide 50 muestra **dos capturas lado a lado**, transcriptas tal cual:

```js
// Forma 1 — createCollection con viewOn
db.createCollection(
  "<viewName>",
  {
    "viewOn" : "<source>",
    "pipeline" : [<pipeline>],
    "collation" : { <collation> }
  }
)
```

```js
// Forma 2 — createView
db.createView(
  "<viewName>",
  "<source>",
  [<pipeline>],
  {
    "collation" : { <collation> }
  }
)
```

| Parte | Qué es | Equivalente en `CREATE VIEW` |
| --- | --- | --- |
| `<viewName>` | nombre de la vista; **se lista junto a las colecciones** *(`show collections`, `db.getCollectionNames()`)* | `nom_vista` |
| `<source>` | colección **o vista** de origen, **de la misma base** *(nombre solo, sin prefijo de base)* | el `FROM` |
| `[<pipeline>]` | arreglo de etapas de agregación *(`$match`, `$project`, `$lookup`, `$group`, …)* que define la vista | `expresión_consulta` |
| `collation` | *opcional*: reglas de comparación de strings *(mayúsculas, acentos)*. Si el origen es otra vista, **debe ser la misma** | — *(no hay equivalente en la cláusula; en MySQL es el `COLLATE` de las columnas)* |

Las dos formas son **equivalentes**: `createView` es una abreviatura de `createCollection` con la
opción `viewOn`. Y `db.createView` **se escribe igual en el shell `mongo` viejo y en `mongosh`**: es
uno de los pocos comandos del deck 12 que **no** necesita traducción *(a diferencia de `insert`,
`count`, `remove`, `ensureIndex` → [[MongoDB]])*.

> [!warning] Lo que la sintaxis del slide no dice y la documentación sí *(verificado el 16/09)*
> - El pipeline de una vista **no puede incluir `$out` ni `$merge`**, tampoco dentro de un `$lookup`
>   o `$facet` embebido. Una vista **nunca escribe**.
> - La vista debe crearse **en la misma base** que su colección origen.
> - **La definición es pública**: `db.getCollectionInfos()` y `explain` sobre la vista **muestran el
>   pipeline**. Si la vista se usa para ocultar datos, hay que evitar poner valores sensibles en la
>   propia definición *(por ejemplo, un `$match` con el nombre de la persona que se quiere excluir)*.

> [!question] Y lo que la documentación **no** dice — *sin verificar*
> Qué pasa con la vista si se **borra la colección origen**. Las páginas *Views*, *Create and Query a
> View* y `db.createView()` del manual **no lo tratan**: la única restricción de ciclo de vida que
> documentan es *"You cannot rename a view once it is created"*. La afirmación de que la vista queda
> inválida sin aviso —como en MySQL, que ignora `RESTRICT`/`CASCADE` en `DROP VIEW` *(§ *Eliminar*)*—
> es una **conjetura pendiente de probar en el contenedor del TP9**, no un dato del manual.

## El ejemplo del deck — slides 51 y 52

La colección de origen, rotulada *"Collection: Survey"* en el slide 51:

```js
{ _id: 1, empNumber: "abc123", feedback: { management: 3, environment: 3 }, department: "A" }
{ _id: 2, empNumber: "xyz987", feedback: { management: 2, environment: 3 }, department: "B" }
{ _id: 3, empNumber: "ijk555", feedback: { management: 3, environment: 4 }, department: "A" }
```

La vista, rotulada *"View: managementFeedback"*:

```js
db.createView(
   "managementFeedback",
   "survey",
   [ { $project: { "management": "$feedback.management", department: 1 } } ]
)
```

Y su uso, en el slide 52 —`db.managementFeedback.find()`, seguido de *"The operation returns the
following documents:"*—:

```js
{ "_id" : 1, "department" : "A", "management" : 3 }
{ "_id" : 2, "department" : "B", "management" : 2 }
{ "_id" : 3, "department" : "A", "management" : 3 }
```

Lo que enseña el ejemplo, leído desde esta página:

| Qué hace el pipeline | En términos de la vista relacional |
| --- | --- |
| `department: 1` → incluye el campo | la **proyección** π: la lista del `SELECT` |
| `"management": "$feedback.management"` → **campo nuevo** con el valor de un **subcampo** *(notación de punto)* | una **columna renombrada y "aplanada"**: `feedback.management AS management`. Es la regla 1 de nombres de columna, pero **por campo**, no con una lista completa |
| `empNumber` y `feedback.environment` **no salen** | lo que la vista **oculta**: seguridad por columnas *(§ *Para qué sirven*)* |
| `_id` sale aunque no se lo pida | `_id` se incluye siempre en un `$project` salvo `_id: 0` |
| No hay `$match` | no hay σ: la vista **no filtra filas**; solo recorta columnas |

> [!important] El uso canónico es el mismo que daba el deck 07, slide 18: **control de acceso**
> La vista `managementFeedback` existe para **mostrar la opinión sobre la gerencia y ocultar la del
> ambiente** —y el número de empleado—. Es la quinta ventaja de la tabla de § *Para qué sirven*
> *("dando privilegios selectivamente sobre distintas vistas")*, ahora en un motor donde la clase de
> seguridad no la nombró. La documentación lo enuncia como primer caso de uso: crear una vista sobre
> los empleados *"to exclude any personally identifiable information (PII)"*. Lo que **falta**, igual
> que en la mitad relacional, es el otro lado —**quién puede leer la vista y quién la colección**—:
> ningún deck de MongoDB trae usuarios ni roles *(→ [[1.11.01 - Seguridad en bases de datos|Seguridad]]
> § *8*, la fila "vistas como control de acceso")*.

> [!bug] `"Survey"` en el rótulo, `"survey"` en el comando
> Los nombres de colección en MongoDB **distinguen mayúsculas**. Si la colección se llamara `Survey`,
> `createView("managementFeedback", "survey", …)` crearía la vista **sobre una colección
> inexistente**, sin error, y `find()` devolvería vacío. Vale el comando, no el rótulo. *(Registrado
> también en [[Clase 12 - Introduccion a NoSQL|Clase 12]] § *Slide 51*.)*

> [!note] De dónde sale la captura del deck — y dónde encontrarla hoy *(verificado el 18/09 contra el manual)*

## Vista relacional vs. vista de MongoDB — sección por sección de esta página

**Razonamiento propio:** el cruce no está en ningún deck. Cada fila toma un apartado de esta página
y dice qué pasa con él en MongoDB *(la columna del medio remite a la sección de arriba; la derecha
sale de los slides 50–52 y de la documentación verificada el 16/09)*.

| Apartado | Vista relacional *(Clases 06–07, MySQL)* | Vista de MongoDB *(Clase 12, `mongosh`)* |
| --- | --- | --- |
| **Definición** | nombre + `SELECT` | nombre + **pipeline de agregación** |
| **Nivel de la arquitectura** | esquema **externo** | igual: recorta lo que un grupo de usuarios ve, sin tocar la colección |
| **¿Guarda datos?** | no; tabla virtual, se recalcula al consultar | no; *"computed on-demand when a client queries the view"* |
| **Nombres de columna** | lista completa entre paréntesis, o los del `SELECT` | por campo, en el `$project` *(`nuevo: "$viejo.sub"`)*; no hay lista aparte |
| **`FROM` otra vista** | sí; `Vi` actualizable si `Vi-1` lo es | sí *("views on views")*; la regla de la cadena **no existe** porque nada es actualizable; lo que se hereda es la **`collation`**, que debe coincidir. Al leer, MongoDB **antepone** el pipeline de la vista al de la consulta |
| **`DROP` y dependencias** | `RESTRICT` *(default)* / `CASCADE` — **MySQL los ignora** | `db.vista.drop()`; qué pasa al **borrar el origen** no está documentado en el manual — **sin verificar** *(callout de § *Sintaxis*)* |
| **¿Actualizable?** | a veces: criterio de **preservación de la clave**, cuatro condiciones, σ-π-⋈ | **nunca**: *"Write operations on views return an error"*. Toda la segunda mitad de esta página no aplica |
| **`WITH CHECK OPTION`** | evita la migración de tuplas | **no existe** *(no hay escritura que controlar)* |
| **`INSTEAD OF`** | lo que el estándar ofrece y MySQL no tiene | **no existe**; se escribe contra la colección origen |
| **Materializada** | opcional en PostgreSQL/Oracle/SQL Server; **MySQL no las admite** | **no como objeto**: la vista es siempre virtual. La documentación llama *"on-demand materialized view"* a una **colección real** escrita con `$merge`/`$out` al final de un `aggregate` y refrescada a mano — la **misma emulación** que el callout de § *Virtual vs. materializada* proponía para MySQL con `INSERT … SELECT` |
| **Índices** | sobre las tablas base; en materializadas, propios | **solo los de la colección origen**: no se pueden crear, borrar ni listar índices sobre la vista → [[2.14.02 - Índices en MongoDB\|Índices en MongoDB]] |
| **Seguridad** | privilegios sobre la vista con `GRANT` *(GMUW 10.1.1)* | mismo uso *(ocultar campos)*, pero **la definición es pública** vía `getCollectionInfos()`/`explain`, y los decks no traen usuarios ni roles |
| **Desde cuándo** | SQL-86 | MongoDB **3.4** *(2016; dato de la página de la Clase 12, no señalado por la documentación actual)* |

> [!tip] La versión corta para el parcial
> **Lo que se conserva:** consulta con nombre, virtual, evaluada al leer, definida sobre colecciones
> u otras vistas, y usada para **simplificar consultas** y **ocultar datos**.
> **Lo que cambia:** se define con un **pipeline**, es **siempre de solo lectura** y **nunca
> materializada** *(sin `$out`/`$merge` en su definición)*. Por eso **no hay** preservación de clave,
> `WITH CHECK OPTION` ni `INSTEAD OF`: los tres mecanismos existen para escribir a través de una vista,
> y en MongoDB eso no ocurre.

## En el motor de la cursada — `mongosh` y el TP9

| Operación | Comando | Nota |
| --- | --- | --- |
| Crear | `db.createView("v", "origen", [ pipeline ])` | igual en `mongo` y `mongosh`; **no está deprecado** |
| Crear *(forma larga)* | `db.createCollection("v", { viewOn: "origen", pipeline: [ … ] })` | la forma 1 del slide 50 |
| Consultar | `db.v.find(filtro)` · `db.v.aggregate([ … ])` · `db.v.countDocuments()` | como una colección; el pipeline de la vista se ejecuta **antes** del de la consulta |
| Listar | `show collections` · `db.getCollectionNames()` | las vistas aparecen mezcladas con las colecciones |
| Distinguir vista de colección | `db.getCollectionInfos({ type: "view" })` | devuelve `type: "view"` y la `options.pipeline` completa |
| Borrar | `db.v.drop()` | no hay `DROP VIEW`; es el mismo `drop()` de una colección |
| Escribir | `db.v.insertOne(…)`, `updateOne`, `deleteOne` | **error**: la vista es de solo lectura |
| Plan | `db.v.find().explain("executionStats")` | muestra el pipeline de la vista → [[1.08.01 - Plan de ejecución\|Plan de ejecución]] § MongoDB |

> [!important] El TP9 pide la primera vista de MongoDB de la cursada — **y no enseña la sintaxis**
> El **ejercicio 10** del TP9 dice, textual: *"Promedio de integrantes por género en orden alfabético,
> usando una vista llamada bandas_resumen (que deberán crear) que tenga solo los datos del solista, el
> género de la banda, el barrio y los integrantes"*, y el **11** reutiliza *"la vista creada en el
> punto anterior"*. **Ninguno de los 34 pasos guiados del TP trae `createView`**: la única fuente de
> la cursada es el slide 50 de la Clase 12. La resolución propuesta —un `$project` de cuatro campos con
> `_id: 0`, y el `$group` con `$avg` corrido **sobre la vista**— está en
> [[Práctica 2026-09-15]] § *Ejercicio 10*. Dos cosas que ese ejercicio demuestra sin decirlo:
> la vista **no materializa** *(refleja el `$inc` del ejercicio 4 al instante)* y **se puede agregar
> sobre una vista** *(el `aggregate` del ejercicio 10 corre sobre `bandas_resumen`, no sobre `bandas`)*.

## Cuadro de bolsillo

| Pregunta | Respuesta |
| --- | --- |
| ¿Qué es una vista? | Relación **derivada**: nombre dado a una expresión de consulta |
| ¿En qué nivel vive? | **Esquema externo** |
| ¿Guarda datos? | **No** — tabla virtual. Salvo materializadas |
| ¿Sobre qué se define? | Una o más **tablas y/o vistas** definidas previamente |
| ¿Cómo se consulta? | **Como cualquier tabla** |
| ¿Cómo se borra? | `DROP VIEW nom [RESTRICT\|CASCADE]` — `RESTRICT` default, **MySQL las ignora** |
| Tabla → vista | Automático, por **recálculo** o **mantenimiento incremental** |
| Vista → tabla | **No siempre.** Criterio: **preservación de la clave** |
| ¿Cuándo preserva la clave? | Cuando **cada fila de la tabla aparece como máximo una vez** en la vista. **Propiedad del esquema, no de los datos** |
| Las 4 condiciones | conserva la PK · sin agregación ni derivados · sin `DISTINCT` · sin subconsultas en el `SELECT` |
| ¿Cómo se llaman esas vistas? | **σ-π** (una tabla) · **σ-π-⋈** (con joins por FK→PK) |
| En una cadena `T→V1→…→Vn` | `Vi` actualizable **si `Vi-1` lo es**; un eslabón roto rompe todo |
| ¿Migración de tuplas? | Que la fila actualizada **deje de pertenecer** a la vista |
| ¿Cómo se evita? | `WITH CHECK OPTION` |
| `CASCADED` vs. `LOCAL` | `CASCADED` (default) chequea la vista **y las subyacentes**; `LOCAL` sólo la propia |
| ¿Sobre qué vistas funciona WCO? | **Sólo sobre vistas automáticamente actualizables** |
| Si no es actualizable y hay que escribir | Trigger **`INSTEAD OF`** — **que MySQL no tiene** |
| ¿Vistas + `GRANT` en la teórica de seguridad? | **No**: la Clase 11 no nombra las vistas. Se arma juntando Clase 07 slide 18 + Clase 11 slide 10 *(GMUW 10.1.1)* |
| ¿Y en MongoDB? *(Clase 12, slides 50–52)* | `db.createView("v", "origen", [ pipeline ])` — o `createCollection` con `viewOn` |
| ¿Qué conserva la vista de MongoDB? | consulta con nombre · virtual · evaluada al leer · sobre colecciones u otras vistas · para ocultar campos |
| ¿Qué cambia? | se define con un **pipeline** · **siempre de solo lectura** · **nunca materializada** *(sin `$out`/`$merge`)* · sin índices propios · sin preservación de clave, WCO ni `INSTEAD OF` |
