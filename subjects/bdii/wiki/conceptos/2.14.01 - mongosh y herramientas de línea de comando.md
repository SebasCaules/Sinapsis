# mongosh y herramientas de línea de comando

## Resumen general

Esta página documenta las herramientas de línea de comando de MongoDB de la
[[Clase 14 - MongoDB Features|Clase 14]] (slides 10–19 y 30) y del [[Práctica 2026-09-15|TP9]]: los
tres binarios (`mongod` servidor, `mongosh` cliente actual, `mongo` shell legado eliminado en 6.0),
cómo entrar —local o en Docker con el contenedor `Mymongo`—, orientarse (`help`, `show dbs`, `use`,
`db`, `show collections`), cargar datos con `mongoimport`, la tabla de Database Tools (`mongodump`,
`mongoexport`, `mongorestore`, `mongostat`, `mongotop`, `mongofiles`, `bsondump`) y las GUIs
(Compass, DataGrip, Studio 3T, NoSQLBooster). No cubre CRUD
([[2.12.07 - CRUD y consultas en MongoDB|CRUD y consultas en MongoDB]]), índices
([[2.14.02 - Índices en MongoDB|Índices en MongoDB]]) ni `mongod --replSet`/`mongos`
([[2.12.02 - Escalabilidad horizontal — sharding y replicación|Escalabilidad horizontal]]).

Importa porque el TP9 es el primer TP escrito para el mismo shell que se usa: los TPs sobre
[[MySQL]] traían sintaxis de otros motores (el TP1 y el TP6 no tocan motor). Las
[[Clase 12 - Introduccion a NoSQL|Clases 12]] y [[Clase 13 - NoSQL-EmbebidosVSNormalizado|13]] usan
comandos de shell sin decir en cuál corren. El parcial puede preguntar servidor vs. cliente, la
secuencia de orientación y backup binario vs. exportación en texto.

Reglas clave: (1) `mongod` y `mongosh` se instalan por separado; (2) `mongo` fue eliminado en 6.0 y
casi todo el material —salvo el TP9— está escrito en `mongo`; (3) `use <base>` no crea la base, se
crea con el primer documento insertado; (4) `use` es un *helper* del shell, no JavaScript, y en un
script se reemplaza por `db.getSiblingDB()`; (5) una función sin paréntesis (`db.col.findOne`)
muestra su código fuente en vez de ejecutarla; (6) las Database Tools se distribuyen aparte del
servidor desde 4.4, igual que `mongosh`.

Para el parcial: la tabla `mysql` ↔ `mongosh` de la § 7 y el cuadro de bolsillo al final resumen
todo esto.

## Qué es

> [!quote] Slide 10 — textual
> **levantando el servicio y entrando al shell (mongosh)**
> ```
> # prender y apagar el servicio
> #
> $ sudo service mongod start
> $ sudo service mongod stop
>
> # levantar el shell
> #
> $ mongosh --host localhost --port 27017  # es equivalente a
> $ mongosh  # esta otra instrucción
>
> > show dbs
> # mostrar las bases de datos
> ```
> Recuadro *(captura de la documentación oficial)*: *"**MongoDB Shell, mongosh** — The MongoDB Shell
> (mongosh) is not installed with MongoDB Server. You need to follow the mongosh installation
> instructions to download and install mongosh separately."*

**Tres binarios con nombre parecido, y conviene no mezclarlos:**

| Binario | Qué es | Dónde aparece | Estado hoy |
| --- | --- | --- | --- |
| **`mongod`** | el **servidor**: escucha en **27017**, guarda datos en `--dbpath` | slide 10 (`service mongod start`) · slide 41 (`mongod --replSet book --dbpath ./mongo1 --port 27011`) | vigente; en el TP9 corre dentro del contenedor Docker |
| **`mongosh`** | el **cliente interactivo actual**: intérprete de JavaScript con *helpers* (`use`, `show`, `db`) | slide 10 · TP9 p. 1 | el único shell soportado desde 6.0; se instala aparte del servidor |
| **`mongo`** | el **shell legado**, el que usan *Seven Databases* y las capturas viejas del deck | slide 11 (`help` con *"quit the mongo shell"*) · 25 (`WriteResult`) · 41 (`$ mongo localhost:27011`) | deprecado en 5.0, **eliminado en 6.0** (el deck se declara de la 6.0.5 en su slide 2) |

> [!important] (clave) El shell es un **cliente**, y esa separación es la misma que en MySQL
> `mongod` : `mongosh` es lo que `mysqld` : `mysql` en la [[Práctica 2026-08-04]]: un proceso que
> escucha en un puerto y un programa que se le conecta por TCP. Los valores por defecto del slide
> —`localhost` y `27017`— son lo que el `docker run … -p 27017:27017` del TP9 expone hacia el host.
> Como el shell es **JavaScript**, `db` es un objeto, `db.players` una propiedad y `find` una
> función (las dos rarezas que se derivan de eso están en § 2).

## 1 · Entrar — las formas de conexión

Las que traen el deck y el TP, más las dos que hacen falta con Docker:

| Forma | Fuente | Cuándo |
| --- | --- | --- |
| `mongosh` | slide 10 | servidor local en el puerto por defecto; abre la base `test` |
| `mongosh --host localhost --port 27017` | slide 10 | equivalente a la anterior; cambia host o puerto (slide 41: puertos 27011–27013) |
| `mongosh "mongodb://localhost:27017"` | (propuesta propia) | URI de conexión, mismo formato que `pymongo` en los slides 26 y 39 |
| `docker exec -it Mymongo bash` → `mongosh` | TP9 p. 1 | lo que pide el enunciado: `bash` dentro del contenedor, después el shell |
| `docker exec -it Mymongo mongosh` | [[Práctica 2026-09-15]] (atajo) | la imagen oficial `mongo` trae `mongosh` adentro; el `bash` intermedio es opcional |
| `mongosh lab tp9.js` · `load("tp9.js")` | [[Práctica 2026-09-15]] § *Todo el TP en un script* | ejecuta un archivo; ahí `use lab` se reemplaza por `db = db.getSiblingDB("lab")` |

> [!quote] TP9, p. 1 — la instalación por Docker
> Instalar Docker Desktop (Windows/Mac) o Docker Engine (Linux) y correr, en orden: descargar la
> imagen oficial `docker pull mongo`; levantar el contenedor
> `docker run --name Mymongo -p 27017:27017 -d mongo`; entrar con `docker exec -it Mymongo bash`;
> apagar con `docker stop Mymongo` e iniciar con `docker start Mymongo`; listar containers con
> `docker ps -a`; copiar archivos al contenedor con `docker cp <filename> Mymongo:/<filename>`.

> [!warning] `service mongod start` (slide 10) y `docker start Mymongo` (TP) son la misma acción en dos mundos
> Instalación nativa en Linux vs. contenedor: `service mongod start/stop` en el primero,
> `docker start/stop Mymongo` en el segundo; el recuadro del slide 10 vale para la nativa, no para
> la imagen Docker, que sí trae el shell. Dos diferencias más con el `docker run` de MySQL del 04/08
> ([[Práctica 2026-09-15]]): no se fija versión (`mongo` sin tag = `latest`, contra `mysql:9.7.2`) y
> no hay credenciales (arranca sin autenticación).

## 2 · Orientarse — `help`, `show`, `use`, `db`

> [!quote] Slide 13 — textual
> **colecciones o tablas?**
> *"probar estas 3 instrucciones"*
> 1. `> show collections`
> 2. `> show tables`
> 3. `> db.getCollectionNames()`
>
> `> show dbs  // para listar las bases de datos`

> [!quote] Slide 20 — las líneas de orientación, textuales
> ```
> use DATABASE_NAME  # crea o usa una DB
> show dbs  # muestra las
> db  # te informa en que DB estas
> show collections
> ```
> *"Se puede ver cómo está implementada una función, si la llamamos sin los parentesis, ej:
> db.town.findOne"* **[sic: "parentesis", "estas", "que"]**

Las órdenes de orientación, con lo que devuelven y su estado en `mongosh`:

| Orden | Qué hace | Slide / TP | En `mongosh` hoy |
| --- | --- | --- | --- |
| `help` | ayuda general del shell | slide 11 | ✓ pero la pantalla del slide es la de `mongo` (abajo) |
| `db.help()` · `db.<col>.help()` | ayuda del objeto base / de la colección | slide 11 · TP9 p. 2 | ✓ |
| `rs.help()` · `sh.help()` | ayuda de replica set / de sharding | slide 11 | ✓ |
| `show dbs` | lista las bases existentes con su tamaño | slides 10, 13, 20 | ✓ |
| `use <db>` | selecciona la base; **la crea recién con el primer documento** | slides 12, 20 · TP9 paso 2 | ✓ (helper del shell, no JavaScript → en un script es `db.getSiblingDB()`) |
| `db` | imprime el nombre de la base actual | slide 20 | ✓ |
| `show collections` | lista las colecciones de la base actual | slides 13, 20 | ✓ |
| `show tables` | alias de la anterior | slide 13 | ✓ sigue aceptado |
| `db.getCollectionNames()` | lo mismo, pero devuelve un arreglo JavaScript | slide 13 · TP9 pasos 3 y 5 | ✓ la forma que usa el TP |
| `db.stats()` | estadísticas de la base | TP9 paso 1 | ✓ |
| `it` | sigue iterando el cursor del último `find()` | slide 11 | ✓ |
| `exit` · `quit()` | salir | slide 11 | ✓ |
| `DBQuery.shellBatchSize = x` | documentos que muestra `find()` por lote | slide 11 | ✗ legado → `config.set("displayBatchSize", x)` |

> [!bug] El slide 10 dice `mongosh` y el slide 11 muestra la ayuda de **`mongo`**
> La captura del slide 11 termina en *"exit — quit the **mongo** shell"* y trae
> `DBQuery.shellBatchSize` y `help mr` (mapreduce): es la ayuda del shell legado. En `mongosh`,
> `help` es más corto (lista `use`, `show`, `exit`, y remite a `db.help()`, `rs.help()`,
> `sh.help()`), pero los tres `.help()`, los `show`, `use`, `it` y `exit` siguen igual. Es la
> primera de las tres apariciones del shell viejo en el deck (11, 25, 41) →
> [[Clase 14 - MongoDB Features]] § *Contradicciones internas*.

> [!important] (clave) Las dos rarezas de un shell que es JavaScript
> 1. **`use` no es JavaScript**: es un *helper* que el shell interactivo intercepta. En un archivo
> cargado con `load()` o pasado por argumento no existe; ahí se escribe `db = db.getSiblingDB("lab")`.
> Es la trampa que el TP9 no menciona → [[Práctica 2026-09-15]] § *Todo el TP en un script*.
> 2. **Una función sin paréntesis es un valor, no una llamada.** `db.town.findOne` imprime el código
> fuente de `findOne`; `db.town.findOne()` lo ejecuta. El TP9 lo advierte: *"si ejecuta un comando y
> omite los paréntesis (), se mostrará el cuerpo del método en lugar de la ejecución del mismo"*.

> [!note] "Colecciones o tablas?" — el vocabulario que el slide 13 deja en el aire
> `show tables` funciona porque el shell lo acepta como alias, no porque MongoDB tenga tablas: base →
> *database* · tabla → *collection* · fila → *document* · columna → *field*
> ([[2.12.06 - Modelo de documentos — JSON, BSON y ObjectId|Modelo de documentos]]). Y `use test` +
> `db.createCollection("usuarios")` del slide 12 son dos pasos opcionales: `test` es la base que
> `mongosh` abre por defecto, y la colección se crea sola con el primer `insert`.

## 3 · Cargar datos — `mongoimport`

> [!quote] Slide 14 — textual
> **Importando un archivo .tsv (mongoimport)**
> ```
> $ mongoimport --headerline --db test --collection internos --type tsv < internos.tsv
>
> connected to: 127.0.0.1
> 2018-10-03T15:40:31.471-0300 check 9 290
> 2018-10-03T15:40:31.472-0300 imported 289 objects
>
> > db.internos.count()  ← en gris claro
> > db.internos.countDocuments()
> 289
> ```
> *(Una flecha va desde `--headerline` hasta el `290` de la línea `check`.)*

| Flag | Qué hace | Observación |
| --- | --- | --- |
| `--headerline` | la **primera línea** del archivo da los nombres de campo | es lo que explica la flecha: 290 líneas, **289** documentos |
| `--db test --collection internos` | destino; **los dos se crean si no existen** | la colección `internos` nace aquí |
| `--type tsv` | separador tabulación | el default es **JSON**; también acepta `csv` |
| `< internos.tsv` | el archivo entra por **stdin** | el equivalente explícito es `--file internos.tsv` |
| *(ausente)* `--jsonArray` | para un `.json` que es **un arreglo** de documentos | sin él, `mongoimport` espera un documento por línea |
| *(ausente)* `--host`, `--port` | otro servidor | *Seven Databases* impresa 130 *(PDF 143)* lo usa con `--host localhost:27020`; los puertos alternativos del slide 41 *(27011–27013)* son de `mongod`/`mongo`, no de `mongoimport` |

> [!important] Lo que la flecha enseña, y no es obvio: **`mongoimport` infiere tipos**
> El `findOne()` del slide 15 muestra `"int" : 4741` sin comillas: el campo llegó como entero aunque
> el TSV es texto; `mongoimport` convierte lo que parece número, y `nombre` entró como cadena única,
> tal como venía la columna, sin esquema que lo reparta. Comparado con el `LOAD DATA INFILE` de
> MySQL —que carga contra columnas ya tipadas—, aquí los tipos los decide la herramienta, fila por
> fila.

> [!warning] (crítico) `mongoimport` **no está en la imagen del slide 10**: es una *Database Tool*, y en Docker vive dentro del contenedor
> Desde **4.4** las herramientas `mongoimport`, `mongoexport`, `mongodump`, `mongorestore`,
> `mongofiles`, `mongostat`, `mongotop` y `bsondump` se distribuyen aparte del servidor, como
> *MongoDB Database Tools* (numeración propia, 100.x), igual que `mongosh`. En una instalación
> nativa hay que instalarlas; en el TP9 la imagen `mongo` las trae, pero corren dentro del
> contenedor: el archivo se copia primero con el `docker cp <filename> Mymongo:/<filename>` de la
> p. 1 —que el TP lista y no usa en ninguno de sus 34 pasos, probablemente pensado para la Parte II
> o para un dataset propio— y después se importa desde `docker exec -it Mymongo bash`. Qué versión
> de las Database Tools trae hoy la imagen no está verificado → § Dudas abiertas.

El slide 14 es también el único del deck que **corrige un deprecado en cámara**: `count()` en gris,
`countDocuments()` en negro. La regla y sus excepciones están en
[[2.12.07 - CRUD y consultas en MongoDB|CRUD y consultas en MongoDB]].

### 3.1 · El caso completo del TP9 Parte II: CSV con `--headerline` y JSON, vía `docker cp`

El `docker cp` que la Parte I listaba sin usar se usa en la Parte II *(ejercicios 4.a y 5)*: dos
archivos del host se copian al contenedor y se importan desde ahí. El enunciado lo dice textual: *"si
estás con docker primero deberás copiar el archivo dentro del contenedor usando docker cp <filename>
Mymongo:/<filename>"*.

```bash
# 1 · copiar del host al contenedor (el TP lo llama Mymongo)
docker cp egresados.csv Mymongo:/egresados.csv
docker cp mongoCities_fixed.json Mymongo:/mongoCities_fixed.json

# 2 · CSV con encabezado: --type csv + --headerline
docker exec Mymongo mongoimport --db academica --collection egresados \
  --type csv --headerline --file /egresados.csv
# → 8223 document(s) imported successfully. 0 document(s) failed to import.

# 3 · JSON de un documento por línea: sin --type ni --jsonArray
docker exec Mymongo mongoimport --db lab --collection cities --file /mongoCities_fixed.json
# → 99838 document(s) imported successfully. 0 document(s) failed to import.
```

*(Salidas reales en MongoDB 8.3.11, con `mongoimport` 100.18.0 dentro del contenedor, sobre los
archivos de `raw/Unidad-02/Practica/`; resolución completa en [[Práctica 2026-09-22|Práctica 2026-09-22]] § *Setup del
entorno* y ejercicios 4 y 5.)*

| Punto | Qué pasa | Por qué importa |
| --- | --- | --- |
| `docker cp` antes que nada | `mongoimport` corre **dentro** del contenedor y no ve el disco del host | sin la copia: `Failed: open /archivo: no such file or directory` y `0 document(s) imported` *(verificado)* |
| `docker exec` sin `-it` | alcanza para un comando que no pide interacción | con `-it Mymongo bash` y después `mongoimport` es lo mismo en dos pasos, como lo pide la Parte I |
| `--headerline` en el CSV | la primera fila (`legajo,nivel,titulo,colacion,promedio,promedio_lineal`) da los nombres de campo | encabezado + 8223 filas → **8223** documentos: la misma cuenta que la flecha del slide 14 |
| tipos inferidos | el tipo se infiere **valor por valor, no por columna**: `legajo` es numérico en los 8223 documentos; `promedio` y `promedio_lineal` son números en 3079 y la **cadena vacía `""`** en los otros 5144 (filas como `47578,Grado,Ingeniero en Petróleo,47,,`); `colacion` es `""` en un documento (legajo 19115); `titulo` y `nivel`, cadenas | `findOne()` muestra `legajo: 50233, colacion: 58, promedio: 4.76` sin comillas, pero una misma columna queda con **tipos mezclados**: sin `CREATE TABLE` no hay tipo de columna que lo impida *(verificado: `countDocuments({promedio: {$type: "number"}})` → 3079, `countDocuments({promedio: ""})` → 5144)* |
| JSON sin `--type` | el default de `mongoimport` es JSON | `mongoCities_fixed.json` es **un documento por línea**, no un arreglo: por eso no lleva `--jsonArray` |
| base y colección | `academica` y `lab` se crean con la importación | es la regla de `use`: la base existe recién cuando tiene un documento |

> [!tip] Cómo reconocer si un `.json` necesita `--jsonArray`
> Mirar el primer carácter del archivo: si es `[`, es un arreglo y lleva `--jsonArray`; si es `{` y
> cada línea es un documento completo *(el caso de `mongoCities_fixed.json`)*, va sin el flag.

## 4 · Las herramientas de línea de comando *(slide 30)*

El slide 30 es una **imagen sin título**: la tabla del recuadro *"Mongo's Many Useful CLI Tools"* de
*Seven Databases* (impresa **114**), reproducida entera. La función es la del libro, resumida; la
columna de la derecha es de esta página.

| Herramienta | Función (según el libro) | Hoy |
| --- | --- | --- |
| `mongodump` | exporta datos a `.bson` — colecciones/bases enteras o filtradas por query | ✓ Database Tools |
| `mongofiles` | manipula archivos **GridFS** (BSON > 16 MB) | ✓ Database Tools |
| `mongooplog` | consulta los logs de operaciones de replicación | ✗ no está en el paquete actual (a verificar); (ok) ausente en la imagen de MongoDB 8.3.11 *(Database Tools 100.18.0)* |
| `mongorestore` | restaura bases/colecciones desde un backup de `mongodump` | ✓ Database Tools |
| `mongostat` | estadísticas básicas del servidor | ✓ Database Tools |
| `mongoexport` | exporta datos a CSV o JSON, entero o filtrado por query | ✓ Database Tools |
| `mongoimport` | importa datos desde JSON, CSV o TSV | ✓ Database Tools — el slide 14 |
| `mongoperf` | pruebas de rendimiento definidas por el usuario | ✗ no está en el paquete actual (ídem); (ok) ausente también |
| `mongos` | enruta datos en un cluster *sharded* ("MongoDB shard") | ✓ pero **no es una Database Tool**: es un proceso servidor, hermano de `mongod` |
| `mongotop` | uso por colección | ✓ Database Tools |
| `bsondump` | convierte archivos BSON a otros formatos (p. ej. JSON) | ✓ Database Tools |

> [!important] (clave) La tabla se lee en **pares**
> `mongodump`/`mongorestore` (binario BSON, backup fiel, análogo a `mysqldump`) ·
> `mongoexport`/`mongoimport` (texto JSON/CSV/TSV, intercambio, pierde tipos BSON, análogo a
> `LOAD DATA INFILE`) · `mongostat`/`mongotop` (monitoreo de servidor/colección, análogo a
> `SHOW STATUS`/`SHOW PROCESSLIST`) · `mongofiles` + `bsondump` (GridFS e inspección de `.bson`). El
> deck usó el par de texto (slide 14); para llevarse una base entera —lo que va a hacer falta en el
> TPO— el par correcto es el binario.

> [!note] Tres cosas que la tabla deja dichas de paso
> - **GridFS y los 16 MB**: única mención a GridFS en todo el deck. Un documento BSON no puede
> superar **16 MB**; un archivo mayor se guarda partido en *chunks* en dos colecciones (`fs.files` y
> `fs.chunks`), y `mongofiles put/list/get` es su cliente (*Seven Databases* impresas 131–132;
> Corbellini § 6, p. 15: *"BSON files larger than 16 MB"*).
> - **`mongos`** reaparece en el slide 37 (cabecera del diagrama de MapReduce); el slide 44 trata el
> sharding sin nombrar el router.
> - La tabla es de **2018** (MongoDB 3.x): no sabe de las Database Tools separadas (4.4) ni de
> `mongosh`. Es la razón de las dos filas ✗.

> [!tip] (clave) La pestaña *Schema* de Compass es la respuesta práctica a "¿y si no hay esquema?"
> Compass infiere el esquema muestreando documentos y reporta, por campo, qué tipos aparecen y con
> qué frecuencia; así se descubre que la colección `internos` del slide 15 (`nombre`/`user`/`int`/…)
> y la del slide 16 (`apellido`/`nombre`/`interno`/…) son dos importaciones distintas en la misma
> colección —septiembre de 2020 y octubre de 2018, según sus `ObjectId`—. En MySQL eso lo contesta
> `DESCRIBE tabla`; aquí la alternativa en el shell es un `findOne()` y mirar.

## 6 · La tercera vía: los *drivers* *(slides 26 y 39)*

Shell y GUI son para personas; una aplicación entra por un **driver**. El deck lo muestra dos veces
con **`pymongo`**: `MongoClient('mongodb://…')` → `db = client['elecciones-2019']` →
`news_collection.update_one(myquery, newvalues)` (slide 26) y un recorrido con
`collection.find({},{'name':1})` (slide 39, en Python 2). Detalles y erratas en
[[Clase 14 - MongoDB Features]] § *Slides 25–26* y § *Slide 39*; lo que importa aquí es la
correspondencia:

| Nivel | Herramienta | Idioma | Nombres |
| --- | --- | --- | --- |
| interactivo | `mongosh` | JavaScript | `insertOne`, `updateOne`, `find` *(camelCase)* |
| aplicación | `pymongo` *(y el driver de cada lenguaje)* | Python | `insert_one`, `update_one`, `find` *(snake_case)* |
| gráfico | Compass, DataGrip, Studio 3T, NoSQLBooster | — | los mismos comandos, con formulario o con un `mongosh` embebido |

El shell, la GUI y el driver hablan **el mismo protocolo** con el mismo `mongod`; cambia solo el
envoltorio. Es la misma foto que en la primera mitad: `mysql`, Workbench/DataGrip y el conector JDBC.

## 7 · En el motor de la cursada — shell legado → `mongosh`

> [!warning] (crítico) Los tres decks de la U2 y *Seven Databases* están escritos en el shell **`mongo`**; el TP9 corre en **`mongosh`**
> Casi todo corre igual, pero no todo, y el aviso `DeprecationWarning` va a aparecer. Esta tabla
> cubre lo que es del shell (cómo se entra, cómo se orienta uno, cómo se imprime); la traducción de
> los métodos CRUD (`insert` → `insertOne`, `count` → `countDocuments`, `update` → `updateOne/Many`,
> `remove` → `deleteOne/Many`, `ensureIndex` → `createIndex`) vive en
> [[2.12.07 - CRUD y consultas en MongoDB|CRUD y consultas]] y en [[MongoDB]].

## Para el parcial

| Pregunta probable | Respuesta corta, con cita |
| --- | --- |
| ¿Qué diferencia hay entre `mongod` y `mongosh`? | `mongod` es el servidor (`service mongod start`); `mongosh` es el cliente interactivo que se conecta por `--host`/`--port`, por defecto `localhost:27017` (slide 10) |
| ¿Por qué el shell no viene con el servidor? | Se instala aparte, según el recuadro del slide 10; desde 6.0 es el único shell, porque `mongo` fue eliminado. Lo mismo las Database Tools desde 4.4 |
| ¿Qué es el shell `mongo`? | El shell legado, eliminado en 6.0; es el de *Seven Databases* y de las capturas viejas del deck (slides 11, 25, 41). `mongosh` lo reemplaza y acepta los métodos viejos con `DeprecationWarning` |
| ¿Cómo se listan las bases y las colecciones? | `show dbs` · `show collections` (o `show tables`, alias; o `db.getCollectionNames()`, arreglo) (slides 13 y 20) |
| ¿`use` crea la base? | No todavía: la base y la colección se crean con el primer documento (TP9 paso 2) |
| ¿Cómo se importa un CSV/TSV? | `mongoimport --headerline --db <db> --collection <col> --type tsv < archivo` (slide 14): `--headerline` consume la primera línea como nombres de campo |
| ¿Qué diferencia hay entre `mongodump` y `mongoexport`? | `mongodump`/`mongorestore` son binarios (BSON, backup fiel); `mongoexport`/`mongoimport` son texto (JSON/CSV/TSV, intercambio) (slide 30) |
| ¿Para qué sirve `mongofiles`? | Para GridFS: archivos que superan **16 MB** por documento BSON, guardados en *chunks* (slide 30; Corbellini § 6) |
| ¿Qué pasa si se escribe `db.col.findOne` sin paréntesis? | Se imprime el código fuente del método en vez de ejecutarlo (slide 20; TP9 NOTA) |
| ¿Con qué se ve el "esquema" de una colección? | No hay `DESCRIBE`; la pestaña Schema de Compass infiere tipos y frecuencias por muestreo (slide 17) |

> [!tip] (clave) Si la pregunta es "elegir herramienta", la respuesta tiene tres niveles
> **Shell** para explorar y para el TP *(`mongosh`)*, **GUI** para ver el esquema inferido y armar
> pipelines *(Compass; DataGrip por continuidad con MySQL)*, **driver** para la aplicación
> *(`pymongo`)*. Y para mover datos, **binario** para respaldar y **texto** para intercambiar.

## Cuadro de bolsillo

| Pregunta | Respuesta |
| --- | --- |
| Servidor / cliente | **`mongod`** / **`mongosh`** *(el `mongo` legado murió en 6.0)* |
| Puerto por defecto | **27017** — `mongosh --host localhost --port 27017` ≡ `mongosh` |
| En el TP9 | `docker run --name Mymongo -p 27017:27017 -d mongo` → `docker exec -it Mymongo bash` → `mongosh` |
| Orientarse | `help` · `show dbs` · `use <db>` · `db` · `show collections` · `db.getCollectionNames()` |
| `use` | selecciona; **crea recién con el primer documento**; en un script es `db.getSiblingDB()` |
| Sin paréntesis | muestra el **código fuente** del método |
| Importar | `mongoimport --headerline --db test --collection internos --type tsv < internos.tsv` |
| Backup vs. intercambio | `mongodump`/`mongorestore` *(BSON)* vs. `mongoexport`/`mongoimport` *(JSON/CSV/TSV)* |
| GridFS | `mongofiles` — documentos de más de **16 MB** en *chunks* |
| `mongos` | **no** es una herramienta: es el *router* del sharding, un proceso servidor |
| Database Tools | aparte del servidor desde **4.4**; `mongosh` se instala aparte *(slide 10)* y es el único shell desde **6.0** |
