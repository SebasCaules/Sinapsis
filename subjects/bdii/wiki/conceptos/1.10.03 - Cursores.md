# Cursores

## Resumen general

Un cursor es una variable que recorre las filas de un conjunto de datos en forma secuencial y sin volver a una fila anterior: el puente entre el SQL de conjunto y el código procedural, que trabaja con una cosa por vez. Aparece en los slides 9 a 11 de la Clase 10, en PL/pgSQL, donde todo cursor es del tipo `refcursor` y el ciclo es siempre el mismo: `DECLARE` → `OPEN` → `FETCH … INTO` → `CLOSE`, con la variable `FOUND` para saber si el último `FETCH` trajo fila. El deck da tres formas de declararlo: genérico (`refcursor`, la consulta se fija al abrirlo), ligado o *bounded* (`CURSOR FOR <select>`, se fija al declararlo) y parametrizado (argumentos que se pasan en el `OPEN`).

Importa porque la cursada corre sobre MySQL y el TP7 obliga a traducir. MySQL tiene solo la forma ligada, siempre con `DECLARE`; no existen `refcursor`, cursores con parámetros, `OPEN … FOR`, `OPEN … FOR EXECUTE`, `%rowtype` ni `FOUND`. Su reemplazo es un `CONTINUE HANDLER FOR NOT FOUND` de sentido inverso (`FOUND` dice "trajo fila", `done` dice "se acabó"), y traducirlos sin más invierte la lógica sin error de compilación. El orden de `DECLARE` es además rígido: variables, *conditions*, cursores, handlers. El `FOR … IN (SELECT …) LOOP` del slide 13 es un cursor implícito, y como MySQL no tiene `FOR`, se reescribe como cursor explícito.

Trampas del propio deck: `curs3 CURSOR (…) IS` es sintaxis de Oracle, y el ejemplo del slide 11 no compila (`menaje` por `mensaje`, dos `;` faltantes, declaración invertida). Regla de uso: el cursor es el último recurso; si el problema se resuelve con una sentencia de conjunto (`INSERT … SELECT`, `UPDATE … WHERE`, `EXISTS`, un agregado), esa es la respuesta correcta, y el ejercicio 4.a del TP7 está armado para comprobarlo.

## Qué es

> [!quote] Slide 9 — la definición, textual
> *"Un cursor es un **tipo de variable** que nos permite acceder a las filas de un conjunto de datos
> (Tabla, consulta, etc.) en forma **secuencial**, **no pudiendo volver a una fila anterior** una vez
> que se avanza el puntero."*
>
> *"Todo el acceso a cursores en **PL/pgSQL** es a través de variables del tipo cursor, las cuales son
> siempre del tipo de datos especial **`refcursor`**."*

| Propiedad | Consecuencia |
| --- | --- |
| **secuencial** | se ve **una fila por vez**, no el conjunto |
| **sin retroceso** | si hace falta la fila anterior, **hay que guardarla en una variable** |
| **es una variable** | se declara, se abre y **se cierra**; un `SELECT` se autoadministra |

> [!important] (clave) Para qué existe: es el puente entre lo **de conjunto** y lo **procedural**
> SQL trabaja con **conjuntos** (una sentencia, todas las filas, sin orden de proceso); un `IF`, un
> `WHILE` o una variable trabajan con **una cosa por vez**. El cursor traduce el conjunto en una
> secuencia que el código procedural puede recorrer: es el ***impedance mismatch*** de Garcia-Molina
> *(GMUW 9.3.1)*, resuelto dentro del motor en vez de en la aplicación.

## 1 · Declararlo — las tres formas *(slide 9)*

Gramática del slide:

```sql
nombre CURSOR [ ( argumentos ) ] FOR select_query ;
```

Sus tres ejemplos:

```sql
DECLARE
  curs1 refcursor;  (puede utilizarse para cualquier consulta)
  curs2 CURSOR FOR SELECT * from voluntario;  // solo se utiliza con la consulta declarada
  curs3 CURSOR (key int) IS
  SELECT * from voluntario where id_voluntario = key;  // consulta parametrizada, key será
  // reemplazado por un valor de parámetro entero cuando se inicialice el cursor
```

| | Forma | Cuándo | La consulta se fija… |
| :---: | --- | --- | --- |
| **`curs1`** | **genérico** *(unbounded)* — `refcursor` a secas | sirve para **cualquier** consulta | …al **abrirlo** |
| **`curs2`** | **ligado** *(bounded)* — `CURSOR FOR <select>` | solo para **esa** consulta | …al **declararlo** |
| **`curs3`** | **parametrizado** | esa consulta, con **argumentos** que se pasan en el `OPEN` | …al declararlo, con huecos |

> [!bug] (crítico) `curs3 … IS` es Oracle: el slide se contradice dentro del mismo bloque
> La gramática dice **`FOR`** y `curs2` la respeta, pero **`curs3` escribe `IS`**: `CURSOR (…) IS
> SELECT …` es **PL/SQL de Oracle**, no PL/pgSQL — primera filtración de Oracle del deck; la segunda
> es el `months_between(sysdate, …)` del slide 17. No confundir con `%rowtype` / `%type` / `ALIAS FOR`,
> también de linaje Oracle pero que **PL/pgSQL sí tiene** (herencia, no error) →
> [[1.10.02 - Stored procedures y funciones|Stored procedures y funciones]] § 4 · [[PostgreSQL]].

> [!bug] Dos erratas más en el mismo slide, transcritas `[sic]`
> - **`(puede utilizarse para cualquier consulta)`** va pegado a `curs1` **sin `//` ni `--`**: no es
> comentario sino sintaxis, y copiado tal cual no compila.
> - Los otros dos comentarios usan **`//`**, que no es comentario en ningún motor *(va `--`)* — mismo
> tic que el slide 8.

## 2 · Abrirlo, recorrerlo y cerrarlo *(slide 10)*

> [!quote] Textual
> *"Para utilizar un cursor hay que abrirlo, para hacerlo **depende del tipo de cursor**."*
> - **GENERICO** — `OPEN CURSOR FOR SELECT …..` → `OPEN curs1 for select * from Pais;`
> - `OPEN CURSOS FOR EXECUTE ….` → `OPEN curs1 for execute “select * from Pais”;`
> - **Ya Especificado (BOUNDED CURSOR)** → `OPEN curs2;` · `OPEN curs3(4444);`
> - *"Para traer fila a fila se utiliza el **FETCH** y no olvidarse de cerrarlo con un **CLOSE**."*
> → `Fetch curs2 into variable;` · `Close curs2;`
>
> *"Utilizar la variable **FOUND** para ver si trajo una fila o no."*

Los slides 9 y 10 son **un solo ejemplo**: el 9 declara `curs1`, `curs2` y `curs3`, y el 10 los abre en
ese orden — `OPEN curs3(4444);` pasa el argumento `key` declarado en el 9, cerrando el circuito de la
parametrización.

**El ciclo completo, siempre el mismo:**

```
DECLARE  →  OPEN  →  FETCH … INTO  →  (¿FOUND?)  →  … CLOSE
  ↑______________|
```

| Paso | Qué hace | Notas |
| --- | --- | --- |
| **`OPEN`** | ejecuta la consulta y deja el puntero **antes de la primera fila** | genérico: lleva la consulta · bounded: no lleva nada · parametrizado: lleva los argumentos |
| **`FETCH … INTO`** | trae **una** fila y avanza el puntero | necesita **tantas variables como columnas** *(o una `%rowtype`)* |
| **`FOUND`** | booleana de PL/pgSQL: **¿el último `FETCH` trajo fila?** | se consulta **después** del `FETCH` |
| **`CLOSE`** | libera el cursor | *"no olvidarse"*, dice el slide |

> [!note] `OPEN … FOR EXECUTE` es **SQL dinámico**
> La consulta se arma como **texto** en tiempo de ejecución: permite decidir la tabla o el `WHERE`
> con código, y abre la puerta a inyección si se concatena con entrada del usuario. **MySQL no lo
> tiene**: sus *prepared statements* no se pueden abrir como cursor → § 5.

> [!bug] Tres erratas del slide 10, transcritas `[sic]`
> 1. **`OPEN CURSOS FOR EXECUTE`** — *"CURSOS"* por `CURSOR`.
> 2. **`OPEN curs1 for execute “select * from Pais”;`** con **comillas dobles tipográficas**: en
> PostgreSQL las comillas dobles delimitan **identificadores**, no cadenas *(`EXECUTE` espera comilla
> simple)*, y las curvas no las acepta el parser.
> 3. **`GENERICO`** sin tilde.
>
> Además, **`curs1` se abre dos veces**: son **dos alternativas ilustrativas**, no una secuencia — un
> `OPEN` sobre un cursor ya abierto da error en PostgreSQL.

## 3 · El ejemplo completo *(slide 11)*

```sql
CREATE FUNCTION ….
DECLARE
  cursor cur1 for select * from pais;
  mifila pais%rowtype;
  mensaje TEXT DEFAULT 'no hay registros';
Begin
 open cur1;
 fetch cur1 into mifila;

 if FOUND then
  menaje := 'Por lo menos hay un registro'
 end if;

 close cur1;
  Return mensaje;
end
……
```

Enseña el ciclo entero en catorce líneas, el `%rowtype` como destino natural de un `FETCH` *(una
variable en vez de una por columna)* y `FOUND` como la forma de preguntar si había algo.

> [!bug] (crítico) Cuatro errores en catorce líneas — no compila
> 1. **`menaje := …`** [sic] por `mensaje`: la variable de retorno nunca se toca, así que **la función
> devolvería siempre `'no hay registros'`**, incluso con la tabla llena — el error más caro, silencioso
> y con la lógica dada vuelta.
> 2. Esa misma línea no termina en `;`.
> 3. El `end` final va sin `;`.
> 4. (crítico) **La declaración está invertida**: `cursor cur1 for select …`, cuando la gramática del
> slide 9 es `cur1 CURSOR FOR select …`, con el nombre primero.
>
> *(Tampoco lleva `RETURNS` ni `AS $$ … $$ LANGUAGE plpgsql`: pseudocódigo recortado, como el del
> slide 8.)*

> [!warning] Y el ejemplo, aun bien escrito, **es el caso donde un cursor no hace falta**
> Preguntar si una tabla tiene alguna fila sale en una línea:
> ```sql
> SELECT EXISTS (SELECT 1 FROM pais);
> ```
> Sirve como ejemplo mínimo de la mecánica, no como modelo de cuándo usar un cursor → *Cuándo usarlo
> y cuándo no*.

## 4 · El `FOR … IN (SELECT …) LOOP` es un cursor disfrazado

El slide 13 recorre una consulta con `FOR var_r IN (SELECT …) LOOP … END LOOP` sin mencionar
cursores, pero por dentro **es uno**: PL/pgSQL abre un cursor implícito, hace `FETCH` en cada vuelta y
lo cierra al salir *(Garcia-Molina, **GMUW 9.4.6**, recuadro *Why Do We Need Names in For-Loops?*)*.

| | `FOR … IN … LOOP` | Cursor explícito |
| --- | --- | --- |
| Declararlo, abrirlo, cerrarlo | **lo hace el motor** | a mano, y **hay que acordarse del `CLOSE`** |
| Detectar el fin | **implícito**: el bucle termina | a mano, con `FOUND` |
| Control fino *(saltear, mirar dos veces, abrir condicionalmente)* | ✗ | ✓ |
| **En MySQL** | (crítico) **no existe** — hay que escribir el cursor explícito | ✓ existe |

> [!important] (clave) Por esto los cursores importan **para el TP7**
> El deck resuelve los recorridos con `FOR … IN … LOOP`. **MySQL no tiene `FOR`**, así que todo
> recorrido del deck se reescribe como cursor explícito: la traducción más cara de toda la Clase 10 →
> [[1.10.02 - Stored procedures y funciones|Stored procedures y funciones]] § 6.

## 5 · En MySQL

> [!warning] (crítico) De las tres formas de declarar, MySQL tiene **una**
> Un cursor de MySQL **no es un valor**: es una declaración. No se asigna, no se pasa como parámetro,
> no se devuelve, y su consulta se fija en el `DECLARE`.

| Del deck *(PL/pgSQL)* | En **MySQL** |
| --- | --- |
| `curs1 refcursor;` *(genérico)* | ✗ **no existe.** MySQL no tiene variables de tipo cursor |
| `curs2 CURSOR FOR SELECT …;` *(bounded)* | (clave) **`DECLARE curs2 CURSOR FOR SELECT …;`** — **la única línea del bloque que traduce**: solo hay que anteponerle `DECLARE` |
| `curs3 CURSOR (key int) IS SELECT …;` *(parametrizado)* | ✗ **doblemente inválido**: el `IS` es Oracle, y **MySQL no admite cursores con parámetros**. Sustituto: variable local asignada **antes** del `OPEN`, referenciada desde el `SELECT` del cursor |
| `OPEN curs1 for select …;` | ✗ el `OPEN` de MySQL **no lleva consulta** |
| `OPEN curs1 for execute "…";` *(dinámico)* | ✗ **no existe.** Hay `PREPARE`/`EXECUTE`, pero **no se puede abrir un cursor sobre un prepared statement**; y las prepared statements **no se admiten dentro de funciones ni triggers** *(sí en procedimientos)* |
| `OPEN curs3(4444);` | ✗ ver cursor parametrizado |
| `OPEN curs2;` · `FETCH … INTO …;` · `CLOSE curs2;` | ✓ **iguales** *(`FETCH [NEXT] FROM cur INTO …`)*. El `FETCH` necesita **tantas variables como columnas**, y sin `%rowtype` hay que enumerarlas |
| `mifila pais%rowtype;` | ✗ **no existe** → una variable por columna |
| (crítico) **`if FOUND then`** | ✗ **`FOUND` no existe.** El reemplazo **no es una variable sino un handler declarado** *(§ 5.1)* |
| *(ausente en el deck)* | para **DML**, no para `FETCH`, el análogo de `FOUND` es **`ROW_COUNT()`** |

### 5.1 · (clave) `FOUND` → `CONTINUE HANDLER FOR NOT FOUND`, y va **al revés**

```sql
DECLARE done INT DEFAULT 0;
DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1;
-- … y después de cada FETCH:
IF done = 1 THEN LEAVE bucle; END IF;
```

| | PL/pgSQL | MySQL |
| --- | --- | --- |
| Qué es | una **variable** que el motor setea | un **handler**: código que se dispara ante una condición |
| Qué significa `TRUE` | **`FOUND` = "trajo fila"** | **`done` = "se acabó"** |
| Hay que declararlo | no | **sí**, y con nombre propio *(`done` es convención, no palabra reservada)* |

> [!warning] La inversión es la trampa: `FOUND` y `done` significan **lo contrario**
> Traducir `IF FOUND THEN …` a `IF done THEN …` invierte la lógica y **no da error de compilación**:
> equivalente, entre cursores, al `||` que en MySQL es OR y no concatena.

> [!note] El orden de los `DECLARE` en MySQL es **rígido**, y el cursor va tercero
> **variables → *conditions* → cursores → handlers.** Fuera de ese orden el `CREATE` no compila —se
> olvida al traducir porque en PL/pgSQL el `DECLARE` no tiene orden.

### 5.2 · El molde MySQL de un recorrido

```sql
DELIMITER $$

CREATE PROCEDURE recorrer_paises()
BEGIN
  DECLARE done INT DEFAULT 0;  -- 1. variables
  DECLARE v_nombre VARCHAR(50);
  DECLARE cur1 CURSOR FOR SELECT nombre FROM pais;  -- 2. cursores
  DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1;  -- 3. handlers

  OPEN cur1;
  bucle: LOOP
  FETCH cur1 INTO v_nombre;
  IF done = 1 THEN
  LEAVE bucle;
  END IF;
  -- … procesar v_nombre …
  END LOOP;
  CLOSE cur1;
END$$

DELIMITER ;
```

*(Traducción propia del slide 11 más el `FOR … IN … LOOP` del slide 13: la teórica no muestra una sola
línea de MySQL.)*

## 6 · Una segunda traducción independiente llega a la misma estructura

Material complementario de la Clase 10, sin número propio, archivado junto al deck
*(`ejercicio de teoria de PosgreSQL hecho en MySQL.sql`; ver
[[Clase 10 - Restricciones integridad-Parte 2]] § *Material complementario (b)*)*: una segunda
traducción a MySQL de `voluntarioscadax` *(el `FOR`-sobre-resultado del slide 13, § 5.2 arriba)*,
hecha por otra vía y sin relación con la que ya proponía esta página.

| PL/pgSQL — slide 13 | Este archivo de `raw/` | La traducción que ya proponía § 5.2 |
| --- | --- | --- |
| `FOR var_r IN (SELECT …) LOOP` *(implícito)* | `DECLARE cur CURSOR FOR SELECT …;` + `DECLARE CONTINUE HANDLER FOR NOT FOUND SET done = 1;` | idéntico en estructura *(cursor `cur1` + handler `done`)* |
| `var_r record;` | una variable por columna *(`v_nro`, `v_apellido`, `v_nombre`)* | una variable por columna *(`v_nombre`, mismo recurso)* |
| `IF (i % x = 0) THEN … RETURN NEXT; END IF;` | `IF (i % x = 0) THEN INSERT INTO tmp_resultado VALUES (…); END IF;` | mismo reemplazo: `RETURN NEXT` → `INSERT` en tabla temporal |
| `END LOOP; END;` | `CLOSE cur;` + `SELECT * FROM tmp_resultado;` | `CLOSE cur1;` — la tabla temporal hace de valor de retorno |

Las dos llegan, de forma independiente, a la misma estructura canónica —**cursor + `CONTINUE HANDLER
FOR NOT FOUND` + tabla temporal**—, lo que confirma que no es una elección arbitraria entre varias
formas posibles de traducir un `FOR`-sobre-resultado, sino la única forma que MySQL admite.

**Corrida real en MySQL 9.7.2**, con nueve voluntarios de prueba y `x = 3`:

```
nro_voluntario  apellido  nombre
1               Perez     Ana
4               Ruiz      Pedro
7               Ibañez    Noa
```

Confirma **"una de cada tres", empezando por la primera fila** *(`i` arranca en 0, y `0 % 3 = 0`)* —lo
mismo que [[1.10.02 - Stored procedures y funciones|Stored procedures y funciones]] § 5.2 señalaba
como una redundancia inofensiva en el `i := 0` del slide 13: acá queda verificado con datos reales,
no solo razonado.

## Cuándo usarlo y cuándo no

> [!important] (clave) La regla es corta: **un cursor es el último recurso, no el primero**
> Un `UPDATE` que toca mil filas las toca **de una vez**; un cursor que las recorre hace **mil**
> operaciones y le impide al optimizador ver el conjunto. La versión de conjunto es casi siempre más
> corta, más rápida y más fácil de leer.

| Usar un cursor cuando… | **No** usarlo cuando… |
| --- | --- |
| cada fila necesita **una acción distinta**, decidida por su contenido | se puede escribir como **una sentencia de conjunto** — `INSERT … SELECT`, `UPDATE … WHERE`, `GROUP BY` |
| hay que **llamar a un procedimiento** por cada fila | solo hace falta saber **si hay filas** → `EXISTS` *(el ejemplo del slide 11)* |
| el proceso es **fila a fila por naturaleza**: generar un archivo, mandar un aviso, escribir un log | hace falta un **agregado** → `COUNT`, `AVG`, `MAX` lo resuelven solos |
| hay que **comparar una fila con la anterior** y el motor no tiene funciones de ventana | el motor **sí** tiene funciones de ventana |

> [!warning] (crítico) El TP7 pone esta trampa a propósito
> El ejercicio **4.a** pide *"el medio más apropiado"* para la **carga inicial** de una tabla derivada,
> **en un TP de SQL procedural**. La respuesta correcta es **declarativa**:
> `INSERT INTO … SELECT … GROUP BY …`, una sola sentencia. Que la respuesta sea declarativa **es el
> punto del ejercicio**. → [[Práctica 2026-09-01]]

## Cuadro de bolsillo

| Pregunta | Respuesta |
| --- | --- |
| ¿Qué es un cursor? | una **variable** que recorre un conjunto **secuencialmente y sin volver atrás** |
| El ciclo | **`DECLARE` → `OPEN` → `FETCH … INTO` → `CLOSE`** |
| Las tres formas de declararlo | **genérico** *(`refcursor`)* · **ligado** *(bounded)* · **parametrizado** |
| ¿Cuándo se fija la consulta? | genérico: al **abrirlo** · bounded y parametrizado: al **declararlo** |
| ¿Cómo se sabe si trajo fila? | PL/pgSQL: **`FOUND`** · MySQL: **`CONTINUE HANDLER FOR NOT FOUND`**, y significa **lo contrario** |
| ¿Qué tipo es un cursor en PL/pgSQL? | siempre **`refcursor`** |
| ¿`FOR … IN (SELECT …) LOOP` usa cursor? | **sí, uno implícito** — y **MySQL no tiene `FOR`** |
| Lo que MySQL **no** tiene | `refcursor` · cursores parametrizados · `OPEN … FOR` · `OPEN … FOR EXECUTE` · `FOUND` · `%rowtype` |
| ¿Cuándo usarlo? | **último recurso**: cuando cada fila necesita una acción distinta |
