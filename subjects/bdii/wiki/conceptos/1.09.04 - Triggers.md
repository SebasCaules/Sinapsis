## Qué es: una regla **evento-condición-acción**

> [!quote] Slide 26
> *"pieza de código (**no declarativo**) almacenada que "se dispara" automáticamente ante la
> ocurrencia de un evento sobre la base de datos"* · *"Puede considerarse una regla
> **evento-condición-acción (ECA)**"*

| | Definición del deck |
| --- | --- |
| **Evento** | *"sentencia o situación que dispara su ejecución"* |
| **Condición** | *"expresión booleana que debe evaluar en VERDADERO para que el trigger se active. Si evalúa en FALSO o DESCONOCIDO **no se ejecuta**. **Solo para Triggers a nivel fila**"* |
| **Acción** | *"procedimiento que contiene las sentencias SQL a ser ejecutadas"* |

### La otra definición: **por quién lo invoca** *(slide 3 de la Clase 10)*

> [!quote] Clase 10, slide 3 — las dos mitades del contraste
> - *"**Trigger**: Es un procedimiento que es invocado **automáticamente por el DBMS** en respuesta a
>   un evento **especifico** de la BD."* [sic: *"especifico"* sin tilde]
> - *"**Stored Procedure**: Es un procedimiento que es invocado **explícitamente por el usuario**."*

> [!important] 🎯 Las dos definiciones son complementarias, y conviene tener las dos
> | | Qué dice | De qué sirve |
> | --- | --- | --- |
> | **ECA** *(deck 09, slide 26)* | de qué **está hecho**: evento + condición + acción | descomponerlo para escribirlo |
> | **por invocación** *(deck 10, slide 3)* | cuándo **aparece**: lo llama el motor, no el usuario | **decidir si el problema es de trigger** |
>
> La segunda es la operativa: **si hace falta que corra solo ante un evento, es un trigger; si hace
> falta control de flujo, es un procedimiento** *(deck 10, slide 5)*. El trigger es el único de los
> tres elementos de [[1.10.01 - SQL procedural|SQL procedural]] que **nadie llama**.

> [!important] La regla de `NULL` acá es **la opuesta** a la de los `CHECK`
> | Cláusula | `TRUE` | `FALSE` | `UNKNOWN` |
> | --- | :---: | :---: | :---: |
> | `CHECK` | acepta | rechaza | **acepta** |
> | `WHEN` de un trigger | dispara | no dispara | **no dispara** |
>
> La misma expresión booleana con el mismo `NULL` adentro, comportándose al revés en dos cláusulas del
> mismo deck. Es exactamente el tipo de detalle que se pregunta.

## Sintaxis — la del deck es **PostgreSQL**

> [!warning] El slide 27 se titula literalmente ***"TRIGGERS – SINTAXIS PostgreSQL"***
> No hay ambigüedad: lo que sigue no es SQL estándar ni MySQL.

```sql
CREATE [ CONSTRAINT ] TRIGGER nombre_del_trigger
{ BEFORE | AFTER | INSTEAD OF }                       -- tiempo de activación
{ INSERT [ OR ] UPDATE [ OF nombre_columna [, ... ] ] -- EVENTO
   [ OR ] DELETE [ OR ] TRUNCATE }
   ON nombre_tabla_o_vista
   [ FOR [ EACH ] { ROW | STATEMENT } ]               -- granularidad
   [ WHEN ( condición ) ]                             -- CONDICIÓN
   EXECUTE PROCEDURE nombre_función;                  -- ACCIÓN
```

`DROP TRIGGER <nombre>` para eliminarlo. *(El slide dice que la función *"debe ser de tipo
**ttrigger**"* — es un tipeo por `trigger`.)*

### Tiempo de activación *(slide 28)*

| | Cuándo corre | Para qué se usa |
| --- | --- | --- |
| **`BEFORE`** | *"antes de la sentencia disparadora"* | **validar o corregir** el valor antes de escribirlo. Es el único que puede modificar `NEW` y abortar limpiamente |
| **`AFTER`** | *"después de la sentencia disparadora"* | **propagar**: contadores, logs, otras tablas. Los datos ya están escritos y validados |
| **`INSTEAD OF`** | *"en lugar de la sentencia disparadora"* | **solo sobre vistas**: hacer escribible una vista no actualizable → [[1.06.01 - Vistas\|Vistas]] |

### Granularidad *(slide 29)*

| | Qué hace |
| --- | --- |
| **`FOR EACH ROW`** | *"se ejecuta una vez por cada fila afectada"* |
| **`FOR EACH STATEMENT`** | *"se ejecuta una vez para la sentencia SQL disparadora, independientemente de la cantidad de filas"* |

> [!warning] **El default es `FOR EACH STATEMENT`**, y sorprende
> Casi todo el mundo escribe triggers `FOR EACH ROW`, así que el default del estándar es
> contraintuitivo — y es lo que se pregunta. **En MySQL `FOR EACH ROW` es obligatorio** y no hay
> statement-level.
>
> Se conecta con el slide 26: la condición `WHEN` es *"solo para triggers a nivel fila"*, o sea que el
> trigger del default es justamente el que **no puede tener condición**.

### Referencias a los valores *(slide 30)*

| Evento | valor viejo | valor nuevo |
| --- | :---: | :---: |
| `INSERT` | ❌ | ✅ |
| `UPDATE` | ✅ | ✅ |
| `DELETE` | ✅ | ❌ |

### La acción *(slide 31)*

> [!quote] Textual
> - *"una sentencia SQL aislada o un conjunto de sentencias, delimitadas en un bloque `BEGIN … END`"*
> - *"Pueden incluir **sentencias de control** (`IF … ELSE`, `FOR`, `WHILE`, …)"*
> - *"**No pueden incluir sentencias del DDL** (`CREATE`, `ALTER`, `DROP`)"*
> - *"Un trigger `BEFORE` **no debería** contener sentencias SQL que alteren datos … esto puede
>   disparar otros triggers BEFORE (sus acciones van quedando pendientes)"*
> - *"La acción del trigger es un **procedimiento atómico** → si cualquier sentencia del cuerpo falla,
>   la acción completa se deshace, **incluyendo las correspondientes a la sentencia que lo disparó**"*

> [!important] La atomicidad es lo que hace usable un trigger **como RI**
> **Si el trigger falla, se deshace todo — incluida la sentencia original.** Sin esa garantía, un
> trigger no serviría para forzar una restricción: podría rechazar a medias y dejar la base
> inconsistente. Es la **A de ACID** aplicada al par (sentencia, trigger).
>
> Y es lo que habilita el patrón *"rechazo"*: el trigger llama a algo que **falla a propósito** y con
> eso aborta la operación entera.
> - PL/pgSQL: `RAISE EXCEPTION`
> - MySQL: **`SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '…'`**

> [!note] *"Pueden incluir sentencias de control"* **es** la diferencia declarativo/procedural
> Un `CHECK` es una **expresión booleana**: no tiene `IF`, ni bucles, ni orden de ejecución. Un trigger
> es **código**. Ésa es toda la bifurcación del slide 4 —*"Declarativa o Procedural"*— y también por
> qué el slide 37 dice que hay que preferir lo declarativo: el `CHECK` es analizable por el motor, el
> trigger es una caja negra.

### Cascadas *(slide 32)*

> [!quote] Textual
> *"Ante un cierto evento sobre una tabla → **pueden activarse varios triggers**!"* ·
> *"Si la activación de un trigger T1 dispara otro trigger T2: **se suspende** la ejecución de T1, se
> ejecuta el trigger anidado T2 y luego **se retoma** T1"* → *"esto podría dar lugar a una cadena
> "**infinita**" de activaciones!"* · *"Los DBMS suelen **limitar la longitud** de las cadenas"*

> [!note] Es una **pila** (LIFO), igual que las llamadas a función
> Y MySQL agrega una restricción que el deck no menciona: **un trigger no puede modificar una tabla que
> ya está siendo usada por la sentencia que lo invocó** *(error 1442)*. Impide el caso más obvio de
> recursión — y también muchos triggers legítimos.

> [!warning] El ejemplo del slide 32 es **el que el slide 31 dice que no hay que escribir**
> El 31 desaconseja que un `BEFORE` altere datos; el 32 muestra un `BEFORE UPDATE` que hace `INSERT` y
> dispara otro `BEFORE INSERT`. **No es contradicción: el 32 muestra *por qué* el 31 lo desaconseja.**
> Pero leídos sueltos parecen decir lo contrario, así que conviene tenerlos juntos.

## Los dos ejemplos del deck

### Forzar una RI de transición *(slide 34)*

*"Verificar que el sueldo de un empleado no se reduzca"*:

```sql
CREATE TRIGGER sueldo_no_se_reduce
  BEFORE UPDATE OF sueldo ON Empleado
  FOR EACH ROW
  WHEN (:old.sueldo > :new.sueldo)     -- ⚠️ en PostgreSQL: (OLD.sueldo > NEW.sueldo)
  EXECUTE PROCEDURE funcion_error();
```

Y la plantilla que da el mismo slide:

```sql
create trigger <nombre>
before <operación crítica sobre la BD>
when <condición por la que una RI es incumplida>
< acción(es) del trigger >   -- → rechazo (acción pasiva) / reparación (acción activa)
```

> [!important] **Es el ejemplo canónico de RI de transición de estados**
> Compara `:old` contra `:new` — ningún `CHECK` puede hacer eso. Cierra el arco que abrió el slide 2
> con *"un voluntario puede cambiar de tarea solamente dos veces al año"*.
>
> Y la distinción **acción pasiva** *(rechazo)* vs. **acción activa** *(reparación)* de la plantilla es
> la misma que la de las acciones referenciales del slide 9. El vocabulario se repite a propósito.

### Mantener un dato derivado *(slides 35–36)*

```sql
CREATE TRIGGER Incrementar_EmpArea
AFTER INSERT OR UPDATE OF AreaT OR DELETE ON Empleado
FOR EACH ROW
EXECUTE PROCEDURE cant_total_empleados();
```

```sql
CREATE FUNCTION cant_total_empleados ( )
RETURNS trigger AS $body$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE area set CantEmp = CantEmp + 1 where IdArea = new.AreaT;
        RETURN NEW;
    END IF;
    IF TG_OP = 'UPDATE' THEN
        UPDATE area set CantEmp = CantEmp - 1 where IdArea = old.AreaT;
        UPDATE area set CantEmp = CantEmp + 1 where IdArea = new.AreaT;
        RETURN NEW;
    END IF;
    IF TG_OP = 'DELETE' THEN
        UPDATE area set CantEmp = CantEmp - 1 where IdArea = old.AreaT;
        RETURN OLD;
    END IF;
END; $body$
LANGUAGE 'plpgsql'
```

Cuatro cosas que enseña y el slide no comenta:

| | |
| --- | --- |
| **`TG_OP`** | variable de PL/pgSQL con el evento que disparó. Permite **un solo trigger para los tres eventos**. En MySQL, donde cada evento necesita su propio trigger, no existe ni hace falta |
| **`RETURN NEW` / `RETURN OLD`** | una función trigger de PostgreSQL **tiene que devolver algo**. En un `AFTER` se ignora; en un `BEFORE ROW`, devolver `NULL` **cancela la operación** |
| **`AFTER`, no `BEFORE`** | correcto: se cuenta lo que **ya** pasó. Con `BEFORE` el contador se adelantaría a una operación que las RI declarativas todavía podrían rechazar *(slide 38, paso 2b)* |
| **el contador es dato derivado** | o sea **redundancia deliberada**: se acepta a cambio de no recontar. Es el mismo trade-off que la **vista materializada**, hecho a mano |

> [!bug] El ejemplo tiene dos bugs *(razonamiento propio; el slide lo da como correcto)*
> 1. **No maneja `NULL` en `AreaT`.** `where IdArea = NULL` no matchea nada y el contador queda
>    desfasado en silencio. Y el DER del slide 11 dice `(0,1)`: `AreaT` **puede** ser nulo.
> 2. **No hay `RETURN` fuera de los tres `IF`.** Si `TG_OP` fuera otra cosa, la función termina sin
>    `RETURN` y PL/pgSQL da error en ejecución.
>
> Además, el `UPDATE` **resta y suma sin chequear si `old.AreaT = new.AreaT`**: si el área no cambió,
> resta y suma sobre la misma fila. Funciona por casualidad, no por diseño.

## 🎯 Triggers **no** son restricciones de integridad

> [!quote] Slide 37 — las tres frases más importantes del bloque
> - *"Triggers → permiten definir y forzar reglas de integridad, pero **NO son una restricción de
>   integridad**"*
> - *"Un trigger definido para forzar una RI **no verifica su cumplimiento para los datos ya
>   almacenados** en la BD (una RI declarativa verifica la carga existente en la BD)"*
> - *"Los triggers **deberían usarse sólo cuando una RI no puede ser expresada mediante una cláusula
>   declarativa**"*

> [!success] 🎯 **La Clase 10 repite la tercera frase tres veces, con énfasis creciente** — es la mejor cita disponible
> Es lo **único** que el deck 10 repite del bloque 25–38 de la Clase 09, y no lo repite una vez: lo
> martilla en los tres primeros niveles de restricción.
>
> | Slide | Nivel | Textual |
> | :---: | --- | --- |
> | **14** | atributo | *"Esto por supuesto que puede ser controlado con triggers, pero **lo más correcto es controlarlo con un constraint**."* |
> | **15** | fila | *"Esto por supuesto también puede ser controlado por Triggers, pero **sigue siendo lo más correcto** controlarlo con un constraint."* |
> | **17** | tabla | *"Esto por supuesto también puede ser controlado por triggers, **PERO SIGUE SIENDO** lo más correcto controlarlo con un constraint."* |
>
> Si hay que citar una sola cosa en el parcial sobre trigger vs. constraint, es ésta: **dos decks
> distintos, cuatro enunciados, la misma doctrina.** El deck 10 lo dice, además, **sin haber enseñado
> un solo `CREATE TRIGGER`** — o sea que no está vendiendo la herramienta que acaba de mostrar: está
> diciendo que no se use.

> [!important] 🔴 Pero en el nivel 3 la escalera **se rompe**, y ahí el trigger deja de ser opcional
> El propio slide 17 se contesta a sí mismo dos renglones después: *"**Postgres NO implementa este tipo
> de checks**, Postgres no permite un select dentro de un constraint…. ☹ Entonces….. Lamentablemente
> se tendrá que pensar…. se deberá analizar **ante qué eventos y en qué tiempo** se debe disparar él o
> los triggers asociados a EMPLEADO"*.
>
> Y en el nivel 4 se rompe del todo *(slide 18)*: *"Ninguna base de datos comercial implementa
> Assertions. **Se deberá controlar la restricción con triggers en varias tablas**"*.
>
> **La doctrina y la realidad se separan exactamente entre el nivel tupla y el nivel tabla** — el mismo
> corte de [[1.09.03 - CHECK, DOMAIN y ASSERTION|CHECK, DOMAIN y ASSERTION]] § *En MySQL*, y **no es
> un corte de MySQL: es de todos los motores.**

> [!quote] 🎯 Y el slide 19 da el argumento que faltaba: **por qué un trigger no alcanza**
> *"Se deben generar triggers en **DEPARTAMENTO y en EMPLEADO** para que controlen esta restricción, ya
> que si sólo se hiciera sólo en una, por ejemplo EMPLEADO, **uno podría cambiar el jefe en la tabla de
> DEPARTAMENTO y el trigger en Empleado no se despertaría**."* [sic: *"si sólo se hiciera sólo"*]
>
> *"Claramente se deberá analizar la **granularidad, eventos y tiempo de activación** de cada trigger
> involucrado."*
>
> Hasta acá, que una `ASSERTION` se convierta en *varios* triggers era **razonamiento propio** del
> vault. **Ahora tiene el porqué, con contraejemplo concreto:** una restricción que cruza tablas se
> puede violar **por cualquiera de las tablas**, y un trigger solo ve la suya. Es también el cierre
> conceptual de la clase, y reusa los tres ejes de diseño de arriba —**granularidad, eventos, tiempo
> de activación**— dándolos por sabidos.

> [!important] La segunda es la que más se cobra en la práctica
> `ALTER TABLE … ADD CONSTRAINT CHECK (…)` **valida las filas que ya están**: si alguna no cumple, el
> `ALTER` **falla**. `CREATE TRIGGER` **no mira nada** de lo ya cargado: empieza a actuar recién en la
> próxima operación.
>
> Consecuencia: **una base "protegida" solo por triggers puede tener datos que violan la regla**, y
> nadie se entera. Migrar una RI a trigger deja la validación del histórico como un paso **aparte y
> manual**.
>
> Y esto es lo que hace caro el ejercicio 3.c del TP6: en MySQL, todo lo de ámbito **tabla** y **base
> de datos** va a trigger — y **pierde la validación del histórico**. No es una traducción
> equivalente: **es una degradación**, y hay que decirlo al entregar.

| | RI declarativa | Trigger |
| --- | --- | --- |
| Valida los datos **ya cargados** | ✅ al crearla | ❌ nunca |
| El motor la **entiende** | ✅ puede usarla para optimizar | ❌ caja negra |
| Cantidad de piezas | **una** | **una por evento y por tabla** |
| Expresa RI de **transición** | ❌ | ✅ *(lo único que puede)* |
| Acciones distintas del rechazo | ❌ | ✅ |

## El modelo de ejecución SQL-99 *(slide 38)*

Del paper *"Semantic Integrity Support in SQL-99 and Commercial (Object-)Relational Database
Management Systems"*, de **Türker y Gertz**:

```
                    SQL-Statement
                          │
         ┌────────────────▼─────────────────┐
         │  Determine Set of Affected Rows  │
         └────────────────┬─────────────────┘
         ┌────────────────▼─────────────────┐
         │  Execute BEFORE Triggers         │──▶ Error
         └────────────────┬─────────────────┘
  ╔═══════════════════════▼══════════════════════╗
  ║  Enforcement of Declarative Constraints      ║
  ║   1. Apply RESTRICT Rules              ──────╫──▶ Error
  ║   2. Apply CASCADE, SET NULL,                ║
  ║      SET DEFAULT Rules                 ──────╫──▶ Error
  ║   3. Apply NO ACTION Rules                   ║
  ║      and Evaluate Constraints          ──────╫──▶ Error
  ╚═══════════════════════▼══════════════════════╝
         ┌──────────────────────────────────┐
         │  Execute AFTER Trigger           │──▶ Error
         └──────────────────────────────────┘
```

Y los pasos en castellano, textuales:

> 1. *"Ejecuta todos los triggers **BEFORE-statement**"*
> 2. *"Realiza un ciclo por todas las filas afectadas por la sentencia SQL"*
>    a. *"Ejecuta todos los triggers **BEFORE-row**"*
>    b. *"Bloquea y actualiza cada fila y ejecuta los chequeos de integridad declarat. (**El bloqueo no
>       se levanta hasta el final de la transacción**)"*
>    c. *"Ejecuta todos los triggers **AFTER-row**"*
> 3. *"Completa las acciones correspondientes a la **verificación diferida** de integridad expresada
>    declarativamente"*
> 4. *"Ejecuta todos los triggers **AFTER-statement**"*

> [!important] 🎯 Este slide contesta tres preguntas que quedaron abiertas antes
> 1. **Por qué `RESTRICT` ≠ `NO ACTION`** *(slide 9)*. Están en cajas distintas: `RESTRICT` va
>    **primero**, antes de las reparaciones; `NO ACTION` va **último**, junto con *"Evaluate
>    Constraints"*. → [[1.09.02 - Integridad referencial y acciones referenciales|Integridad referencial]]
> 2. **Por qué un `BEFORE` no debería alterar datos** *(slide 31)*. Corre **antes** de los chequeos
>    declarativos: lo que escriba puede terminar deshecho.
> 3. **Por qué el contador del slide 35 va en un `AFTER`.** El `AFTER-row` corre en 2c, **después** de
>    que la fila fue escrita y validada.
>
> Y agrega una cuarta: **el bloqueo se toma en 2b y no se suelta hasta el `COMMIT`**. Eso es
> concurrencia — tema del programa que todavía no se dictó.

> [!warning] La Clase 10 le pone un matiz importante: **este modelo es normativo, no descriptivo**
> El slide 2 del deck 10 dice, sobre las extensiones procedurales del estándar: *"El SQL-1999
> incorporó estas características, pero **poco de lo definido anteriormente se ajustaba a un
> estándar**"*, y remata la lista de flujo de control con *"(**consultar manual del DBMS**)"*.
>
> Aplicado acá: el diagrama de Türker y Gertz describe **lo que SQL-99 manda**, no lo que hace ningún
> motor concreto. **MySQL, por ejemplo, no tiene los pasos 1, 3 y 4** —no hay triggers de sentencia ni
> chequeo diferido—, así que su modelo real es el 2 solo. Sirve para **entender el orden de las
> cosas** y para responder por qué un `AFTER` va después de los chequeos; **no** para predecir qué
> hace la base de la cursada. → [[1.10.01 - SQL procedural|SQL procedural]] § *Las extensiones
> procedimentales*

## En MySQL

| Del deck *(PostgreSQL / SQL-99)* | En [[MySQL]] |
| --- | --- |
| `INSTEAD OF` | ❌ solo `BEFORE` / `AFTER` |
| `INSERT OR UPDATE OR DELETE` combinados | ❌ **un evento por trigger** |
| `UPDATE OF columna` | ❌ → chequear a mano con `IF NEW.c <> OLD.c` |
| `TRUNCATE` como evento | ❌ |
| `FOR EACH STATEMENT` | ❌ **solo `FOR EACH ROW`**, y es obligatorio |
| `WHEN (condición)` | ❌ → un `IF` adentro del cuerpo |
| `EXECUTE PROCEDURE fn()` | ❌ el cuerpo va **inline**, entre `BEGIN … END` |
| trigger `ON` una **vista** | ❌ **solo sobre tablas** |
| `:new` / `:old` | `NEW.col` / `OLD.col`, **sin dos puntos** |
| `TG_OP` | ❌ no existe *(no hace falta: un trigger por evento)* |
| `RAISE EXCEPTION` | **`SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '…'`** |
| pasos 1, 3 y 4 del slide 38 | ❌ no hay triggers de sentencia ni **chequeo diferido** |

> [!note] De ocho cláusulas del slide 27, **MySQL no tiene ninguna igual**
> Es la tabla de traducción más densa del vault. La forma MySQL de un trigger de integridad:
>
> ```sql
> DELIMITER $$
> CREATE TRIGGER tr_nombre
> BEFORE INSERT ON tabla
> FOR EACH ROW
> BEGIN
>     IF <condición de violación> THEN
>         SIGNAL SQLSTATE '45000'
>           SET MESSAGE_TEXT = 'mensaje de error';
>     END IF;
> END$$
> DELIMITER ;
> ```
>
> El `DELIMITER` hace falta porque el cuerpo tiene `;` adentro. Y hay que escribir **uno por evento**:
> `BEFORE INSERT` y `BEFORE UPDATE` como mínimo.
> *(Razonamiento propio: la teórica no muestra sintaxis de MySQL.)*

## Cuadro de bolsillo

| Pregunta | Respuesta |
| --- | --- |
| ¿Qué es un trigger? | regla **evento-condición-acción**, código **no declarativo**, persistente |
| Los tres tiempos | `BEFORE` *(validar)* · `AFTER` *(propagar)* · `INSTEAD OF` *(solo vistas)* |
| Granularidad, y default | `FOR EACH ROW` · `FOR EACH STATEMENT` — **default: STATEMENT** |
| ¿La condición `WHEN` con `NULL`? | **no dispara** — al revés que un `CHECK` |
| ¿Un `BEFORE` puede alterar datos? | *"no debería"* — corre antes de los chequeos declarativos |
| ¿Qué pasa si el trigger falla? | **se deshace todo**, incluida la sentencia que lo disparó |
| Cascadas | pila LIFO; los motores **limitan la profundidad** |
| ¿Trigger = RI? | **No.** Y **no valida los datos ya cargados** |
| ¿Cuándo usarlo? | **solo** cuando la RI no se puede expresar declarativamente *(slide 37 · y los slides 14, 15 y 17 de la Clase 10, tres veces más)* |
| Lo único que **solo** un trigger puede | las **RI de transición de estados** |
| ¿Trigger o procedimiento? | **evento → trigger · control de flujo → procedimiento** *(Clase 10, slide 5)* |
| ¿Por qué una `ASSERTION` son varios triggers? | porque la restricción **se puede violar por cualquiera de las tablas** *(Clase 10, slide 19)* |
| En MySQL | un evento por trigger · solo `FOR EACH ROW` · sin `WHEN` · cuerpo inline · `SIGNAL` |
