# CQL y modelado orientado a consultas

## Resumen general

CQL (*Cassandra Query Language*) es el lenguaje de Cassandra: se parece a SQL (`CREATE TABLE`,
`INSERT`, `SELECT … WHERE`), pero es **un derivado reducido** (slide 13): no tiene *joins* ni
subconsultas, no acepta `OR`, y el `WHERE` y el `ORDER BY` dependen de cómo se definió la clave de
la tabla. Esa reducción obliga a **modelar al revés** que en relacional: se parte de **las consultas
que va a hacer la aplicación** y se diseña **una tabla por consulta**, con los datos
**desnormalizados** (copiados donde se los necesita). La página cubre los slides 13–20, 48–49, 62 y
72–74 de la [[Clase 15 - Introduccion a Cassandra|Clase 15]] y el TP10.

Las tres reglas del slide 16, en rojo en el deck: guiarse por el **patrón de acceso a los datos**;
**definir bien la clave de partición**, porque reparte los datos y puede crear cuellos de botella; y
**minimizar las particiones** que lee una consulta. El resto de CQL se entiende desde ahí: el índice
secundario es una tabla oculta para consultar por otra columna, la vista materializada es una tabla
desnormalizada que mantiene el motor (deshabilitada en Cassandra 5.0), y las agregaciones corren
bien dentro de una partición y mal sobre toda la tabla, que es lo que advierte el slide 6.

Para el parcial: saber por qué no hay *joins* y qué se hace en su lugar, diseñar una tabla a partir de
una consulta (los finales piden *rankings* de un videojuego y promedios de sensores; el Recuperatorio
1Q2026 descartó Cassandra para una tabla de posiciones), y reconocer las sintaxis del deck que ya no
corren tal cual. La clave primaria y `ALLOW FILTERING` están en
[[3.15.06 - Clave primaria en Cassandra — partition key, clustering key y ALLOW FILTERING|Clave primaria en Cassandra]].

## Qué es

> [!quote] Slide 13 — *"Lenguaje CQL"*, textual
> *"Cassandra Query Language (CQL) es el lenguaje de acceso a datos en Cassandra, es un derivado
> reducido de SQL"* · *"En Cassandra los datos están desnormalizados de manera que el concepto de
> joins o subqueries no existe"* · *"Podemos interactuar con Cassandra mediante CQL a través de la
> shell. de CQL, cqlshell **[sic]**"* · *"También podemos usar herramientas gráficas como DevCenter o a
> través de los drivers soportados para múltiples lenguajes de programación"*

| Fuente | Qué dice de CQL |
| --- | --- |
| Corbellini § 5.2 *(p. 13)* | *"Regarding querying, Cassandra offers a SQL-Like query language called CQL (Cassandra Query Language)"* |
| Documentación oficial, *Overview* | *"an SQL-like language, to create, modify, and delete database schema, as well as access data"*; y *"Cassandra explicitly chooses not to implement operations that require cross-partition coordination as they are typically slow and hard to provide highly available global semantics"*: no hay transacciones entre particiones, *"Distributed joins"* ni *"Foreign keys or referential integrity"* |
| Documentación oficial, *Dynamo* § *Simple Query Model* | *"Cassandra chooses to offer fast, consistent, latency at any scale for single partition operations"* |

La shell se llama **`cqlsh`** (el slide dice *"cqlshell"*); el TP10 usa además DataGrip, y DevCenter no
se verificó → [[Cassandra|Cassandra]] § *`cqlsh` — comandos útiles*.

> [!important] (clave) La regla detrás de todo el capítulo: **una consulta, una partición**
> Cassandra es rápida cuando la consulta lleva la **clave de partición** completa: el coordinador
> calcula el token y va derecho a las réplicas
> ([[3.15.02 - Arquitectura de Cassandra — anillo peer-to-peer, particionado y replicación|Arquitectura de Cassandra]] § 6).
> Todo lo que CQL no tiene —*joins*, subconsultas, `OR`, `ORDER BY` libre— son operaciones que
> obligarían a **cruzar particiones** en nodos distintos. En vez de ofrecerlas lentas, no las ofrece.

## 1 · Lo que CQL no tiene, verificado *(slides 13, 18–19, 67)*

Todo corrido en Cassandra 5.0.9 (keyspace `c15conceptosa`), con dos tablas del estilo del TP10:
`canciones (id int PRIMARY KEY, titulo text, artista text)` y `listas (lista int, nro int, cancion_id
int, titulo text, artista text, PRIMARY KEY (lista, nro))`.

| Lo que se intenta | Resultado en 5.0.9 | Qué se hace en su lugar |
| --- | --- | --- |
| `SELECT * FROM listas JOIN canciones ON listas.cancion_id = canciones.id;` | `SyntaxException: line 1:21 no viable alternative at input 'JOIN'` | **desnormalizar**: `listas` ya copia `titulo` y `artista` (§ 2) |
| `… WHERE cancion_id IN (SELECT id FROM canciones WHERE …);` | `SyntaxException: … mismatched input 'SELECT' expecting ')'` | dos consultas desde la aplicación, o una tabla por la segunda clave |
| `… WHERE lista = 10 OR lista = 11;` | `SyntaxException: … no viable alternative at input 'OR'` | `WHERE lista IN (10, 11)` → corre |
| `… WHERE titulo = 'Asilo (en vivo)' OR titulo = 'Todo se transforma';` *(con índice SAI sobre `titulo`)* | la misma `SyntaxException` en `'OR'` | una consulta por valor |
| `… WHERE titulo LIKE 'As%';` | `LIKE restriction is only supported on properly indexed columns. titulo LIKE 'As%' is not valid.` — **también con** el índice SAI sobre `titulo` | precalcular (p. ej., una columna o tabla con el prefijo); el índice SASI viene deshabilitado (`sasi_indexes_enabled: false`, [[Cassandra\|Cassandra]]) y no se probó |
| `SELECT artista, COUNT(*) FROM canciones GROUP BY artista;` | `Group by is currently only supported on the columns of the PRIMARY KEY, got artista` | una tabla con `artista` en la clave (§ 3) |
| `SELECT … FROM puntaje_por_usuario ORDER BY score DESC LIMIT 3;` | `ORDER BY is only supported when the partition key is restricted by an EQ or an IN.` | una tabla ordenada por `score` como *clustering* (§ 4.1) |
| `SELECT * FROM canciones WHERE artista = 'Jorge Drexler';` *(sin índice)* | `Cannot execute this query as it might involve data filtering … use ALLOW FILTERING` | índice, otra tabla, o `ALLOW FILTERING` → [[3.15.06 - Clave primaria en Cassandra — partition key, clustering key y ALLOW FILTERING\|Clave primaria en Cassandra]] |

Por qué el *join* distribuido es caro lo explica la bibliografía relacional: con las dos relaciones en
nodos distintos, hay que **mandar una de ellas por la red** (GMUW cap. 20.4.1 *The Distributed Join
Problem*, impresa 1000). Cassandra elige no hacerlo nunca.

### 1.1 · Lo que CQL hace distinto de SQL

| | SQL (MySQL) | CQL (Cassandra 5.0.9) |
| --- | --- | --- |
| `INSERT` sobre una clave que existe | error de clave duplicada | **la actualiza** (*upsert*): `INSERT … VALUES (1, 'Asilo (en vivo)', …)` sobre `id = 1` deja el título nuevo, sin aviso |
| `UPDATE` sobre una clave que no existe | 0 filas afectadas | **crea la fila**: `UPDATE canciones SET titulo = 'Todo se transforma' WHERE id = 2` dejó `2 \| null \| Todo se transforma` |
| Verificar si existe | `INSERT` normal | `INSERT … IF NOT EXISTS` → `[applied] False` y la fila actual; usa Paxos y cuesta *"a non-negligible performance cost"* (documentación, *Data Manipulation*) |
| Claves foráneas | `FOREIGN KEY`, acciones referenciales | **no existen**; `DELETE` en cascada tampoco |

La documentación lo dice sin rodeos: *"Unlike in SQL, INSERT does not check the prior existence of
the row by default. The row is created if none existed before, and updated otherwise."* Los `INSERT`
del TP10 (pasos 4, 6 y 7) y el `UPDATE` del paso 13 se leen con esta semántica →
[[Práctica 2026-09-29|Práctica 2026-09-29]].

### 1.2 · El *"Ejemplo de CQL"* del slide 20, en el motor

El slide encadena las cuatro sentencias básicas: `CREATE KEYSPACE MiEspacioClaves WITH REPLICATION =
{ 'class' : 'SimpleStrategy', 'replication_factor' : 3 };`, `USE MiEspacioClaves;`, `CREATE
COLUMNFAMILY MisColumnas (id text, Apellido text, Nombre text, PRIMARY KEY(id));` y un `INSERT` de
`('1', 'Perez', 'Juan')`, con el resultado `id | nombre | apellido` · `(1 fila)`. En 5.0.9 todo corre
(el *keyspace* con el aviso `Your replication factor 3 … is higher than the number of nodes 1`), pero
la salida real es otra:

```text
 id | apellido | nombre
----+----------+--------
  1 |    Perez |   Juan

(1 rows)
```

Los identificadores sin comillas dobles pasan a **minúsculas**, y `SELECT *` devuelve primero la clave
de partición y después las demás columnas **en orden alfabético**, no en el orden del `CREATE` (una
tabla `(id int PRIMARY KEY, zeta text, alfa text, medio text)` sale `id | alfa | medio | zeta`) →
[[Clase 15 - Introduccion a Cassandra|Clase 15]] § *Lo que el deck dice…*, fila 1.

## 2 · Desnormalizar: la respuesta a la falta de *joins* *(slides 13, 17–19)*

> [!quote] Slide 19 — *"Cuándo Cassandra es la mejor solución (cont.)"*, textual
> *"Es cierto que quizás la parte más compleja de la adopción de esta base de datos sea cambiar la forma
> de pensar a la hora de diseñar el modelo, pues éste se debe basar en las consultas que haremos en la
> aplicación, y no en la relación de datos entre sí"* · *"Recuerda, en Cassandra no existen los JOIN
> entre tablas"*

La misma decisión ya apareció en MongoDB: **embeber** (copiar) o **referenciar** →
[[2.13.01 - Documentos embebidos vs. referencias|Documentos embebidos vs. referencias]]. Corbellini
la formula para todo NoSQL: el desarrollador *"must decide whether to perform joins at the
application level or, alternatively, denormalize data"* (§ 1, p. 2). En Cassandra la documentación
elige: *"create a denormalized second table that represents the join results for you. This latter
option is preferred in Cassandra data modeling. Performing joins on the client should be a very rare
case"* (*Data Modeling › RDBMS design* § *No joins*).

El TP10 es el ejemplo de la cursada: *"en Cassandra se deben desnormalizar los datos porque los joins
no son soportados"*, y la tabla `lista_reproduccion` **copia** `titulo`, `album` y `artista` de
`canciones` → [[Práctica 2026-09-29|Práctica 2026-09-29]] § *Paso 5*.

> [!warning] (atención) El precio de desnormalizar
> Si el mismo dato está en dos tablas, **actualizarlo es actualizar las dos**, y nada en el motor
> garantiza que coincidan (no hay integridad referencial). La documentación lo acepta como parte del
> modelo: *"in Cassandra, denormalization is, well, perfectly normal"* (*RDBMS design* §
> *Denormalization*). Es el costo que el slide 16 paga a cambio de lecturas de **una sola partición**.

## 3 · Modelar por consulta: las tres reglas del slide 16 *(slides 14–17)*

> [!quote] Slide 16 — *"Modelado de datos"*, textual (en rojo en el deck lo que va en negrita)
> - *"Cuando diseñemos nuestro modelo debemos de guiarnos por el **patrón de acceso a los datos**, hay
>   que hacer un análisis de las queries que pretendemos ejecutar contra nuestro sistema y de esta forma
>   podremos diseñar un modelo eficiente que pueda sacar partido de las ventajas de Cassandra"*
> - *"Es importante también **definir adecuadamente la clave de partición** de nuestro datos, ya que
>   Cassandra se basará en esta clave para distribuir los datos a lo largo del cluster. Si queremos
>   aprovechar nuestro cluster debemos pensar en distribuir los datos para evitar cuellos de botella"*
> - *"También es recomendable, dado nuestro patrón de consulta, intentar **minimizar el número de
>   particiones** a las que hay que acceder durante una lectura"*

| Regla del slide 16 | Qué significa en el diseño | La documentación oficial *(Data Modeling)* |
| --- | --- | --- |
| **patrón de acceso** | listar las consultas **antes** de crear tablas; una tabla por consulta, con nombre `entidad_by_atributo` | *"in Cassandra you don't start with the data model; you start with the query model"* (*RDBMS design* § *Query-first design*); la convención de nombres `hotels_by_poi` (*Logical data modeling*) |
| **clave de partición** | que tenga **muchos valores** y tráfico parejo entre ellos: si pocos valores concentran la carga, esos nodos son el cuello de botella | *"The design of the primary key is extremely important, as it will determine how much data will be stored in each partition"* (*Logical data modeling*) |
| **pocas particiones** | que cada consulta se resuelva, idealmente, **en una sola partición**; si una partición crece sin límite, partirla agregando una columna a la clave (*bucketing*) | *"minimize the number of partitions that must be searched in order to satisfy a given query"* (*RDBMS design* § *Designing for optimal storage*); para particiones demasiado grandes, *"add an additional column to the partition key"* o *bucketing* (*Evaluating and refining data models*) |

Y una cuarta regla que el deck muestra en el slide 67 sin enunciarla: **el orden es una decisión de
diseño**. *"The sort order available on queries is fixed, and is determined entirely by the selection
of clustering columns you supply in the CREATE TABLE command"* (*RDBMS design* § *Sorting is a design
decision*).

> [!note] La mejor página de libro para esto es de DynamoDB
> *Seven Databases* cap. 7 § *Location, Location, Location* *(impresas 228–230)* da las mismas reglas
> para la clave de partición de DynamoDB: evitar ***hotspots*** (*"partition keys that don't cluster
> around just a few values"*), elegir claves que la aplicación conozca de antemano, y en claves
> compuestas *"opt for fewer partition keys and more range keys"*. Su ejemplo es un videojuego
> (*Bonestorm*, un millón de jugadores, estadísticas diarias): clave `usuario` + `fecha` sí, `fecha` +
> `usuario` no, porque todos los jugadores del día caerían en la misma partición. Es el caso del
> Final 1Jul2025 (§ 4.1). Y *Seven Databases* cap. 9 *(impresa 307)* da el criterio general:
> *"it's best to design your schema based on how you plan to query the data"* →
> [[3.15.01 - Bases de datos tabulares — familias de columnas y keyspaces|Bases de datos tabulares]] § 5.

## 4 · Dos consultas de examen, modeladas en el motor

### 4.1 · *"Los mejores puntajes"* de un videojuego *(Final 1Jul2025, pregunta 4)*

La respuesta larga del examen elige Cassandra porque las consultas (*"score de un usuario, mejores
scores, scores de amigos"*) se conocen de antemano. Modelarlas muestra **qué implica** eso:

**Modelo 1, desde la entidad** (como en relacional): `puntaje_por_usuario (user_id text PRIMARY KEY,
score int)`. *"Score de un usuario"* es una sola partición y corre. *"Los tres mejores"*:

```text
SELECT user_id, score FROM puntaje_por_usuario ORDER BY score DESC LIMIT 3;
InvalidRequest: … message="ORDER BY is only supported when the partition key is restricted by an EQ or an IN."
```

**Modelo 2, desde la consulta:** una tabla cuyo **orden** es el del *ranking*.

```sql
CREATE TABLE ranking_por_juego (juego text, score int, user_id text,
  PRIMARY KEY ((juego), score, user_id)) WITH CLUSTERING ORDER BY (score DESC, user_id ASC);
-- ana 870, beto 990, caro 910, dani 640
SELECT user_id, score FROM ranking_por_juego WHERE juego = 'tetris' LIMIT 3;
```

```text
 user_id | score
---------+-------
    beto |   990
    caro |   910
     ana |   870
```

Una sola partición, ya ordenada: la lectura es barata. Pero el diseño tiene **dos costos** que el
examen no menciona:

1. **Actualizar un puntaje no pisa: agrega.** `score` es parte de la clave, así que `INSERT …
   ('tetris', 950, 'ana')` crea **otra fila**:

   ```text
    user_id | score
   ---------+-------
       beto |   990
        ana |   950
       caro |   910
        ana |   870
       dani |   640
   ```

   Hay que borrar la fila vieja (`DELETE … WHERE juego = 'tetris' AND score = 870 AND user_id = 'ana'`)
   y, para saber cuál era, mantener también el Modelo 1: **dos tablas para la misma información**.
2. **Toda la escritura del juego va a una partición.** Con `juego` como clave de partición, las 10⁹
   escrituras por segundo del enunciado caen en las mismas réplicas: el cuello de botella que el
   slide 16 pide evitar. La salida habitual es partir la clave (*bucketing*: `(juego, dia)` o `(juego,
   region)`) y aceptar que el *ranking* global se arma leyendo varias particiones.

*(resolución del vault)* Cassandra sirve para **registrar** puntajes a ese volumen y para *rankings*
acotados por partición; un *ranking* **global** que cambia a cada escritura no es la consulta natural
de este modelo.

> [!important] (clave) Cuando el enunciado dice *"tabla de posiciones"*, la clave del parcial es Redis
> El [[Recuperatorio 1Q2026|Recuperatorio 1Q2026]] (P25, 4 puntos) pide un motor para *"una tabla de
> posiciones"* con `UserID` y `Score` y un millón de transacciones por segundo: la clave de la
> plataforma es **Redis**, no Cassandra (el vault lo justifica con los *sorted sets*); el alumno
> eligió MongoDB y sacó 0/4. Es lo que muestran los dos costos de arriba: Cassandra ordena solo
> **dentro de una partición**, así que un *ranking* global concentra todo en una. El Final 1Jul2025 no habla de tabla de posiciones sino de
> 10⁹ **escrituras**, y ahí se sostiene Cassandra. Lo que decide es la consulta, no el volumen.

### 4.2 · *"La temperatura promedio de cada sensor en la última semana"* *(Final 1Dic2025, pregunta 5)*

La respuesta del examen propone como clave de partición `(sensor_id, ventana_temporal)`. En el motor,
con un día por partición:

```sql
CREATE TABLE lecturas_por_sensor_dia (sensor_id text, dia date, ts timestamp, temperatura double,
  PRIMARY KEY ((sensor_id, dia), ts)) WITH CLUSTERING ORDER BY (ts DESC);
-- 2 sensores × 3 días × 4 lecturas
SELECT dia, COUNT(*) AS lecturas, AVG(temperatura) AS promedio FROM lecturas_por_sensor_dia
  WHERE sensor_id = 'cam-01' AND dia IN ('2026-09-27', '2026-09-28', '2026-09-29') GROUP BY dia;
```

```text
 dia        | lecturas | promedio
------------+----------+----------
 2026-09-27 |        4 |    3.775
 2026-09-28 |        4 |    4.175
 2026-09-29 |        4 |    2.925

(3 rows)

Warnings :
Aggregation query used on multiple partition keys (IN restriction)
```

Sin el `GROUP BY`, la misma consulta da el promedio de los tres días juntos (`3.625`), con el mismo
aviso. Lo que **no** corre es pedir el promedio de un sensor sin nombrar los días, porque la clave de
partición está incompleta (`WHERE sensor_id = 'cam-01'` → el error de `ALLOW FILTERING`). Y *"de cada
sensor"* sin decir cuáles:

```text
SELECT sensor_id, dia, AVG(temperatura) FROM lecturas_por_sensor_dia GROUP BY sensor_id, dia;
 sensor_id | dia        | system.avg(temperatura)
    cam-02 | 2026-09-29 |                   5.275
    …                                            (6 rows)
Warnings :
Aggregation query used without partition key
```

corre, pero **recorre toda la tabla** (el aviso lo dice). Con `TRACING ON`, la diferencia entre las
dos formas de leer:

| Consulta | Trazado |
| --- | --- |
| `COUNT(*) … WHERE sensor_id = 'cam-01' AND dia = '2026-09-29'` | `Executing single-partition query on lecturas_por_sensor_dia` → `Read 4 live rows and 0 tombstone cells` |
| `COUNT(*) … WHERE temperatura > 7 ALLOW FILTERING` | `Submitting range requests on 17 ranges …` → `Executing seq scan across 1 sstables for (min(-9223372036854775808), min(-9223372036854775808)]` → `Read 24 live rows` para devolver **3** |

*(resolución del vault)* La respuesta del examen es correcta en la elección y en la clave; para el
promedio, lo que responde bien es **una consulta por sensor sobre sus siete particiones** (`dia IN
(…)`), o, si la consulta es frecuente, una **tabla de agregados** que la aplicación actualiza al
escribir. Es la tensión entre el slide 6 y el 73 (§ 5).

## 5 · Agregaciones: el slide 6 contra el slide 73

| Slide 6 *(cuándo NO usar una base tabular)* | Slide 73 *(Functions)* |
| --- | --- |
| *"Consultas de agregación de datos (sum o avg) ya que deben hacerse del lado del cliente."* | *"aggregate functions that aggregate multiple rows resulting from a SELECT statement"* · `SELECT SUM (players) FROM plays;` |

Las dos cosas son ciertas en el motor: `SUM`, `AVG`, `COUNT`, `MIN` y `MAX` existen (el slide 73 corre:
[[Clase 15 - Introduccion a Cassandra|Clase 15]] § *Lo que el deck dice…*, fila 24), pero **dentro de
una partición** son baratas y **sobre toda la tabla** son un recorrido completo, con el aviso
`Aggregation query used without partition key`. `GROUP BY` solo acepta columnas de la clave primaria,
en su orden (*"the GROUP BY option only accepts primary key columns in defined order as arguments"*,
documentación, *Data Manipulation*). (atención) `AVG` sobre una columna `int` **trunca**: devuelve un
`int` (fila 24 de la misma tabla); para promedios, la columna tiene que ser `double` o `decimal`, como
en § 4.2.

La lectura correcta del slide 6: una base tabular **no es para consultas analíticas ad hoc sobre todos
los datos** (eso es un *column store*, →
[[3.15.01 - Bases de datos tabulares — familias de columnas y keyspaces|Bases de datos tabulares]] § 3).

## 6 · Colecciones *(slide 57, TP10 pasos 12–14)*

El slide 57 lista `SET`, `LIST` y `MAP` entre los tipos de columna. Guardan varios valores en **una**
columna de la fila, sin crear otra tabla: son la forma de desnormalizar una relación uno a muchos
chica.

| Colección | Literal | Qué hace | En el motor |
| --- | --- | --- | --- |
| `set<text>` | `{'rock','pop'}` | sin duplicados, ordenado | `{'rock','pop','rock'}` se guarda como `{'pop', 'rock'}` |
| `list<timestamp>` | `['2026-09-28 19:00:00+0000']` | ordenada por posición, admite duplicados | `[3, 1, 3]` (en una `list<int>`) se guarda tal cual |
| `map<text,text>` | `{'idioma':'es'}` | clave → valor, ordenado por clave | `{'b':'2','a':'1'}` se devuelve `{'a': '1', 'b': '2'}` |

El TP10 agrega un `set<text>` con `ALTER TABLE`, lo actualiza con `etiquetas = etiquetas + {…}` y lo
consulta con `CONTAINS` sobre un índice → [[Práctica 2026-09-29|Práctica 2026-09-29]] § *Pasos 12–14*.
Las actualizaciones concurrentes de colecciones no chocan: usan el mismo mecanismo de timestamps que
las columnas, y *"concurrent updates to maps and sets are guaranteed to resolve as well"*
(documentación, *Dynamo* § *Data Versioning*).

## 7 · Índices secundarios y SAI *(slide 62)*

> [!quote] Slide 62 — *"Índices Secundarios"*, textual
> *"Son índices sobre columnas."* · *"Se implementan como una tabla oculta, separada de la tabla que
> contiene los valores originales."* · *"No se recomienda su uso para consultas que requieran comprobar
> un gran volumen de datos para finalmente retornar un pequeño conjunto de resultados"*

Un índice secundario deja consultar por una columna que **no** es la clave de partición sin
`ALLOW FILTERING`. La documentación de Cassandra 5.0 distingue tres mecanismos (*Indexing concepts*):

| Índice | Cómo se crea | Qué es | Recomendación oficial |
| --- | --- | --- | --- |
| **primario** | es la clave de partición | ubica la fila en el anillo | *"the most efficient and fast lookup of data"* |
| **secundario (2i)** — el del slide 62 | `CREATE INDEX … ON t (col);` | *"stored in a hidden table on each node … separate from the table that contains the values being indexed"* | *"only recommended when used in conjunction with a partition key"* |
| **SAI** *(Storage-Attached Index, nuevo en 5.0; no está en el deck)* | `CREATE INDEX … ON t (col) USING 'sai';` | el índice viaja **con cada SSTable**, en el mismo nodo | *"the most appropriate indexing method for most use cases"* |

En el motor, los dos sobre `canciones`:

```text
 index_name           | kind       | options
----------------------+------------+-------------------------------------------
 canciones_artista_2i | COMPOSITES |                     {'target': 'artista'}
 canciones_titulo_sai |     CUSTOM | {'class_name': 'sai', 'target': 'titulo'}
```

Con los índices creados, `WHERE artista = 'Jorge Drexler'` (2i) y `WHERE titulo = 'Asilo (en vivo)'`
(SAI) devuelven `1 | Asilo (en vivo)` sin `ALLOW FILTERING`; el `OR` y el `LIKE` siguen sin correr (§ 1).
(atención) *(resolución del vault)* Por qué el slide 62 los desaconseja para consultas poco selectivas: el índice de cada
nodo solo conoce **sus** filas, así que una consulta sin clave de partición pregunta a **todos** los
nodos. Es una tabla más por consulta, pero **local**, en vez de repartida por la columna indexada. El
TP10 presenta el índice como la alternativa a `ALLOW FILTERING` (paso 11); la documentación lo matiza
como se ve en la tabla. `ALLOW FILTERING` y su costo →
[[3.15.06 - Clave primaria en Cassandra — partition key, clustering key y ALLOW FILTERING|Clave primaria en Cassandra]];
el índice relacional → [[1.08.02 - Índices|Índices]].

## 8 · Vistas materializadas *(slide 72)*

> [!quote] Slide 72 — *"Materialized Views"*, textual
> ```sql
> CREATE MATERIALIZED VIEW monkeySpecies_by_population AS
> SELECT * FROM monkeySpecies
> WHERE population IS NOT NULL AND species IS NOT NULL
> PRIMARY KEY (population, species)
> WITH comment='Allow query by population instead of species';
> ```
> Recuadro: *"A materialized view cannot be directly updated, but updates to the base table will cause
> corresponding updates in the view"*

El código y el recuadro son **copia textual** de la documentación oficial (*Materialized Views*). La
vista es la **desnormalización automática** del § 2: la misma información con **otra clave primaria**,
para consultar por `population` en vez de por `species`, y el motor la mantiene sincronizada. Las
columnas de la clave de la vista no pueden ser nulas: *"they must always be at least restricted by a IS
NOT NULL"* (documentación); por eso el `WHERE` del slide. *(resolución del vault)* Una fila sin
`population` no tendría token en la vista, y una sin `species` no tendría clave de *clustering*: no
podría ubicarse en ella. La documentación la presenta así: *"Beginning with the 3.0
release, Cassandra provides a feature known as materialized views which allows you to create multiple
denormalized views of data based on a base table design"* (*RDBMS design* § *Denormalization*).

> [!warning] (crítico) En Cassandra 5.0.9 vienen **deshabilitadas**
> `CREATE MATERIALIZED VIEW canciones_por_artista AS SELECT * FROM canciones WHERE artista IS NOT NULL
> AND id IS NOT NULL PRIMARY KEY (artista, id);` →
> `InvalidRequest: … message="Materialized views are disabled. Enable in cassandra.yaml to use."` La
> página *Overview* las lista como *"(Experimental) materialized views"*. Para el TP10, la alternativa
> es la **segunda tabla** escrita por la aplicación.

Compárese con la vista materializada relacional (PostgreSQL), que es el resultado guardado de una
consulta y se refresca a mano → [[1.06.01 - Vistas|Vistas]].

## 9 · Funciones *(slide 73)*

> [!quote] Slide 73 — *"Functions"*, textual
> *"CQL supports 2 main categories of functions:"* · *"scalar functions that take a number of values and
> produce an output"* — *"For example the last two days of data can be retrieved using: SELECT * FROM
> myTable WHERE date >= currentDate() - 2d;"* · *"aggregate functions that aggregate multiple rows
> resulting from a SELECT statement"* — `SELECT SUM (players) FROM plays;`

Texto copiado de la documentación (*Functions*), que hoy escribe `current_date()`. En 5.0.9 **corren
los dos nombres**: `SELECT currentDate(), current_date(), toDate(now()) FROM system.local;` →
`2026-09-29 | 2026-09-29 | 2026-09-29`. El ejemplo escalar del slide, sin fijar la partición, pide
`ALLOW FILTERING` ([[Clase 15 - Introduccion a Cassandra|Clase 15]] § *Lo que el deck dice…*, fila
23). Otras funciones que usa la cursada: `now()` (TP10, paso 7), `token()`
([[3.15.02 - Arquitectura de Cassandra — anillo peer-to-peer, particionado y replicación|Arquitectura de Cassandra]]),
`WRITETIME()` y `TTL()` ([[3.15.01 - Bases de datos tabulares — familias de columnas y keyspaces|Bases de datos tabulares]]).

## 10 · *Triggers* *(slide 74)*

> [!quote] Slide 74 — *"Triggers"*, textual
> ```text
> CREATE TRIGGER myTrigger
> ON myTable
> #(java class)
> USING 'org.apache.cassandra.triggers.AuditTrigger‘
> ```
> *"The actual logic that makes up the trigger can be written in any Java (JVM) language and exists
> outside the database, i.e. in a lib/triggers subdirectory of the Cassandra installation directory"*
> · *"It loads during cluster startup, and exists on every node that participates in a cluster. The
> trigger defined on a table fires before a requested DML statement occurs, which ensures the
> atomicity of the transaction"* · `DROP TRIGGER myTrigger;`

| | *Trigger* en MySQL | *Trigger* en Cassandra |
| --- | --- | --- |
| Dónde está la lógica | en la base, en SQL procedural | **fuera** de la base, en una clase Java instalada en **cada nodo** |
| Cómo se declara | `CREATE TRIGGER … BEFORE/AFTER … FOR EACH ROW BEGIN … END` | `CREATE TRIGGER nombre ON tabla USING 'clase.Java';` |
| Cuándo se dispara | antes o después, por fila | **antes** de la sentencia DML |

El recuadro es copia de la documentación (*Triggers*), que usa otra clase de ejemplo
(`org.apache.cassandra.triggers.InvertedIndex`). En 5.0.9 el código del slide **no corre**: tal cual
da `Invalid syntax` (`#` no es comentario en CQL y la comilla de cierre es tipográfica); corregido, `CREATE
TRIGGER t1 ON canciones USING 'org.apache.cassandra.triggers.AuditTrigger';` →
`Trigger class 'org.apache.cassandra.triggers.AuditTrigger' couldn't be loaded`, porque la clase no
viene instalada. `DROP TRIGGER` exige la tabla: `DROP TRIGGER myTrigger ON myTable;` (la gramática de
la documentación y el motor coinciden; sin `ON`, `mismatched input ';' expecting K_ON`). (atención) En
la imagen oficial no existe `lib/triggers`: el directorio de *triggers* es `/etc/cassandra/triggers/`
y solo trae un `README.txt` (*"Place triggers to be loaded in this directory, as jar files."*) →
[[Clase 15 - Introduccion a Cassandra|Clase 15]] § *Lo que el deck dice…*, filas 25–26. Los
*triggers* relacionales → [[1.09.04 - Triggers|Triggers]].

## 11 · Seguridad: roles, usuarios y permisos *(slides 48–49)*

> [!quote] Slide 48 — *"Seguridad"* (extracto)
> *"Seguridad a nivel de usuarios: logins con passwords y permisos de gestión y administración vía
> GRANT/REVOKE."* · cifrado *"entre clientes y clústeres como entre nodos"* · backups *"de forma regular
> ante errores como los borrados accidentales"* · herramientas externas (DataStax Enterprise) para
> *"autentificación externa, encriptación de tablas, y auditoría de datos"*.

El **slide 49** *("Securidad (cont.)" **[sic]**)* trae ocho sentencias en tres grupos —*Roles*
(`CREATE ROLE alice WITH PASSWORD = 'password_a' AND LOGIN = true;`, `GRANT report_writer TO alice;`,
`REVOKE report_writer FROM alice;`, `LIST ROLES;`), *Users* (`CREATE USER alice WITH PASSWORD
'password_a' SUPERUSER;`) y *Permissions* (`GRANT SELECT ON ALL KEYSPACES TO data_reader;`, `REVOKE
SELECT ON ALL KEYSPACES FROM data_reader;`, `LIST ALL PERMISSIONS ON keyspace1.table1 OF bob;`)—, todas
ejemplos de la documentación (*Security*). Dos precisiones:

- **Usuario = rol con `LOGIN`.** *"The CREATE USER command is equivalent to CREATE ROLE where the LOGIN
  option is true"* (documentación). Es el mismo modelo de roles que MySQL →
  [[1.11.02 - Usuarios, privilegios y roles|Usuarios, privilegios y roles]].
- **Con la imagen del TP10 no corre nada.** La autenticación viene desactivada
  (`AllowAllAuthenticator`): `CREATE ROLE alice WITH PASSWORD = 'password_a' AND LOGIN = true;` →
  `org.apache.cassandra.auth.CassandraRoleManager doesn't support PASSWORD`; `LIST ROLES` y `GRANT
  SELECT ON ALL KEYSPACES TO data_reader` → `Unauthorized: … You have to be logged in and not anonymous
  to perform this request`. Hace falta `PasswordAuthenticator` y `CassandraAuthorizer` en
  `cassandra.yaml` → [[Cassandra|Cassandra]] § *Autenticación: desactivada en la imagen*.

## Cuadro de bolsillo

| Pregunta | Respuesta |
| --- | --- |
| CQL | *"derivado reducido de SQL"* (slide 13) |
| No tiene | `JOIN`, subconsultas, `OR`, claves foráneas, `ORDER BY` fuera del *clustering* |
| `INSERT` | *upsert*: crea o reemplaza sin avisar |
| Diseño | **consultas primero**, una tabla por consulta, desnormalizada |
| Tres reglas (slide 16) | patrón de acceso · clave de partición que reparta · pocas particiones por lectura |
| Partición que crece | *bucketing*: `(sensor_id, dia)` |
| Agregaciones | baratas en una partición; recorrido completo sin ella (aviso del motor) |
| Colecciones | `set` · `list` · `map` |
| Índice secundario | tabla oculta local; SAI en 5.0 |
| Vista materializada | otra clave primaria, mantenida por el motor; **deshabilitada** en 5.0 |

| Roles | `CREATE USER` = `CREATE ROLE … LOGIN = true`; requieren autenticación activada |
| Shell | `cqlsh` (no *"cqlshell"*) |
