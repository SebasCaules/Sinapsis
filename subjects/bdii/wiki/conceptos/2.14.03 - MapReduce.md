# MapReduce

## Resumen general

MapReduce es el modelo de programación que MongoDB ofrece como comando para una agregación programable: `map` recorre cada documento y llama a `emit(clave, valor)` —cero, una o varias veces—, `reduce` recibe una clave con la lista de sus valores y los combina en uno, y `finalize`, opcional, corre una vez por clave al final. Responde la misma pregunta que `GROUP BY` en SQL y que `$group` en el aggregation pipeline; la diferencia está en el cómo: dos fases explícitas y programables en JavaScript, a cambio de perder índices, optimizador y sintaxis declarativa.

En la cursada aparece solo en la Clase 14 (slides 35–37, tomados de *Seven Databases* 2ª ed., impresas 119–123) y en el handout `Ejemplo_MapReduce_MongoDB.pdf`; el TP9 Parte I no lo usa y no está confirmado si entra al parcial. Las reglas: `reduce` corre por lotes y por shard, así que debe ser asociativa, conmutativa e idempotente y devolver el mismo tipo que emite `map`, y no se invoca para las claves con un solo valor; un promedio no se calcula en `reduce` sino emitiendo `{ suma, cantidad }` y dividiendo en `finalize`; el resultado va a la colección de `out` como `{ _id: clave, value: valor }` —una vista materializada— o `inline`, con el límite de 16 MB del BSON; los contadores del slide 36 (25 719 `reduce` para 3 479 claves) prueban que `reduce` se llama sobre resultados parciales; y el comando está deprecado desde MongoDB 5.0, cosa que el deck (referencia 6.0.5) no dice.

Para el parcial: escribir un MapReduce en tres piezas (qué clave y qué valor emitir, un `reduce` asociativo del mismo tipo, el `out`), cerrar con su traducción a `$group` + `$sum` + `$out`, y tener a mano el handout: `laptop 3000 · mouse 250 · keyboard 240`.

## Qué es

> [!quote] Slide 35 — la definición, textual *(en inglés en el slide)*
> *"In MongoDB, the map step involves creating a mapper function that calls an `emit()` function.
> The benefit of this approach is you can emit more than once per document. The `reduce()` function
> accepts a single key and a list of values that were emitted to that key. Finally, Mongo provides
> an optional third step called `finalize()`, which is executed only once per mapped value after the
> reducers are run. This allows you to perform any final calculations or cleanup you may need."*
>
> *"[2004] MapReduce: Simplified Data Processing on Large Clusters"* *(link)* ·
> `https://en.wikipedia.org/wiki/MapReduce`

Es la impresa **120** de *Seven Databases* 2ª ed. *(§ *Mapreduce (and Finalize)*)*, palabra por
palabra *(el deck no lo dice)*; el ejemplo que el slide 36 llama *"de la página 120"* empieza ahí y sigue en la 121.

Como modelo general *(GMUW **20.2** *The Map-Reduce Parallelism Framework*, impresa 993)*: el usuario
escribe `map` y `reduce`; *"a master controller divides the input data into chunks, and assigns
different processors to execute the map function on each chunk"*, y otros procesadores corren
`reduce` sobre la salida de `map`. El nombre viene del paper de **Dean y Ghemawat (Google, 2004)**
que el slide 35 enlaza; Hadoop lo popularizó como *framework*, y MongoDB lo ofrece como **un
comando** cuyas funciones se escriben en JavaScript.

> [!important] (clave) Es la misma pregunta que `GROUP BY`
> *"Por cada valor de X, calcular algo sobre todos los documentos que lo comparten"*: **agregación**,
> la de `GROUP BY` *([[1.05.01 - SQL — consultas|SQL — consultas]])* y la de `$group`

> **programables** las dos fases que el motor relacional esconde detrás de una cláusula, a cambio de
> perder el optimizador, los índices y la sintaxis declarativa.

## 1 · Las tres funciones y sus reglas

| Función | Firma en MongoDB | Qué hace | Regla |
| --- | --- | --- | --- |
| **`map`** | `function() { emit(clave, valor); }` — sin parámetros; **`this` es el documento** | por cada documento, emite **cero, uno o varios** pares *(clave, valor)*. *"you can emit more than once per document"* *(slide 35)* | no puede tocar la base ni depender de nada externo; solo lee `this` |
| **`reduce`** | `function(clave, valores) { return valor; }` | recibe **todos los valores emitidos para una clave** *(o resultados parciales de otros `reduce`)* y los reduce a **uno** | **asociativa, conmutativa e idempotente**; devuelve **el mismo tipo** que emite `map` |
| **`finalize`** *(opcional)* | `function(clave, valorReducido) { return valor; }` | se ejecuta **una vez por clave**, después de todos los `reduce` | para promedios, renombres, redondeos: lo que no se puede calcular parcialmente |

Las reglas de `reduce` salen de **cómo se ejecuta** *(§ 4)*. GMUW **20.2.3** *The Reduce Function*
*(impresa 995)*: *"When reduce is associative and commutative, it is possible to speed up the
execution of reduce by starting to apply its operation to the pairs produced by the map processes,
even before they finish"*.

| Regla | Por qué |
| --- | --- |
| **Asociativa y conmutativa** | los valores llegan en cualquier orden y **en lotes**: `reduce(k, [a, b])` seguido de `reduce(k, [resultado, c])` tiene que dar lo mismo que `reduce(k, [a, b, c])` |
| **Idempotente** | `reduce(k, [reduce(k, valores)])` = `reduce(k, valores)`: un resultado de `reduce` puede volver a entrar a otro |
| **Mismo tipo que `map`** | la entrada de `reduce` **mezcla** emisiones de `map` con resultados de otros `reduce`. Si `map` emite `{ count: 1 }` y `reduce` devuelve `{ total: n }`, el segundo `reduce` recibe objetos de dos formas *(`reduce2.js`, impresa 123)* |
| **No se llama si la clave tiene un solo valor** | el valor emitido pasa **directo** a la salida *(`mouse` y `keyboard` en el handout, § 3)* |

> [!note] La "clave" de `emit` es el criterio de agrupación, no una clave de la base
> GMUW 20.2.2 *(impresa 994)*: *"there can be many pairs with the same key value"*. Es el `_id` del
> `$group` o la columna del `GROUP BY`: un valor simple *(`this.product`)* o un documento
> *(`{ digits, country }`)*. En la salida, cada clave distinta es el **`_id`** de un documento.

El slide **no muestra `map` ni `reduce`**: los delega a tres archivos del sitio del libro
*(impresas 120–121, transcripto del PDF)*:

```javascript
// distinctDigits.js — helper: el arreglo de dígitos distintos de un número
distinctDigits = function(phone){
  var number = phone.components.number + '', seen = [], result = [], i = number.length;
  while(i--) { seen[+number[i]] = 1; }
  for (var i = 0; i < 10; i++) { if (seen[i]) { result[result.length] = i; } }
  return result;
}
db.system.js.save({_id: 'distinctDigits', value: distinctDigits})

// map1.js — clave compuesta {digits, country}, valor {count: 1}
map = function() {
  var digits = distinctDigits(this);
  emit({ digits: digits, country: this.components.country }, { count : 1 });
}

// reduce1.js — suma los count
reduce = function(key, values) {
  var total = 0;
  for (var i = 0; i < values.length; i++) { total += values[i].count; }
  return { count : total };
}
```

Lo implícito: `distinctDigits` va a **`system.js`** porque `map` corre **en el servidor** y sus
*helpers* tienen que estar ahí *(el puente con el slide 38)*; la clave es **un documento**
`{ digits, country }`, que después se consulta con `find({'_id.country': 8})` *(impresa 121)*; y el
valor es `{ count: 1 }` y no `1` *(*"we emit the value 1 (each document represents one item to
count)"*, impresa 121)*: el campo con nombre permite renombrarlo a `total` con `reduce2` o `finalize`
*(impresa 123)* — **lectura propia**, el libro no da esa razón. El handout emite el número directo.

**La salida es el dato pedagógico del slide**:

| `counts` | Valor | Lectura |
| --- | ---: | --- |
| `input` | 100 000 | documentos leídos de `phones` |
| `emit` | 100 000 | **uno por documento** — este `map` emite exactamente una vez |
| `reduce` | 25 719 | **menos que las emisiones** *(las claves con un solo valor no lo invocan)* y **más que las claves de salida** *(se llama por lotes y sobre resultados parciales)* — la prueba empírica del § 1 |
| `output` | 3 479 | claves distintas → documentos en `phones.report` |

> [!tip] `out: 'phones.report'` produce una **colección**: el libro la llama *materialized view*
> *"It's a materialized view that you can see in the `show tables` list"* *(impresa 121)*: el
> pariente NoSQL de las **vistas materializadas** que la [[1.06.01 - Vistas|Clase 06]] nombró y MySQL
> no tiene —la [[Clase 07 - Vistas-Parte 2]] lo anticipa como *"el mismo trade-off que reaparece en
> NoSQL"*—: precalculado, guardado y **potencialmente desactualizado**; hay que volver a correr el

## 3 · El ejemplo del handout — total vendido por producto

El caso mínimo: clave simple, valor numérico y `reduce` = suma *(transcripción completa, **traza a
mano**, la nota sobre `Array.sum` —helper del shell, no JavaScript estándar— y la comparación
**método vs. comando**: [[Clase 14 - MongoDB Features]] § *Material complementario*, (c))*.

```javascript
// colección 'orders'
{ "_id": 1, "product": "laptop",  "quantity": 2, "price": 1000 }
{ "_id": 2, "product": "mouse",  "quantity": 5, "price": 50 }
{ "_id": 3, "product": "laptop",  "quantity": 1, "price": 1000 }
{ "_id": 4, "product": "keyboard", "quantity": 3, "price": 80 }

// "Objetivo: Calcular el total vendido por producto."
db.orders.mapReduce(
  function() { emit(this.product, this.quantity * this.price); },  // map
  function(key, values) { return Array.sum(values); },  // reduce
  { out: "total_ventas_por_producto" }
)
```

Resultado esperado *(verificado a mano)*: `{ _id: "laptop", value: 3000 }` ·
`{ _id: "mouse", value: 250 }` · `{ _id: "keyboard", value: 240 }`; `mouse` y `keyboard` tienen un
solo valor emitido y no pasan por `reduce`. La forma `{ _id: <clave>, value: <valor> }` no se elige:
`_id` es la clave emitida y `value` lo que devolvió `reduce` *(o lo que emitió `map`)*; para otros
nombres, `finalize` o una proyección.

## 4 · Cómo se ejecuta — el diagrama del slide 37

La figura de la impresa 122, sin texto propio:

```
  db.runCommand({'mapReduce'...})
  ▲
  ┌─────────────┴─────────────┐
  │  mongos  [ reduce ]  │
  └───────▲─────────────▲─────┘
  ┌─────────────┴───┐  ┌─────┴───────────┐
  │ mongod 1  │  │ mongod 2  │
  │  [ reduce ]  │  │  [ reduce ]  │
  │  ▲  ▲  ▲  │  │  ▲  ▲  ▲  │
  │ map map map  │  │ map map map  │
  └─────────────────┘  └─────────────────┘
```

Es la **única vez que el deck dibuja un cluster shardeado** *(el slide 44, que presenta el sharding,
es solo texto —*"allows sharding from version 1.6"*, URL del manual— y remite a la impresa 127)*:
`mongod 1` y `mongod 2` son dos *shards* y `mongos` el router
*([[2.12.02 - Escalabilidad horizontal — sharding y replicación|Escalabilidad horizontal — sharding y replicación]])*.
Cada shard corre `map` y `reduce` sobre **sus** documentos; los resultados parciales suben a `mongos`,
que vuelve a correr `reduce` para fusionarlos. *Seven Databases* *(impresa 122)*: *"Reducers can have
either mapped (emitted) results or other reducer results as inputs. […] Each server must run its own
`map()` and `reduce()` functions and then push those results to be merged with the service that
initiated the call […]. Classic divide and conquer."*

> [!important] (clave) Este diagrama es **la razón de todas las reglas del § 1**
> Si `laptop` tiene documentos en los dos shards, `mongos` recibe **dos resultados parciales** para
> la misma clave y los combina con el mismo `reduce`: por eso asociativo, conmutativo, idempotente y
> del mismo tipo que `map` *(en la segunda ronda las entradas **son** resultados de `reduce`)*. Y por
> eso un **promedio no se calcula en `reduce`**: el promedio de promedios no es el promedio. Se emite
> `{ suma, cantidad }`, `reduce` suma y **`finalize`** divide una vez por clave — las *"final
> calculations"* del slide 35.

Corbellini **§ 5.1.3** *MapReduce* *(p. 12)* lo presenta desde BigTable: *"a framework based on the
division of labor for parallelizing data-intensive computations on large datasets"*. La misma sección
anota que *"even relatively simple queries can often span multiple lines of code"* y que Google creó
**Sawzall** como azúcar sintáctica porque las funciones `reduce` *"are usually provided as generic
operations. Sum and average are examples"*: el mismo diagnóstico que llevó a MongoDB a deprecar
`mapReduce` a favor de un pipeline con `$sum` y `$avg` prefabricados *(§ 6)*.

## 5 · Dónde va el resultado — la opción `out`

| `out` | Efecto | Fuente |
| --- | --- | --- |
| `"nombre"` *(cadena)* | crea la colección `nombre`, **reemplazándola** si existe | slide 36; handout |
| `{ inline: 1 }` | devuelve los resultados **en la respuesta**, sin colección. **Límite: 16 MB** *(el tamaño máximo de un documento BSON)* | *Seven Databases* impresa 122: *"As of Mongo 2.0, that limit is 16 MB"* |
| `{ replace: "nombre" }` · `{ merge: "nombre" }` · `{ reduce: "nombre" }` | reemplazar · **fusionar** con la existente *(las claves nuevas se agregan, las repetidas se pisan)* · **volver a reducir** con la existente *(las claves repetidas se combinan con `reduce`: acumular por lotes)* | documentación oficial; **no están en el deck ni en el libro** |

> [!warning] Los 16 MB de `inline` son los **mismos** 16 MB de la [[Clase 13 - NoSQL-EmbebidosVSNormalizado|Clase 13]]
> La respuesta de un comando es un documento BSON y ningún documento BSON supera los 16 MB
> *([[2.12.06 - Modelo de documentos — JSON, BSON y ObjectId|Modelo de documentos — JSON, BSON y ObjectId]])*:
> si el reporte puede ser grande, va a una colección. La Clase 13 cita la misma frase *(impresa
> **122**)* como límite del resultado `inline`, no como límite de documento.

## 6 · En el motor de la cursada — MongoDB: deprecado desde 5.0, y cómo se escribe hoy

> [!warning] (crítico) `mapReduce` está **deprecado desde MongoDB 5.0**, y ni el deck ni el handout lo dicen
> El slide 2 del deck fija la referencia en *"Stable release 6.0.5 / 2023-03-13"*; en esa versión el
> comando **ya estaba deprecado** desde hacía dos ramas: la documentación oficial lo marca
> *deprecated* desde 5.0 y remite al **aggregation pipeline**. Sigue existiendo en 6.0 y posteriores
> —corre, pero es **código que no hay que escribir nuevo**— y en `mongosh` debería aparecer con
> aviso de deprecación *(ambas cosas a verificar contra la imagen `mongo` del TP → [[MongoDB]]; lo
> verificado es la frase del manual)*. Los tres slides y el handout hablan del deck *(construido
> sobre un libro de 2018 que documenta MongoDB 3.6)*, no del motor.

### 6.1 · La traducción: `mapReduce` → `$group` *(+ `$out`)*

El handout, escrito como se escribe hoy:

```javascript
db.orders.aggregate([
  { $group: { _id: "$product", value: { $sum: { $multiply: ["$quantity", "$price"] } } } },
  { $out: "total_ventas_por_producto" }
]);
```

Mismo resultado, mismos nombres de campo, **sin JavaScript**. Las **cuatro piezas básicas** —clave →
`_id` del `$group`, valor → `$multiply`, `reduce` → `$sum`, `out` → `$out`— están tabuladas en la
[[Clase 14 - MongoDB Features]] § *Material complementario*, (c). Lo que excede al handout:

| MapReduce | Aggregation pipeline | Nota |
| --- | --- | --- |
| clave **compuesta** `emit({ digits, country }, …)` *(slide 36)* | `_id: { digits: "$…", country: "$…" }` | el `_id` del `$group` puede ser un documento |
| `reduce` que no es una suma | `$avg`, `$min`, `$max`, `$push`, `$addToSet`, `$first`, `$last`, … | `$avg` calcula el promedio bien sin `{ suma, cantidad }` ni `finalize` |
| `query` *(filtro previo, opción de `mapReduce`)* | `$match` **antes** del `$group` | y **usa índices**, cosa que `map` no hace |
| `sort` / `limit` *(opciones)* | `$sort` / `$limit` | — |
| `{ replace: "coll" }` *(forma explícita de `out: "coll"`)* | `{ $out: "coll" }` | reemplaza la colección; tiene que ser la **última etapa** |
| `{ merge: "coll" }` · `{ reduce: "coll" }` | `{ $merge: { into: "coll", whenMatched: "replace" \| "merge" \| <pipeline> } }` | `$merge` existe desde 4.2; el caso *reduce* se escribe con un pipeline en `whenMatched` |
| `{ inline: 1 }` | *(sin `$out` ni `$merge`)* | el resultado sale como cursor, **sin el límite de 16 MB** |
| lógica que no cabe en operadores | `$accumulator` *(en `$group`)* y `$function` *(en expresiones)* | JavaScript **dentro** del pipeline, desde 4.4 |

> [!important] (clave) Por qué la deprecación: cinco razones, todas del lado del motor
> 1. El pipeline corre **en C++ dentro del motor**; `mapReduce` levanta el intérprete JavaScript
> *(SpiderMonkey)* y serializa cada documento hacia él.
> 2. El pipeline **usa índices** en `$match` y `$sort`; en `mapReduce` solo la opción `query`.
> 3. En un cluster, `$group` **se ejecuta por shard y se fusiona en `mongos` automáticamente** — el
> slide 37 sin escribir un `reduce` asociativo.
> 4. Con JavaScript **deshabilitado** *(`--noscripting`)* no corren `mapReduce`, `$where`, `$function`
> ni `$accumulator`; `$group` sí.
> 5. Desde **4.4**, `mapReduce` **se implementa internamente sobre el pipeline** *(según las notas de
> versión de 4.4; a verificar)*: su salida perdió los `counts` y `timeMillis` del slide 36 — en
> `mongosh` moderno la respuesta es `{ result: 'total_ventas_por_producto', ok: 1 }` *(a verificar
> en el motor del TP)*.

> [!note] En MySQL no hay MapReduce, y no hace falta
> ```sql
> SELECT product, SUM(quantity * price) AS value FROM orders GROUP BY product;
> ```
> `GROUP BY` es el `emit` de la clave, `SUM` el `reduce`, y un `HAVING` o una expresión en el
> `SELECT` hacen de `finalize`. Lo que MySQL **no** tiene es la ejecución distribuida del slide 37.
> La forma "programable" sería un [[1.10.02 - Stored procedures y funciones|stored procedure]] con un
> [[1.10.03 - Cursores|cursor]] — el *"último recurso"* que esa página desaconseja, por la misma
> razón: lo declarativo optimiza mejor.

## 7 · Cuándo tenía sentido, y qué lo reemplazó

Hasta la rama **4.x**, `mapReduce` convivía con `aggregate` para agrupar y sumar, contar o promediar;
hoy cada una de sus piezas tiene su etapa en el pipeline *(la tabla del § 6.1)*, y la lógica que no
cabe en operadores *(parsear una cadena, un cálculo con ramas)* va a `$function` / `$accumulator`
*(4.4)* o se mueve a la aplicación. Lo único que el pipeline no reemplaza es el **cómputo masivo
sobre un cluster de muchos nodos** —MapReduce como **framework** *(Hadoop)*—, que hoy es Spark o el
conector de MongoDB para Spark: **fuera de la cursada**.

> [!tip] (clave) Para elegir motor, MapReduce es un dato en contra del que lo necesita
> *Seven Databases* lo usa como columna de comparación *(A1, tabla 3, impresa 312: MongoDB →
> *"Commands, mapreduce"* como *Ad Hoc Query* y *"JavaScript"* como *Mapreduce*; PostgreSQL → *"SQL"* y
> *"No"*)* y como criterio en el cap. 9 § *Making a Choice*
> *([[2.12.03 - Persistencia políglota|Persistencia políglota]])*: si el caso exige **consultas ad
> hoc** y solo se dispone de MapReduce, la elección es mala. En 2018 MongoDB ya ofrecía las dos cosas;
> hoy la respuesta es *"pipeline, y `mapReduce` solo para leer código viejo"*.

## Para el parcial

| Pregunta probable | Respuesta corta, con cita |
| --- | --- |
| ¿Qué es MapReduce? | Un modelo de cómputo en dos funciones: `map` transforma cada documento en pares *(clave, valor)* llamando a `emit()`, `reduce` recibe una clave y la lista de sus valores y los combina en uno *(slide 35; GMUW 20.2, impresa 993)*. Paper de Dean y Ghemawat, 2004 *(slide 35)* |
| ¿Qué hace `finalize`? | Paso opcional, **una vez por clave** después de los `reduce`, para cálculos finales o limpieza *(slide 35)*: dividir suma por cantidad, o renombrar `count` a `total` *(Seven Databases, impresa 123)* |
| ¿Puede `map` emitir más de una vez? | Sí: *"you can emit more than once per document"* *(slide 35)*. Cero, una o varias veces |
| ¿Qué condiciones debe cumplir `reduce`? | Asociativa, conmutativa, idempotente y del mismo tipo que emite `map`, porque se llama **por lotes y sobre resultados parciales** — el slide 37 y los 25 719 `reduce` para 3 479 claves del slide 36 |
| ¿Por qué un promedio no va en `reduce`? | El promedio de resultados parciales no es el promedio total. Se reduce `{ suma, cantidad }` y se divide en `finalize` |
| ¿Cómo se ejecuta en un cluster? | Cada shard corre `map` y `reduce` sobre sus datos; `mongos` vuelve a correr `reduce` para fusionar *(slide 37; Seven Databases impresa 122: *"classic divide and conquer"*)* |
| ¿Dónde queda el resultado? | En la colección de `out` *(`{ _id: clave, value: valor }`)*, una *materialized view* *(impresa 121)*; o `inline`, con límite de **16 MB** *(impresa 122)* |
| Total vendido por producto | `emit(this.product, this.quantity * this.price)` · `reduce = Array.sum(values)` · `out: "total_ventas_por_producto"` → `laptop 3000, mouse 250, keyboard 240` *(handout)*; con el pipeline, `$group: { _id: "$product", value: { $sum: { $multiply: ["$quantity", "$price"] } } }` + `$out` *(§ 6.1)* |
| ¿Está vigente? | **Deprecado desde MongoDB 5.0** a favor del pipeline: `$group` reemplaza `map`/`reduce`, `$project` a `finalize`, `$out`/`$merge` a `out`, `$function`/`$accumulator` al JavaScript. El deck *(6.0.5)* no lo dice |
| ¿Equivalente relacional? | `SELECT clave, agregado FROM … GROUP BY clave` *([[1.05.01 - SQL — consultas\|SQL — consultas]])*; sin equivalente en MySQL para la ejecución distribuida |

> [!tip] (clave) Si la pregunta es "escriba un MapReduce para X"
> Tres piezas y en este orden: **(1)** qué clave emitir *(el criterio de agrupación)* y qué valor
> *(lo que se va a combinar; si hay promedio, `{ suma, cantidad }`)*; **(2)** el `reduce` como
> operación **asociativa** sobre la lista, devolviendo el **mismo tipo** que emite `map`; **(3)** el
> `out`. Y cerrar con la frase que distingue: *"en la versión actual esto se escribe como `$group`
> con `$sum`; `mapReduce` está deprecado desde 5.0"*.

## Cuadro de bolsillo

| Pregunta | Respuesta |
| --- | --- |
| Las tres funciones | `map` *(emite pares con `emit(k, v)`; `this` = documento)* · `reduce(k, [v…]) → v` · `finalize(k, v) → v` *(opcional, una vez por clave)* |
| Reglas de `reduce` | asociativa · conmutativa · idempotente · mismo tipo que `map` · **no se llama** si la clave tiene un solo valor |
| Salida | colección `out` con `{ _id: clave, value: valor }` · o `inline` ≤ 16 MB |
| Ejecución en cluster | `map` + `reduce` por shard → `reduce` otra vez en `mongos` *(slide 37)* |
| Los números del slide 36 | 100 000 input · 100 000 emit · **25 719 reduce** · 3 479 output |
| Handout | `laptop 3000 · mouse 250 · keyboard 240` — `mouse` y `keyboard` **no pasan por `reduce`** |
| Dos sintaxis | `db.coll.mapReduce(map, reduce, { out })` · `db.runCommand({ mapReduce: 'coll', map, reduce, out })` |
| Estado | **deprecado desde 5.0**; sigue existiendo en 6.0 y debería correr con aviso; en 4.4 ya se implementaba sobre el pipeline *(las dos últimas, a verificar en el `mongosh` del TP)* |
| Traducción | `emit(k, v)` → `$group: { _id: k, …: { $sum: v } }` · `finalize` → `$project` · `out` → `$out` / `$merge` · JS → `$function` / `$accumulator` |
| En MySQL | `GROUP BY` + función de agregado; sin ejecución distribuida |
| Paper | Dean y Ghemawat, *MapReduce: Simplified Data Processing on Large Clusters*, 2004 *(slide 35)* |
