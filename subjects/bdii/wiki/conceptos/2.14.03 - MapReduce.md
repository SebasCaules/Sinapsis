## Qué es

> [!quote] Slide 35 — la definición, textual *(en inglés en el slide)*
> *"In MongoDB, the map step involves creating a mapper function that calls an `emit()` function.
> The benefit of this approach is you can emit more than once per document. The `reduce()` function
> accepts a single key and a list of values that were emitted to that key. Finally, Mongo provides
> an optional third step called `finalize()`, which is executed only once per mapped value after the
> reducers are run. This allows you to perform any final calculations or cleanup you may need."*
>
> *"[2004] MapReduce: Simplified Data Processing on Large Clusters"* *(link)* ·
> `https://en.wikipedia.org/wiki/MapReduce`

El párrafo es la impresa **120** de *Seven Databases* 2ª ed. *(§ *Mapreduce (and Finalize)*)*,
palabra por palabra. El deck no lo dice. El ejemplo que el slide 36 llama *"de la página 120"*
empieza ahí *(`distinctDigits.js` y su `db.system.js.save`)* y sigue en la 121 *(`map1.js`,
`reduce1.js` y el `runCommand`)*.

**MapReduce** es un **modelo de programación para cómputos sobre datos grandes y distribuidos**: el
usuario escribe dos funciones —`map`, que transforma cada registro en pares *(clave, valor)*, y
`reduce`, que combina todos los valores de una misma clave— y el sistema se encarga de repartir el
trabajo entre nodos, agrupar por clave y juntar los resultados. El nombre viene del paper de
**Dean y Ghemawat (Google, 2004)** que el slide 35 enlaza; Hadoop lo popularizó como *framework*, y
MongoDB lo ofrece como **un comando** cuyas dos funciones se escriben en JavaScript.

> [!quote] GMUW **20.2** *The Map-Reduce Parallelism Framework*, impresa 993 — la definición general, textual
> *"Map-reduce is a high-level programming system that allows many important database processes to
> be written simply. The user writes code for two functions, map and reduce. A master controller
> divides the input data into chunks, and assigns different processors to execute the map function
> on each chunk. Other processors, perhaps the same ones, are then assigned to perform the reduce
> function on pieces of the output from the map function."*

> [!important] 🎯 Lo que MapReduce responde es la misma pregunta que `GROUP BY`
> *"Por cada valor de X, calcular algo sobre todos los documentos que lo comparten."* Es
> **agregación**: la misma operación que en la primera mitad se escribió con `GROUP BY` y funciones
> de agregado *([[1.05.01 - SQL — consultas|SQL — consultas]])* y que en MongoDB hoy se escribe con
> `$group` *([[2.12.08 - Aggregation pipeline|Aggregation pipeline]])*. La diferencia no está en el
> **qué** sino en el **cómo**: MapReduce hace explícitas las dos fases que el motor relacional
> esconde detrás de una cláusula, y las hace **programables** —cualquier cosa que quepa en una función
> de JavaScript— a cambio de perder el optimizador, los índices y la sintaxis declarativa.

## 1 · Las tres funciones, y las reglas que cada una tiene que cumplir

| Función | Firma en MongoDB | Qué hace | Regla |
| --- | --- | --- | --- |
| **`map`** | `function() { emit(clave, valor); }` — sin parámetros; **`this` es el documento** | por cada documento, emite **cero, uno o varios** pares *(clave, valor)*. *"you can emit more than once per document"* *(slide 35)* | no puede tocar la base ni depender de nada externo; solo lee `this` |
| **`reduce`** | `function(clave, valores) { return valor; }` | recibe **todos los valores emitidos para una clave** *(o resultados parciales de otros `reduce`)* y los reduce a **uno** | **asociativa, conmutativa e idempotente**; devuelve **el mismo tipo** que emite `map` |
| **`finalize`** *(opcional)* | `function(clave, valorReducido) { return valor; }` | se ejecuta **una vez por clave**, después de todos los `reduce` | para promedios, renombres, redondeos: lo que no se puede calcular parcialmente |

Las reglas de `reduce` no son estilo: salen de **cómo se ejecuta**, y son las que el diagrama del
slide 37 justifica *(§ 4)*:

| Regla | Por qué |
| --- | --- |
| **Asociativa y conmutativa** | los valores de una clave pueden llegar en cualquier orden y **en lotes**: `reduce(k, [a, b])` y después `reduce(k, [resultado, c])` tiene que dar lo mismo que `reduce(k, [a, b, c])` |
| **Idempotente** | `reduce(k, [reduce(k, valores)])` tiene que devolver lo mismo que `reduce(k, valores)`: el resultado de un `reduce` puede volver a entrar a otro |
| **Mismo tipo que `map`** | porque los valores de entrada de `reduce` son **una mezcla** de lo que emitió `map` y de lo que devolvieron otros `reduce`. Si `map` emite `{ count: 1 }` y `reduce` devuelve `{ total: n }`, el segundo `reduce` recibe objetos de dos formas — es el caso de `reduce2.js` del libro *(impresa 123)* |
| **No se llama si la clave tiene un solo valor** | el valor emitido pasa **directo** a la salida sin pasar por `reduce`. Es otra razón de la regla anterior: si `reduce` cambiara el tipo, las claves con un valor saldrían con forma distinta *(el handout lo muestra sin decirlo: `mouse` y `keyboard`, § 3)* |

> [!quote] GMUW **20.2.3** *The Reduce Function*, impresa 995 — de dónde sale la regla, textual
> *"When reduce is associative and commutative, it is possible to speed up the execution of reduce by
> starting to apply its operation to the pairs produced by the map processes, even before they
> finish. Moreover, if a given map process produces more than one intermediate pair with the same
> key, then the reduce operation can be applied on the spot to combine the pairs, without waiting
> for them to be passed to the reduce process for that key."*

> [!note] Las "claves" que emite `map` no son claves en el sentido de la base
> GMUW lo aclara en 20.2.2 *(impresa 994)*: *"there can be many pairs with the same key value"*. La
> clave de `emit` es el **criterio de agrupación** —el `_id` del `$group`, la columna del `GROUP BY`—
> y puede ser un valor simple *(`this.product`)* o un documento compuesto *(`{ digits, country }` en
> el ejemplo del libro)*. En la salida, cada clave distinta se convierte en el **`_id`** de un
> documento.

```javascript
// distinctDigits.js — helper: el arreglo de dígitos distintos de un número
distinctDigits = function(phone){
  var number = phone.components.number + '', seen = [], result = [], i = number.length;
  while(i--) { seen[+number[i]] = 1; }
  for (var i = 0; i < 10; i++) { if (seen[i]) { result[result.length] = i; } }
  return result;
}
db.system.js.save({_id: 'distinctDigits', value: distinctDigits})

// map1.js — clave compuesta {digits, country}, valor {count: 1}
map = function() {
  var digits = distinctDigits(this);
  emit({ digits: digits, country: this.components.country }, { count : 1 });
}

// reduce1.js — suma los count
reduce = function(key, values) {
  var total = 0;
  for (var i = 0; i < values.length; i++) { total += values[i].count; }
  return { count : total };
}
```

Tres cosas que el ejemplo enseña y el slide deja implícitas:

| Detalle | Qué muestra |
| --- | --- |
| `distinctDigits` se guarda en **`system.js`** | `map` corre **en el servidor**, así que las funciones auxiliares tienen que estar ahí también *(es el puente con el slide 38)* |
| La clave es **un documento** `{ digits, country }` | agrupar por dos criterios = emitir una clave compuesta; después se consulta con `find({'_id.country': 8})` *(impresa 121)* |
| El valor es `{ count: 1 }` y no `1` | el libro emite un objeto con un campo con nombre *(dice *"we emit the value 1 (each document represents one item to count)"*, impresa 121)*; tener un campo con nombre es lo que después permite renombrarlo a `total` con `reduce2` o con `finalize` *(impresa 123)* — **lectura propia**, el libro no da esa razón. El handout, más simple, emite el número directo |

## 3 · El ejemplo del handout — total vendido por producto

El handout `Ejemplo_MapReduce_MongoDB.pdf` es el caso mínimo: una clave simple, un valor numérico y
`reduce` = suma. La transcripción completa, la **traza a mano** documento por documento, la
observación sobre `mouse`/`keyboard` *(un solo valor emitido: `reduce` no se invoca)*, la de
`Array.sum` *(helper del shell, no JavaScript estándar)* y la comparación **método vs. comando**
están en la [[Clase 14 - MongoDB Features]] § *Material complementario*, (c), y no se repiten
aquí. Lo que hace falta para leer el resto de la página:

```javascript
// colección 'orders'
{ "_id": 1, "product": "laptop",   "quantity": 2, "price": 1000 }
{ "_id": 2, "product": "mouse",    "quantity": 5, "price": 50 }
{ "_id": 3, "product": "laptop",   "quantity": 1, "price": 1000 }
{ "_id": 4, "product": "keyboard", "quantity": 3, "price": 80 }

// "Objetivo: Calcular el total vendido por producto."
db.orders.mapReduce(
    function() { emit(this.product, this.quantity * this.price); },   // map
    function(key, values) { return Array.sum(values); },              // reduce
    { out: "total_ventas_por_producto" }
)
```

Resultado esperado del handout *(verificado a mano en la Clase 14)*:
`{ _id: "laptop", value: 3000 }` · `{ _id: "mouse", value: 250 }` · `{ _id: "keyboard", value: 240 }`.
La forma `{ _id: <clave>, value: <valor> }` no se elige: `_id` es la clave emitida y `value` lo que
devolvió `reduce` *(o lo que emitió `map`, si no hubo `reduce`)*; para cambiar los nombres hay que
usar `finalize` o consultar la colección con una proyección.

## 4 · Cómo se ejecuta — el diagrama del slide 37 y por qué `reduce` se llama tantas veces

El slide 37 es la figura de la impresa 122 del libro, sin texto propio. Lo que dibuja:

```
                db.runCommand({'mapReduce'...})
                            ▲
              ┌─────────────┴─────────────┐
              │   mongos      [ reduce ]  │
              └───────▲─────────────▲─────┘
        ┌─────────────┴───┐   ┌─────┴───────────┐
        │ mongod 1        │   │ mongod 2        │
        │   [ reduce ]    │   │   [ reduce ]    │
        │   ▲   ▲   ▲     │   │   ▲   ▲   ▲     │
        │ map map map     │   │ map map map     │
        └─────────────────┘   └─────────────────┘
```

Es la **única vez que el deck dibuja un cluster shardeado** *(el slide 44, que presenta el sharding,
es solo texto —definición, *"allows sharding from version 1.6"*, URL del manual— y remite a la
impresa 127 del libro)*: `mongod 1`
y `mongod 2` son dos *shards*, cada uno con una parte de la colección; `mongos` es el router
*([[2.12.02 - Escalabilidad horizontal — sharding y replicación|Escalabilidad horizontal — sharding y replicación]])*.
Cada shard corre `map` sobre **sus** documentos y `reduce` sobre **sus** claves; los resultados
parciales suben a `mongos`, que vuelve a correr `reduce` sobre ellos para fusionar lo que cada
shard calculó por separado.

> [!quote] *Seven Databases* 2ª ed., impresa 122 — la explicación del diagrama, textual
> *"Reducers can have either mapped (emitted) results or other reducer results as inputs. Why would
> the output of one reducer feed into the input of another if they are mapped to the same key? Think
> of how this would look if run on separate servers […]. Each server must run its own `map()` and
> `reduce()` functions and then push those results to be merged with the service that initiated the
> call, gathering them up. Classic divide and conquer."*

> [!important] 🎯 Este diagrama es **la razón de todas las reglas del § 1**
> Si `laptop` tiene documentos en los dos shards, `mongos` recibe **dos resultados parciales** para
> la misma clave y los combina con el mismo `reduce` — por eso tiene que ser asociativo *(no importa
> cómo se partió la lista)*, conmutativo *(no importa qué shard respondió primero)*, idempotente *(un
> resultado de `reduce` puede volver a entrar)* y devolver el mismo tipo que `map` *(porque en la
> segunda ronda los valores de entrada **son** resultados de `reduce`)*. Y por eso un **promedio no
> se puede calcular en `reduce`**: el promedio de promedios no es el promedio. Se emite
> `{ suma, cantidad }`, `reduce` suma las dos, y **`finalize`** divide una vez por clave. Ese es
> exactamente el uso de `finalize` que el slide 35 describe como *"final calculations"*.

Corbellini lo presenta desde el lado de BigTable, como el modelo general del que MongoDB toma la
idea:

> [!quote] Corbellini **§ 5.1.3** *MapReduce*, p. 12 — textual
> *"MapReduce is a framework based on the division of labor for parallelizing data-intensive
> computations on large datasets. Basically, this framework consists of two programming abstractions
> that must be instantiated by programmers: map and reduce. The map function is responsible for
> processing key-value pairs and generating as output a set of key-value pairs with intermediate
> results. In turn, the reduce function is responsible for generating a list of results from such
> intermediate results."*

La misma sección *(§ 5.1.3, p. 12)* anota, dos párrafos después, que *"even relatively simple
queries can often span multiple lines of code"*
y que Google creó **Sawzall** como *azúcar sintáctica* sobre MapReduce, porque las funciones `reduce`
*"are much less varied and thus are usually provided as generic operations. Sum and average are
examples"*. Es, en 2017 y para BigTable, **el mismo diagnóstico** que llevó a MongoDB a deprecar
`mapReduce` a favor de un pipeline con `$sum` y `$avg` prefabricados *(§ 6)*.

## 5 · Dónde va el resultado — la opción `out`

| `out` | Efecto | Fuente |
| --- | --- | --- |
| `"nombre"` *(cadena)* | crea la colección `nombre`, **reemplazándola** si existe. Es lo que usan el slide 36 y el handout | slide 36; handout |
| `{ inline: 1 }` | devuelve los resultados **en la respuesta**, sin colección. **Límite: 16 MB** *(el tamaño máximo de un documento BSON)* | *Seven Databases* impresa 122: *"As of Mongo 2.0, that limit is 16 MB"* |
| `{ replace: "nombre" }` · `{ merge: "nombre" }` · `{ reduce: "nombre" }` | reemplazar la colección · **fusionar** con la existente *(las claves nuevas se agregan, las repetidas se pisan)* · **volver a reducir** con la existente *(las claves repetidas se combinan con `reduce`: es la forma de acumular por lotes)* | documentación oficial; **no están en el deck ni en el libro** |

> [!warning] El límite de 16 MB de `inline` es el **mismo** 16 MB de la [[Clase 13 - NoSQL-EmbebidosVSNormalizado|Clase 13]], visto desde otro lado
> La respuesta de un comando es un documento BSON, y ningún documento BSON supera los 16 MB
> *([[2.12.06 - Modelo de documentos — JSON, BSON y ObjectId|Modelo de documentos — JSON, BSON y ObjectId]])*.
> Si el reporte puede ser grande, va a una colección. La [[Clase 13 - NoSQL-EmbebidosVSNormalizado]]
> cita esta misma frase del libro como límite del resultado `inline` —no como límite de documento—
> y la ubica en la impresa **122** *(verificado)*.

## 6 · En el motor de la cursada — MongoDB: deprecado desde 5.0, y cómo se escribe hoy

> [!warning] 🔴 `mapReduce` está **deprecado desde MongoDB 5.0**, y ni el deck ni el handout lo dicen
> El slide 2 del deck fija la referencia en *"Stable release 6.0.5 / 2023-03-13"*; en esa versión
> el comando **ya estaba deprecado** desde hacía dos ramas. La documentación oficial lo marca
> *deprecated* desde 5.0 y remite al **aggregation pipeline**. El comando **sigue existiendo** en 6.0
> y en las ramas posteriores *(a verificar contra la versión que traiga la imagen `mongo` del TP →
> [[MongoDB]])*: corre, pero es **código que no hay que escribir nuevo**, y en `mongosh` debería
> aparecer con aviso de deprecación *(a verificar en el `mongosh` del TP: nadie en el vault corrió
> todavía el handout; lo verificado es la frase del manual → [[MongoDB]])*. Que el deck le dedique
> tres slides y un handout es información sobre el
> deck *(está construido sobre un libro de 2018 que documenta MongoDB 3.6)*, no sobre el motor.

### 6.1 · La traducción: `mapReduce` → `$group` *(+ `$out`)*

El handout, escrito como se escribe hoy:

```javascript
db.orders.aggregate([
  { $group: { _id: "$product", value: { $sum: { $multiply: ["$quantity", "$price"] } } } },
  { $out: "total_ventas_por_producto" }
]);
```

Mismo resultado, mismos nombres de campo *(`_id` y `value`)*, **sin JavaScript**. La correspondencia
de las **cuatro piezas básicas** —clave → `_id` del `$group`, valor → `$multiply`, `reduce` →
`$sum`, `out` → `$out`— está tabulada en la [[Clase 14 - MongoDB Features]] § *Material
complementario*, (c). Lo que esa tabla **no** tiene, porque excede al handout:

| MapReduce | Aggregation pipeline | Nota |
| --- | --- | --- |
| clave **compuesta** `emit({ digits, country }, …)` *(slide 36)* | `_id: { digits: "$…", country: "$…" }` | el `_id` del `$group` puede ser un documento, igual que la clave de `emit` |
| `reduce` que no es una suma | acumuladores `$avg`, `$min`, `$max`, `$push`, `$addToSet`, `$first`, `$last`, … | y `$avg` calcula el promedio bien sin que el usuario emita `{ suma, cantidad }` ni escriba `finalize` |
| `query` *(filtro previo, opción de `mapReduce`)* | `$match` **antes** del `$group` | y **usa índices**, cosa que `mapReduce` no hace en `map` |
| `sort` / `limit` *(opciones)* | `$sort` / `$limit` | — |
| `{ replace: "coll" }` *(forma explícita de `out: "coll"`)* | `{ $out: "coll" }` | reemplaza la colección; tiene que ser la **última etapa** |
| `{ merge: "coll" }` · `{ reduce: "coll" }` | `{ $merge: { into: "coll", whenMatched: "replace" \| "merge" \| <pipeline> } }` | `$merge` existe desde 4.2; el caso *reduce* se escribe con un pipeline en `whenMatched` |
| `{ inline: 1 }` | *(no poner `$out` ni `$merge`)* | el resultado sale como cursor, **sin el límite de 16 MB** |
| lógica que no cabe en operadores | `$accumulator` *(en `$group`)* y `$function` *(en expresiones)* | JavaScript **dentro** del pipeline, desde 4.4 — es la válvula de escape oficial |

> [!important] 🎯 Por qué la deprecación: cinco razones, todas del lado del motor
> 1. El pipeline se ejecuta **en C++ dentro del motor**; `mapReduce` levanta el intérprete JavaScript
>    *(SpiderMonkey)* y serializa cada documento hacia él.
> 2. El pipeline **usa índices** en `$match` y `$sort`; en `mapReduce` solo la opción `query` los
>    aprovecha, y `map` recorre todo lo que pase el filtro.
> 3. En un cluster, `$group` **se ejecuta por shard y se fusiona en `mongos` automáticamente** — el
>    diagrama del slide 37, sin que el usuario tenga que escribir un `reduce` asociativo ni pensar
>    en promedios de promedios.
> 4. Un servidor puede arrancar con JavaScript **deshabilitado** *(`--noscripting`)*: ahí `mapReduce`,
>    `$where`, `$function` y `$accumulator` no corren; `$group` sí.
> 5. Desde **4.4**, `mapReduce` **se implementa internamente sobre el pipeline** *(según las notas de
>    versión de 4.4; a verificar)*: el comando quedó como una capa de compatibilidad, y su salida
>    perdió los `counts` y `timeMillis` del slide 36 — en `mongosh` moderno la respuesta es
>    `{ result: 'total_ventas_por_producto', ok: 1 }` *(a verificar en el motor del TP)*.

> [!note] Y el motor de la primera mitad: no hay MapReduce en MySQL, y no hace falta
> El handout en MySQL es una línea:
> ```sql
> SELECT product, SUM(quantity * price) AS value FROM orders GROUP BY product;
> ```
> `GROUP BY` es el `emit` de la clave, `SUM` es el `reduce`, y un `HAVING` o una expresión en el
> `SELECT` hacen de `finalize`. Lo que MySQL **no** tiene es la ejecución distribuida del slide 37:
> un solo servidor agrupa todo. La forma "programable" de hacerlo en MySQL sería un
> [[1.10.02 - Stored procedures y funciones|stored procedure]] con un
> [[1.10.03 - Cursores|cursor]] — exactamente el *"último recurso"* que esa página desaconseja, y
> por la misma razón por la que MongoDB deprecó `mapReduce`: lo declarativo optimiza mejor.

## 7 · Cuándo tenía sentido, y qué lo reemplazó

| Situación | Antes *(≤ 4.x)* | Hoy |
| --- | --- | --- |
| Agrupar y sumar / contar / promediar | `mapReduce` o `aggregate` | **`$group`** con acumuladores |
| Filtrar antes de agrupar | opción `query` | `$match` *(con índices)* |
| Lógica que no cabe en operadores *(parsear una cadena, un cálculo con ramas)* | `map` en JavaScript | `$function` / `$accumulator` *(4.4)*, o mover la lógica a la aplicación |
| Guardar el resultado en una colección | `out` | `$out` / `$merge` |
| Acumular resultados por lotes *(un reporte que crece cada noche)* | `out: { reduce: "coll" }` | `$merge` con `whenMatched` como pipeline |
| Cómputo masivo sobre un cluster de muchos nodos | MapReduce como **framework** *(Hadoop)* | Spark, o el conector de MongoDB para Spark — **fuera de la cursada** |

> [!tip] 🎯 Para elegir motor, MapReduce es un dato en contra del que lo necesita
> *Seven Databases* lo usa como columna de comparación *(A1, tabla 3, impresa 312: MongoDB → *"Commands,
> mapreduce"* como *Ad Hoc Query* y *"JavaScript"* como *Mapreduce*; PostgreSQL → *"SQL"* y *"No"*)*
> y como criterio en el cap. 9 § *Making a Choice* *(→
> [[2.12.03 - Persistencia políglota|Persistencia políglota]])*: si el caso exige **consultas ad hoc**
> y solo se dispone de MapReduce, la elección es mala. En 2018 MongoDB ya ofrecía las dos cosas;
> hoy la respuesta es *"pipeline, y `mapReduce` solo para leer código viejo"*.

## Para el parcial

| Pregunta probable | Respuesta corta, con cita |
| --- | --- |
| ¿Qué es MapReduce? | Un modelo de cómputo en dos funciones: `map` transforma cada documento en pares *(clave, valor)* llamando a `emit()`, `reduce` recibe una clave y la lista de sus valores y los combina en uno *(slide 35; GMUW 20.2, impresa 993)*. Nombre del paper de Dean y Ghemawat, 2004 *(slide 35)* |
| ¿Qué hace `finalize`? | Paso opcional, **una vez por clave** después de los `reduce`, para cálculos finales o limpieza *(slide 35)*. Ejemplo: dividir suma por cantidad para un promedio, o renombrar `count` a `total` *(Seven Databases, impresa 123)* |
| ¿Puede `map` emitir más de una vez? | Sí: *"you can emit more than once per document"* *(slide 35)*. Cero, una o varias veces |
| ¿Qué condiciones debe cumplir `reduce`? | Asociativa, conmutativa, idempotente y devolver el mismo tipo que emite `map`, porque se llama **por lotes y sobre resultados parciales** — el diagrama del slide 37 y los 25 719 `reduce` para 3 479 claves del slide 36 |
| ¿Por qué un promedio no va en `reduce`? | Porque el promedio de resultados parciales no es el promedio total. Se reduce `{ suma, cantidad }` y se divide en `finalize` |
| ¿Cómo se ejecuta en un cluster? | Cada shard corre `map` y `reduce` sobre sus datos; `mongos` vuelve a correr `reduce` para fusionar *(slide 37; Seven Databases impresa 122: *"classic divide and conquer"*)* |
| ¿Dónde queda el resultado? | En la colección de `out` *(documentos `{ _id: clave, value: valor }`)*, que el libro llama *materialized view* *(impresa 121)*; o `inline`, con límite de **16 MB** *(impresa 122)* |
| Total vendido por producto con MapReduce | `emit(this.product, this.quantity * this.price)` · `reduce = Array.sum(values)` · `out: "total_ventas_por_producto"` → `laptop 3000, mouse 250, keyboard 240` *(handout)* |
| Lo mismo con el pipeline | `$group: { _id: "$product", value: { $sum: { $multiply: ["$quantity", "$price"] } } }` + `$out` *(§ 6.1)* |
| ¿Está vigente? | **Deprecado desde MongoDB 5.0** a favor del aggregation pipeline: `$group` reemplaza `map`/`reduce`, `$project` a `finalize`, `$out`/`$merge` a `out`, `$function`/`$accumulator` al JavaScript. El deck *(6.0.5)* no lo dice |
| ¿Equivalente relacional? | `SELECT clave, agregado FROM … GROUP BY clave` *([[1.05.01 - SQL — consultas|SQL — consultas]])*; lo que no tiene equivalente en MySQL es la ejecución distribuida |

> [!tip] 🎯 Si la pregunta es "escriba un MapReduce para X"
> Tres piezas y en este orden: **(1)** qué clave emitir *(el criterio de agrupación)* y qué valor
> *(lo que se va a combinar; si hay promedio, `{ suma, cantidad }`)*; **(2)** el `reduce` como
> operación **asociativa** sobre la lista, devolviendo el **mismo tipo** que emite `map`; **(3)** el
> `out`. Y cerrar con la frase que distingue: *"en la versión actual esto se escribe como
> `$group` con `$sum`; `mapReduce` está deprecado desde 5.0"*.

## Cuadro de bolsillo

| Pregunta | Respuesta |
| --- | --- |
| Las tres funciones | `map` *(emite pares con `emit(k, v)`; `this` = documento)* · `reduce(k, [v…]) → v` · `finalize(k, v) → v` *(opcional, una vez por clave)* |
| Reglas de `reduce` | asociativa · conmutativa · idempotente · mismo tipo que `map` · **no se llama** si la clave tiene un solo valor |
| Salida | colección `out` con `{ _id: clave, value: valor }` · o `inline` ≤ 16 MB |
| Ejecución en cluster | `map` + `reduce` por shard → `reduce` otra vez en `mongos` *(slide 37)* |
| Los números del slide 36 | 100 000 input · 100 000 emit · **25 719 reduce** · 3 479 output |
| Handout | `laptop 3000 · mouse 250 · keyboard 240` — `mouse` y `keyboard` **no pasan por `reduce`** |
| Dos sintaxis | `db.coll.mapReduce(map, reduce, { out })` · `db.runCommand({ mapReduce: 'coll', map, reduce, out })` |
| Estado | **deprecado desde 5.0**; sigue existiendo en 6.0 y debería correr con aviso; en 4.4 ya se implementaba sobre el pipeline *(las dos últimas, a verificar en el `mongosh` del TP)* |
| Traducción | `emit(k, v)` → `$group: { _id: k, …: { $sum: v } }` · `finalize` → `$project` · `out` → `$out` / `$merge` · JS → `$function` / `$accumulator` |
| En MySQL | `GROUP BY` + función de agregado; sin ejecución distribuida |
| Paper | Dean y Ghemawat, *MapReduce: Simplified Data Processing on Large Clusters*, 2004 *(slide 35)* |
