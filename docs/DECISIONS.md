# Decisiones de arquitectura (N0)

Registro numerado de las decisiones tomadas por el orquestador durante la ejecución autónoma
del Sprint 1. El usuario pidió "cualquier decisión dejarla para el final": aquí están todas,
con su porqué, para revisarlas en bloque. Cada una se puede revertir; se anota el costo.

| # | Decisión | Por qué | Costo de revertir |
|---|---|---|---|
| N0-1 | **Monorepo pnpm** con `apps/web` (SPA), `apps/api` (servidor), `packages/contract`, `packages/markdown`, `packages/cli`. | Un solo `pnpm install`, tipos compartidos sin publicar paquetes, deploy de API + estáticos desde un repo. | Bajo. |
| N0-2 | **SQLite vía `@libsql/client` + Drizzle ORM**, archivo local `apps/api/data/sinapsis.db`. | Volumen chico (miles de páginas markdown), cero operación local, y el mismo cliente apunta a Turso (libSQL en la nube) cambiando solo la URL cuando haya deploy. FTS5 disponible para búsqueda. | Medio si se quisiera Postgres: Drizzle abstrae el esquema pero FTS5 y algunos tipos cambian. |
| N0-3 | **API en Hono** (`@hono/node-server`) en vez de Express/Fastify. | Tipado, liviano, corre en Node hoy y en Bun/edge mañana; middlewares de cookies y zod integrados. | Bajo: rutas finas, lógica en servicios. |
| N0-4 | **Autenticación: Google Identity Services en el cliente → ID token → verificación en el servidor (`google-auth-library`) → cookie de sesión httpOnly firmada**, sesiones en tabla `sessions`. | Sin proveedor externo de sesión, funciona en localhost y en deploy. | Bajo. |
| N0-5 | **Bypass de desarrollo**: con `AUTH_DEV_BYPASS=1` y `NODE_ENV!=production`, `POST /api/auth/dev` inicia sesión como usuario local. | El Client ID de Google requiere una acción del usuario en Google Cloud Console que el agente no puede hacer; el MVP debe poder probarse de punta a punta sin ese paso. El bypass está prohibido en producción por código. | Ninguno: se elimina la variable. |
| N0-6 | **Materias globales, landing por usuario.** `subjects` es global (la plataforma es personal; el CLI sincroniza sin usuario); `user_subjects` guarda cuatrimestre y posición por usuario; `progress` es por usuario. | Es lo que hace el mockup: el usuario ordena SU landing; el sync viene de un CLI local. Evita multi-tenant prematuro. | Medio: agregar `owner_id` a `subjects` cuando haya más de un usuario real. |
| N0-7 | **Token de sync estático** (`SYNC_TOKEN` en `.env` del API) para `PUT /api/subjects/:slug/sync`. | El CLI corre en la misma máquina; tokens por usuario son Sprint 2+. | Bajo. |
| N0-8 | **Tema global por usuario** (`users.theme`), no por materia. Resuelve la "decisión pendiente" del mockup. | Una preferencia de lectura es de la persona, no del contenido; evita saltos de piel al cambiar de materia. Se persiste además en localStorage para pintar antes del primer paint. | Bajo: agregar override por materia después. |
| N0-9 | **Rutas de navegador** (`/m/:subject/p/:slug`), no hash. | SPA con servidor propio; URLs limpias y compartibles; el API sirve `index.html` como fallback. | Bajo. |
| N0-10 | **Markdown en el cliente con `react-markdown` + `remark-gfm` + `remark-math` + `rehype-katex`** y plugins propios para wikilinks `[[slug|texto]]` y callouts de Obsidian `> [!tipo]`. El cuerpo viaja crudo desde la API. | Mismo pipeline que Obsidian; el servidor no renderiza HTML (menos superficie XSS); KaTeX ya vendorizado en el baseline. | Medio si se quisiera SSR. |
| N0-11 | **Rail: grupos FIJOS los dibuja la plataforma; los grupos SLOT vienen del `sinapsis.config.json`.** Ítems con `kind` = `builtin` / `page` / `link` / `tool`. En el Sprint 1 `tool` muestra "Próximamente". | Es el contrato 00 del mockup. Las herramientas React propias por materia (plugins) son Sprint 3. | Bajo. |
| N0-12 | **Escala de color de división paramétrica** (N ≤ 9: `--u1…--u9`; N > 9: barrido oklch), implementada en `@sinapsis/contract` y compartida por web y CLI. | Decisión visible en el mockup 00; una sola implementación. | Bajo. |
| N0-13 | **El compilador del wiki es un paquete TypeScript (`@sinapsis/markdown`)** que reimplementa el contrato de `build.py` (frontmatter, wikilinks, headings, orden). | Un solo lenguaje en el repo; el CLI y los tests lo usan directamente; `build.py` queda como referencia. | Bajo. |
| N0-14 | **Primera materia real: Probabilidad y Estadística**, con `sinapsis.config.json` escrito por el orquestador a partir del HANDOFF (unidades 1-9, 0, eval; tipos concepto/distribución/teorema/técnica/formulario/fuente). El config vive en `examples/proba/` del repo y se copia al vault cuando el usuario lo apruebe. | Valida el sync con 200 páginas reales sin tocar el vault del usuario. | Ninguno. |
| N0-15 | **Estilos: CSS plano con los tokens del design system EstudioDS** (los tres temas, tipografías vendorizadas) + CSS Modules por componente. Sin Tailwind. | El mockup y el baseline son token-first; Tailwind duplicaría la paleta. | Alto (reescritura visual). |
| N0-16 | **Estado del cliente: TanStack Query para datos del servidor, Zustand para UI (tema, panel plegado, divisiones abiertas).** | Estándar, chico, testeable. | Bajo. |
| N0-17 | **Vite proxy `/api` → `localhost:3000` en desarrollo; en producción el API sirve `apps/web/dist`.** Un solo origen: sin CORS, cookies `SameSite=Lax`. | Simplicidad y seguridad. | Bajo. |
| N0-18 | **Alcance del Sprint 1 (MVP)**: landing completa (grilla por cuatrimestre, agregar/quitar/mover/reordenar, vacía, temas, login), shell de materia (rail FIJO+SLOT, índice adaptable, cabecera, migas, Inicio con progreso, Lector con KaTeX/wikilinks/TOC/fuentes/backlinks/marcar estudiado, catálogo "Todo el wiki" con búsqueda y filtros, índice plegado), API + DB + sync, CLI, skill `/sinapsis` (init/sync/status). **Fuera**: pestañas múltiples, grafo, flashcards/quiz, plan/kits, figuras interactivas, herramientas React por materia, tokens por usuario, deploy. | Es el corte que deja la plataforma usable con una materia real y el contrato probado. Lo demás son sprints 2-4. | — |
| N0-19 | **Modelos de trabajo**: orquestación en la sesión (Fable) para contratos, integración y adjudicación final; agentes de construcción y verificación de ola en Opus 5. | Instrucción del usuario del 2026-09-05. | — |
